## Deliverables and boundary

In `crates/marathon-apple`, mirroring the Kotlin packages (`plist`, `plist::bundle`, `xctestrun::{v0,v1,v2}`), each module starting with `//! Port of <kotlin path>` (CLAUDE.md):

1. **Plist value layer and reading.** A pinned `plist` dependency (`=1.10.3`, the version already in `Cargo.lock`) wrapped in the equivalent of `PropertyList.from` (`B/plist/PropertyList.kt:15-22`): read from path, bytes and reader; XML and binary inputs (both occur in the real bundles, below). dd-plist's `parse(String)` overload takes a *file path*, not content — do not replicate that ambiguity; name the Rust entry points `from_path`/`from_bytes`/`from_reader`. All models are dictionary-rooted; a non-dictionary root is an error, never a panic. Keep the layer synchronous over bytes/readers: file opening is blocking I/O, so callers run it off the core executor per `lifecycle.md`; no `unwrap()`/`expect()` on I/O or parse results.
2. **Delegate-equivalent accessors.** The `NSDictionary` delegates of `B/plist/Delegates.kt` as typed get/set helpers over a live, mutable dictionary (required, optional, array, nested-model and model-list flavours, `:22-143`). Models wrap the same underlying dictionary the caller holds — unknown keys, their values and their order survive a read→modify→write round trip untouched (the stated design intent, `Delegates.kt:12-21`). Do **not** eagerly extract fields into plain structs: in Kotlin nothing is read until a property is touched, and several production paths rely on never touching most keys (see the missing-key behaviour below).
3. **xctestrun v0/v1/v2 models** (9 files, below) with the same keys, required/optional split, constructors and mutation surface Kotlin exposes, including v2 `TestTarget::with_artifact_reinstall`/`with_artifact_reuse` for 4.5b. Field *values* such as `__TESTROOT__`/`__TESTHOST__` path strings are opaque here; expanding them is xcodebuild's and the fake world's business, not this WP's.
4. **Byte-exact XML writer.** Our own writer (PLAN §4.2) reproducing dd-plist 1.28 `XMLPropertyListWriter` output byte for byte for every value the models and the round-trip can carry, to a `File` and to an in-memory/`Write` sink (Kotlin: `saveAsXML(File|OutputStream)`, `PropertyList.kt:33-39`). This is the writer `TestRootFactory` uses at `B/xctestrun/TestRootFactory.kt:49-57` (temp file, push, delete — the push is 4.5b's, the bytes are this WP's).
5. **Info.plist models.** `BundleInfo` and the facets it actually exposes (`B/plist/bundle/BundleInfo.kt:6-12`): `Categorization`, `Identification`, `Naming`, `OperatingSystemVersion`, `Undocumented`, with exactly their keys (below).
6. **Mach-O detection.** The `File.isAppleBinary` check and the six magic constants of `B/model/AppleTestBundle.kt:12-27,163-170`, extracted as a small function 4.4 calls (see open question 1 on the inventory split). Detection only: directory scanning, the extensionless-file filter and the 0/1/many selection with its warnings and `ConfigurationException` texts (`AppleTestBundle.kt:70-133`) stay in 4.4.

**Frozen 0.6 traits:** this WP implements none and must not invent any. In `crates/marathon-core/src/vendor.rs`, `TestBundle::id` is the only bundle surface core sees, `BundleRef` equality is `Arc` identity, and `TestBundleIdentifier::identify` is 4.8's; `BundleInfo`, the xctestrun models and Mach-O detection are inputs to 4.4's `AppleTestBundle`, which is where the `TestBundle` implementation lands. ## Behaviours to reproduce (with sources)

- **Minimally invasive round trip.** Parsing never drops or reorders unknown keys, and never rewrites values the models do not model (`Delegates.kt:12-21`). Correctness is pinned by v1 `testWrite`: read `UITesting_iphonesimulator11.2-x86_64.xctestrun`, replace two fields, and every other key (incl. `BundleIdentifiersForCrashReportEmphasis`, `ToolchainsSettingValue`) comes out unchanged and in place. There is no `__xctestrun_metadata__`-driven version dispatch anywhere: the caller picks v0/v1/v2, and files with metadata claiming one version but shaped like another are simply read through whichever model was asked for (`Delegates.kt:16-17`). Production at `e47352f2` only ever *writes* v2 (`TestRootFactory.kt:51`, `Metadata(2)`) and only ever *reads* Info.plists; reading xctestrun files is test-only — but the tests are parity rows, so all three read models are in scope.
- **Delegate reads are lazy and fail at access, with dd-plist conversion rules.** `delegateFor` (`Delegates.kt:25-29`) converts via `NSObject.toJavaObject()`: missing key → `IllegalArgumentException("plist does not define property <name>")`, wrong runtime type → the same naming the Java class. Nothing is converted at parse time, so a malformed value under an untouched key never fails a run. Conversions to replicate or deliberately tighten (P4/P9): dictionary values become string-keyed maps without checking the value type (a non-string env value slips through the cast and fails later, elsewhere); `arrayDelegateFor` converts each element to the requested class (`:72-74`), so `UIDeviceFamily` integers arrive as `Int`; `Metadata.formatVersion` is `Int` (`v2/Metadata.kt:16`) while dd-plist numbers can be wider.
- **"Optional" is three different things; keep them apart.** (a) `optionalDelegateFor`: missing → `null`, and *setting* `null` still writes `NSObject.fromJavaObject(null)` into the dictionary (`Delegates.kt:40-48`); (b) `optionalArrayDelegateFor`/`arrayDelegateFor(optional=true)`: missing → empty array, never `null` (`:52-67`); (c) `optionalPlistDelegateFor`: missing → `null`, and setting `null` is a **no-op** — the key can never be cleared (`:132-141`). On top of that, most `BundleInfo` fields and several target fields are declared nullable but use the *required* `delegateFor`, so reading them throws on a missing key instead of returning `null` (e.g. `plist/bundle/Identification.kt:14`, `OperatingSystemVersion.kt:20,31`, `v0/TestTarget.kt:54-96`). Two upstream consequences to confirm by oracle probe and then record as new rows in `docs/known-kotlin-bugs.md` (next A-numbers; D5 keeps them): `AppleTestBundle.appId`'s `ConfigurationException("No bundle identifier specified…")` (`AppleTestBundle.kt:53-55`) is unreachable when the key is absent — the delegate throws first — and is only reached with no application at all; and `TestRootFactory`'s `lsMinimumSystemVersion != null` guard (`TestRootFactory.kt:82-91`) never sees `null` for a macOS bundle lacking the key — it throws out of validation instead.
- **Constructors write in a fixed order, and write nulls.** dd-plist 1.28 preserves insertion order from parse through write, and replacing a key keeps its original position (visible in `expect_1.xctestrun`); new keys append. So constructor assignment order *is* output order: v0 target fields in `v0/TestTarget.kt:27-41` order, then v2's `BlueprintName` and its optional fields in `v2/TestTarget.kt:184-198` order, v2 root as metadata → configurations → plan → coverage (`v2/Xctestrun.kt:298-301`), coverage fields in `CodeCoverageBuildableInfo.kt` constructor order. Any Rust API that passes these through a `HashMap`/`BTreeMap` (including env-variable maps, `LinkedHashMap` from Kotlin `mapOf`) breaks byte parity — take ordered maps. The v0 constructor also assigns its first three fields **unconditionally, including `null`** (`:27-29`), which the artifact-reuse path hits (no bundle/host path, `v2/TestTarget.kt:78-131`): what `NSObject.fromJavaObject(null)` stores and what the writer then emits must be probed on the JVM before the Rust constructors are frozen (open question 4).
- **Writer bytes (dd-plist `XMLPropertyListWriter`), as pinned by the three `expect_*.xctestrun` fixtures and the 0.4b pushed-xctestrun evidence:** header `<?xml version="1.0" encoding="UTF-8"?>` and the `//Apple//DTD PLIST 1.0//EN` doctype on their own lines; `<plist version="1.0">`; one tab of indent per depth; `<key>` and value on separate lines; `<true/>`/`<false/>`, `<integer>2</integer>`; an empty array is written as `<array>` + newline + indented `</array>`, **not** `<array/>` (Xcode-written inputs use `<array/>` — the parser must accept both, the writer emits only dd-plist's form); **no trailing newline** after `</plist>` (the Kotlin `testWrite`s compare against `expected.trim()`, and the 0.4b pushed bytes end at `</plist>`; port the Rust tests to compare exact bytes, untrimmed). String/key XML escaping, empty string/dict forms, and `real`/`date`/`data`/wide-integer renderings do not occur in the `expect_*` files — pin them with JVM oracle probes (below), never by guessing what the `plist` crate's own writer does; that writer is not used.
- **Equality is by delegate content, and class-sensitive.** `PropertyList.equals` requires the same `javaClass` and equal delegates (`PropertyList.kt:41-50`); dictionary equality is key-order-insensitive (which is why v2 `testRead` passes although `man_v2.xctestrun`'s key order differs from the constructed expected value), arrays stay order-sensitive, `hashCode` is the delegate's (`:52-54`). Verify the pinned `plist` crate's `Dictionary` equality is likewise order-insensitive before relying on it — the `-reordered` fixture exists precisely for this. A v0 and a v2 `TestTarget` over identical dictionaries are *not* equal in Kotlin; in Rust they are different types, so keep cross-type comparison impossible rather than adding a shared equality. Wrappers share the live dictionary: mutating through one wrapper is visible through every other, and v0/v1 `targets` are `by lazy` (`v0/Xctestrun.kt:175`, `v1/Xctestrun.kt:9`) — computed once, stale after later mutation of the root dictionary. v0 `targets` also casts *every* value to a dictionary (a non-dictionary top-level value is a `ClassCastException`), where v1 filters those and the metadata key out.
- **Info.plist reading is local, at parse time, in both plist encodings.** `AppleTestBundle` reads `<bundle>/Info.plist`, or `<bundle>/Contents/Info.plist` for macOS (`AppleTestBundle.kt:39-67`), during stage-(a) bundle validation on the *host* (PLAN §6.4 host-side table). The fields actually consumed downstream are few — `identification.bundleIdentifier` (4.4), `naming.bundleName` (4.4), `undocumented.bundleSupportedPlatforms` and `operatingSystemVersion.lsMinimumSystemVersion` (4.5b) — but the model surface above is what's ported. `bundleSupportedPlatforms` is the optional-array flavour: a bundle without `CFBundleSupportedPlatforms` yields an empty array and then fails 4.5b's platform check as incompatible, it does not fail the plist read (`Undocumented.kt:8`, `TestRootFactory.kt:66-80`).
- **Mach-O detection is a 4-byte prefix test with a fixed magic set.** Exactly `FAT_MAGIC` (`ca fe ba be`), `MH_MAGIC` (`fe ed fa ce`), `MH_MAGIC_64` (`fe ed fa cf`) and each reversed (`AppleTestBundle.kt:164-169`). Files shorter than 4 bytes are not binaries (`:15`). Note what is *absent*: no 64-bit fat magic (`ca fe ba bf`), so a fat-64-only executable is not detected and the bundle later reports missing test binaries — keep the set as-is under D5. The Kotlin code opens the stream before the length check and does a single `read()` of 4 bytes (`:14-18`); see P7 for the readable-file simplifications proposed there.

## Proposed simplifications (pragmatic parity — for orchestrator approval, **not decided**)

Per the user's direction: few users; do not emulate quirks only exotic inputs reach. Until one is approved (as a PLAN §3.11-style deviation, recorded like D9–D11), the behaviours above stand and a divergence is a bug.

- **P1, OpenStep/ASCII plist input.** dd-plist's parser accepts the ASCII format; the `plist` crate does not, and no fixture or Xcode-produced `Info.plist`/xctestrun uses it. Propose: reject it with a clear "unsupported plist format" error instead of writing an OpenStep parser.
- **P2, binary plist writing.** `saveAsBinary` has no production or test caller at `e47352f2`. Propose: do not port the binary writer at all (reading binary stays — real iOS bundles need it).
- **P3, dead Info.plist facets.** `Help`, `Launch`, `LaunchConditions`, `Localization`, `Version` (137 lines) are unreachable from `BundleInfo` and constructed nowhere. Propose: set those five inventory rows `n/a` with that reason (needs a reviewer's agreement per CLAUDE.md) instead of porting unused accessors.
- **P4, delegate error fidelity.** Propose one `PlistError` vocabulary (missing key / wrong type / not a dictionary / IO / parse, each naming the key) with our wording, instead of reproducing the Java exception classes and message texts (`IllegalArgumentException` including the reflective "should define primary constructor…" message of `Delegates.kt:89`, `ClassCastException` from v0 `targets`, dd-plist's parse exceptions). Accept/reject and the offending key stay identical; only class/message text differs (§3.10 sanctions this for Jackson errors; extending it here needs the orchestrator's word).
- **P5, `plistListDelegateFor` reading.** Its getter converts with `toJavaObject()`, casts to `Array<T>` and reflectively constructs models from the *converted* elements (`Delegates.kt:109-117`) — on its face this cannot yield working nested models, and no test ever calls it: v2 `testRead` passes on delegate equality alone, and production never reads an xctestrun. Propose: after the JVM probe establishes what Kotlin actually does, implement the intended read (wrap each element dictionary) rather than reproducing a throw, recording the difference as a deviation if the probe shows one.
- **P6, exotic scalar renderings in the writer.** The models emit only string/integer/bool/array/dict; `real`, `date`, `data`, `UID` and out-of-`i64` values can only appear as unknown keys carried through a read→write round trip (test-only today). Propose: support them, but oracle-pin byte-exactness only for the renderings listed in the probe set; anything further (e.g. NaN/infinite reals) gets the `plist`-crate-compatible rendering and a findings note, not a dd-plist emulation effort.
- **P7, Mach-O file-reading quirks.** Propose `is_apple_binary(bytes_or_reader)` over the first four bytes actually read (`<4` ⇒ false), with a missing/unreadable file surfacing as the caller's IO error — instead of Kotlin's open-stream-then-check-length ordering and single-`read()` short-read hazard (`AppleTestBundle.kt:14-18`). The magic set itself is **not** simplified (no fat-64 addition; that's user-visible detection behaviour under D5).
- **P8, hashing.** Kotlin's `hashCode` is Java's map hash over the delegate. Nothing observable persists it. Propose: implement `PartialEq`/`Eq` per the equality rules above and make no attempt at Java-hash-compatible `Hash` (add a Rust-internal `Hash` only if a consumer needs one, consistent with the order-insensitive equality).
- **P9, strictness of converted collections.** Kotlin's unchecked casts let a non-string env value or a mixed-type array through the accessor, to explode at some later use. Propose: check element types at access and fail there with the P4 error. Diverges only on plists whose modelled keys carry wrong-typed values in positions Kotlin happens never to touch.

## Open questions for the orchestrator

1. **Mach-O ownership split.** PLAN §7 puts "Mach-O detection" in 4.5a, but its only Kotlin home, `model/AppleTestBundle.kt`, is assigned to 4.4 (which also "owns" the local Info.plist/Mach-O reads in its row). The inventory gives a file one WP. Recommend: 4.5a extracts the 4-byte check + constants into `marathon-apple` for 4.4 to call, the file row stays 4.4, and the findings note the split — or move detection wholly to 4.4 and strike it from this WP's row. Decide before implementation; `scripts/check.sh`'s inventory check will not flag either way, so this is purely a boundary call.
2. **9 of the 15 parity rows cannot be ported as assigned.** The commented-out `xctestrun/XctestrunTest.kt` tests a legacy API (`targetName`, `isSkipped`, `clone()`, `environment(…)`, `toXMLString()`) that does not exist at `e47352f2`. Recommend: those 9 rows become `n/a` with that reason (reviewer agreement required), and the three ideas that still mean something — equality ignoring key order (the `-reordered` fixture), the metadata/target-key case (the `12.1` fixture) and serialize→parse round trip — are re-expressed against the v1 model as new Rust tests without parity rows. The 6 live rows are this WP's parity acceptance.
3. **Does nested-model reading work at all in Kotlin?** `plistListDelegateFor` (used for `TestConfigurations`, `TestTargets`, `CodeCoverageBuildableInfos`) looks broken for reads and is exercised by no test or production call (P5). A JVM probe must settle it before the accessor design is frozen, because "fix it" vs "reproduce the throw" changes the v2 read API 4.5b might later lean on.
4. **Null writes from constructors.** What does dd-plist store and emit for the v0 constructor's unconditional null assignments, and for `optionalDelegateFor` set to `null`? Probe (ii) above answers it; the answer decides whether the Rust constructors model these as absent keys, an explicit null-equivalent, or a construction-time error — and whether 4.5b's artifact-reuse xctestrun bytes can match at all without it.
