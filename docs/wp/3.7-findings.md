## API handed to 3.8 (`marathon_core::execution::queue`)

- `QueueMessage`: `RequestBatch(RequestBatch { device, worker_id })`, `RequestBatches(Vec<RequestBatch>)`,
  `IsEmpty(tokio::sync::oneshot::Sender<bool>)`, `Completed(DeviceInfo, TestBatchResults)`,
  `ReturnBatch(DeviceInfo, BatchRef, JavaString)`, `RejectBatch(DeviceInfo, BatchRef)`,
  `ConfirmOutcome(DeviceInfo)`, `Terminate`. Devices are `DeviceInfo` snapshots; bookkeeping is by serial.
  A queue that closes before answering IsEmpty drops the sender, so the receiver errors; awaitQueue's
  `select { processed.onAwait; queue.job.onJoin }` is `select(rx, handle.job().join())`.
- `QueueHandle`: `try_send(message) -> bool` (never throws; 3.8 logs the drop as `sendToQueue` does),
  `job() -> JobRef` (the actor's owner job, for awaitQueue), `close()` (cancel and discard), `actor()`.
- `SharedProgress = Rc<tokio::sync::Mutex<PoolProgressAccumulator>>`: the one accumulator the pool, the
  queue and the Scheduler's `aggregateResult` share (`Scheduler.kt:115`, `DevicePoolActor.kt:71`).
- `QueueActor::prepare(vendor, analytics: Arc<Analytics>, &Configuration, cancellation) ->
  OperationResult<PreparedQueue>`: builds the sorting and batching strategies, prefetches the union of their
  `metrics_keys()` on the vendor runtime (`call_vendor`), and keeps `analytics.lookup()` plus the analytics
  itself for `observe_execution_times`. 3.8 awaits it before it builds the pool.
- `QueueActor::spawn(core, prepared, &Configuration, shard, pool: Rc<dyn Actor<DevicePoolMessage>>, pool_id,
  timer, bundle_identifier, progress, parent, hooks) -> QueueHandle`: synchronous on core. It builds
  `JavaPriorityQueue::new(sorting.process(lookup, hooks))`, runs `add_all(tests ++ flaky_tests)` (the
  constructor's comparisons), builds the retry strategy (one per queue, C30) and starts the
  `RuntimeActor` with logger `QueueActor[DevicePoolId(name=<pool>)]` under `parent` (the pool supervisor).
  As for `DeviceActor`, `pool` must be the pool actor's own long-lived handle: the queue keeps it weak.
  `hooks` is the run's single `ReplayHooks`; 3.7 never constructs one.
- `test-support` only: `PreparedQueue::from_parts(configuration, lookup, metrics)`,
  `with_comparator(wrapper)` (records comparisons) and `with_observer(callback)` (a `QueueSnapshot` of the
  backing array, `retryWorkers` and `activeBatches` keys after each message, also after a failing one).

## Decisions taken and simplifications applied

- **Decision 3, accumulator ownership: design (b), an async lock.** Kotlin's `testStarted`/`testEnded`
  (`PoolProgressAccumulator.kt:268–303`) and `retryTest`/`removeTest` (305–311) are plain functions with no
  suspension point. `testEnded` is called only by the queue (`QueueActor.kt:137, 143, 296, 309, 319`),
  inside one handler; `DevicePoolActor` only passes the accumulator on (`DevicePoolActor.kt:71`) and the
  Scheduler reads `aggregateResult` after the pools (`Scheduler.kt:71`). `testStarted` has no production
  caller (C4). So no other coroutine can observe an accumulator half way through `testEnded`, and design
  (a), splitting the 3.5 module, buys nothing. `tokio::sync::Mutex` works on the `!Send` core (its guard is
  not a `RefCell` borrow; clippy's `await_holding_refcell_ref` stays clean). The queue takes the lock once per
  outcome message, from before the first `testEnded` to before `onBatchReleased`, so locking adds no await
  between steps Kotlin runs without suspending. No change to the merged 3.5 module.
- **Handler state** is owned by the `ActorHandler` (`&mut self` in the receive loop), so no borrow crosses an
  await. Maps Kotlin iterates are `IndexMap`s (`activeBatches`, whose keys the debug line joins, and
  `retryWorkers`, which Notify flattens); removals use `shift_remove`, keeping LinkedHashMap order. The others
  (`workers`, `activeRetries`, `uncompletedTestsRetryCount`, `groupingBy` counts) are `HashMap`s used only for
  lookups.
- **`pool.send` failure.** Kotlin's `pool.send` throws on a closed pool and the exception ends the queue. The
  port returns the error from the handler: a `SendError` with a cause becomes that failure, one without (a
  cancelled pool) or a pool that is gone becomes a cancellation. 3.8 never closes the pool before the queue
  in normal operation (`terminate` awaits the queue first).
- **Errors that escape a handler** (a `BatchingError`, a tracker or output failure from `test_ended`, a timer
  error, an observe error) end the actor through 3.1's `RuntimeActor`, which logs
  `CoroutineContext closing due to unrecoverable error` under the queue's logger; the JVM probe shows the
  same line (row “a batching exception restores the copies set aside”).
- **Cancellation:** `test_ended` gets the queue receiver job's signal (3.5 handoff), so `close()` also stops a
  tracker delivery in flight.
- **Start:** `spawn` starts the actor at once, like `DeviceActor::spawn` and Kotlin's eager actor.
- **P1 (approved):** `prepare` fails with the prefetch's error. The provider absorbs fetch failures, so this
  is in practice a cancellation; no queue is built on fallbacks.
- **P2 (approved):** an `Err` from `observe_execution_times` ends the actor like any handler error.
- **P3 (approved):** after a handler error the state is what the `?` early return left; only "the actor
  ends, the error is logged, later sends fail" is pinned (`queue_behaviour::handler_failure_ends_the_queue`,
  the oracle's batching-exception row).
- **P4 (approved):** K2, K3 and the duplicate-incomplete partition are ported literally; the oracle rows use
  only shapes a run produces (ClassName batching with flaky copies, sharding copies).

## Deviations from the brief

- `QueueMessage::RequestBatch` wraps the `RequestBatch` struct, so `RequestBatches(Vec<RequestBatch>)` and
  single requests share one type. `Completed` and `ConfirmOutcome` carry their `DeviceInfo` (Q:363, 370).
- `prepare` also takes the vendor runtime and a cancellation signal: it runs the prefetch through
  `call_vendor`, i.e. off core, which a plain `&Analytics` future awaited on core would not.

## Known Kotlin bugs reproduced (D5)

- **K1 → C45 (confirmed):** under fast ALL_SUCCESS the failed attempt completes the test, its copies are
  removed, and it is still queued as a retry; it runs again and is tracked with `final = false`.
- **K2 → C46 (confirmed):** with two failed copies of one test in a ClassName batch and quota for one retry,
  the second copy never gets `testEnded` (one Track call, test left `Passing` with total 4).
- **K3 (refuted):** `dispatched` counts after the batch removed its copy, but ClassName takes every copy of
  a test and FixedSize never batches two, so each copy still takes one retry worker while any is left; both
  K3 rows show the intended per-copy bookkeeping. No row added.
- **K4 → C47 (confirmed):** a batch rejected after its test completed on another device queues the test
  again; it runs once more, tracked `final = false`.
- **C5:** the queue replay shows the refused retry's phantom total (`queue_oracle::phantom_add_retry_through_the_queue`).
- **C30:** one strategy per queue (`queue_behaviour::retry_quota_applies_per_pool`).
- **C4:** the queue never calls `test_started`; the corpus has only ended lines.
- **C33:** the execution-time row's first FixedSize:3 batch has two tests because the flaky copy took a slot.

## Review round 1

- **R1-sol-1:** `QueueActor::prepare` now observes the caller signal passed into the
  `call_vendor` body, preserving the cancellation reason (including timeout scope).
  The cancellation race is inside the vendor task; the bridge itself is always
  awaited through completion, so preparation never detaches vendor work. A final
  caller-signal check also covers cancellation while the completed result resumes
  on core.
- Cancelling preparation drops only that call's `Analytics::prefetch` future,
  matching 3.4a P4 and its aborted-holder semantics. An interrupted fetch releases
  the single-flight mutex without publishing a cache entry or query logs. The
  run-wide analytics signal is unchanged; another pool can refetch, and cancelling
  a waiting pool leaves the active holder's query and memoised result intact.
  No changes to the analytics provider or vendor bridge were needed.
- `queue_prepare.rs` adds four regressions: the reviewer's blocked-fetch witness
  with exact timeout-reason preservation; prompt holder cancellation without a
  fetch release, with no detached work/logs/cache and successful refetch; waiter
  cancellation preserving another pool's single-flight query; and cancellation
  before an empty prefetch. Requested and parent cancellation reasons are also
  checked exactly.
