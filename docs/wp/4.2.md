## Behaviours to reproduce (exact sources)

**Connect and auth.**
- `withRetrySync(connectionAttempts, 0, logger)` wraps only `newClient()` + `connect` (`S/SshjCommandExecutorFactory.kt:49-53`, `Retry.kt:26-41`). Every attempt uses a fresh client. A failed one is closed and the close error suppressed (:67-78). Any throwable is retried, with WARN `Retrying after failure` plus the throwable on `…sshj.SshjCommandExecutorFactory`. That logger is ERROR unless marathon `debug`, so the line is normally invisible. The last failure is rethrown.
- Host-key rejection happens inside `connect`, so it costs 4 attempts (T17). Authentication runs once, outside the retry (:54-55; T12: wrong password = 1 attempt).
- sshj resolves with `InetAddress.getByName` (the first address) and uses no client connect timeout (OS timeout; T12 M: 4 × ~17 s). Its transport reply timeout is 30 s (KEX, auth, channel open/close). Add no client-side timeout of our own.
- `authPassword` tries `password` and then `keyboard-interactive`, answering a `Password:` prompt (R4). `PublicKey` loads the key file eagerly. A missing file is `FileNotFoundException`, not wrapped. Decryption of an encrypted key fails at auth inside `UserAuthException` (T13 chains). Unencrypted PPK v2/v3 must load (no deviation; `ssh_key` `from_ppk`). Exhaustion is `UserAuthException[UNKNOWN]("Exhausted available authentication methods")` (T12).
- The method sequence on the wire must match the auth events in the Kotlin fake-worker evidence.

**Host keys (R3).**
- Port sshj's measured matching: unparseable lines are skipped, not fatal; any matching key of the negotiated algorithm accepts, even with a differing same-algorithm entry before or after it; tabs and runs of spaces; hashed `|1|` entries; `[host]:port`; comma lists; `*`/`?` wildcards; the literal `![127.0.0.1]:port,*` **accepted** (do not infer OpenSSH negation); case-sensitive host names; an entry of another algorithm only means unknown.
- A missing file behaves as empty. Rejection is `TransportException[HOST_KEY_NOT_VERIFIABLE]`, non-transient, after 4 attempts. Its exact message (with fingerprint) comes from the oracle, not from memory.
- **sshj reorders its host-key algorithm proposal** by `HostKeyVerifier.findExistingAlgorithms(host, port)`. `javap` shows `KeyExchanger` calling it while building the client proposal, so a known_hosts entry decides which server key is negotiated. Reproduce it by ordering russh's `Preferred::key` per connection from the verifier. Accept-any returns none.
- Markers (`@cert-authority`, `@revoked`) are unmeasured (P4).

**Keep-alive (R7, §3.6).**
- Interval = `keepAliveInterval.toSeconds().toInt()` (:86): 1500 ms → 1 s; 999 ms, 0 and negative values → disabled.
- `KeepAliveRunner` (`javap`): sleep one interval; only once the connection service is active (after auth); drop answered promises (a `REQUEST_FAILURE` reply counts as answered); then, if `outstanding >= maxAliveCount`, kill the transport with `ConnectionException[CONNECTION_LOST]("Did not receive any keep-alive response for <max × interval> seconds")`; otherwise send `keepalive@openssh.com` with want-reply and queue it.
- Channel traffic never clears outstanding requests: T25 is lost at ~3 s while output keeps flowing. Loss after `(max+1) × interval` of silence (T09 5.9 s for 2 s × 2, T10 3.0 s). An in-flight `await()` then fails and `connected` turns false.
- Disable russh's own keep-alive and run this as an owned task. The loss also logs ERROR `TransportImpl - Dying because - <message>` by default (P1).

**Execute** (`S/SshjCommandExecutor.kt:37-65`).
- `startSession` checks run first (A17).
- Channel open failure: `OpenFailException`, a subclass of `ConnectionException` (T08, MaxSessions; fake `max_sessions` answers code 4). `safeExecute` must still catch it. 4.1's `safe_execute` matches the exact class string today (`crates/marathon-apple/src/cmd/mod.rs:133-160`), so the hierarchy has to be represented (open question 2).
- Exec rejection: `ConnectionException[UNKNOWN]("Request failed")`, connection still usable (T23). Check with the fake whether Kotlin leaves that opened channel holding a session slot. If so it is a new A-row, and Rust reproduces it.
- `env` and `workdir` are ignored (A2). Charset is UTF-8 (D10).
- **`shell_command`** byte-identical (:79-102; A12, T03): an argument that starts and ends with `'` or with `"` passes through untouched; otherwise any of the 22 characters at :97 → `'` + replace `'` with `\'` + `'`; else verbatim. Joined with a single space. An empty argument stays empty, and a one-character `"`/`'` argument counts as "escaped".
- **Readers** (:50-52): one shared `lastOutputTimeMillis` taken from 4.1's labelled clock seam at execute time. stdout and stderr (extended type 1) each run 4.1's reader with `can_read = channel open && !EOF` and capacity `channel_capacity`. EOF ends both readers after their buffered data. Idle timeout text is `idle timeout <Duration.toString()> reached` (T14). U10/H5: on local close, drain buffered tails regardless of the closing flag (T14.timeout_partial: `exit=null stdout=[partial]`).
- Transport death ends the readers normally, because sshj's `available()` doesn't throw and `isOpen` turns false. The error surfaces through the exit wait (this answers R2-wonder-3 for SSH; test it).
- **Late or invalid data** (`PatchedExecChannel.kt`): data after EOF or close is dropped silently. An extended type other than 1, or a malformed packet, makes sshj's reader thread die with that `ConnectionException[PROTOCOL_ERROR]`, which kills the **whole connection**. Confirm the extent with the fake's `extended: 42`.
- **Exit wait** (:104-123):
  - Poll with `PollBackoff`. While open, never call `join`. Once not open, `join(1 ns)`: a poll timeout (a `ConnectionException` caused by `TimeoutException`) is retried; any other `ConnectionException` is rethrown.
  - Then `close()`, then `exitStatus ?: (TERM → 143, else null)`. No exit status and no signal → null.
  - Keep the poll structure behind a seam, so that the 5 mock rows port literally and the up-to-20 ms granularity stays.
- **Timeout branch** (:53-62):
  - `withTimeoutOrNull(timeout)` (`toMillis`, through `VendorClock`). On expiry the cancelled wait leaves the channel alone, then TERM, then `close()`.
  - That close waits for the peer's CLOSE up to 30 s and can throw, so the exit cell **fails** with `ConnectionException(TimeoutException)`, and `safeExecute` turns that into null (T15h: failure at ~31 s; T15t: an ignored TERM gives null after ~8 s, and the executor stays usable).
  - **D7:** when the wait itself returned null (a non-TERM signal, or no status), do **not** send TERM. The following close is a no-op on the already-closed channel.
  - TERM, CLOSE and session `close` must reach the wire in call order. A synchronous `terminate()` therefore enqueues onto an ordered per-channel queue; it never blocks or spawns unordered.

**Session** (`S/SshjCommandSession.kt`).
- `is_alive` is the value captured at construction (A11, T22).
- `terminate`/`kill` send `signal` TERM/KILL without want-reply. A dead transport is a `TransportException`.
- `close` (A14):
  - Only the first call does anything; the `closed` flag is set before the work (:32).
  - If the channel is open, TERM; then `command.close()`: send CLOSE if not yet sent, wait up to 30 s for the peer's CLOSE, and throw after that, before the join. Then an unbounded `join()` (T15h: a later close still waits at 60 s). Then `super.close()`, which cancels and joins the session scope. No KILL escalation.
  - Await cancellation kills nothing remotely, and the executor survives (T22).
- **Await concurrent with close (T07/T14)**: Kotlin's await observes `JobCancellationException`, because `cancelAndJoin` usually beats the exit poll's ≤ 20 ms backoff after `join()` returns. The Rust spike returned instead. See P2.
- **T14's 45 s Kotlin close delay** (unresolved) is consistent with window starvation. Kotlin readers stop reading, so they stop adjusting the window, once close makes `isOpen` false, while sshd still has output queued. Test that hypothesis with the fake (flood + close) before choosing a design. It interacts with the flow-control item below.

**Flow control (new; not in the spike checklist).**
- russh adjusts the window when data is **received** and then `send(...).await`s into each channel's bounded mpsc **on the session loop** (`vendor/russh/src/client/encrypted.rs:586-600, 613-631`).
- If one command's consumer stalls, the whole connection stalls. Every channel, every simulator sharing the worker connection (`shareWorkerConnection`) and the keep-alive replies all wait, and keep-alive could then report a healthy-but-busy worker as lost.
- sshj adjusts the window only as each `ChannelInputStream` is read, so a stalled consumer stops only its own channel, and the remote blocks on that channel alone.
- Required test: two channels on one connection, one consumer stalled, while the other channel and keep-alive keep progressing (fake `keepalive: answer`). Design choice: open question 1.

**Executor.**
- `connected` = transport alive.
- `close()` disconnects. An I/O error is logged at ERROR as `Error disconnecting <addr><port>` (:71), and the colon really is missing: a new A-row candidate, kept under D5.
- Logger `com.malinskiy.marathon.apple.cmd.remote.ssh.sshj.SshjCommandExecutor`, level set at construction (C18).
- `safeExecute`'s two log lines are 4.1's.

**Known Kotlin bugs:** A2, A11, A12, A14 and A17 are reproduced, each confirmed by a named Rust test. A13 is not kept (D7). A15 needs P3. A16 lives in `ConnectionFailures.kt` (4.3) but depends on 4.2 reporting a no-common-KEX failure as `TransportException[UNKNOWN]` (T26). Candidates to add: the missing colon at :71, and the exec-rejection channel leak if measured.

## Proposed simplifications (pragmatic parity: for orchestrator approval, **not decided**)

Few users, so don't emulate quirks that only exotic inputs reach. D7 and D10 already apply. Until a proposal is approved, the behaviour above stands. Each approved item becomes a PLAN §3.11 entry and marks its evidence rows; nothing is silently dropped.

- **P1, sshj's own log lines:** emit only the two library lines that are visible by default. These are ERROR `TransportImpl - Dying because - <message>` on transport death and the exec channel's DEBUG `Will request to exec \`<command>\`` under `ssh.debug` (the line `PerformanceDefaultConfigTest` and 4.3's `WriteFile` secrecy rely on). Drop `Promise - <<kex done>> woke to: …` and the rest of sshj's DEBUG chatter. Under `ssh.debug`, russh's own records go to DEBUG under their crate targets. Thread names already differ (§3.10).
- **P2, await concurrent with close:** make Kotlin's dominant outcome deterministic. An `await()` that hasn't completed by the time `close()` finishes its join observes `Cancelled` (T07/T14), rather than whichever task wins. Only that race changes.
- **P3, A15 not reproduced:** implement password → keyboard-interactive correctly and do not try to recreate the 30 s macOS wrong-password timeout, whose cause is unresolved and which can't be reproduced deterministically. A wrong password then fails fast and is non-transient (the worker is retired, not retried). Record A15 as "not reproduced", with that reason.
- **P4, known_hosts edges:** support exactly the T17 matrix plus malformed-line skipping. Treat `@cert-authority`/`@revoked` lines as unparseable (skipped) unless an oracle probe shows that sshj 0.39 uses them.
- **P5, second close:** after a failed first close, a later `close()` skips the backend (as Kotlin does) but still cancels and joins the session scope (4.1's retry path), instead of leaving readers and the exit task running. The difference is visible only after a 30 s close failure.
- **P6, rows:** `SshTest.testSigint` → `n/a` ("body commented out; asserts nothing"), which needs reviewer agreement. Don't port the memoised random factories (no observable effect).
- **P7, numeric edges:** saturate instead of wrapping `toSeconds().toInt()` for intervals above `Int.MAX_VALUE` seconds, and saturate `max × interval` in the loss message. Neither is reachable by a sane config.
- **P8, address selection:** connect to the first resolved address only, which is Java's behaviour and simple to do. Listed only so that nobody "improves" it to try every address.

## Open questions for the orchestrator
