# x1: an Android device that disconnects during prepare and reappears with the same serial

## Trigger

A CI run of the Rust build (4 adb hosts × 2 emulators, debug off): one emulator's device actor was still in `prepare` when
adam failed with `RequestRejectedException: closed`. About 0.25 s later the provider logged
`Device emulator-5556 changed state to DISCONNECTED` and the actor's initialize job was cancelled. About 4.3 s later the
same serial (and its sibling `emulator-5554`, late to boot) logged `CONNECTED` again. The reconnected device did not run a
test in the remaining ~7 minutes. A code read found Rust matching Kotlin step by step.

## What was built

| What | Where |
|---|---|
| Strict fake-adb scripts (20 remote-discovered tests, 4 s each; a hung or failing prepare; the drop and re-list on the fake's timeline) | `fixtures/fake-adb/android-reconnect/script/`, generated by `tools/oracle/android-reconnect-probes/generate` |
| Kotlin and Rust **CLI** runs of the same scripts on fresh loopback fakes (real time) | `tools/oracle/android-reconnect-probes/run` → `fixtures/fake-adb/android-reconnect/expected/` (`SHA256SUMS`) |
| Rust regression tests: the real provider, scheduler, pool, device actor, installer and runner in one `run_virtual` executor against in-process fakes | `crates/marathon-android/tests/reconnect_test.rs` |

The Rust tests step Marathon's virtual clock (50 ms steps, 4 ms real pause for the loopback sockets after each step) and
apply the script's timeline events at the same virtual times, but only once the run has reached the state the scenario
needs: the provider's earlier events have reached the scheduler (the provider is wrapped so the test sees what the
scheduler receives), every device the fake lists has finished setup (its logcat stream is open), and a device about to
drop is in the hung step of prepare (the `rm` request has arrived). Until then virtual time keeps stepping, so an event can
be late (the test fails if it is more than 3 virtual seconds late) but never early. The fake's real-time timeline and
`delay_ms` are removed; a test takes four virtual seconds through a wrapper around the real `AndroidRunnerExecutor`. Each
test compares state changes, batches run, and per server/serial whether a batch started before the drop and after the
reconnect with the Kotlin CLI's recorded outcome (`expected/<scenario>-kotlin.json`, `compare`), asserts that the strict
fakes recorded no warning, and, for the same-server case, that the scheduler received Connected(old), Disconnected(old) and
Connected(new) with two different device objects. The four tests take about 12-14 s together and were stable over 10 consecutive runs, and 3 runs with the CPU loaded.

## Scenarios and results

All timeline times are fake-relative: `emulator-5556` is dropped at 8 s and listed again at 12 s; its first `rm` (the second
step of prepare, after the installer) hangs, so prepare is in progress at the drop.

| Scenario | Rust test | Kotlin CLI | Rust CLI | Rust virtual-time test |
|---|---|---|---|---|
| `same-server`: two emulators on one server; 5556 appears at 4 s, hung in prepare, dropped, re-listed | `reconnected_device_gets_work_after_prepare_was_interrupted` | CONNECTED, CONNECTED, DISCONNECTED, CONNECTED; 20 batches; 5556 runs batches after the reconnect | identical | identical |
| `same-server-flaky`: as above, and the reconnected 5556 fails `cmd package install` 6 times (two prepare attempts of three) before succeeding | `reconnected_device_gets_work_after_transient_prepare_failures` | 6 `Error while installing`, 5556 gets work after two 10 s retries | identical | identical |
| `cross-host`: two servers, each with `emulator-5556`; the map entry is the dropped device (A's appeared last) | `same_adb_serial_on_two_servers_drops_the_right_device_when_it_is_the_latest_entry` | A disposed, B keeps working, A's new device gets work after the reconnect; 20 batches | identical | identical |
| `cross-host-shadowed`: the same, but B's device appeared last (the map entry is B's healthy device) | `same_adb_serial_on_two_servers_disposes_the_healthy_device_when_it_shadows_the_dropped_one` | see below; 21 batches | identical | identical |

**No Kotlin/Rust difference was found in any scenario** (state-change lines, number and placement of batches, exit code,
final line). Interleavings of equal-time log lines differ between runs of either build (for instance whether
`initialization failed. Retrying` precedes `changed state to DISCONNECTED` at the drop) and are not compared.

## Verdict

1. **Same server, same serial: the reconnected device does get work**, in Kotlin and in Rust, also after transient prepare
   failures (the 30 × 10 s retry). The old actor is terminated, a fresh actor is initialized for the new device object and
   receives batches. This scenario does not reproduce the "never ran a test" symptom.
2. **Same adb serial on two servers (N27) is the only path found that strands a device**, and it is the Kotlin behaviour,
   kept. The provider's `devices` map is keyed by adb serial alone, so a drop on server A is reported against whichever
   device object was stored last for `emulator-5556`:
   - if that is B's (`cross-host-shadowed`), B's healthy actor is terminated and its running batch returned; A's actor is
     not removed; A's reconnect is ignored by the pool (`W device emulator-5556 already present in pool omni`); A's old
     actor recovers only after its own 10 s prepare retry, and B never gets work again (2 of 21 batches).
   - A production run with 4 hosts that all have `emulator-5554` and `emulator-5556` has this collision for every serial,
     so which device is lost depends on the order the hosts' lists were processed. With real emulators the stale actor's
     retries may keep failing (the fake lets a new session through at once), which would give "the reconnected device never
     ran a test". That part is not shown here.
   Recorded in `docs/known-kotlin-bugs.md` (N27, extended with this witness). No product code was changed.
3. Nothing in the Rust code diverges from Kotlin on this path, so the Rust run needs no fix for parity. If the owner wants
   the multi-host case fixed (key the map by `host:port:serial`), that is a deliberate deviation (a new D-entry in
   PLAN §3.11), not a bug fix.

## Notes on the harness

- Timeline events are relative to the fake's start; the CLIs need 2–4 s to reach prepare, so the scripts keep the second
  emulator out of the remote parser's way (it borrows a random device, and a hang or install failure there changes the
  scenario): the late device connects at 4 s (same server) or 2 s (cross-host).
- The first attempt at `cross-host` had both devices present at start: the winner of the map entry was a race (Kotlin kept
  A's, Rust B's in one run each), and the runs differed. Staggering the appearance (`cross-host` vs `cross-host-shadowed`)
  makes each order deterministic and both builds agree in both.
- `tools/oracle/android-reconnect-probes/run` takes about 7 minutes for all scenarios and both CLIs; it needs the built
  Kotlin distribution and `cargo build -p fake-adb -p marathon-cli`.

None found in third-party code or tools.
