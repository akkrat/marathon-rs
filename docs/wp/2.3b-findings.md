## Other notes and open questions

- Frame EOF class: closed in review round 1. A real ktor socket gives
  `kotlinx.coroutines.channels.ClosedReceiveChannelException` in every
  segment and on a frame boundary (`frame-eof-probe`); `Truncated`
  carries that class and ktor's messages.
- Extraction writes files in central-directory order and stops at the
  first failing entry, leaving partial trees exactly where Kotlin
  would; S1 rejection happens at the escaping entry, so earlier
  entries are already extracted (Kotlin would have extracted them
  too, plus the escaping one outside). A default destination that
  survives its cleanup fails before any entry (review round 2).
- The two-item Watch rule is evaluated lexically on the search-root
  spelling (all matches share it), instead of Kotlin's
  `File.relativeTo`, which throws for differing roots that cannot
  occur under one root.
- `bind_devices_bytes` does not force `Profile::Marathondevices`; the
  caller supplies the context (WP 2.4's loader builds a P2 context for
  `devices`). Passing a P1 context would re-enable P1 `File`
  canonicalisation — noted for WP 2.4.

**Recorded simplifications (orchestrator-accepted).** Each has a probe
row that `bundle_probe_matches_jvm` asserts as a divergence:

- R1-sol-3, duplicate entry names (F28): the zip crate keeps the last
  copy at the first one's position, `ZipFile` keeps both. Only an
  extraction that fails between the copies ends differently (probe
  `duplicate-entries`: the JVM leaves `FIRST`, the port `LAST`).
- R1-sol-4, failed `mkdirs()` (F26): reported as `java.io.IOException`
  (`cannot create directory <path>: a file is in the way`) where Kotlin
  goes on (probe `mkdirs-ignored`, which the JVM validates). The same
  check makes a file entry under a file parent an `IOException` where
  Kotlin's `FileOutputStream` throws `FileNotFoundException`.
- R1-sol-7, CRC (F27): a stored entry with a wrong CRC is rejected
  (`java.io.IOException`, the crate's checksum message); the JVM
  extracts the corrupt bytes (probe `bad-crc-stored`).
- R1-sol-8, cause chains: extraction errors keep one class and our
  message, not the JVM chain (for example `FileNotFoundException →
  FileSystemException` for a file parent, probe `duplicate-entries`).
  Only exotic broken archives produce such chains.
- R1-claude-5, symlinked extraction dir (F25, next to F20): the cleanup
  unlinks it and recreates a plain directory; Kotlin's
  `deleteRecursively` follows it and empties the target (probe
  `symlinked-destination`). Not reproduced, a safety fix like S1.

**Disagreement / deviation from the brief.** Item 3 said to build paths
from `entry.name_raw()`. In zip 2.6.1 that is not the stored name when a
valid 0x7075 field is present: `read.rs` replaces `file_name_raw` itself
with the field's UTF-8 name, so `name_raw()` would still follow the
field Java ignores (checked: the `unicode-path-extra` row fails with
`name_raw()`). The port therefore reads the name from the entry's
central-directory header (`central_header_start()`, a 46-byte fixed
part, then the name), which is what `ZipFile` decodes. No other
disagreement.

**Recorded simplifications (orchestrator-accepted).** Both need a
malformed archive:

- R2-sol-2, an invalid 0x7075 payload (probe `unicode-path-invalid`,
  asserted as a divergence): the JVM never reads the field and
  validates; the zip crate's directory parse fails on the non-UTF-8
  payload, so the port fails with `java.util.zip.ZipException`
  (`invalid Zip archive: Could not find EOCD`). The port's own walk
  starts from the crate's central-directory offset, so the first parse
  still sees the field.
- R2-sol-3, a prefixed ZIP64 archive whose ZIP64 locator and offsets
  were not shifted: the JVM rejects it (`ZipException: invalid END
  header (bad central directory size)`), the zip crate finds the
  directory and the port extracts it. Ordinary ZIP64, prefixed ordinary
  zips and prefixed ZIP64 with corrected offsets behave alike on both
  (Sol's `more.log`, re-run). No probe row: the JVM probe would need a
  hand-written ZIP64 writer; Sol's harness is the evidence.

**Carried to 2.4.** The Marathondevices binding profile: `bind_devices_bytes`
takes the caller's context, so WP 2.4's loader must build the P2 context
for `devices` (see "Other notes"). Cloned bundle validation:
`post_process_*_with_bundle_validation` validates a fresh resolved copy
of the bound bundle (Kotlin's factory builds a new one) and every
`validate()` re-extracts the archives, so WP 2.4 decides how stage (b)
holds and reuses the mutable, resolved bundle.

**Carried to 5.5a.** Off-core binding: `FrameDecoder::feed` and
`bind_devices_bytes` block (documented) and must be called off the core
executor. Terminal EOF: the decoder's `Truncated` (boundary close
included) must stop the provider for good, wired into A1's permanent
stop.

No disagreement with the orchestrator's decisions.
