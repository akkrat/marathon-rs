# WP 8.7: An ordered test queue instead of the Java `PriorityQueue` port

Effort **M**. Branch `wp/8.7-ordered-test-queue`, based on `main` after WP 8.6b (commit `a830d106`).

## Why

Phase 8 removes Java emulation while keeping the contract in PLAN.md §3.12. Test queues still use
`jcompat::JavaPriorityQueue` (`crates/jcompat/src/priority_queue.rs`), a port of the JDK 21 binary heap
driven by a stateful comparator (`strategy/sorting.rs` `TestComparator`). Its JVM artefacts are visible:

- **Ties have no order.** Equal-priority tests (all of them under `NoSorting`, many under the other
  strategies) come out in whatever order the heap's sift steps leave them, not the order they were added.
- **Iteration follows the backing array.** `queue.iter()` (`execution/queue.rs` retry bookkeeping, the
  test-support `QueueSnapshot`) sees heap layout, not priority order.
- **Comparator call order is observable.** Keys (metrics lookups, `RandomOrder` draws) are computed lazily
  inside comparisons, so which key is computed first depends on heap shape (see the `sorting.rs` header
  and D34).

## Scope

1. **A small ordered queue type** in `marathon-core` (for example `strategy/queue.rs` or next to
   `sorting.rs`): a `BTreeMap<(Key, u64), Test>` or equivalent, where `Key` is the strategy's sort key and
   `u64` an insertion sequence, so equal keys come out first-in, first-out. Keep the operations the core
   uses (`add`/`offer`, `add_all`, `poll`, `peek`, `remove_all` with duplicates, `len`, `is_empty`, `iter`)
   with the same meaning, except that `iter` now yields priority order.
2. **Keys instead of comparators.** Each sorting strategy computes a test's key once, when the test is
   added: execution time from the queue's metrics snapshot (D34's rule that a queue keeps the history of
   its build stays), success rate likewise, a random key per test for `RandomOrder` (drawn through the
   existing replay hook `RANDOM_KEY`, once per test, in insertion order), and a constant for `NoSorting`.
   Keep the strategies' direction and tie rules as they are where they define one (descending duration,
   the success-rate order, and so on); the sequence only breaks ties the strategy leaves.
   - Floating-point keys need a total order: use `f64::total_cmp` or an ordered wrapper, with NaN placed
     where `jnum::double_compare` placed it today.
3. **Delete `JavaPriorityQueue`** and its tests once nothing uses it, and the CLAUDE.md rule that names
   it ("Use `JavaPriorityQueue`, never `BinaryHeap`, for test queues"): replace it with a pointer to the
   new type. PLAN.md §3 entries that describe the heap port as a parity requirement get a "superseded by
   D60" note, not a rewrite.

**Out of scope:** batching rules (`strategy/batching.rs` keeps its logic and only switches type), the
sorting strategies' configuration and meaning, any other scheduling change.

## Behaviour change (D60)

Add **D60** to PLAN.md §3.11 (same format as D55–D59): rc.1 orders tests of equal priority, iterates the
queue and computes sort keys in the order of the JDK heap; 8.7 orders equal priorities first-in,
first-out, iterates in priority order, computes each key once when a test is queued, and draws
`RandomOrder` keys in insertion order (so a given seed may give a different random order than rc.1).
State exactly which visible things change: test execution order among equal priorities, batch contents
where a batch takes from the queue front, retry bookkeeping order, log lines that list the queue.

## Rules

- Tests that pin heap layout, tie order or comparator call traces are rewritten to the new order or
  deleted; list each in `docs/wp/8.7-test-changes.md` with a one-line reason. Parity rows of deleted
  tests become `n/a` with reason `8.7: D60`. Tests of strategy order on distinct keys keep their
  expectations.
- Property test: for random sequences of add/poll/remove_all on random keys, the queue behaves like a
  stable sort by key (a small reference model in the test).
- Never edit a copied fixture under `fixtures/`; add new files instead.
- Keep `//! Port of ...` headers and comment density; delete comments that only explained the heap.
- No `unwrap()`/`expect()` on I/O, process or network results.
