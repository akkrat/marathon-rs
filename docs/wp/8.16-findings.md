# WP 8.16: native image handling (D63)

The milestone-1 design at `034eb7ed` was approved for implementation as D63.
The inventory in [the design](8.16-design.md#inventory-and-per-item-decisions)
is the baseline; this document records the implementation and independent proof.

## Incidental bugs: U190, independently proving the RGB10 output

The source is the unchanged `fixtures/adam/fixture/screencap_1_unaligned.bin`.
Its 48-byte header advertises a 1080×1920, 32-bit image with offsets/lengths:
R `(0,10)`, G `(10,10)`, B `(20,10)`, A `(30,2)`. Protocol version 1 has no
profile tag, so these encoded RGB samples are interpreted as sRGB. No ICC
transform is involved in this proof.

Decode each little-endian word as the integer decomposition
`R + 1024*G + 1048576*B + 1073741824*A`. Each RGB range is 0..1023 and alpha is
0..3. Normalize the advertised ranges to 0..255, rounding RGB to nearest.
Independent integer division/remainders plus Python Decimal `ROUND_HALF_UP`
produce the following fixed values, without calling the Rust decoder:

| Pixel (x,y) | Source bytes | Word | R10, G10, B10, A2 | Expected sRGB RGBA8 |
|---|---|---|---|---|
| 0,0 | `34 82 86 de` | `0xde868234` | 564,416,488,3 | 141,104,122,255 |
| 500,600 | `b8 a3 49 ef` | `0xef49a3b8` | 952,616,756,3 | 237,154,188,255 |
| 1079,1919 | `1c 51 c3 d4` | `0xd4c3511c` | 284,212,332,3 | 71,53,83,255 |
| 100,100 | `2c 53 c9 eb` | `0xebc9532c` | 812,596,700,3 | 202,149,174,255 |

For example, `564*255/1023 ≈ 140.5865`, rounding to 141. All four samples now
match both adapters and `get_argb`; the regression checks the source words and
literal expected pixels, not a generated expected hash.

The old emulation left-shifted a channel by `8 - length`. For length 10 this
wrapped to shift 30. A census of all 2,073,600 source words finds **zero**
violations of “all RGB samples divisible by four; alpha =3”. Thus every old
RGB component shifted to zero, while alpha became `3 << 6 =192`. Independent
Pillow decoding of the baseline Rust PNG finds exactly one color:
**2,073,600 occurrences of `(0,0,0,192)`**. It was entirely flat black, not a
correct screenshot. The source words plainly contain nonzero, varying colors.

D63 fixes this emulation bug, recorded as **U190** in `docs/found-bugs.md`.
The corrected PNG is 394,679 bytes, compared with 12,352 before; every pixel
changes. Maximum/mean absolute difference over all RGBA bytes is
254 / 132.57370502989968. The large error and file-size increase represent
restored image information, not degradation. A one-level difference from some
historical buffered/8-bit fixture pixels follows the approved 10-bit range
normalization; it does not invalidate the independent raw-word proof.

The independent four-pixel calculation is reproducible from the repository root:

```python
from decimal import Decimal, ROUND_HALF_UP
from pathlib import Path
source = Path('fixtures/adam/fixture/screencap_1_unaligned.bin').read_bytes()
for x, y in [(0, 0), (500, 600), (1079, 1919), (100, 100)]:
    offset = 48 + 4 * (1080*y + x)
    word = int.from_bytes(source[offset:offset+4], 'little')
    values = [word % 1024, (word // 1024) % 1024,
              (word // 1048576) % 1024, word // 1073741824]
    rgb = [int((Decimal(v)*255/1023).quantize(Decimal(1),
                rounding=ROUND_HALF_UP)) for v in values[:3]]
    print(x, y, hex(word), values, rgb + [values[3]*85])
```

## Transparency after quantization

`gif` 0.13.3 normalizes nonzero alpha to 255 but chooses one transparent palette
index from a source zero-alpha pixel. Canonicalizing all zero-alpha hidden RGB
values to zero ensures they quantize together. After quantization, the writer
sets each source zero-alpha pixel to that index. If an opaque pixel received the
same index, it selects the closest RGB palette entry excluding the transparent
one. This keeps the exact binary mask, including opaque black; it does not
force a particular palette index or modify the quantizer for opaque frames.
The guarantee concerns each encoded frame: disposal 0 still lets transparent
pixels retain earlier canvas content when a viewer composites later frames.

The high-color regression uses three 64×64 patterns (ordinary, dark and bright
colors), each with more than 256 distinct opaque RGB colors, mixed zero/128/255
alpha, and different hidden RGB values under zero alpha. Each is encoded
in a two-frame sequence with complementary transparency masks. Decoding checks **every alpha value in all 24,576 frame
pixels**, plus dimensions, 120 ms delay, disposal 0 and one loop extension.
A separate controlled palette-collision test forces the fallback branch and
checks that opaque pixels stay opaque. The small copied alpha witness separately
pins exact retained RGB and the zero/nonzero alpha policy.

## Byte identity and intended differences

SHA-256 regressions pin the pre-D63 **encoded** outputs, not only pixels:

| Common output | Bytes | SHA-256 |
|---|---:|---|
| `screencap_1` opaque 8-bit PNG | 395,051 | `4c685a153a993f373fc74cd4b614e75d175bd76f0d4e3f00b3d5c93159939025` |
| Opaque 32×32 gradient GIF, one frame | 1,470 | `99041382c522e495f239b4c36cad29d340d36fab74e5ecb4de4c6188360cba83` |
| Opaque 2×3 flat-color GIF, one frame | 88 | `92447fc0a7c30b135c647e1defb811c011bbe8d5e3afe694913b47d183db00e0` |

These identity claims apply to unchanged sampling/geometry and the ordinary
unprofiled 8-bit path. They do not hide the approved exceptions: explicit sRGB
tags lose one-level ICC noise (3 raw pixels in `screencap_3`), P3 sources change
colors (raw 32×32 witness mean/max 7.384033203125/115; buffered
0.010498046875/1), nearest ties change edge pixels, partial-alpha GIF pixels
become visible, and repeated loop extensions disappear even from opaque
multi-frame GIFs. The two-frame opaque prototype goes 156→137 bytes with equal
pixels, frame count and delays. These differences are stated in D63; the full
supplemental tables in the design remain applicable.
