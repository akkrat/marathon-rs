# WP 6.3 findings

Instrumentation parser, `TestAnnotationParser` v2–v4, logcat `-v long` parser.
Brief: `docs/wp/6.3.md`; its "Orchestrator decisions (2026-10-24)" section
governs where it conflicts with earlier text.

## Decisions taken

All five open questions were settled by the orchestrator decisions in the
brief, and implemented as decided:

1. `LogcatListener`/`LogcatProducer` moved to 6.3 (inventory already updated);
   they are synchronous `Arc` traits in `crates/marathon-android/src/logcat_listener.rs`,
   shaped like core's `LogProducer`. 6.6a consumes them.
2. `InstrumentOptionsTest`/`TestRunnerRequestTest` belong to 6.6a; not ported here.
3. The event model (`TestEvent`, `TestIdentifier`, `Status`, `TokenType`) and
   the transformer live in `marathon-adb` (`testrunner.rs`, `instrumentation.rs`),
   with the `process`/`transform` seam 6.1 feeds.
4. Logcat evidence is source-derived tests plus fixtures; no Kotlin fake-adb run
   in this WP. U26 is handled by reproducing the year-header rejection and by
   the new corrected stream `fixtures/adam/logcat-long.txt`; the fake-adb
   fixture was not edited.
5. v3 annotations are ported from source with derived tests
   (`v3_uses_the_v2_regex_with_v4_parameter_framing` and neighbours).

Further local decisions:

- The logcat parser takes no device: Kotlin's `AndroidDevice` parameter is
  unused (`getPackageName` is a stub returning `"?"`). 6.5's `LogcatManager`
  adaptation is a one-line call-site difference.
- Inputs Kotlin throws on become `InstrumentationError` returns, never panics:
  non-numeric `numtests` (`toInt()`, not `toIntOrNull()`) and malformed atoms
  (a parameter piece with no `=` reaches adam's `substring(0, -1)`; see
  Incidental bugs).
- P2's WARN has no logger sink to go through: the transformer is a pure parser
  and 6.6a owns logging. Unknown codes are therefore returned to the caller
  as structured warnings (`InstrumentationWarning::UnknownStatusCode`,
  drained via `take_warnings()`); their `Display` text is exactly
  `unknown INSTRUMENTATION_STATUS_CODE: <code>, atom ignored` for 6.6a to
  route to the marathon log at WARN. (Originally written to stderr with
  `eprintln!`; changed in review round 1, R1-sol-1/R1-spark-1.)

## Simplifications applied (P1–P6 approved in the brief; R1-sol-3 approved in review round 1)

- **P1** — the protobuf transformer is not ported. Marathon never selects it
  (no caller passes `protobuf = true`, no config key reaches it). Its single
  adam test is marked `n/a` in the parity matrix with that reason.
- **P2** — unknown `INSTRUMENTATION_STATUS_CODE` values are ignored (counting
  nothing) with a warning of the unknown code returned to the caller
  (`take_warnings()`; 6.6a logs it at WARN), instead of adam's
  `Status.UNKNOWN -> TODO()` crash.
- **P3** — `transform()` sets the finished flag in the failure branches too,
  so a repeated finish returns nothing instead of re-emitting (and
  re-prepending `"No test results\n"`).
- **P4** — an annotation length overrun (or negative length) stops extraction
  and returns what was collected, instead of Kotlin's
  `StringIndexOutOfBoundsException`. Knock-on: 6.6a will not retry remote
  parsing in that case.
- **P5** — the dead `Log.mSpaceLine` hex-dump prep and `LogCatHeader`'s Java
  `hashCode` arithmetic are not ported; `LogLevel`, header equality and both
  `toString` forms are.
- **P6** — the accumulating listener's stray trailing `"` is kept (D5) and
  recorded as known Kotlin bug **N7** in `docs/known-kotlin-bugs.md`.
- **R1-sol-3** — malformed UTF-8 in instrumentation output is decoded with
  per-chunk `String::from_utf8_lossy`, whose U+FFFD replacement-character
  count can differ from Java `String(bytes, UTF_8)`'s for the same invalid
  byte sequence. Matching Java's count is exotic-input emulation and an
  approved non-goal (orchestrator decision, review round 1); per-chunk
  decoding — and with it the loss of a multi-byte character split across
  chunks, which Java shares — stays. The comment at the decode site in
  `instrumentation.rs` states the difference.

No `docs/deviations.md` exists in the repo yet; the approved P-items are
recorded here and in the code comments at each divergence site. Creating that
file (and back-filling earlier WPs' deviations) is left to the orchestrator.

## Carried to 6.5/6.6a

- **P2 warnings (6.6a):** drain `take_warnings()` after `process`/`transform`
  and log each warning's `Display` text
  (`unknown INSTRUMENTATION_STATUS_CODE: <code>, atom ignored`) at WARN in
  the marathon log. Nothing is logged (or written to stderr) by 6.3 itself.
- **Synchronous logcat listeners (R1-spark-2; 6.5 owns the stream loop,
  6.6a consumes the listeners):** `LogcatListener::on_message`
  (`crates/marathon-android/src/logcat_listener.rs`) is a plain synchronous
  call where Kotlin's `onMessage` is `suspend`. Backpressure on a hanging
  or slow stream therefore differs: in Kotlin a suspended listener suspends
  the producing coroutine (cancellable, without holding a thread), while
  here the stream loop cannot read further logcat output until
  `on_message` returns, and a listener that blocks stalls the loop (and
  its thread) outright. 6.5/6.6a must account for this when wiring the
  loop — e.g. keep `on_message` implementations non-blocking, and decide
  explicitly what bounds a stuck listener (buffering, timeout, or a
  hand-off queue) rather than assuming coroutine semantics.
- Already noted above: the logcat parser takes no device (6.5 call-site
  difference), and P4 means 6.6a will not retry remote parsing after an
  annotation length overrun.
