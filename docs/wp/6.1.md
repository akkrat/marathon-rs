## Deliverables and boundary

The client goes in `crates/marathon-adb`, next to the server and with no cargo feature. `tokio` becomes a normal dependency (`net`, `io-util`, `time`, `sync`, `rt`), and the `server` feature keeps its extra dependencies. Do not refactor `server/`. Sharing a few constants is fine; the client's framing gets its own module and tests.

1. **Transport and framing** (adam `request/Request.kt`, `extension/Socket.kt` minus the sync and file writers, `transport/*` as semantics only, `Const.kt`). It covers:
   - one TCP connection per request;
   - the optional `host:transport:<serial>` switch (`misc/SetDeviceRequest.kt`) before the request;
   - `createBaseRequest`, which frames a request as `%04X` (uppercase) of the UTF-8 byte length followed by the payload (`Request.kt:59-67`);
   - the targets `host:`, `host-serial:<s>:`, `host-usb:`, `host-local:` and none (`request/Target.kt`);
   - OKAY/FAIL handshakes, protocol strings, optional protocol strings and read-to-EOF status (`Socket.kt:83-136,197-211`).

   The connect timeout and the idle timeout behave as below. A client-wide `close()` stands in for `socketFactory.close()`, which is `vertx.close()` (`VertxSocketFactory.kt:47-51`, called from `AdamDeviceProvider.kt:210`): it ends every live connection. The client exposes `host` and `port`, which 6.5 uses to build serials (`AdamAndroidDevice.kt:108,111`).
2. **Request model.** It mirrors adam's split.
   - `ComplexRequest` covers handshake, read and return. It is validated before connecting, and a failure is thrown as `RequestValidationException("Request <SimpleName> did not pass validation: <msg>")` (`AndroidDebugBridgeClient.kt:46-62,50`).
   - Channel requests (`AsyncChannelRequest`) stream items. Connect, transport-switch and handshake errors arrive **in the stream**, as its terminal error, never from the call (everything runs inside `produce`, `:64-116`). Validation is still synchronous (`:65-69`).
   - `ValidationResponse` and its message helpers are what 6.2 needs.

   This is the seam 6.2 ports about 20 request types onto (open question 2).
3. **Host services:**
   - `host:version`, parsed as hex through the optional-protocol-string path (`misc/GetAdbServerVersionRequest.kt:29-34`);
   - `host:devices` (`device/ListDevicesRequest.kt:25-71`, including `DeviceState.from`, where anything else is `UNKNOWN`);
   - `host:track-devices` as a stream of device lists, one per protocol string (`device/AsyncDeviceMonitorRequest.kt:25-45`);
   - device features through `host-serial:<serial>:features` with no transport switch (`device/FetchDeviceFeaturesRequest.kt:27-30`, `request/Feature.kt:104-130`). Unknown names are dropped, order is kept, and names are written in lowercase with `Locale.ENGLISH`.
4. **Shell v1 with the exit trick** (`shell/v1/*`):
   - the sync `shell:<cmd>;echo x$?` request (`SyncShellCommandRequest.kt:38,41`), read to EOF and parsed by `ShellResultResponseTransformer.kt:31-45`;
   - the v1 **channeled** `shell:<cmd>` stream (`ChanneledShellCommandRequest.kt:33-46`). Logcat always uses it, even on shell_v2 devices: Kotlin's transcript shows `shell:logcat -v long`.
5. **Shell v2:** the channeled `shell,v2,raw:<cmd>` stream with stdout, stderr and exit chunks and an optional stdin back-channel (`shell/v2/ChanneledShellCommandRequest.kt:38-93`, `MessageType.kt`).
6. **Compat shell stream** (`shell/AsyncCompatShellCommandRequest.kt:46-77`). `SHELL_V2` in the supplied feature list selects v2; otherwise v1 is used, and each chunk is re-encoded as a stdout chunk (`:69`). This is the shell-v2 negotiation of PLAN §3.9. 6.6a feeds its stdout into 6.3's `process`/`transform`.
7. **`exec:` and `abb_exec:` raw services.**
   - A generic raw service session: `exec:<cmd>` over the device transport, then raw write, read to EOF, and the status trimmed as `StringResponseTransformer` does (`transform/StringResponseTransformer.kt:23,30`).
   - `AbbExecRequest`'s NUL-joined `abb_exec:` serialisation and its `ABB_EXEC` validation (`abb/AbbExecRequest.kt:39,41-50,53`). 6.2's `StreamingPackageInstallRequest` uses both (Kotlin transcript: `abb_exec:package\0install\0-r\0-S\0<n>`).
8. **Errors and logs.**
   - The error type keeps the Java classes marathon branches on:
     - `ConnectException`, which includes netty's connect-refused and connect-timeout subclasses (`AdamDeviceProvider.kt:75,85`);
     - `RequestRejectedException`, which 6.5 maps to `DeviceLostException` (`AdamAndroidDevice.kt:480-481`);
     - `RequestValidationException`;
     - `IllegalStateException`, for a write after close (`VertxSocket.kt` `writeFully`);
     - other `IOException`s.
   - It can be converted into a `Failure`-shaped value (class name, message, cause) without 6.1 depending on core.
   - Log lines:
     - the WARN `adb server rejected command <framed request, hex prefix included>` under logger `com.malinskiy.adam.request.Request` (`Request.kt:44-52`);
     - the DEBUG `Exception during cleanup. Ignoring` under `com.malinskiy.adam.AndroidDebugBridgeClient` (`AndroidDebugBridgeClient.kt:111`).

## Behaviours to reproduce (adam file:line)

### Wire behaviour

- **Framing.** `createBaseRequest` computes the length twice, as UTF-16 units and then as bytes (`Request.kt:59-67`). Below 0x10000 the net effect is exact UTF-8 byte length in four uppercase hex digits; the result `000Ashell:test` is pinned by `AsyncShellCommandRequestTest`. Above that see P5.
- **Handshakes** (`Socket.kt:197-211,83-100`).
  - A short read is "not OKAY": `isOkay` requires `limit()==4`, and `readFully` at EOF does **not** throw (`VertxSocket.kt:125-139`).
  - In that case the code reads an optional protocol string. If the first four bytes are not hex, it reads the trimmed status to EOF.
  - As a result, a connection closed by the server before replying gives `RequestRejectedException("")`, with an empty message rather than `"no message received"`, and 6.5 turns that into device loss. Pin it.
  - FAIL followed by `XXXXx` gives the message `"x"`, as in adam's test.
- **Protocol strings** (`Socket.kt:104-120`).
  - Fewer than four length bytes gives `RequestRejectedException("Unexpected string length: <what was read>")`, and a short body gives `"Incomplete string received"`.
  - **track-devices at EOF** (adb killed) therefore ends its stream with `Unexpected string length: `, an error, not a clean end. 6.5's survive-kill-server loop depends on this (`AdamDeviceProvider.kt:123-135`).
  - Bodies are decoded as UTF-8 with no trim. `ListDevices` and `track-devices` apply Kotlin `lines()`, skip empty lines, `trim()` each line and `split("\t")`; P6 covers a line with no tab.
- **Version.** `readOptionalProtocolString` then `toIntOrNull(16)`, else `RequestRejectedException("Empty/corrupt response")`.

### Shell

- **Shell v1 exit trick** (`ShellResultResponseTransformer.kt:31-45`).
  - The whole output is read to EOF and decoded once with JDK replacement (`decode_utf8`).
  - The code takes the **last** `'x'`. If there is none, the error is `RequestRejectedException("No exit code delimiter found in <output>")`.
  - stdout is the prefix. The exit code is the suffix, Kotlin-`trim()`med and passed to `toIntOrNull()`, else `"Unexpected exit code value <s>"`.
  - stdout is handed on re-encoded from the decoded string, so bytes are not raw. Marathon only reads `.output` (`A/adam/extension/ShellCommandResult.kt`), so decoding once is enough.
  - Pinned by the 2 + 2 adam tests, including `testReturnsNonStrippedStdout`.
- **v1 channeled** (`ChanneledShellCommandRequest.kt:33-43`). It reads up to 64 KiB (`MAX_FILE_PACKET_LENGTH`), and each read becomes one `String` decoded **independently** (P3). A zero-byte read is skipped, and -1 ends the stream cleanly.
- **v2 channeled** (`v2/ChanneledShellCommandRequest.kt:38-90`).
  - STDOUT and STDERR carry a little-endian **signed** `i32` length. Data is emitted in pieces of at most 16 KiB (`MAX_PACKET_LENGTH`), and a length ≤ 0 emits nothing.
  - For EXIT, the length is read and ignored, then one byte is read and **sign-extended** (`readByte().toInt()`, `:65`), so exit codes 128–255 arrive as −128…−1. The stream ends after the exit chunk.
  - Any other id (STDIN, CLOSE_STDIN, WINDOW_SIZE_CHANGE, INVALID) is skipped **as that single byte**, with no length consumed (`:70`). adam's v2 channeled test pins this, because server-stub sends bare id bytes.
  - stdin chunks go out as `STDIN` with a length, and `close=true` sends `CLOSE_STDIN` with length 0 (`:80-90`). The stream **stops reading** once a supplied stdin channel is closed for receive (`AndroidDebugBridgeClient.kt:95-97`). The compat path never closes its own stdin channel.
- **Compat shell** (`AsyncCompatShellCommandRequest.kt:50-74`). v2 forwards stdout, stderr and exit chunks unchanged; the consumer (6.6a) uses stdout only. v1 wraps each decoded string as `stdout = string.toByteArray(UTF_8)` (`:69`, P3).

### Connections, timeouts and cancellation

- **Connect and idle timeouts.** These are transport (netty) timers, not scheduler time (open question 4).
  - The connect timeout is 10,000 ms (`AndroidDebugBridgeClientFactory.kt:39-40`; marathon never sets it). A connect timeout and a refusal both count as `ConnectException`.
  - **The idle timeout has a unit bug that must be kept.** adam passes milliseconds to `NetClientOptions.setIdleTimeout(int)` (`VertxSocketFactory.kt:39-40`), and vert.x 4.4.6's unit defaults to **seconds**. `javap` on the cached jar shows `TCPSSLOptions.DEFAULT_IDLE_TIMEOUT_TIME_UNIT = TimeUnit.SECONDS`. The rule is:
    1. Start from the timeout in milliseconds, either per request or `socketIdleTimeout.toMillis()` (`AdamDeviceProvider.kt:64`).
    2. Convert it with `toTimeoutInt` (`:53-57`): `as i32` with wrapping, and a negative result becomes `i32::MAX`.
    3. Use that number as **seconds**, where 0 means no idle timeout. The default `PT30S` becomes 30,000 s.
    4. Requests with `Long.MAX_VALUE` (track-devices `:25`, logcat, instrumentation) end at `i32::MAX` seconds.
  - Idle means neither a read nor a write for that long, after which the connection is closed. A v1 sync shell then fails with "No exit code delimiter found in …".
  - Fixing the bug is **not** an option. `screenrecord` runs as a silent v1 `ShellCommandRequest` for up to 180 s (`AdamAndroidDevice.kt:422`), so an honest 30 s idle timeout would break video recording.
  - Add a known-Kotlin-bug row. The fake-adb `delay_ms` field lets a test pin it in about 1 s, since `socketIdleTimeout` 1 ms gives an idle timeout of 1 s.
- **Cancellation.**
  - Dropping any request future or stream closes its socket, which is the Kotlin `use {}` close (`SuspendCloseable.kt`). It leaves no task running: the v2 stdin writer is aborted on drop (cf. 0.5 F2).
  - A consumer that stops listening produces fake-adb `client_closed` and no warning.
  - `request.close()` runs only at normal stream end, and compat's `close` is not run on failure (`AsyncCompat…:59,72`).
  - The client does **not** implement marathon-level timeouts. They wrap its futures in 6.5 and 6.6a, through `VendorClock`.
- **Producer semantics, for the consumers' briefs.** Kotlin starts each channel request as `scope.produce` (`AndroidDebugBridgeClient.kt:70`). The provider passes its `produce` scope; the device (`AdamAndroidDevice.kt:128`) and `LogcatManager` (`:19`) pass scopes with **no Job**, only an exception handler, so a producer's failure is logged there and the stream just closes. 6.1 exposes the terminal error on the stream. Whether it cancels anything, and whether it is logged, is decided by 6.5 and 6.6a.

## Proposed simplifications (pragmatic parity; for the orchestrator, **not decided**)

Each approved item becomes a `docs/deviations.md` entry (P3 would be a D10-style D11). Until then the behaviour above stands.

- **P1, dead code.** Do not port the 9 dead files listed above, and set their 13 test rows to `n/a`, giving "marathon never calls this at `e47352f2`" as the reason (a reviewer must agree). This is the same rule as 2.1's approved P7.
- **P2, no vert.x emulation.** Do not port the buffer pools: commons-pool `maxTotal=1024`, which blocks forever when exhausted (`BufferFactory.kt:31-33`). Do not port the record parser, the verticle per socket, or `ExecInRequest`'s busy spin. Keep the per-read caps (16 KiB and 64 KiB) as the chunk maxima, because they cost nothing. Chunk boundaries depend on TCP timing in both implementations.
- **P3, incremental UTF-8 for streamed text.** For the v1 channeled stream (logcat) and `StringResponseTransformer`, decode across reads instead of per read (`ChanneledShellCommandRequest.kt:38`, `StringResponseTransformer.kt:23`). For the v1 compat path, pass the raw bytes through instead of decoding and re-encoding (`AsyncCompat…:69`). The output differs only when a multi-byte character straddles a read boundary: Kotlin shows U+FFFD there, Rust shows the character. This mirrors D10.
- **P4, truncated v2 packets.** At EOF inside a v2 header or body, Kotlin's `readFully` returns without failing, and `readByte`/`readIntLittleEndian` then return **stale pooled-buffer bytes** (`VertxSocket.kt:125-171`). The result is nondeterministic garbage, then the clean end that `isClosedForRead` produces. Proposal: emit the bytes actually received, then end cleanly with no exit chunk and no error, exactly as Kotlin does at EOF between packets.
- **P5, oversized requests.** A request whose framed payload exceeds 0xFFFF fails locally with a `RequestRejectedException`-class error (our wording) instead of sending Kotlin's corrupted five-digit header (`Request.kt:61-66`). Only an `am instrument` with a very large `-e class` list can get there, and the adb protocol cannot carry it anyway.
- **P6, malformed device lines.** A `devices`/`track-devices` line without a tab becomes a typed malformed-response error instead of Kotlin's `IndexOutOfBoundsException` (`ListDevicesRequest.kt:32-35`, `AsyncDeviceMonitorRequest.kt:34-37`). Real adb always writes the tab.
- **P7, exit-code digits.** Accept only ASCII digits in the v1 exit code. Kotlin's `toIntOrNull` takes any Unicode digit; D9 already does this for config. `echo $?` only prints ASCII.

   This totals 237. `GetPropRequest` could go to 6.1 instead, since it is only a v1 request with a parser; the recommendation is 6.5, which uses it.
2. **API shape.** Recommended: thin request traits mirroring adam's `ComplexRequest` (`serialize`, `validate`, `process(conn)`) and channel requests (`handshake`, then pulled items), plus convenience methods for marathon's calls. 6.2 ports about 20 request types, and adam's tests assert `serialize()` bytes per type. The alternative is plain functions per service. Approve the shape before 6.2 starts, judged on the 22 ports plus one 6.2-shaped request (for example `CompatStatFileRequest`).
3. **Pull streams versus producer tasks.** Recommended: pull-based streams with no internal task except the stdin writer. They are cancel-on-drop by construction, and the hand-off is effectively a rendezvous. The cost is that Kotlin's one-item read-ahead and its parent-scope failure propagation are not built in; the consumers reproduce them where observable (see "Producer semantics").
4. **Transport timers.** Confirm that connect and idle timeouts may use `tokio::time` inside `marathon-adb`. They are netty timers in Kotlin, not the coroutine clock, and `lifecycle.md:274-276` forbids direct tokio only for replay-controlled operations. Tests would use real short durations, given the ×1000 unit.
