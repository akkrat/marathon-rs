# WP 8.16 design stop: image handling

Milestone-1 record. Approved for milestone 2 as D63; see
[implementation findings](8.16-findings.md), [test changes](8.16-test-changes.md)
and [golden audit](8.16-golden-diff.md). Baseline: `0852de20`, following the WP 8.15 implementation
at `f4244c70`. The milestone-1 proposal below did not itself approve a
contract change, assign a D number, change production code, or update goldens.
Effort remains **M**. WP 8.17 is independent and outside this work package.

## Recommendation

Use owned straight-alpha RGBA throughout, a single framebuffer decoder,
`image::imageops::resize(..., FilterType::Nearest)`, and the existing `gif`
crate quantizer. Replace JDK-specific color conversion and GIF shims while
keeping geometry, orientation, capture scheduling, delay, loop value, disposal,
frame order, paths and report references. Retain `png` for explicit sRGB output
metadata. Keep Little CMS through the already-pinned `lcms2` crate for genuine
Display P3 conversion; treating P3 samples as sRGB would lose their meaning.

The largest intentional changes are not encoding noise: raw P3 currently
roundtrips sRGB through a P3 raster rather than interpreting P3 source samples;
the raw 10-bit path can produce black pixels; the alternate buffered RGB565
path swaps byte order; ImageIO discards every partially opaque GIF pixel.
These need an explicit reviewed D-row even though today's native views do not
exercise them. Do not infer a broad image-comparison tolerance from this spike.

## Prototype method and coverage

Two temporary Cargo examples exercised the real public core/adb image APIs on
baseline and modified sources. Changes were limited to the replacements above;
validation/lifecycle refactoring was not implemented. Both examples and all
production edits were removed before the gate. Scratch scripts, outputs and the
prototype patch were retained under ignored `target/wp-8.16-prototype/` for local
inspection; they are not release artifacts or copied fixtures.

The prototype retained the RGB16 LCMS flags/intent/rounding but constructed the
sRGB destination with `Profile::new_srgb()`. It used one P3 source transform,
32-bit component normalization, the existing raw RGB565 math, crate nearest,
canonical zero-alpha RGB, no transparent-index remap, and one repeat extension.
No dependency or lockfile change was needed (`image` 0.25.8, `gif` 0.13.3,
`png` 0.18.1, `lcms2` 6.1.1).

The native experiment used the documented harness's `build_vendor_binaries`,
`capture(name, 'native', ...)`, `contract` and `evidence.normalized(...,
native=True)` functions for every registered adapter. Baseline and candidate
views were compared both to each other and to the committed generation with
`compare_native_views`; normalized dictionaries were also exactly equal. A
second candidate capture repeated all 18 after the zero-alpha fix. No `bless`
was run, no copied fixture was modified, and no comparator was weakened.
`diff-golden --against f4244c70` remains the milestone-2 audit baseline; design
measurements compare current `0852de20` code with its temporary candidate.

Reproduction inputs for the supplemental examples:

- Decode the four `adam/fixture/screencap_{1,2,1_unaligned,3}.bin` records,
  with version 2 for `screencap_3` and version 1 otherwise. Their file headers
  omit the leading protocol version (12/13 little-endian u32 header words).
  Run both public decode paths, encode through the same `encode_png` method.
- Use 32×32 RGBA samples `[x*255/31, y*255/31, 128, 128]`, integer division,
  with unknown, sRGB and P3 tags. Use a 2×2 RGB565 sample with little-endian
  red, green, blue, white words (`f800,07e0,001f,ffff`).
- Feed the unchanged `alpha-input.png` and `gradient-input.png` to the GIF
  writer with 19 ms delay and infinite repeat. Feed a 2×3 image with
  `[x*255,y*127,0,255]` twice, same delay/repeat. Feed an 8×8 image with
  `[x*32,y*32,100, alpha]`, alpha zero when `(x+y)%3==0`, otherwise 128,
  twice with 120 ms delay and finite repeat 1.
- Resize gradients `[x*255/(w-1),y*255/(h-1),0,255]` at rotation 0 and
  configured width 5, height 8 for the five source sizes below. Keep the
  existing aspect/orientation calculation. Encode PNG through `image` only
  for these scratch transform measurements, identically on both sides.

Pixel metrics below use independent Pillow decoding to composited RGBA frames,
absolute differences over **all RGBA bytes**, mean per channel byte, and count
a pixel changed when any component differs. Transparent hidden RGB is
canonicalized by the candidate; no threshold or color-distance tolerance is
applied. Existing `gif_frames.decode` independently checked GIF metadata and
composited hashes. File sizes are encoded bytes, not compressed golden size.
Timing means encoded GIF presentation delay, not benchmark latency.

pixel had a different hidden RGB color and the crate selects one transparent
palette index. Canonicalizing zero-alpha RGB restores all 42. Milestone 2 must
also test >256-color masks, where NeuQuant could merge transparent and opaque
indices; exact transparency must not be inferred from the small-palette probe.

## Risks and review boundary

- Native coverage has one opaque, one-frame, identity-size screenshot. Add
  native contract witnesses for the uncovered paths; zero golden changes alone
  cannot approve visible color/alpha/resize differences.
- P3 raw interpretation is a semantic correction, not just removing ICC files.
  It changes wide-gamut colors and clips to sRGB. The proposal retains the P3
  source profile and fixed conversion precision to make that decision concrete.
- GIF's nonzero-is-opaque rule can make partially transparent pixels much more
  visible. Zero-alpha canonicalization is essential; >256-color mask behavior
  still needs a dedicated implementation test and potentially native palette
  mask handling. This is the principal remaining implementation risk.
- Sharing the old raw helper without fixing >8-bit arithmetic is demonstrably
  wrong. Wider channels and missing alpha require validated bit extraction;
  synthetic RGB565 colors are necessary because the copied fixture is black.
- Nearest ties can move crisp UI edges by one sampled pixel. Keep geometry and
  rotation independent of the sampler, and document the visible boundary change.
- Crate version changes can change quantization or compression. Existing pins,
  exact native views and explicit supplemental expectations remain useful;
  this proposal does not allow blanket byte or pixel tolerances.
- Retained C64 orientation and empty-GIF quirks are deliberate scope choices.
  They cost little and preserve output behavior; removing them needs a separate
  measured proposal. No cleanup of runtime traits, timers or cancellation is
  part of WP 8.16.

Milestone 1 stopped at `034eb7ed` after the green foreground gate. The user then
approved the design as proposed and authorized milestone 2 with D63, an
independent RGB10 proof, common-case byte pins and high-color alpha coverage.
The linked findings and audit record the implementation; the draft above is
retained as the historical design proposal.
