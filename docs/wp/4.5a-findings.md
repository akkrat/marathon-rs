All orchestrator decisions and P1–P4, P6–P9 are implemented; P5 under its condition.

1. **Mach-O split (decision 1):** `mach_o` holds the six constants and
   `is_apple_binary`/`is_apple_binary_reader`; `model/AppleTestBundle.kt` stays owned by
   4.4 in the inventory (no inventory change for it), 4.4 calls the function.
2. **Parity (decision 2):** 6 rows `ported`; the 9 commented rows are `n/a` via a
   `TEST_RULES` entry in `scripts/source_inventory.py` (reason; both reviewers agreed
   in review round 1). The 3 still-meaningful legacy ideas are Rust tests against v1
   (`equality_ignores_key_order`, `metadata_key_does_not_hide_the_target`,
   `serialize_then_parse_round_trip`), no parity rows.
3. **`plistListDelegateFor` (decision 3 / P5):** probed first — it is broken for every
   present array (new known bug **A29**) and no production path reads it (production only
   *sets* the three list properties, in constructors; grep-verified). Implemented as the
   intended read: wrap each element dictionary.
4. **Null writes (decision 4):** the probe result overturns the brief's guess but makes
   this simpler. `NSObject.fromJavaObject(null)` is Java `null` and dd-plist's
   `NSDictionary.put` **ignores** a null value (probes `null-writes`, `put-null-direct`):
   an absent key stays absent, a present key keeps its value. So *every* null write —
   the v0 constructor's unconditional ones, `optionalDelegateFor`, `optionalPlistDelegateFor`
   — is a no-op, and the artifact-reuse xctestrun simply has no `TestBundlePath`/
   `TestHostPath` keys. Reproduced byte-exactly (`null_writes_store_nothing_and_never_clear`).
5. **Placement/pin (decision 5):** as decided; nothing shared with `tools/fake-worker`.
6. **Errors (decision 6 / P4):** one `PlistError` — `Io { is_not_found }`, `NotAPlist`,
   `UnsupportedFormat` (OpenStep, P1), `RootNotDictionary`, `MissingKey`, `WrongType` —
   keeping the distinctions 4.4/2.3b stage on. Two notes: dd-plist's wrong-type surface is
   a *mix* of `IllegalArgumentException` and (erasure) `ClassCastException`/
   `ArrayStoreException` depending on the property type (probe `missing-keys`,
   `int-conversions`); both map to `WrongType`. A non-plist text file sniffs as
   `UnsupportedFormat`, not `NotAPlist` (format sniff before parse; accept/reject identical).
7. **P3 inventory:** the five dead facets (`Help`, `Launch`, `LaunchConditions`,
   `Localization`, `Version`) are `n/a` via an inventory rule with the reason; both
   reviewers agreed in review round 1. **P2:** no binary writer (`plist` reading of
   binary stays — the real iOS `Info.plist`s need it). **P6:** the writer covers every
   probed case below; dates are truncated to whole seconds before formatting, as
   dd-plist's `SimpleDateFormat` does (probe `writer-date-truncate`, added in review
   round 1; this corrects an earlier draft of these findings, which left sub-second
   rendering to the `plist` crate's `to_xml_format` as "unprobed"), and `Real` equality
   is Java `==` (NaN ≠ NaN). **P7:** as decided. **P8:** no `Hash` impl. **P9:** element

## Oracle evidence

`tools/oracle/plist-probes/` (`PlistProbes.java`, `run.sh`, recorded `expected.txt`),
run on the reference JDK against the Kotlin distribution jars (dd-plist 1.28). Run:

```sh
tools/oracle/plist-probes/run.sh out.txt   # diff out.txt tools/oracle/plist-probes/expected.txt
```

Conclusions the implementation pins, each mirrored by a Rust test:
- **Writer:** tab per depth; empty `<string></string>`; empty dict/array as open tag,
  newline, indented close (never self-closing); **no trailing newline**. The golden
  *files* `expect_*.xctestrun` end in an editor newline Kotlin's `trim()` hid — the
  ported `test_write`s strip exactly that byte and compare the rest exactly.
- **Escaping:** in string *values*, characters XML 1.0 cannot carry are dropped (keeps
  `\t\n\r`, 0x7f, U+0085, U+2028; drops other controls and U+FFFE/U+FFFF); a value
  containing `&`, `<` or `>` is CDATA-wrapped, splitting literal `]]>` as
  `]]]]><![CDATA[>`; quotes untouched. *Keys* are never filtered, only CDATA-wrapped
  (probe `writer-key-control`).
- **Reading (XML):** our own reader (`plist::reader`, review round 1) concatenates
  text, entity references and CDATA in scalar values and keys (`getWholeText`
  semantics); CR/CRLF normalise to LF; forbidden XML characters, literal or by
  character reference, are `NotAPlist` (probes `cdata-read`, `encodings`,
  `control-on-parse`). Encoding, number, boolean and date handling follow the round-2
  probes (`encoding-matrix`, `number-text`, `boolean-content`, `date-text`; see
  "Review round 2"). One deliberate divergence: dd-plist parses both `<integer>` and
  `<real>` through `NSNumber(String)`, which infers the number *type from the text*
  (plain digits and `0x…` → integer, anything else `Double.parseDouble` accepts →
  real), ignoring the tag; the Rust reader keeps the tag's type. So `<real>1</real>` is
  integer 1 there, real 1.0 here; `<integer> 42 </integer>` and
  `<integer>18446744073709551615</integer>` are reals there, integers here;
  `<integer>2.0</integer>` is a real there, `NotAPlist` here. No production producer
  writes such text (Xcode and dd-plist's own writer emit the tag that matches), so this
  is an approved simplification (R1-claude-5, orchestrator decision in round 2).
- **Scalars:** `<integer>` full i64 range; `<real>` is Java `Double.toString`
  (`jcompat::jnum::double_to_string`) with `nan`/`+infinity`/`-infinity`; `<data>` is a
  single unwrapped base64 line, deeper-indented; a UID writes as a `CF$UID` dictionary;
  `NSSet` writes as `<array>` (the Rust value layer has no set type; the `plist` crate
  never produces one for XML/binary input).
- **Ordering/equality:** dict equality is order-insensitive (the `-reordered` fixture is
  equal, hash equal), arrays ordered, integer ≠ real ≠ boolean; replacing a key keeps its
  position; duplicate keys on parse take the last value at the first position. (The
  `plist` crate's `Dictionary` derives `PartialEq` over an `IndexMap`, whose equality is
  already order-insensitive — verified via the reordered fixture passing — but the Rust
  layer implements its own equality over its shared nodes and does not rely on the crate's.)
- **Conversions:** `Int` through `delegateFor` follows Java `Number.intValue`
  (long 3000000000 → -1294967296, double 2.9 → 2); through `arrayDelegateFor` reals and
  booleans are rejected (`Cannot map NSNumber to Integer`); string/bool delegates accept
  only their own type.
- **Missing keys:** the two candidate bugs are confirmed and recorded as **A27** and
  **A28** (plus **A29** above and **A30**, the fat-64 gap, reproduced by test).
- **Pushed bytes:** `pushed_xctestrun_bytes_round_trip_exactly` parses the 0.4b
  base64 evidence (ios-smoke, macos-smoke, ios-media, ios-screenshot) with the v2 model
  and writes back byte-identical documents — model construction + writer reproduce
  Kotlin's pushed bytes. Re-deriving them from `TestRootFactory`'s *inputs* remains
  4.5b/7.1, since `TestRootFactory` itself is 4.5b.

## Design notes for consumers (4.4, 4.5b)

- Models wrap a shared ordered dictionary (`Arc<Mutex<…>>` nodes, `Send + Sync`, so a
  `BundleInfo` can live inside 4.4's `TestBundle`): mutating through one wrapper is
  visible through every other, unknown keys/order survive untouched, nothing converts
  until touched. `targets()` keeps Kotlin's `by lazy` staleness.
- Read/write is synchronous over bytes/readers; `from_path` opens the file, so keep it
  off the core executor (`lifecycle.md`). No diagnostics are written to stderr.
- Kotlin nullable-but-required properties read as `PlistResult<T>` (missing ⇒
  `MissingKey`), their setters take `Option<T>` (None ⇒ no-op); genuinely optional ones
  read as `PlistResult<Option<T>>`; optional arrays read empty. Env maps are ordered
  `Vec<(String,String)>` — pass them in write order.

## Incidental bugs

- **The `plist` crate (1.10.3) silently drops CDATA content when reading XML**
  (`stream/xml_reader.rs`, `read_content`: `XmlEvent::CData(_) => { // skip }`). Any
  `<string>` or `<key>` whose content is a CDATA section reads back empty (mixed
  text+CDATA loses the CDATA part), so a round trip through dd-plist-style output —
  which CDATA-wraps every value containing `&`, `<` or `>`, e.g. a URL query string —
  loses data without an error. Found in review round 1 (R1-sol-1/R1-claude-1); the Rust
  port no longer uses the crate for XML (binary reading unaffected). *For the
  orchestrator: please add the `docs/found-bugs.md` row.*
