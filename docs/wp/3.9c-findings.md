6.6b pattern (R1): keep one `Arc<ScreenCapturer>` per device, spawn
`capturer.clone().start_owned(&test, signal)` on the vendor runtime beside the
batch, then cancel and join that task before reading `captures_taken` or
starting the next test, as Kotlin's launch/cancelAndJoin does. Both entry points
share one body; `start_owned` cannot borrow-check against overlap, so the caller
must not run two starts of one capturer at once.

width. Services hold the existing runtime, VendorClock, WallClock, OutputFiles
and ServiceLog. 6.6b owns launch and cancel-and-join; the source must join its
capture I/O before returning cancellation. A source timeout is
`VendorError::Other(Failure { class: "java.util.concurrent.TimeoutException", .. })`;
source I/O errors use `java.io.IOException`. Runtime/external cancellations stay
`VendorError::Cancelled`, including runtime timeouts. Orientation is read once
per start; first dimensions persist across starts. The mutable start borrow
prevents concurrent starts through `start`; `start_owned` relies on the join above. No background job is created beyond
the existing joined vendor dispatch/blocking primitives.

Encoding and frame conversion run on joined blocking work. Cancellation during
a write waits for that block and then explicit GIF finish and fallible stream
close. The wrapper suppresses gif::Encoder's Drop trailer; Drop is not completion
evidence. `GifSequenceWriter::finish(self)` returns the still-open stream and
reports errors. `FrameTransform` is reusable independently. The wall read label
is `core.ScreenCapturer.capture`; the delay uses the frozen VendorClock at the
inventory's `core.ScreenCapturer.scheduler.L55` site. VendorClock has no label
argument, so no second clock/runtime API was introduced.

## P1 measurement (approved in R1)

Flat-colour frames, every rotation case, the alpha witness and all resize
geometries/pixels are exact. Resize sampling follows AWT's ScaledBlit (R1-sol-1,
below); it is exact on every probed map, so the tolerance does not cover resizing.

The tolerance covers only GIF palette quantisation on the 32×32 opaque gradient
with 1,024 colours, where Rust's NeuQuant palette differs from ImageIO's.
Metadata, geometry, frame order/count and pre-quantization pixels are exact. The
**metric** is the absolute difference of every decoded RGBA byte, alpha
included (always 0 here), with the maximum and the mean over all bytes. Because
alpha and the gradient's blue channel never differ, an RGB-only mean is 4/3 of
the RGBA mean. Measured by `persistent_dimensions_and_gradient_palette_measurement`,
which pins all three comparisons:

| Comparison | Max | Mean (RGBA) | Mean (RGB) |
|---|---:|---:|---:|
| Rust GIF vs JVM GIF (the bound) | 77 | 8.3127 | 11.08 |
| Rust GIF vs input | 75 | 8.0647 | 10.75 |
| JVM GIF vs input | 5 | 2.0781 | 2.77 |

Both reviewers approved the bound **max ≤80 per channel, mean ≤9 (RGBA)** for
this gradient witness only. The R1 Claude reviewer also measured each
implementation against the input on larger images (their RGB figures, not
regenerated here). On a realistic 720×1280 image, Rust has mean 7.37 and max 42,
JVM mean 10.35 and max 54. On a UI screenshot, Rust has mean 0.05 and max 71,
JVM mean 0.89 and max 12. NeuQuant is therefore not uniformly worse than ImageIO
against the source, but it can produce larger isolated errors on flat UI colours.
This is not a blanket tolerance for other images or for metadata; P1's
compressed-byte exception remains separate.

The actual JDK output contradicts two requested-metadata descriptions in the
brief: malformed comment metadata emits no comment, and palette conversion
makes nonopaque pixels transparent despite the false flag. The implementation
follows actual Kotlin/JDK behavior, not the requested metadata attributes. These
are reproduced bugs C63/C67, not new intentional deviations.

## Review round 2

Sol R2: R1-sol-1 (resize), R1-sol-2 (invalid XML) and R1-sol-3 are verified. No other regressions were found, and the gate passed.

R2-sol-1 is approved by the orchestrator as a simplification. When an environment value is invalid XML, Rust always leaves an empty `environment.xml`, while Xalan leaves whatever it had already flushed from its buffer. Witness: `Configuration.name` = 100,000 × `a` + U+0001; the JVM leaves 94,836 bytes and Rust leaves 0. Both emit the same TransformerException chain through `environment_errors`. This needs an invalid control character inside a value of tens of kilobytes, which real configurations do not contain. Rust's empty file is the cleaner outcome.
