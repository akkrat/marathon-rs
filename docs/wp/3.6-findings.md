## What was built

- **`execution::DevicePoolMessage`** with `FromScheduler`, `FromDevice` and `FromQueue` (decision 1; the inventory row
  already says 3.6).
- **`execution::device`:**
  - `DeviceState`, `DeviceEvent` and `DeviceAction`. The actor's `DeviceEvent` lives in its own module and does not
    collide with `vendor::DeviceEvent`.
  - `DeviceActor::spawn(core, pool_id, pool, configuration, device, parent, hooks, barriers) -> DeviceActorRef`. It is
    named `spawn` and not `new` because it returns the started actor (`clippy::new_ret_no_self`).
- **The handler runs on 3.1's `RuntimeActor`.** Shared state is an `Rc<Shared>` on core: the machine, both job slots,
  the once-only `Cell<bool>`, the owner `TaskContext` stored in `started`, and a weak actor handle.
- **The pool handle is held weakly.** A dropped pool behaves like a closed one. This means no `Rc` cycle with the
  pool's device map.
- **Transitions borrow the machine only for `transition` itself.** Side effects run after the borrow is released and
  before any await.
- **Readiness, initialize, execute and terminate tasks launch under the stored owner context.** They never launch
  under the task that happens to run the transition.
- **`terminate` uses cancellable joins:** `cancel` followed by `join_in(context.job)`.
- **The completion callback holds a `Weak<Shared>`:** `transition(Terminate)` followed by `notify_terminated()`.
- **Vendor calls** go through `call_vendor`, inside the barriers `core.DeviceActor.prepare:<serial>` (once per
  attempt, inside the `isActive` check) and `core.DeviceActor.execute:<serial>`.
  - Admission races the task's cancellation, and a cancelled wait leaves its token unconsumed.
  - The permit is released after the vendor's own outcome.
  - A barrier error fails the call as a vendor `Other` would.

## Decisions taken and simplifications applied

- **S1:** the state and event text for `Running`/`Execute` is `DeviceState.Running(batch=<id>)` /
  `DeviceEvent.Execute(batch=<id>)`. Kotlin prints the data classes' `toString`, which contains the whole test list and
  a Deferred identity hash. The oracle row "execute at an unclosed terminated actor" is compared with this text
  substituted.
- **S2:** coroutine-internal cancellation messages match the oracle on the paths it shows:
  - `DeferredCoroutine was cancelled` for `Deferred.cancel()` on the initialize and execute jobs;
  - `Job was cancelled` for `Job.cancel()`.
  - No `; job=…@hash` suffix is produced.
- **S3:** every non-cancellation `VendorError` and every panic is an `Exception`: it is retried in prepare and is
  "unknown, recoverable" in execute.
- **S4:** `GetDeviceState` is omitted.
- **S5 (carried item C2):** a wall-clock watchdog thread outside the executor fails a `run_virtual` scenario that
  stalls (`run_virtual_with_watchdog`, 120 s by default). Futures that block inside `poll` remain unsupported. Production
  is unaffected.
- **Decision 6 (two test vehicles; a reviewer must agree). Each test documents the reason.**
  - *`actor failing before a dispatched batch starts executing returns the batch`*:
    - Kotlin's vendor launches a child into the prepare coroutine.
    - `VendorContext` has no job, so a child that the test spawns under the actor job fails it instead.
    - Execute is queued before that child runs, so the execute task never starts (0 execute calls), as in Kotlin.
  - *`results of a completed batch reach the pool even if the actor stops right after`*:
    - Kotlin relies on single-thread dispatcher queueing.
    - In Rust, the recording pool cancels the parent when it receives `CompletedTestBatch`, inside `accountFor`. That
      is after the vendor's return is bridged and before the readiness task first runs.
- **Decision 7:** the test configuration is a three-line Marathonfile (`name: ""`, `outputDir: ""`, vendor
  `type: "stub"`), bound by `MarathonConfigurationLoader::parse_sync`.

## Corrections to the brief found by the oracle

1. **`Execute` and `Terminate` queued together do call the vendor.** The brief says they run before the execute task
   polls, so the vendor is never called. The oracle row "terminate while in progress" shows otherwise:
   - The execute task is queued before the terminate task, so it starts first and the vendor is called.
   - The terminate task then cancels it, and the actor logs WARN `Device execution has been cancelled`
     (`DeferredCoroutine was cancelled`).
   - The batch has already been returned as terminated by the transition.
   - Rust's FIFO launch order gives the same row.
2. **Readiness to a *closed* pool is not silent.**
   - When a plain channel is closed without a cause, `send` throws `ClosedSendChannelException`. That fails the
     readiness launch, the actor job and the test's `Job()` parent. The handler logs ERROR
     `CoroutineContext closing due to unrecoverable error`, and `Terminated` is then dropped (row "readiness to a closed
     pool").
   - Only a *cancelled* channel ends the task silently ("readiness to a cancelled pool").
   - The Rust actor follows the `SendError` it gets back:
     - a `cause` fails the task with that failure;
     - no cause is the cancellation of a cancelled actor, and ends the task silently.
   - In a run, the pool is an actor that is only ever cancelled, so readiness to a closed pool is silent in production.
3. **The `isActive` skip in prepare cannot be reached.** A cancelled initialize task throws from the 10 s retry delay
   before the next attempt's `isActive` check, and a task cancelled before its first poll runs no body. The code is
   kept. Row "retry delay cancelled at its deadline" pins what does happen.

## Post-merge Linux fix

Branch `wp/3.6-entry-race-linux`, from main `45677e5`. The Linux gate failed
`entry_cancellation_matches_the_probe_on_every_run`: 1 of 2,000 runs diverged. macOS passed.

**The gate in `call_vendor` was not the cause.** The test now prints the first divergent row. Reproduced on the Linux
box with 16 copies of the oracle binary at once, the divergent row has no `executeBatch` at all: it logs
`Invalid transition from DeviceState.Initializing event DeviceEvent.Execute`, with `execute: 0` calls. The scenario's
first `run_current()` (after `Initialize`) returned before the vendor's `prepare` had completed and woken the core task.
The same load also produced the other two symptoms of an early drain: `device_actor_rows_are_stable_over_repeated_runs`
with the same `Initializing` row in another scenario, and `finish()` failing with "runnable work remains". Before the fix,
3 of 144 loaded binaries failed.

**Root cause (a WP 3.1 harness race).** `ControlledReplay::drain` treated the core as quiescent when
`tracker.ready == 0 && tracker.polling == 0`: two loads, one after the other. Work moves between the counters in both
directions: a poll start moves a task from `ready` to `polling`, and a vendor poll that completes a result wakes the
core task (`ready + 1`) before its own `polling - 1`. Each hand-off increments before it decrements, so the sum never
reaches zero, but the two loads are not one snapshot. A core thread preempted between them can read `ready == 0` before
the wake and `polling == 0` after the vendor's poll ends. Load makes that preemption likely; Linux's scheduler under the
gate's parallel tests produced it.

**Fix.** `Tracker` keeps one `busy` counter: a runnable ticket, a poll in progress, a wake in progress and a blocking
job each hold one unit, and every hand-off takes its new unit before releasing the old one. `idle()` is a single load,
so it cannot see zero while work is being handed on. `drain` and `assert_quiescent` use it. `call_vendor`'s gate is
unchanged: it is armed from the cancellation state read on the core thread before the spawn, and the cancel also runs
on the core thread, so there is no window there.

**Regression.** `executor::tracking::tests::a_hand_off_between_threads_never_reads_as_idle`: two tracked tasks on two
threads wake each other 200,000 times while a third thread asserts the tracker is never idle before the last poll.
Against the old two-counter tracker (same API, two loads), it failed 4 of 5 runs on macOS, within the first 13,000
hand-offs. The fixed tracker passed 20 of 20 runs on macOS and 20 of 20 on Linux.

**Repeated runs after the fix.**

- Linux, isolated: `entry_cancellation_matches_the_probe_on_every_run` 15 × 2,000 runs, 0 divergences.
- Linux, loaded (16 concurrent copies of the full oracle binary): 576 binaries, each with the 2,000-run test and the
  50-run stability test, 0 failures.
- macOS under CPU load (18 `yes` processes plus 18 concurrent copies of the binary): 108 binaries, 0 failures.

**Not covered.** Tokio's coop budget defers a task's wake until after its poll returns, and a deferred wake would read as
idle. It needs 128 budgeted operations in one poll; replay's vendor tasks come nowhere near that, and no vendor code
calls `yield_now`. Recorded here in case a future replay scenario does.


## Post-merge fix 2

Branch `wp/3.6-fix2-wake`, from main `d32b1f7`. Post-merge review PM-sol-1 found a residual race in the U51
tracker fix (U71): a duplicate wake could observe an already queued ticket, pause before `outer.wake()`, then
forward after the preceding poll consumed that ticket. Its temporary counter unit was released with another
poll queued, so `idle()` returned true prematurely.

`Ticket` now forwards only the wake that creates a counted queued ticket. Duplicate wakes and wakes of completed
tickets are suppressed; the temporary unit still covers the wake's hand-off. The test-only `idle()` gating is unchanged.

The deterministic regression `a_delayed_duplicate_wake_does_not_queue_uncounted_work` uses a hook after the ticket
decision and two barriers to pause a duplicate wake. The test consumes the original queued poll before resuming the
duplicate, then checks that the tracker is idle and no poll is queued. It also checks that a fresh wake is counted and
forwarded and that a wake after completion is suppressed. No sleeps or probabilistic scheduling are involved.

Review (2026-10-26, orchestrator, Claude, cross-family to Sol): merge. A wake that sees the ticket queued (state 1) can skip forwarding, because the counted winner already forwarded, and the poll swaps state to 0 before it polls the inner future, so no notification is lost. The barrier test forces the interleaving deterministically.
