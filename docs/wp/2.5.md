2. **`execute`** (`K/ApplicationView.kt:38-103`): startup log lines, `version`, the `isFile` check, stage-(a) parse through `MarathonConfigurationLoader` (trait or `parse_sync`; run off the core executor, per `lifecycle.md`), the D1 INFO line, the Stub/Empty gate with `No vendor config present in <absolute path>` (`:79`, 0.6 `VendorFactories` doc), and the exit mapping of `:85-96`.
3. **A run seam for 3.10**: a trait or closure pair in `marathon-cli` that 3.10 implements: *construct* (`marathonStartKoin` + `koin.get()`, `:82-83`, outside the inner catch, so its errors take the uncaught path) and *run* (`marathon.run(command)`, `:85-90`, `Ok(bool)` or `Err(Failure)` → crash path). 2.5 owns the mapping around it and tests it with stubs; the shape is open question 2.
4. **Error rendering**: the JVM's uncaught-exception output for errors escaping `execute` (stderr, exit 1) and the logback throwable rendering for the crash log (`:88`), both from `ConfigurationError` (class, message, `causes` outermost-first) or `marathon_core::error::Failure`.
5. **Startup logging wiring**: create the per-process `MarathonLogging` registry (later handed to 3.10 as `VendorDependencies.logging`) and the stdout console sink with `OutputTarget` detection (terminal, pipe, file), `JansiMode::Default` (D2: no `jansi.mode` override). Thread name `main` in startup lines.
6. **`version`**: build-time constant `option_env!("GIT_TAG_NAME")` falling back to `0.10.1` (open question 6); 7.3 sets the variable in CI.
7. **Hidden `marathon config-dump <Marathonfile> [--env-file F] [--now <instant>]`**: same interface, document and exit codes as `tools/oracle/config-dump` (`ConfigDump.kt:33-63`: JSON on stdout, exit 0 for every stage; usage error → `config-dump: <msg>` + usage line on stderr, exit 2). Not listed in help. `--env-file` builds `BindingContext.environment` from the file directly; no re-exec. Includes the canonical configuration renderer (`Canonical.kt`: JVM fields incl. `@JsonIgnore`d and derived values, `by lazy` → `{"lazy": "uninitialized"}` when unset, UTF-16 key order) and the `fsEffects` snapshot (`ConfigDump.kt:182-230`; `sha2` is already a `marathon-config` dependency). Placement is open question 4.

**Not 2.5:** `Marathon.run` itself, `configureLogging()` (runtime layout switch), the shutdown hook, `onFinish`, outputDir wipe, parse output file (3.10 / 3.9b); the replacement for `di/Modules.kt` and vendor factory bodies (3.10, vendor WPs); the config differential corpus (2.6); packaging and CI version injection (7.3); Clikt shell completion and `@argfile` (proposal P4).

**Help** (`-h`/`--help`, stdout, exit 0). Wins over parse errors in the same command (`--bogus -h` → help). Root, with a 79-column layout when not on a terminal (`COLUMNS` is ignored):

## Proposed simplifications (pragmatic parity: for orchestrator approval, **not decided**)

Until approved, the behaviour above stands and a divergence is a bug. Each approved item gets a deviation entry.

- **P1, help width:** always the non-terminal 79-column layout, also on a terminal (Mordant reflows to the terminal width there). The matrix is recorded off-terminal anyway.
- **P2, SLF4J banner:** do not print `SLF4J(I): Connected with provider of type [ch.qos.logback.classic.spi.LogbackServiceProvider]`, which the JVM writes to stderr on every invocation, `--help` included. It is a logging-library artefact like D2's JVM options.
- **P3, stack frames:** errors render as class, message and `Caused by:` chain with no `\tat` lines, both for uncaught errors and in the crash log. There are no JVM frames to show (§3.10 already accepts frame differences); a `Failure.stacktrace` carrying external text (xcodebuild, instrumentation) is still printed verbatim. The 1.6 `... N common frames omitted` row then only constrains that external-text case.
- **P4, Clikt extras:** no `@argfile` expansion (Clikt expands `@file` arguments; witnessed) and no `_MARATHON_COMPLETE` completion script. An `@x` argument becomes `no such subcommand @x`. The other quirks (`-m=x`, `--` then `run`, suggestions, multi-error lines) are trivial in a hand-written parser and stay.
- **P5, identity hashes:** the `version` line's `VersionCommandCliConfiguration@<hash>` uses the class name's `String.hashCode()`, as approved for F29, so it is deterministic and the matrix normalises one rule.
- **P6, reference time:** one `now` per process (0.6 `BindingContext.now`) instead of `Instant.now()` per relative `timeLimit` value; they differ by microseconds.
- **P7, Marathonfile read errors:** `java.io.FileNotFoundException` with the OS error text as message rather than the JVM's `<path> (Permission denied)` spelling.

## Open questions for the orchestrator

1. **Parser library.** PLAN §4.2 names clap "configured to reproduce Clikt 5". Every user-visible text is custom (Mordant help layout, usage line per command, error lines, suggestions, root-usage quirk for `version -m`), so clap would need its help, usage and error output all replaced. Recommend a hand-written parser (four commands, six options, a few hundred lines, table-tested), and amend §4.2. Approve either way before implementation.
2. **Run seam shape.** Recommend a `CliRunner` trait in `marathon-cli` with `construct(config, command, logging) -> Result<Box<dyn MarathonRun>, Failure>` (uncaught path) and `MarathonRun::run() -> Result<bool, Failure>` (crash path), off the core executor's thread rules of `lifecycle.md`. Until 3.10 lands, what does a valid config do? Recommend a placeholder runner that fails construction with `java.lang.UnsupportedOperationException` ("not implemented in this build"), i.e. the uncaught path, exit 1.
3. **config-dump scope.** Recommend 2.5 passes all 30 goldens as whole documents (stage, error class/message/cause classes, canonical config, fsEffects), with §3.10 message differences, F29 hashes, set order, D6 and D9 marked as in 2.4; 2.6 then only adds the corpus. The alternative (stage only, rest in 2.6) leaves the binary's document untested until 2.6.
4. **Where the canonical renderer lives.** Recommend `marathon-config` (a `dump` module next to `render.rs`, which already hand-projects every type twice), so 2.6 can call it in-process; the subcommand and `fsEffects` walker in `marathon-cli`.
5. **Hidden command in release builds.** Kotlin answers `marathon config-dump` with `no such subcommand config-dump`. Recommend a hidden subcommand in every build (2.6 should test the shipped binary), accepted as the one CLI addition PLAN §6.3 sanctions.
6. **Version fallback.** Kotlin's `0.10.1` (recommended, parity for untagged builds) or the crate version.
7. **D1 line text and logger.** Recommend `Crash reporting and usage analytics are not supported by this build; --bugsnag, --analyticsTracking, bugsnagReporting and analyticsTracking are ignored` under `com.malinskiy.marathon.cli.ApplicationView`, printed on run and parse after a successful parse.
