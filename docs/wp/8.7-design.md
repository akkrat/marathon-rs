# WP 8.7 milestone 1: ordered test queue

Design for D60; implementation, the D-row, test rewrites and golden updates wait for milestone 2.

## Type and API

Add `strategy/queue.rs` with `OrderedQueue<T, K: Ord>`: a
`BTreeMap<(K, u64), T>`, a next-insertion sequence and a boxed
`FnMut(&T) -> K + Send`. `TestQueue` aliases `OrderedQueue<Test, SortKey>`;
`TestKey` names its boxed key function. `SortingStrategy::process` returns
`TestKey`, replacing `TestComparator`. Batching accepts `OrderedQueue<Test, K>`
with `K: Ord`, preserving its existing rules and supporting small integer/string
keys in tests. The queue remains `Send` when its elements and keys are `Send`.

API: `new(key)`, `add`/`offer(T) -> bool` (always true),
`add_all(IntoIterator<Item = T>) -> bool` (whether anything was inserted),
`poll() -> Option<T>`, `peek() -> Option<&T>`, `remove_all(&[T]) -> bool`,
`len`, `is_empty`, `iter() -> impl Iterator<Item = &T>`, and `clear`.
`poll` uses `pop_first`; `peek` uses `first_key_value`; `iter` uses `values`.
`clear` removes entries but retains the key function, history view and shared
random cache; its empty queue can reset the sequence.
Only insertion invokes the key function, exactly once per entry. No mutable
access to queued tests or keys. Insertion/poll cost O(log n), iteration O(n).
The old single-element `remove` is used only by historical queue probes and is
not needed in the new API.

Equal keys use insertion sequence, without a test-name or metadata tie-break.
Re-adding a polled or temporarily removed test creates a new sequence: it goes
after surviving entries with the same key, in re-add order. Before sequence
exhaustion, rebuild sequence numbers densely from stored keys in current priority
order, without extracting keys again; this
preserves FIFO within each key and avoids wrapping or replacing a live entry.
Cover this unreachable-in-practice boundary through a unit-test seam.

`remove_all` retains entries whose values are unequal to every probe. Equality
is `Test`'s pkg/clazz/method equality, not key equality or metadata. One probe
removes **all** copies, including copies with different keys or metadata;
repeated probes have no extra effect. Survivors retain their keys and sequence
numbers. Return false for no match, including an empty probe slice. O(n × m)
membership is the existing complexity and avoids introducing another index.

## Keys, snapshots and random draws

`SortKey` is a closed enum; only one strategy's variants occur in a queue.
`FloatKey` canonicalizes every NaN to positive quiet NaN bits
`0x7ff8_0000_0000_0000`, then implements Eq/Ord consistently using `total_cmp`.
This matches `jnum::double_compare`: all NaNs tie above positive infinity and
negative zero sorts below positive zero. Bare `total_cmp` would be wrong for
negative NaNs and payloads. Do not negate floats to reverse their order.

| Strategy | Key (smallest dequeues first) | Result |
|---|---|---|
| ExecutionTime | `Duration(Reverse<FloatKey>)` | Descending duration; NaNs first, then +infinity through -infinity; +0 before -0 |
| SuccessRate, ascending | `Rate(FloatKey)` | Ascending rate; NaNs last; -0 before +0 |
| SuccessRate, descending/default | `DescendingRate(Reverse<FloatKey>)` | Descending rate; NaNs first; +0 before -0 |
| RandomOrder | `Random(i32)` | Ascending signed random integer; collisions FIFO |
| NoSorting | `Constant` | Every entry has the same key: FIFO |

`process` takes `metrics.view().unwrap_or(metrics)` once when the pool's queue
is built in `QueueActor::spawn`, after D13's off-core prefetch. That same view
is captured for every later insertion; a backend refresh reaches the next
queue, never this queue. A lookup returning `None` promises immutable history.
Key extraction runs synchronously from that in-memory view, on insertion,
including the first/singleton entry; comparisons, reads, polls and removal do
not query metrics or draw randomness. Initial insertion order stays
`shard.tests`, then `shard.flaky_tests`, each in vector order.

D34 freezes **history**, not run-local observations: `PinnedMetrics` retains
live observed-duration fallback. Each new entry computes its duration once at
insertion, including retries, rejected batches, FixedSize rejects and retry
avoidance restoration. Thus a reinserted entry may use newer observations when
history is absent, while surviving entries keep their stored keys. Remove the
old per-Test duration-comparator memo; do not freeze observations globally or
take a fresh backend history snapshot on reinsert. Batching still takes its own
fresh snapshot per batch and retains its duration, rejection and last-mile rules.

RandomOrder preserves its strategy-owned `HashMap<Test, i32>` shared across
queues produced by that instance. The first insertion of a previously unseen
Test draws `RANDOM_KEY` once; equal copies, retries and subsequent queues reuse
that key. Draws now follow first insertion order, rather than comparator argument
order; even a lone test draws. A failed draw still caches 0 and leaves replay
failure reporting to the existing hooks. Keep the existing nonblocking
`try_lock` invariant. Different pools currently create separate strategy
instances, so no new cross-pool ordering or sharing is introduced.

| Location | Effect of priority-order iteration |

There is no production log that directly formats the queue's iterator today.
Batch contents and their downstream logs/worker test selectors can change;
retry bookkeeping traversal and test-support queue snapshots can change.
The retry-worker notification map retains insertion-order traversal; changed
batch order can still change its insertion chronology.

## Golden measurement and risks

Measured a temporary prototype using this exact tree/key scheme, eager
insertion keys and the strategy-owned random cache against all **18** registered
native adapters (including all **16** vendor cases). The prototype used the
existing harness capture, normalization and native comparison functions, writing
captures/diffs only under ignored `target/wp87-prototype/`; it did not bless or
edit fixtures. All captures completed. Original Rust sources were restored
before the milestone gate. The prototype is not part of this commit.

| Native view | Changed files | Difference |
|---|---|---|
| `ios-smoke`, `ios-ignore` | `state.json`, `transcript.jsonl` | `sessions[].selected` and xcodebuild selectors: passing/skipping/failing → passing/failing/skipping |
| `macos-smoke`, `macos-ignore` | `state.json`, `transcript.jsonl` | Same fields: pass/skip/fail → pass/fail/skip |
| `android-two-devices`, `android-ignore` | `transcript.jsonl` | The `-e class` list on the first emulator changes from MainActivityTest#testText/MainActivityAllureTest#testFailure to the reverse |

The other **12** native views were unchanged: `local`, `parse`, `ios-media`,
`ios-screenshot`, `android-smoke`, `android-remote`,
`android-instrumentation-eof`, `ios-parse`, `macos-parse`, `android-parse`,
`ios-pass`, `macos-pass`. Every report file and progress/summary view stayed
unchanged in all 18 cases. The scripted devices emit their fixed test result
order even when selectors move; this measurement therefore does not prove that
real-device report order will remain unchanged. New execution-order and
RandomOrder tests must cover what this corpus does not exercise.

The configuration corpus is untouched and must remain unchanged. No golden is
updated in milestone 1. During milestone 2, re-bless only with the documented
`tools/differential/run bless` workflow, run
`tools/differential/run diff-golden --against a830d106`, and record every view,
file and movement in `docs/wp/8.7-golden-diff.md`. Any further difference needs
an explanation under D60 or a fix; do not expand normalization to hide it.

D60 must explicitly describe equal-priority execution order, front-selected
batch contents (and ordered worker selectors), ClassName iteration, retry
bookkeeping/restoration order, insertion-time metrics keys and RandomOrder
draw order. It must also make the per-entry observed-duration fallback above
clear. Add superseded-by-D60 notes to the historical PLAN heap/comparator
requirements and replace CLAUDE.md's queue rule only during milestone 2.

Main risks: canonicalizing NaNs incorrectly; accidentally drawing once per copy
rather than per distinct random Test; allowing refreshed backend history into a
live queue; overlooking live observed fallback on reinsert; changing D50's
rejection limits; weakening oracle accounting checks while replacing obsolete
heap assertions; selector-order changes surfacing in worker transcripts; and
sequence overflow. No batching, retry, configuration or progress-format policy
change is proposed beyond the queue order and key-timing changes above.
