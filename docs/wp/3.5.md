## Deliverables and boundary

Add progress, result and CI modules in `crates/marathon-core`; each ported module starts with `//! Port of <Kotlin path relative to the marathon repo>`.

1. **PoolProgressAccumulator** with one FSM per registered test name, the five Kotlin states and six event forms, nullable `TestAction::Complete`, aggregate outcome and `f32` progress. Implement merged **`strategy::retry::RetryProgress::retry_test(&mut self, &Test) -> Option<TestAction>`**; retain the synchronous AddRetry path. Reuse 3.1's `StateMachine` and 3.2's existing `model::TestAction`, not another runtime/FSM framework or completion enum. Expose `test_started`, `test_ended(final)`, `remove_test`, `progress`, `aggregate_result` for 3.7/3.8; awaited tracking/output work must finish before the caller uses the returned action.
2. **TestRunResultsAccumulator / TemporalTestResult**, with ordered Test-keyed storage, all callback overload semantics, mutable temporal records/metrics, counts, completion/failure flags, and incomplete-result synthesis. Consume frozen **`time::Timer`** and the labelled **`WallClock`/`ReplayHooks`** default-time seam, propagating clock failures. Preserve Test equality without metadata and DeviceInfo snapshots, signed `i32`/`i64` counters/times, batch IDs and attachments. Finish the model predicates required by `model-contract.md`: `TestStatus.plus` (`execution/TestStatus.kt:10–18`), `TestResult.isIgnored/isSuccess` (`execution/TestResult.kt:17–29`); do not change model equality or serializer fields.
3. **ProgressReporter and CI selection/output**, with the exact raw stdout lines below, explicit injected environment for Auto, and no global environment mutation in tests. P1 below proposes omitting the unused standalone reporter; until approved it is in scope.
4. **Async boundary.** Consume frozen **`wiring::Tracker::test`** (a `VendorFuture`, potentially network I/O), **`VendorRuntime`** and the merged off-core bridge. StateMachine listeners are synchronous: retain the transition/effect payload, then await tracker delivery off core, in source order, before returning the action. Do not fire-and-forget tracking or hold a RefCell borrow across an await. Logs use the merged **`Rc<LogQueue>`/`LogRecord`** with Kotlin logger names; no direct registry mutex or stdout I/O on core. Raw progress/CI lines need an additive output adapter (question Q3), not a logback-formatted INFO record. Use the shared process console: raw text follows its `write_text` path; log events keep the startup Jansi state. Preserve PrintStream-style swallowed stdout write errors, not tracker-error suppression. Vendor-side run-results callers remain serial owners; this accumulator does not implement frozen `TestRunListener` itself, whose callback surface is different. Vendor adapters belong to 4.7/6.6a.

**Outside 3.5:** retry quota/watchdog logic (3.2), queue removals/requeue placement/phantom-retry integration (3.7), DeviceActor result Deferred and identity rules (merged 3.6), pool/Scheduler construction and final reduction (3.8), tracker implementations/report summaries/reporters/attachments (3.9a–c), CLI construction/output draining/exit mapping (3.10/2.5), platform parsing, parameterised-result merging and xcresult enrichment (4.7/6.6a). ## Behaviour to reproduce

Here `P` = `K/execution/progress/PoolProgressAccumulator.kt`, `R` = `K/execution/result/TestRunResultsAccumulator.kt`.

- **Registration and unknown tests:** P:258–265 groups `shard.tests + shard.flakyTests` by Test equality, keeps each group's first Test/metadata, counts duplicates, then keys by `toTestName()` (string-name collisions overwrite). No runtime registration: unknown parameterised names warn at P:418–423 and return no action. They still print and reach CI in `testStarted`, but never track because no transition exists. PoolProgressAccumulatorTest.kt:133 requires the original base test to complete before aggregate success.
- **FSM:** Added starts with `total=count,running=0` (P:32–37). Passing/Failing accumulate evidence; ANY_SUCCESS can aggregate true before terminal completion, while ALL_SUCCESS requires a Passed state (P:356–379). Port all state/event branches at P:34–249, including mode/fast asymmetry: fast ANY_SUCCESS terminates on a success, not the first failure with attempts remaining; fast ALL_SUCCESS terminates on failure, not the first success with attempts remaining. Started increments running; result events decrement it; Passed/Failed increment done, Incomplete never does. Final Incomplete ends Added/Failing as Failed, Passing as Passed only under ANY_SUCCESS (P:76–81,132–145,196–201).
- **Terminal bookkeeping:** Passed/Failed never change verdict, but later result events still change done/running and are tracked (P:210–249). AddRetry increases total only in nonterminal states (P:83–85,150–152,206–208); in terminal states it leaves total unchanged and returns **Complete again** (P:223–225,243–245). RemoveAttempts subtracts count without reevaluating completion, including terminal states. Keep signed wrapping arithmetic; no progress clamping or nonnegative running invariant. **C4:** production never calls pool `testStarted`, so negative running and absent CI messages are expected. **C5:** retry runs AddRetry before quota decrement (`FixedQuotaRetryStrategy.kt:21–29`); reproduce phantom totals with the real FSM, leaving queue integration to 3.7.
- **Tracking order and payload:** P:250–255 tracks after storing the transition state. P:313–353 copies the originally registered Test back into each tracked result (restoring discovery metadata), keeps the callback's device snapshot, and sets tracker `final` solely from a Complete side effect. Final Incomplete is copied as FAILURE even if the overall ANY_SUCCESS verdict stays Passed. Late events in terminal states usually have `final=false`; AddRetry's Complete has no result/device and therefore no tracker call. Invalid transitions log before tracking; missing registrations warn without a tracker event. A tracker exception leaves the new state stored and prevents action return; do not rollback or swallow it.
- **Raw stdout and rounding:** `testEnded` prints **before** transition, hence the percentage excludes the just-ended result (P:277–298). IGNORED and ASSUMPTION_FAILURE print `ignored` and take Passed transitions. Exact line: `<percent> | [<pool>]-[<serial>] <test> passed|failed|ignored|incomplete\n`. Started transitions first, calls CI with `progress().toInt()` (the fraction, **not ×100**), then prints `started` (P:268–271). Progress is wrapping Int sums converted to **Float**, `done/total` (P:383–415); display multiplies in f32 by 100, Kotlin `roundToInt` (ties toward positive infinity, NaN throws), then `jcompat::formatting::format_percent` (`%02d%%`, D8; P:426–429). Empty aggregate throws from `reduce` (**C6**, P:356–379); empty progress is NaN. Represent the Kotlin failure explicitly, not a Rust panic or success. Standalone ProgressReporter uses `<batch.id>` instead of a percentage and has only started/failed/passed/ignored (`ProgressReporter.kt:9–24`).
- **CI bugs are contractual:** `CIIntegrationFactory.kt:7–16` chooses explicit None/Teamcity or Auto by an environment **value equal to** `TEAMCITY_VERSION` (**C3**), not existence of that key. `Teamcity.kt:4,8` prints exactly `##teamcity[buildStatus text='Marathon run: <int> %']\n`; it is not a progressStart/progressMessage or statistic message. None prints nothing (`None.kt:3–5`). Preserve C4 in real runs while directly testing this callable API.
- **Run record lifecycle:** R:25–36 initializes `name="not started"`, empty maps, zero elapsed time and creation-time Timer read. `testRunStarted` resets name, completion and failure message/count expectation only; it **does not clear** prior results, metrics or elapsed time (R:115–120). Ordered replacements keep the original Test key/insertion position (R:27,126–149). `testStarted` replaces the whole temporal record, discarding earlier failure/metrics. Updating a missing test creates it with Timer start time and the exact DEBUG message at R:140; only nonblank traces replace a stored trace. Explicit update times replace those fields (R:137–162).
- **Ending and counting:** R:164–175 creates a missing record, changes only INCOMPLETE to PASSED, writes endTime/metrics and **ignores supplied startTime for an existing record**. Default end-time argument is evaluated before the body; for a missing record the default start-time read follows it. R:177–198 fills zero endTimes with a separate Timer read per record. RunFailed sets failure text but not completion; Stopped/Ended add elapsed time and set complete; Ended merges runMetrics. Completed means status != INCOMPLETE (R:44–68), and failed counts include ASSUMPTION_FAILURE even though `TemporalTestResult.isSuccessful` returns true for it (`TemporalTestResult.kt:12–15`). Do not unify that predicate with TestResult.isSuccess. Count cache's dirty flag is never reset (R:73–78,132–134); expectedTestCount is unused.
- **Missing results and time seams:** R:91–112 synthesizes one INCOMPLETE per supplied test, in supplied order, without inserting them into the map: start is maximum endTime across **all** temporal records (including zero/incomplete ones), or construction time only when the map is empty; end is a fresh Timer read for each result, with batch ID/device and failure message or exact fallback text at R:110. `TemporalTestResult.kt:7` defaults through labelled wall read `core.TemporalTestResult.startTime`; R:127–128 invokes that default even though it immediately overwrites startTime. Timer reads use the frozen Timer seam (`core.di.Clock` for SystemTimer), not scheduler/monotonic time. P2 proposes omitting only the overwritten wall read; retain it until approved.
