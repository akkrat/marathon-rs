## Implemented API and consumer handoff

- `execution::progress::{PoolProgressAccumulator, ProgressServices, TestState,
  TestEvent}`: the five-state FSM uses the merged `StateMachine` and
  `model::TestAction`. Construction consumes the shard, strategy config, selected
  CI and frozen tracker/runtime/clock/log services. State is stored before
  tracking, callback device and result-device snapshots stay distinct, original
  discovery metadata is restored, and final incomplete events track FAILURE
  even when ANY_SUCCESS keeps the aggregate passed verdict.
- `PoolProgressAccumulator` implements the frozen synchronous `RetryProgress`.
  `retry_test`/`remove_test` return `Option<TestAction>`; terminal AddRetry
  returns Complete again without increasing total. Neither operation tracks.
  All counters and accumulated elapsed time use Java wrapping arithmetic.
- `test_started`/`test_ended` take the caller's cancellation signal and must be
  awaited to completion. Ended flushes its pre-transition percentage line,
  transitions, flushes diagnostics, and awaits the frozen Tracker through the
  merged bridge before returning the action. Tracker failures retain their
  taxonomy and leave the new state stored. No RefCell borrow crosses an await.
- `progress()` returns f32, including NaN on an empty map and values outside
  [0,1]. `aggregate_result()` returns a typed Kotlin UnsupportedOperationException
  for an empty map. Other aggregates enqueue the exact Kotlin diagnostics.
- `ci::Ci::from_config` takes explicit UTF-16 environment pairs. Auto checks
  values, preserving C3. Teamcity emits the literal buildStatus service message;
  started passes the truncated fraction, not fraction ×100. No production
  testStarted call was added (C4).
- `execution::result::{TestRunResultsAccumulator, TemporalTestResult,
  TemporalResults, Metrics}`: Send, serial vendor-side ownership; all callback
  forms use optional explicit times and propagate Timer failures. Ordered
  Test-keyed replacement keeps the first key/metadata. Mutable temporal values,
  metrics, counts, run flags and missing-result synthesis retain source quirks.
  Metrics enforce unique keys and map equality independently of entry order.
  The count-dirty flag remains set after recomputation. Standalone temporal
  defaults use `WallClock` label `core.TemporalTestResult.startTime`.
- Run callbacks retain diagnostic `LogRecord`s using the merged LogQueue
  machinery, without storing core-local Rc state in the Send accumulator.
  Vendor adapters must call `take_logs` after every callback, also on error,
  and forward these before later effects. Wall timestamps are creation-time;
  scheduler timestamps are zero because vendor callbacks have no core scheduler
  context. Platform adapters and attachment/result enrichment remain 4.7/6.6a.

## Changes to merged crates

**marathon-core:** additive progress/result/CI modules; model-only `TestStatus`
addition and `TestResult::is_ignored/is_success` operations (no equality or
serializer field changes); ordered `OutputRecord` support in `LogQueue` and
`ConsoleSink`/`OutputDriver` in output. Existing log-only `records`/`take`
callers continue to work. A mixed-output run must use `OutputDriver::flush`.

**marathon-cli:** additive `RunConsoleSink`, exported module, and
`Console::write_java_text`. The adapter accepts the startup Arc<Console>, registry
and a local-zone-offset callback. It retains Jansi state for events, uses the
text write path for raw lines, encodes malformed UTF-16 with JVM `?` replacement,
and swallows stdout write/flush failures. WP 3.10 constructs it; no run wiring
or exit behavior was changed.

**jcompat:** additive `jnum::kotlin_round_to_int(f32) -> Option<i32>` centralizes
Kotlin ties toward positive infinity, saturation and NaN rejection. Pool display
uses this and the existing en-US `format_percent`. The JVM Float-bit corpus
checks tie neighbors, nonfinite values and the 2^24 precision boundary.

`LogQueue` reserves an output completion-chain slot on core before dispatch;
later batches wait off core for previous completion, even under reverse vendor
poll order. The completion guard releases subsequent batches on failure or
unwind too. No blocking mutex or stdout I/O is introduced on core. The lifecycle
contract documents the shared-console construction and callback/drain boundaries.

## Integration with 3.4a

Rebased onto main `bfbc686` (WP 3.4a MetricsProvider), keeping every commit.

- **LogQueue.** 3.4a's off-core `incoming` `SegQueue` and 3.5's ordered
  `OutputRecord` list are one queue: the `SegQueue` now carries
  `OutputRecord`s, and core `log`, core `raw` and `LogSender::push` (wrapped
  as `OutputRecord::Log`) all enqueue there. `records`, `take` and
  `take_output` (and so `OutputDriver::flush`) drain it into the ordered list
  first, so push order is the single output order; nothing sent off core is
  skipped or reordered, and `take` still leaves `Raw` records for the driver.
  Witnesses: `log_queue_output.rs` and 3.4a's
  `analytics_concurrency::shared_log_producer_preserves_core_and_vendor_call_order`.
- **RunConsoleSink.** It resolved each new logger with `logger(name, None)`,
  which 3.4a forbids for registered loggers (it resets `Timings`/metrics
  levels after `configure(false)`). It now reuses registered names through
  `slf4j_logger` (new `MarathonLogging::is_registered`) and creates only
  unregistered ones. Witness:
  `core_output::registered_logger_levels_survive_and_sender_records_keep_raw_order`.
- **lifecycle.md.** "Core log records" and "Ordered raw console output" now
  describe the one shared queue, the OutputDriver drain and 3.4a's logger rule.
- **IDs.** Main took C38–C41, so this WP's C38–C40 are now C42–C44. U52 is
  unchanged (main ends at U51). Inventory and parity CSVs regenerated
  unchanged; no Cargo.lock change was needed.
