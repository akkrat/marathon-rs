# WP 8.3: Replace `JavaPath` with `PathBuf`; drop `jcompat::utf8` and `jcompat::net`

Effort **M** (mechanical, with three judgement points). Branch `wp/8.3-native-paths`, based on `main`
after WP 8.2 (commit `870400f7`).

## Why

Phase 8 removes Java emulation while keeping the contract in PLAN.md §3.12. After WP 8.2 text is plain
Rust `String`, but paths are still `JavaPath` (`crates/jcompat/src/file_manager.rs`, a `Vec<u16>` of UTF-16
units, about 570 uses in about 120 files), with `*_utf16` twins of most `FileManager` functions. Two small
modules also emulate the JDK where std or an existing crate does the job: `jcompat::utf8` (the JDK UTF-8
decoder's replacement granularity) and `jcompat::net` (Java socket-address text, `URLEncoder`, OkHttp's
ISO-8859-1 Basic credentials).

`jcompat::jnum` and `jcompat::jtime` are **out of scope**: they implement the input syntax the contract
keeps (Java number and ISO-8601 parsing) and need their own design (a later WP).

## Scope

### 1. `JavaPath` → `std::path::PathBuf` / `&Path`

- Delete `JavaPath`, `path_diagnostic`, `escape_utf16` and every `*_utf16` function or struct in
  `file_manager.rs` (`plan_file_utf16`, `Utf16FileRequest`, `absolute_file_path_utf16`, `new_utf16`,
  `plan_test_result_file_utf16`, `plan_folder_utf16`, ...). Callers use the `&str` versions.
- Fields, parameters and returns that hold a path become `PathBuf` (owned) or `&Path` (borrowed).
  `JavaPath::from_text(s)` sites become `PathBuf::from(s)` or the normalizing constructor below; the
  `to_path_buf()?` / `to_file_path_buf()?` calls disappear.
- **Keep Java `File` normalization** where it exists today (`normalize`, `append`, `file_path`,
  `absolute_file_path`, `child_file`, `relative_file`): repeated and trailing slashes collapse, `.`
  components stay. Port these functions to work on `&str` / `&Path` and return `PathBuf`, with the same
  results. Do not replace them with `Path::components()` round trips, which also drop `.` components.
- **Keep UTF-16 counting for limits.** `maxPath` and `maxFilename` still count UTF-16 units
  (`str::encode_utf16().count()`); diagnostic messages stay as today.
- **The one behaviour change (D56):** when a `maxPath`/`maxFilename` cut falls inside a surrogate pair,
  cut before the pair (the result is one UTF-16 unit shorter than the limit) instead of keeping a lone
  high surrogate. First confirm what rc.1 does in that case (expected: `to_path_buf` fails with
  `InvalidInput`, so that file or folder is not written and the caller reports or swallows the error;
  find which) and write it into D56. Update the existing test(s) that pin the lone-surrogate cut.
- Paths that reach a result file or a log line are rendered from the path text exactly as today. Where a
  `PathBuf` must become text, use `to_str()` with the error the code already returns for an invalid
  path, or `to_string_lossy()` where the old code could not fail; never `unwrap()`.
- NUL in a path: today `to_path_buf` rejects it with `InvalidInput`; std filesystem calls reject it the
  same way, so no explicit check is needed unless a test shows a path that is used before any
  filesystem call (then keep a check there).

### 2. `jcompat::utf8` → `String::from_utf8_lossy`

Replace every `decode_utf8(bytes)` with `String::from_utf8_lossy(bytes)` (`.into_owned()` where an owned
`String` is needed) and delete the module. The only difference is how many U+FFFD replace a malformed
sequence (for example an encoded surrogate `ED A0 80` is one U+FFFD in the JDK and three in Rust). Record
it as **D57** (first bullet). Update the corpus rows or tests that pin the JDK count (for example
`crates/marathon-config/examples/corpus.rs` and its fixture rows: add new expectations as a new file; do
not edit copied fixtures), and say which in the report.

### 3. `jcompat::net` → std and existing crates

- `inet_socket_address`: use `SocketAddr`'s `Display` (`127.0.0.1:5037`, `[::1]:5037`), with the host
  name in front only where the message needs it. Text-only change in error messages; check that no
  result file or golden carries it. D57 second bullet.
- `form_encode` / `query_encode`: use `form_urlencoded::byte_serialize` (already in `Cargo.lock`; it
  produces the same bytes as Java `URLEncoder`) and, for the query variant, `percent-encoding` with a set
  that keeps `.-*_` and alphanumerics only. Keep the existing tests (they pin the bytes; they must still
  pass unchanged). No D-row.
- `basic_credentials`: encode `user:password` as UTF-8 bytes (OkHttp encodes ISO-8859-1, which sends
  `?` for anything outside Latin-1 and so never worked with non-ASCII credentials). D57 third bullet.
- Delete the module.

### 4. Leftovers

Delete any `jcompat::jstring` helper left without callers. Keep `trim`, `is_whitespace`, `lines`,
`take_utf16` and whatever the UTF-16 limit counting needs.

## Rules

- The gate is the proof: `scripts/check.sh` passes, including the native goldens
  (`fixtures/contract/native-v1`), the config corpus golden (`fixtures/contract/config/corpus.json`) and
  every oracle suite. **No golden is re-blessed** in this WP. If one fails, the change is wrong (or it is a
  D56/D57 case: then stop and report it instead of re-blessing).
- Tests may change only where they pin a D56/D57 behaviour or call a deleted `*_utf16` API (port such a
  call to the `&str` API with the same expectation). List every changed test function in
  `docs/wp/8.3-test-changes.md` with a one-line reason.
- Never edit a copied fixture under `fixtures/`; add new files instead.
- Keep `//! Port of ...` headers and the comment density; delete comments that only explained UTF-16
  path handling.
- No `unwrap()`/`expect()` on I/O, process or network results.
- Commit in building steps (jcompat; config and core; vendors; CLI and cleanup).

## Acceptance

- `grep -rn 'JavaPath\|_utf16\b\|decode_utf8\|jcompat::net' crates/` finds nothing (except `take_utf16`
  and limit helpers that count UTF-16 units).
