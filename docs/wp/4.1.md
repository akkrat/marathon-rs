## Deliverables and boundary

In `crates/marathon-apple`, a `cmd` module tree mirroring the Kotlin packages (each ported module starts with `//! Port of <kotlin path>`, CLAUDE.md):

1. **Traits and value types** (Apple-local; 0.6 froze no transport trait): `CommandHost` (`id`, charset), `CommandExecutor` (`host`, `logger`, `connected`, async `execute(command, timeout, idle_timeout, env, workdir, charset) -> session`, explicit async `close`), `CommandSession` (stdout/stderr line receivers, shared exit-code cell `Option<i32>`, `is_alive`, `await`, `drain`, synchronous `terminate`/`kill`, explicit `close`), `CommandResult` (`successful == (exit_code == Some(0))`, `combined_stdout/stderr` joined with the platform line separator, `successful_or_null`), `CommandException`, `FileBridge` (async `send`/`receive -> bool`). Default helpers on the executor with Kotlin's exact composition: `critical_execute` (await, throw on !successful), `safe_execute` (await, `None` only on connection/transport failures), `safe_execute_nohup` (builds the `sh -c "nohup …"` argv). Error/cancellation/timing types are the frozen ones, not new ones: failures carry `marathon_core::error::Failure` (class, nullable message, cause chain), cancellation is `Cancellation`/`VendorError::Cancelled` observed through `VendorContext.cancellation: Arc<dyn CancellationSignal>`, delays and total/idle timeouts go through `VendorClock` (own-scope expiry rules in `lifecycle.md`), signed `jtime::Duration` millis are never clamped into `std::time::Duration`. Blocking process/pipe work runs on the vendor runtime (`VendorRuntime::spawn_blocking`, joinable after awaiter cancellation), never on core, and no `unwrap()`/`expect()` on I/O, process or channel results.
2. **Line channels with a close cause.** Kotlin delivers lines over bounded channels (`Channel.BUFFERED` = 64) that can close normally, close with a failure (the idle-timeout `TimeoutException`), or be cancelled by the consumer; `await()`, `drain()` and `consume_output` each treat those endings differently (below). The Rust channel must preserve that three-way distinction and bounded backpressure; a plain `mpsc` receiver that erases the cause is not enough.
3. **`BaseCommand`** shared session behaviour (`await`/`drain`/`close` over the two receivers + exit-code cell), reused by the local session now and the SSH session in 4.2.
4. **`consume_output(session, on_stdout, on_stderr) -> Option<i32>`**: concurrent consumers, exit code awaited only after both streams end, both receivers cancelled in all exits.
5. **`LineBuffer`**: chunk append with CR/LF/CRLF normalisation, `flush` (terminated lines only), `drain` (plus unterminated tail), close drains; safe under concurrent append/flush, lines delivered exactly once and in order.
6. **Idle-timeout reader** (`produce_lines_manually` equivalent) and **`PollBackoff`** (1 ms doubling to 20 ms): one reader per stream over a shared last-output timestamp, 16 KiB read chunks, immediate flush of complete lines, final drain on `can_read` false, idle expiry closes that stream's channel before drain and discards its partial tail (A24). Pipe EOF while `can_read` stays true keeps polling until idle expiry (A25). The injected `currentTimeMillis` seam of `Reader.kt:46` is kept (tests and replay label `apple.Reader.currentTimeMillis` depend on it).
7. **Local executor**: `KotlinProcessHost` (`id = "local"`), process executor (quote stripping, env, workdir, piped stdout/stderr, total timeout → `None` exit code, per-session supervisor scope), process session (`terminate` = destroy, `kill` = destroy forcibly, close destroys then joins the scope), and `JvmFileBridge` (recursive local copy both ways). Executor `close()` is a no-op; sessions are independent (terminating one never closes the executor).
8. **Small extensions**: `Durations::INFINITE` (7 days) and `bash_escape`. `ConfigurationExtensions.kt` only if open question 2 keeps it here.

**Not 4.1:** the SSH executor, `shellCommand` quoting, `suspendFor`/`autodetectExitCode`, auth/known_hosts/keep-alive/`PerformanceDefaultConfig` (4.2 — but the trait must already let 4.2 express A2 ignored env/workdir, A11 captured `isAlive`, A14 close-then-join with its 30 s wait, and per-command exec channels without a signature change); `ConnectionFactory`, rsync bridge, `WriteFile`, `SharedTransfers` (4.3; `WriteFileTest`/`SharedTransfersTest` rows stay there even though they drive the local executor); tool wrappers and their `criticalExecute` call sites (4.4); `RemoteFileManager` (4.10a, incl. its private duplicate `bashEscape` at `RemoteFileManager.kt:204` — 4.10a deduplicates onto this WP's function); the in-process fake executor for device tests (5.1, on these traits); whole-run local comparison (7.2). `tools/fake-worker` and the scripted Apple world are **not** test vehicles for this WP (no SSH exists yet); the vehicle is PLAN §6.4's hermetic local-transport contract suite: real local processes (`sh`/`echo`/`seq`/`sleep`, as the Kotlin tests do) plus fake binaries in a controlled `PATH` where argv/env/workdir must be observed. The 0.4b backlog items "stream chunks/partial tails, timeouts/TERM" are covered here only for the local reader/executor; their SSH forms belong to 4.2/4.3.

**Substrate warning:** WP 3.1 (the `Job`/`Deferred`/`VendorClock`/`VendorRuntime` implementations) is not merged; `marathon-core` today is traits only, and no workspace crate except `marathon-adb`'s server feature and `tools/fake-worker` depends on tokio (`=1.53.2` in both). See open question 1 — do not invent a second runtime or a private clock while waiting for the answer.

## Behaviours to reproduce (exact sources)

- **`execute` never throws a timeout** (`CommandExecutor.kt:18-23`): total timeout and parallel interruption drain the channels and return a `null` exit code; the caller must fully drain or producers block. `criticalExecute` throws `CommandException` with the exact message shape at :55-60 (`command <joinToString(" ")> failed with exit code <code>:` + platform-separator-joined stdout/stderr, `trimMargin`). `safeExecute` catches only sshj `ConnectionException`/`TransportException` around **both** `execute()` and `await()` (:76-85, corrected in 0.3a F10), logs `Unable to start a remote shell session $command` / `Error starting a remote shell session $command` at error on the executor's logger, and returns `null`; every other failure (incl. A17's `IllegalStateException("Not connected")`) propagates. The Rust taxonomy must keep those two transport classes distinguishable for 4.2 without leaking sshj types into the trait. `safeExecuteNohup` builds exactly `["sh","-c","nohup <args joined by space> > /dev/null 2>&1 & echo $! > <pidfile>"]` (:103) — no quoting of args or pidfile.
- **`BaseCommand.await()`** (`BaseCommand.kt:25-61`): both streams are collected by tasks under the session's supervisor job on the I/O dispatcher, then `awaitAll(stdout, stderr, exitCode)`. A stream that closes **with a cause** (idle timeout) or fails cancels its collector with `CancellationException("Channel closed"/"Channel failed", cause)` (:32-33, :47-48) — so through `await()` an idle timeout surfaces wrapped as cancellation, while through `consume_output` the original `TimeoutException` is rethrown (`CommandSessionOutputTest` `streamFailureCancelsOtherConsumerAndIsRethrown`). Preserve or explicitly simplify (P5); do not silently unify. `drain()` (:63-74) launches both discarding collectors with `async(job)` as children of the command job, outside its `supervisorScope`, and returns immediately. A close-with-cause fails only the detached collector and does not reach the drain caller (A26). `close()` (:76-82) blocks the calling thread in `runBlocking { job.cancelAndJoin() }` only if the job is still active; in Rust this becomes an awaited async close at the same call sites (lifecycle.md: Drop must not do it), and cancelling the session scope must not kill the underlying process by itself — the local/SSH `close()` overrides do that separately.
- **`consume_output`** (`CommandSessionOutput.kt:17-34`): the two callbacks run concurrently; failure or cancellation in either stream or callback cancels the other consumer and is rethrown (cancellation keeps its identity/message); the exit code is awaited only after both streams close (`waitsForExitCodeAfterStreamsAreClosed`); the `finally` cancels both receivers even when the caller was already cancelled before any consumer started (:29-33). After a consumer failure, session `close()` must not block on the unread stream (`BaseCommandExecutorTest:133-153`).
- **`LineBuffer`** (`LineBuffer.kt:14-24`): each chunk is decoded independently as `String(bytes, 0, count, charset)` — a multi-byte character split across chunks decodes with replacement on both sides (P4 proposes not emulating this). `\r\n`→`\n` then `\r`→`\n`; a chunk-ending `\r` is emitted at once and a leading `\n` of the next non-empty chunk is suppressed even across flushes and zero-count appends (:18-20). `flush` emits all but the last `lines()` segment and retains the partial tail verbatim, whitespace included (:26-46); `drain` appends `\n` unless the buffer already ends with `\r`/`\n` (the `\r` arm is unreachable after normalisation — keep the observable behaviour, not the dead check) then flushes (:48-59). Append/flush are lock-guarded but `onLine` is called outside the lock (:43-45); the 20 000-line concurrent test must still deliver every line exactly once.
- **Reader** (`Reader.kt:49-101`): poll `available()`; read at most `min(available, 16384)` bytes; on data, append, stamp the **shared** `lastOutputTimeMillis`, reset backoff, flush, continue without delay (:72-79). Idle check, in this order: data first (output read after the deadline is delivered, no timeout — tested), then `timeSinceLastOutput - maxMillis(20) > idleTimeout.toMillis()` closes the channel with `TimeoutException("idle timeout $idleTimeout reached")` (:84-89; message uses `Duration.toString()`, e.g. `PT0.2S`), then EOF/`!canRead()` ends normally (:92-94), else `delay(backoff.next())`. The 20 ms grace means the other stream's just-arrived output is never reported idle (tested at 1 ms reader offset). `available()` throwing `IOException` ends the reader normally (:55-59). After the loop, `drain()` always runs (:98), including after an idle-timeout close, but the already-closed channel rejects the buffered partial tail: it is discarded and the first receive fails with the timeout (A24). U10 does not override this Kotlin behaviour. Because `available()==0` never reads, termination relies on the `canRead` predicate (`process.isAlive && !exitCode.isCompleted` locally, `cmd.isOpen && !cmd.isEOF` over SSH); keep that predicate a parameter, it is the 4.2 seam.
- **Local executor** (`KotlinProcessCommandExecutor.kt`): the class comment "doesn't support idle timeout currently" (:21-23) is stale — idle timeout is passed to both readers (:70-71) and works. Quote stripping (:47-53): an argument that both starts and ends with `'` or both with `"` (`isShellscaped`, :85-88, no content check) has `removeSurrounding("\"")` then `removeSurrounding("'")` applied — so `"'x'"` loses both layers, a lone interior quote survives. `ProcessBuilder` gets PIPE for both streams, `directory(File(workdir))` when non-null, `environment().putAll(env)` over the inherited environment (:55-61); a missing binary or bad workdir throws out of `execute` from `start()`. Exit cell: `withTimeoutOrNull(timeout) { process.onExit().await(); exitValue() }` (:63-67, :90-93). **On total timeout nothing kills the process**: the cell completes `null`, `canRead` goes false, readers drain and close, `await()` returns — the child keeps running until session close (A21, P2 rejected). Java `exitValue()` for a signalled Unix process is `128+signal` (TERM→143, asserted at `BaseCommandExecutorTest:197,216`); Rust `ExitStatus::code()` is `None` there, so the signal mapping must be synthesised (`ExitStatusExt::signal`). `KotlinProcessCommand.close()` destroys (forcibly iff the executor's `destroyForcibly` flag) before joining the session scope (:27-33); `terminate()`/`kill()` never touch the executor (its `close()` is empty, `connected` is constant `true`).
- **`JvmFileBridge`** (`JvmFileBridge.kt:8-22`): Kotlin stdlib `File.copyRecursively(target, overwrite=true)` semantics both ways (directories created, existing files overwritten, returns `false` rather than throwing on the failures stdlib swallows — pin the exact set with tests/oracle probe before coding). `receive` checks `source.exists()` **after** computing the destination and returns `false` without creating anything; the filename for a directory destination is `src.split("/").last()` (`RemoteFileManager.FILE_SEPARATOR = "/"`, `RemoteFileManager.kt:207`), so a trailing slash yields an empty last segment — reproduce or flag. `send` has no existence pre-check.
- **Logging**: each executor construction takes its logger from `MarathonLogging.logger {}` (local: `KotlinProcessCommandExecutor.kt:28`), i.e. the Kotlin class name, level set on every lookup (PLAN §3.5, bug C18). In Rust the handle comes from the per-run `jcompat` registry (`Arc<Mutex<MarathonLogging>>`, never held across await); construction therefore needs the registry passed in — there is no global logger lookup.

**Known Kotlin bugs:** WP 4.1 records A21–A26 in `docs/known-kotlin-bugs.md` (A23 is not reproduced under approved P4/D10). A2/A11–A17 (4.2) constrain the trait as noted above and must not be "fixed" by trait design (e.g. do not drop `env`/`workdir` because SSH ignores them, do not make `isAlive` a method that forces a live query). Recorded WP=4.1 behaviours: local total-timeout process leak; `await()` wrapping an idle timeout as `CancellationException("Channel closed", …)`; per-chunk decode corruption in `LineBuffer`. Also note for the port (test bug, not a known-bug row): `testInterruptUsingKillShouldNotCloseExecutor` never calls `kill()` — it passes `"&"` as an argv element to `sleep`, which exits non-zero at once. ## Proposed simplifications (pragmatic parity — for orchestrator approval, **not decided**)

Per the user's direction: few users; do not emulate quirks only exotic inputs reach. Until one is approved, the behaviours above stand. Each approved item becomes a PLAN §3.11-style deviation entry and affected rows are marked, not dropped.

- **P1, charset:** support UTF-8 only (JVM default on JDK 21, and sshj's remote charset in practice). Keep the charset parameter in the API for 4.2, but decode as UTF-8 with replacement and ignore other values. Lines are Rust `String`, not `JavaString` (Java decoding already replaces malformed input, so lossless UTF-16 buys nothing here).
- **P2, local timeout:** terminate the local process when the total timeout expires, as the SSH executor does (`SshjCommandExecutor.kt:57-60`), instead of leaking it. Diverges in the worker's process table and in output a leaked process would still write to a drained pipe (then die on SIGPIPE).
- **P3, dead code:** do not port `produceLines` (`Reader.kt:18-37`, no callers) — inventory already assigns the whole file to 4.1; record the function as not ported in findings (no `n/a` row exists for a single function).
- **P4, split characters:** decode incrementally so a character split across read chunks survives, instead of Java's per-chunk replacement. Diverges only when a multi-byte sequence straddles a 16 KiB/`available()` boundary.
- **P5, `await()` idle-timeout shape:** surface the original timeout failure from `await()` too (as `consume_output` does), instead of `CancellationException("Channel closed", cause)`. Affects only callers that distinguish cancellation from failure on this path (DeviceActor classification is 3.6/5.2 territory — check before approving).
- **P6, reader mechanics:** keep the observable contract (shared idle clock, +20 ms grace, poll-count-visible backoff for `ReaderTest`) but implement over non-blocking/async pipe reads on the vendor runtime rather than emulating `InputStream.available()` with `FIONREAD` on blocking threads. Exact poll counts remain test-visible through the `canRead`/clock seams.
