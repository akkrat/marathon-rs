## Host isolation and execution ownership

The implementer prepares reviewable scripts/configs offline; **the orchestrator performs real-host operations**. Never contact the remote Mac without the user's explicit approval. Access its real sshd through an approved loopback SSH port forward (U3: the outer access service can report every command as exit 0). Verify nonzero exit propagation before capture. Endpoint, account, key and known-host material comes from private untracked configuration; never commit host names, user names, keys, tokens or unsanitized captures. Do not enable Remote Login on this Mac. Linux access and the pre-merge remote gate also belong to the orchestrator.

- **iOS:** this Mac's Xcode 27 profile and the remote Mac's Xcode 26.6 profile. Record actual versions/build numbers; those labels are not interchangeable goldens. Every invocation creates a fresh named simulator, records the returned UDID in an ownership ledger and deletes it on completion/failure. Use static `type: simulator` targets with only these UDIDs, never `simulatorProfile` reuse or any existing simulator. Set `lifecycle.shutdownUnused: false`; otherwise provider planning shuts down unrelated booted simulators. No `erase all`, `delete unavailable`, broad process kill or global simulator-service restart. Cleanup addresses only owned UDIDs/PIDs, including any replacement explicitly created by this run; unexpected recovery allocation fails the scope check.
- **Apple worker files:** take an exclusive reservation for the worker's entire `/tmp/marathon`, including `shared/`, before either implementation. Different simulators do not isolate fixed xctestrun/shared paths or rsync `--delete`. Refuse an occupied worker; do not wipe another run. Preserve/restore its agreed baseline between Kotlin and Rust. Record runner cleanup **before** harness cleanup, then remove only owned state. `run-isolated.sh` isolates client files/HOME/TMPDIR, not the Apple worker, simulators or TCC.
- **macOS:** local means both CLI and worker inside a disposable VM on this Mac, using actual local transport. SSH means a disposable VM/equivalent fully restorable worker on the remote Mac, reached through the approved forwarding route. Restore the same full snapshot before **each** side: system/user TCC databases, app/test state, worker files and login-session state. No macOS XCTest execution or TCC/SIP changes on the user's desktop. Omitting permissions does not waive restoration. Without a matching snapshot environment, mark this profile blocked; disjoint machines are not same-host differential evidence.
- **Android:** use the Linux KVM worker, **no Docker**, with a newly created AVD and a private ADB server on an explicitly reserved non-default port. Never start, stop or kill the user's server, or connect to, reset, install on or otherwise touch already-attached devices/emulators. A port alone is insufficient: ADB scans USB and emulator ports (`6.1-findings.md`). Before starting it, require a reserved worker with no other devices/emulators or an isolated network/device namespace exposing only this run's emulator and KVM. Fail preflight if that cannot be established. Use private SDK/AVD HOME state, explicit server selection for every adb command and emulator registration, `adbServers` containing only that endpoint, and exact owned serials. Prove the private server sees only the owned emulator before launching Marathon; abort if inventory changes. Kill only owned server/emulator PIDs and remove owned AVD files. Recreate the AVD from the same clean image for the second side, including external storage and trace/recording files. No fallback to port 5037, an attached phone or the user's Mac emulator.

All cleanup is bounded, awaited and journalled across normal exit, Ctrl-C and harness timeout. A watchdog is harness failure, never the expected test timeout; save evidence first, reclaim only owned resources, and retain any cleanup failure. Test these guards with command-recording doubles, without provisioning real devices in the ordinary gate.

7. **Acceptance bar (user decision, 2026-10-31): outcome-level.** The real-host runs compare Kotlin and Rust at outcome level:
   - CLI exit codes, and test statuses and counts;
   - stdout/stderr summary lines;
   - report files (JUnit, Allure, HTML JSON, xcresult-derived data) and pulled artifacts and file-sync outputs;
   - media sanity per P3.
   Volatile values (timestamps, UUIDs, UDIDs and serials, durations, host paths) are normalized by documented rules, and each rule is justified by a JVM-vs-JVM rerun that shows the same volatility. Command-, transfer- and adb-level causal parity is NOT re-certified on real hosts; it stays covered by the 7.1b fake-worker and scripted-ADB suites. The real transport recorder is not required, so findings item 1 is resolved by this decision. `compare --release` must implement this bar instead of failing unconditionally.
8. **Sorting.** Approved: the templates use `no-sorting`, because the frozen CLI has no lexical strategy. No product strategy is added. Comparisons must not assume execution order where `no-sorting` and parallelism make it unspecified: compare test results as a keyed set, and keep within-test ordering.
9. **The release comparison is a semantic projection (orchestrator, 2026-10-31, applying decision 7).** The first real witness showed that byte-level comparison with patch rules cannot even qualify Kotlin against Kotlin. The causes were UUID-named Allure files, measured durations, and log-line partitioning and order. So `compare --release` gates on a projection that is extracted identically from both sides and compared exactly:
   - CLI exit code, and the stdout `Marathon run finished` summary counts and the stderr execution verdict;
   - for each test, keyed by its fully qualified name: final status, attempt count, failure class and message, and failure source location (path suffix and line);
   - JUnit: the testcase set with its failure, skip and error elements and their messages. Times, timestamps and ordering are ignored.
   - Allure: the multiset of (test name, status, statusDetails message), plus the count of attachments per test by type. File names and UUIDs are ignored.
   - xcresult, extracted via xcresulttool: test, failure and skip counts, plus issue (test, message, location);
   - the set of report and artifact kinds produced per test (logs, xcresult, video, screenshots and so on), by role, not by name; and media sanity per P3.
