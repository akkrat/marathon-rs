# WP 8.17 (design first): Retire the remaining Kotlin coroutine quirks

Effort **M** for the design; implementation WPs are sized by it. Branch `wp/8.17-coroutine-quirks`, based
on `main` after WP 8.15 (commit `f4244c70`). WP 8.16 runs in parallel.

## Why

`docs/design/tokio-tasks.md` §7 item 6 (the reviewed outcome of WP 8.13): after 8.14 and 8.15 the runtime
still reproduces kotlinx.coroutines internals that the reviews found no marathon behaviour depends on,
or depends on only through test witnesses. PLAN.md §3.12 lets Phase 8 remove exotic Kotlin behaviour when
preserving it requires emulation. The owner asked to do this.

Candidates named by the reviews:

- **Child traversal: single-node versus list mode.** `JobSupport`'s node/list representation decides
  whether a child attached during a join is observed (`job.rs` `Node`, `list_mode`, `waiting_child`,
  `join_observed_children`; Scheduler's traversal in `execution/scheduler.rs`; pinned by
  `runtime_races` tests such as `single_child_traversal_misses_later_attachment`). The late-pool
  integration tests show Scheduler does need lazy successor traversal; whether it needs the single-node
  miss is the question.
- **Disposable completion registrations.** `invoke_on_completion` returns a disposable handle; the only
  production registration (DeviceActor) never disposes it.
- **`Cancellation::Parent` versus `Requested`.** No production policy distinguishes the two tags; the
  payload and timeout identity matter.
- Any other construct the inventory finds in the same class (callback ordering witnesses, interleaved
  child/callback node lists).

## What the design must answer

1. For each candidate: classify it as **production dependency** (marathon output or behaviour changes
   without it), **integration witness** (an end-to-end test pins it, but no contract item does) or
   **synthetic coroutine witness** (only a runtime unit test pins it). Prove the class with a prototype
   that removes it and runs the full test suite and the native goldens.
2. For each candidate you propose to retire: the simpler replacement, what it deletes (lines), what
   behaviour changes, which tests change and why, and a **D-row draft**. Check D48 (late devices and pools
   after a run ends) and D52 (bounded cancel) explicitly, since traversal timing can delay run end.
3. A split into implementation WPs (smallest risk first), each mergeable with the gate green.
4. A recommendation: which to retire, which to keep.

## Process

1. Sol writes `docs/design/coroutine-quirks.md` with prototypes (outside the repository or removed before
   commit) and commits it. No runtime code changes.
2. Independent critiques by two other models; the orchestrator merges the design after the critiques are
   answered, then commissions the implementation WPs.
