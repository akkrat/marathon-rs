Branch `wp/3.10-run-flow`, based on main `d8c5d09`, rebased onto `5b3d5bf`. Reference: Kotlin `e47352f2`; oracle build `tools/oracle/build.sh reference`
(JBR 21.0.10, `ORACLE_GRADLE_FLAGS=--offline`).

## What was built

- `marathon-core::marathon` (Marathon.kt, ShutdownHook.kt): `run_async` and the supervised `run` / `run_under`, timings,
  filters, shard/flakiness with the D13 flakiness prefetch, coverage, Scheduler construction, the outputDir wipe, onFinish
  with the C25 guard, the catch (`kotlin.Unit` + NoDevices → false, anything else → ignoreFailures), the debug-only hook
  and the P3 `SignalRelay`.
- `marathon-core::construction` (di/Modules.kt): `construct(core, RunInputs)` builds the per-run graph in Koin's
  resolution order (Track and Timer, vendor services, parser/log configurator checks, TrackerFactory with the nine reporter
  slots and the optional backend, AnalyticsFactory, parse command) and the `RunServices` holder (concrete `Rc<CoreExecutor>`,
  OutputDriver, Ci, filter services, P1 facts, relay). No downcast; the frozen `RunDependencies` is unchanged.
- `marathon-core::execution::parse_command` (MarathonTestParseCommand.kt, ParseCommandResult.kt) over 3.9b's
  `parse_results`; `marathon-core::executor::timeout` (Timeout.kt's Duration adapters over 3.1's scopes).
- `marathon-cli::runner::ProductionRunner` implements `CliRunner`/`MarathonRun` on a dedicated core-executor thread;
  `main` uses it. Vendor factories that do not exist yet (`missing_vendors()`) fail construction with
  `java.lang.UnsupportedOperationException: The <vendor> vendor is not supported by this build yet` (uncaught path, exit 1).
  The analytics clients (3.4b) are injected as `MetricsSetup`/`BackendFactory` from the CLI; core gains no HTTP edge.
- `marathon-test-support`: StubDevice, StubDeviceProvider, StubTestBundle(Identifier), ConfigurationFactory, MarathonFactory,
  JSON/XML assertions, a recording console, and the scenario harness that drives the version-1 inputs in
  `tools/oracle/scenarios` with `ControlledReplay::event` and logs device calls in the replay transcript's shape.

## Decisions applied

- **P1 (D12 extension).** `System Information:` is followed by exactly these lines, in order (CLI values):
  `os.name: <std::env::consts::OS>`, `os.version: <uname -r, else unknown>`, `os.arch: <std::env::consts::ARCH>`,
  `available.processors: <available_parallelism>`, `marathon.version: <VERSION>`, `user.dir: <cwd>`, `user.home: <$HOME>`.
  They go to the `com.malinskiy.marathon.Marathon` logger at INFO, so (as in Kotlin, whose logger is created after
  `configureLogging`) they are invisible with `debug: false`. Replay tests use the single fact `os.name: test` and drop it
  together with the JVM's `java.*`/`os.*` lines.
- **P2.** StubExecutionResults (empty, unreferenced) and Mockito/Koin machinery are not ported; Mocks.kt is
  `StubTestParser`/`MockLogConfigurator`/`MockTestBundleIdentifier`/`CounterTimer`, MarathonFactory.kt is
  `factory::MarathonFactory` over the production `construct`. Call-site audit: StubExecutionResults has no reference in the
  repository; Mocks.TestParser.DEFAULT is used only by MarathonFactory. All builder defaults are kept. StubDevice's own
  debug lines (`Preparing`, `Disposing`) are not routed to a console (no vendor log channel exists in the frozen contract).
- **P3.** One relay per run; the hook flag is set only for debug (C10) and cleared after a successful `run_async`; the relay
  task runs on core and awaits the guarded onFinish before exiting. JVM registration failures are not emulated.
- **Decision 5.** `FileExtensions.kt` moved to 3.9c in `scripts/source_inventory.py` (inventory regenerated). 3.9c's
  existing `jcompat::file_manager::relative_file` is its port; nothing is duplicated here.
- **Decision 6.** Stub runs go through non-CLI injection only (`MarathonFactory`, `ProductionRunner` with a stub factory in
  `crates/marathon-cli/tests/production_runner.rs`); the CLI's Stub/Empty gate is untouched.

  Exception in completion handler InvokeOnCompletion@… for DeferredCoroutine{Cancelled}@…` on stderr (probe

  the process has the default disposition and is killed by the signal, so the shell still sees 130/143 (128+n), but no

  exit is ignored.

## Review round 1

Cross-family review: merge after fixes. It regenerated the three JVM evidence files (they matched) and agreed with the 20
ports, P1, P2 and the Q1/Q3 exceptions. Orchestrator decisions on its findings:

- **R1-sol-1 (High), fixed.** The OS SIGINT/SIGTERM handlers were registered during construction (blocking core on the
  registration) while the relay only ran later, so a signal during vendor construction left the process alive.
  `SignalRelay::os` now only records the vendor runtime; the listener is spawned when the run starts
  (`Marathon::start_relay`), and nothing waits for it to register. The accepted windows: before the run the default
  disposition ends the process (the shell sees 130/143); during the run the relay exits 130/143 in both debug modes; after
  the run the signal is ignored. A registration failure leaves the default disposition in place instead of failing
  construction. Real-subprocess coverage (`crates/marathon-cli/tests/signal_windows.rs`): the test binary re-runs itself as
  a child on the production runner with the Stub vendor and receives kill(2) while the vendor factory is suspended (killed
  by the signal) and while the parse is suspended (exit 130/143, `debug` false and true). `nix` (signal feature) is a new
  dev-dependency of marathon-cli.
- **R1-sol-2, not reproduced (approved simplification).** The reviewer's JVM probe confirmed that Kotlin's outputDir wipe
  follows a directory symlink and deletes the external target's sentinel. Rust deliberately does not: deleting outside
  outputDir is destructive. C68's row records the witness ("reproduced: no, deliberately");
  `run_flow_witnesses.rs::wipe_removes_a_directory_symlink_without_following_it` is the regression.
- **R1-sol-3, fixed.** The scenario loader panicked on `scripted.json` ("unsupported scenario event prepare-done") and
  always used `runAsync`. `StubDeviceOptions::scripted` ports the replay driver's `scripted` behaviour
  (`tools/oracle/module/.../ReplayDevice.kt`): prepare and execute suspend until `prepare-done`/`prepare-failed` or
  `batch-result`/`batch-failed` (with `reportEmptyResultsFirst` and the three exception kinds), and a mis-timed event is a
  replay error, as in the driver. `load` honours `entry` (`run` drives `Marathon::run_under`), and also reads
  `testTimeMillis`/`reportResultsBeforeCrash`. `scripted.json` and a new input, `scripted-failures.json`, are captured
  with the patched build and `scenario-tape.json` (`entry: run` needs the hooked `runBlocking`); `capture_scenarios.py`
  runs them as TAPED rows (`"taped": true`) and `run_flow_oracle.rs` compares both like the other scenarios (outcome,
  log, raw.json, manifest, reporter text). The other 13 rows were regenerated in the same run; they differ from the
  previous capture only in random UUIDs and wall-clock values, which the comparison masks.
- **R1-sol-4, fixed.** The reporter masks erased ordinary data (`contact.foo@deadbeef` vs `@cafebabe`, distinct 13-digit
  test names). Identity hashes are now masked only in `allure-results/environment.xml`, for the nine configuration keys
  whose values print `Class@hash`; epoch millis only right after the `start`/`stop` (Allure) and `startDate`/`endDate`
  (HTML) fields; the outputDir path only in environment.xml. `report_masks_keep_ordinary_data_literal` pins it.
- **R1-sol-5, fixed.** `scripts/parity_matrix.py` records the implementation commit of the 20 rows (the rebased commit
  that added each suite), and the CSVs are regenerated.

## Review round 2

- **R2-sol-1 (Medium), fixed.** SIGINT and SIGTERM were registered as a pair, so a failed SIGTERM registration abandoned the
  SIGINT stream that had already registered. Tokio keeps an installed handler, so SIGINT was swallowed and the process
  survived. Each signal is now registered on its own (`SignalRelay::listen`). A signal that registered is always relayed,
  and one that failed keeps its default disposition. The registration goes through `SignalHooks::registration`, which
  defaults to `tokio_registration`. `signal_windows.rs::a_signal_whose_registration_failed_keeps_its_default_disposition`
  injects a failure for each signal in turn. The failed signal kills the child, and the other one exits with 130 or 143.
  A mutant that drops the relay on any failure fails this test, because the child survives.
- **R2-sol-2 (Medium), fixed.** The 300 ms sleep is gone. `SignalHooks::ready` runs once both registrations have been
  attempted. The test child prints `MARKER ready` from it, and the parent waits for that marker and for `MARKER run`
  before it calls kill. `main` passes `SignalHooks::default()` (no hook), so production behaviour is unchanged; the hooks
  reach the relay through `RunInputs::signal_hooks` and `ProductionRunner::signal_hooks`. Sol's 1.5 s `delay-int.dylib`
  witness now passes (6.5 s for the suite). Stress results, on 18 CPUs with 18 `yes` hogs, where each suite run makes 10
  signalled children:
  - 64 parallel workers: 1280 suite runs, all passed (12,800 signals).
  - 24 workers: 240 suite runs, all passed.
  - With `delay-int.dylib` injected and 32 workers: 96 suite runs, all passed.
- **Inherited ignored signals (round 3, orchestrator decision 2026-10-25: match HotSpot).** The first stress harness ran
  from `( … ) &` shell jobs, which start with SIGINT ignored. There the construction-window SIGINT test failed because
  the child survived, as it should. A JVM probe (`Hook.java` with a shutdown hook, started with SIGINT and SIGTERM set to
  SIG_IGN) showed that HotSpot then installs no handler for either signal, so both stay ignored. Tokio's registration
  replaces SIG_IGN, so before this round such a process exited with 130 or 143 during the run. Now the relay asks
  `marathon::signal_ignored` before it registers each signal, and skips a signal that is already ignored. That function
  is a read-only `sigaction(sig, NULL, &old)` and the workspace's only `#[allow(unsafe_code)]`, with a `// SAFETY:`
  comment. The workspace lint stays `unsafe_code = "deny"`, which a local allow overrides, so nothing broader is
  permitted. It is Unix only; other targets keep their old behaviour. Tests in `signal_windows.rs`:
  - `a_signal_ignored_at_start_stays_ignored_during_the_run` starts the child through `sh -c "trap '' INT; exec …"`,
    then the same with TERM. The child survives the ignored signal for 1 s, and the other signal is still relayed
    (exit 130 or 143). The test fails when the check is removed.
  - When the test process itself ignores a signal, the other tests skip the cases that need that signal's default
    disposition, and print why: a child inherits the ignored disposition, and `sh` cannot reset a signal that was
    ignored on entry. The suite passes when it is run under `trap '' INT` and under `trap '' TERM`.
