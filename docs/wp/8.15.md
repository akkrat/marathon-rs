# WP 8.15: Concrete core runtime handles instead of single-implementation traits

Effort **M**. Branch `wp/8.15-concrete-core-handles`, based on `main` after WP 8.14 (commit `2b1d44b4`).

## Why

`docs/design/tokio-tasks.md` §7 (the reviewed outcome of WP 8.13): `Job`, `CoreRuntime` and
`TimeoutScope` each have exactly one implementation in the workspace, tests included. Because `JobRef`
is `Rc<dyn Job>` and `TaskContext` carries `Rc<dyn CoreRuntime>`, `CoreExecutor` keeps a pointer-keyed
weak registry of jobs, sweeps it, and resolves erased handles back to `RuntimeJob` with a `resolve()`
that can panic (`executor/mod.rs`, `executor/clock.rs`, `runtime.rs`). Using the concrete types removes
that machinery without changing scheduling.

## Scope

1. A concrete job handle (for example `JobHandle` around `Rc<RuntimeJob>`, or `JobRef = Rc<RuntimeJob>`)
   replaces `Rc<dyn Job>` everywhere; delete the `Job` trait, the job registry, its sweep and `resolve()`.
2. `TaskContext` carries the concrete `CoreExecutor` (or a concrete handle to it) instead of
   `Rc<dyn CoreRuntime>`; delete the `CoreRuntime` trait.
3. `TimeoutScope` becomes concrete; delete the trait.
4. `Deferred`: make it concrete only if the compiler shows it is easy (vendors already name
   `SharedDeferred`); otherwise leave it and say why.
5. **Keep as traits:** `VendorRuntime`, `VendorClock`, `CancellationSignal`, `EventChannel`, `Actor`, and
   any trait with more than one implementation (check each before touching it).
6. Runtime ownership must stay explicit: a job handle from one runtime must not be usable with another
   (today the registry enforces it implicitly; keep that guarantee through private construction or an
   explicit owner identity, with a test).

**No semantic change:** the same cancellation, callback, completion, traversal and timeout rules; the
same task spawning and polling order. Every existing `runtime_*` test, the oracle suites, the native
goldens and the config corpus pass with unchanged expectations.

## Rules

- Mechanical, compiler-guided; commit in building steps (job handle; core runtime; timeout scope;
  cleanup).
- `git diff 2b1d44b4 -- fixtures/` empty. Test changes only where a test names a deleted trait or
  constructs a fake implementation of it; list each in `docs/wp/8.15-test-changes.md`.
- Update `docs/design/lifecycle.md` and `docs/design/tokio-tasks.md` where they describe the traits.
- Keep `//! Port of ...` headers. No `unwrap()`/`expect()` on I/O, process or network results; the
  removed `resolve()` panic must not reappear as another panic.

## Acceptance

- `grep -rn 'trait Job\b\|trait CoreRuntime\|trait TimeoutScope\|fn resolve' crates/marathon-core/src`
  finds nothing for the removed items.
- `scripts/check.sh` passes (export `MARATHON_KT` to the Kotlin checkout first; see CLAUDE.md).
- Report: commits, the handle types, what was deleted (with line counts), the ownership guarantee and
  its test, `Deferred`'s outcome, every test changed.
