## Deliverables and boundary

In `crates/marathon-android`, the five artifact listeners plus their factory wiring into 6.6a's slots:

1. **File sync** (`L/filesync/FileSyncTestRunListener.kt`): per-`InstrumentationInfo` remote-dir reset, push-before/pull-after over 6.5's `pushFile`/`pushFolder`/`safePullFolder`, aggregation into `device-files/` via core `OutputFiles::create_folder`.
2. **Video** (`L/video/ScreenRecorder.kt`, `L/video/ScreenRecorderTestBatchListener.kt`): the `screenrecord` supervisor loop with API-34 chunking, the ps/`kill -2` stop dance, policy-gated pull, batch-video salvage on run failure.
3. **Screenshot GIF** (`L/screenshot/ScreenCapturerTestRunListener.kt`): owns one merged 3.9c `ScreenCapturer` per batch; launch on test start, cancel-and-join on end/failure, `ON_FAILURE` deletion, batch rename. The capturer, `GifSequenceWriter` and `Rotation` are 3.9c's — do not re-port them.
4. **Adam screen capture** (`L/screenshot/AdamScreenCaptureTestRunListener.kt`): pulls on-device captures named by the instrumentation metrics map. The on-device `AdamScreenCaptureProcessor` is test-side adam code; only its metrics key is consumed here.
5. **Profiling** (`L/profiling/ProfilingRunListener.kt`): perfetto via a substituted pbtxt, `pidof`, trace pull into `profiling/`, `AttachmentType::Profiling`.
6. **Factory wiring**: fill 6.6a's injected slots in Kotlin composite order — recorder → log adapter → results → debug → adam capture → file sync → profiling (`M/BaseAndroidDevice.kt:290-300`, whole file owned by 6.5; the `:236-335` construction moved to 6.6a/6.6b by 6.5 decision 2) — and register the attachment providers in source order (recorder, profiling, log, adam capture; `:253-288`) so attachment visibility at results completion matches Kotlin. Recorder selection itself is 6.5's `RecorderTypeSelector` (`M/RecorderTypeSelector.kt:8-26`): preferred type if supported+enabled, else VIDEO, else SCREENSHOT, else none.

All five implement 6.6a's Android listener trait (the 12-callback `AndroidTestRunListener`, `L/AndroidTestRunListener.kt:6-30` — not core's 4-callback `TestRunListener`); the four attachment producers also implement core `AttachmentProvider`. Callbacks run off core on the vendor runtime; per-test recorder/capturer/perfetto jobs are owned, cancelled and **joined** by their listener — no detached work, no cleanup in `Drop`, no `Thread::sleep`, no `unwrap()`/`expect()` on I/O, process or network results. Delays and deadlines go through `VendorClock`; a dropped execute future must not strand a recording (lifecycle: explicit cleanup ownership survives dropped futures).

**Not 6.6b:** the device API, shell wrappers, `safePull/safePush` timeout policy, `RemoteFileManager` remote names, `toScreenRecorderCommand`, serial/feature detection (6.5); the runner, composite, results/log/debug listeners, remote parser, exception wrapper (6.6a); GIF encoding, rotation, resize (3.9c); attachment collection/emptiness, `FileManager` materialisation, reporters and their media links (3.9a/3.9c); config schema/defaults (2.3a — note video *and* screenshot default `enabled: true`, so the recorder path is on by default); Apple media listeners (5.3); whole-run manifest comparison (7.1).

## Behaviours to reproduce (with sources)

**Factory and gating** (`M/BaseAndroidDevice.kt:236-300,303-335`, construction owned per 6.5 decision 2): profiling listener exists only when `profilingConfiguration.enabled && pbtxt != null`, else a no-op in its slot (`:258-273`); file-sync and adam-capture listeners are **always** constructed (`:284-288`); the recorder slot is a no-op when the selector returns null (`:253-255`). Composite callbacks are sequential in registration order and stop at the first throw (6.6a); a listener exception therefore aborts later listeners for that callback — preserve which of the calls below can throw (critical shell, `createFile`, pbtxt read) versus swallow (safe shell/pull).

**File sync** (`L/filesync/FileSyncTestRunListener.kt`):

## Proposed simplifications (pragmatic parity — for orchestrator approval, **not decided**)

Until approved, the behaviours above are binding.

- **P1, recorder stop sleep:** `Thread.sleep(300)` (`ScreenRecorder.kt:80-87`) becomes a `VendorClock` delay; its `InterruptedException` warn-and-continue maps to typed cancellation. Likewise the listeners' `catch (InterruptedException)` arms (`ScreenRecorderTestBatchListener.kt:113-115,153-155`) are unreachable from coroutine code — do not invent an interruption source for them. Timing-only; command sequence unchanged.
- **P2, profiling setup failures:** an unreadable `pbtxt`, an empty batch, or an unregistered first test currently throws out of `beforeTestRun`/`testRunStarted` and kills the batch. Propose: log the same error and disable profiling for that batch (no perfetto, no attachment). Success-path commands unchanged; only already-broken profiling configs diverge.
- **P3, screenshot `ON_FAILURE` delete:** delete the GIF directly after the join instead of reproducing register-`invokeOnCompletion`-on-a-completed-job. Observable difference only if the probe shows the handler does *not* fire (then Kotlin keeps the file and this proposal is void — keep Kotlin's result either way, by the direct route).
- **P4, profiling run-failure cleanup:** on `testRunFailed`, `killall perfetto` and join the job without pulling (mirrors 6.6a's approved P2 cleanup). Diverges only in device state after a failed run; requires the JVM leak witness (N34).
- **P5, recorder state ownership:** Kotlin mutates a plain `HashMap`/`MutableList`/`@Volatile` flag from the recorder coroutine and the callback thread unsynchronised (`ScreenRecorderTestBatchListener.kt:51-55`). Propose single-owner state behind the listener with the loop reporting chunk starts through a channel; no emulation of the data race. Sequential-callback behaviour identical.
