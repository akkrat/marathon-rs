## Deliverables and boundary

In `crates/marathon-apple` (`logparser/`, `listener/`, `test/`):

1. **`TestEvent`** (`B/test/TestEvent.kt`): the seven variants, with a Kotlin data-class rendering (`TestStarted(id=Test(pkg=…, clazz=…, method=…, metaProperties=[]))`, `trace=null`) because the parser fixtures compare `toString()` output. Reuse a core Kotlin `Test.toString` rendering if one exists; otherwise add it next to `Test`.
2. **Parsers:** `DeviceFailureParser`, `TestRunProgressParser`, `XctestEventProducer` (one `process(line) -> Result<Option<Vec<TestEvent>>, _>` entry point; `TestEventProducer` stays a trait only if open question 4 says so). Synchronous and allocation-light: they run on the line-reading task 4.8 owns, never block, never panic.
3. **`AppleTestRunListener`**: a vendor-local, object-safe async trait with the nine no-op defaults (`B/listener/AppleTestRunListener.kt:6–16`). Callbacks return `VendorResult<()>`, since Kotlin exceptions propagate through the composite. **`CompositeTestRunListener`** over `Vec<Arc<dyn AppleTestRunListener>>`.
4. **Result listeners:** `AccumulatingTestResultListener` as a reusable component that owns a `TestRunResultsAccumulator` behind a short non-async lock (Rust has no abstract class; composition, same calls), and **`TestResultsListener`** on top of it: the xcresult enrichment, the `TestBatchResults` built in `afterTestRun` and completed through the core `Deferred`, and `impl AttachmentListener` delegating to core `AttachmentCollector`. Accumulator `take_logs()` are forwarded after every callback, failures included (lifecycle.md:562–568).
5. **Adapters and diagnostics:** `TestRunListenerAdapter` (wraps a core `TestRunListener`, in practice 3.9a's `LogListener`), `DebugTestRunListener` (needs only core `Device`), `ArtifactFinderListener` with `DiagnosticLogsPathFinder`/`SessionResultsPathFinder` (each is both an `AppleTestRunListener` and a core `LineListener`, hence `Arc`-shared), `DebugLogPrinter` (`LineListener`).

**Not 4.7:**
- Turning events into listener calls, `TestRunFailed` → `DeviceFailureException`, the "got stuck" `testRunFailed` on cancellation, `afterTestRun` in `finally`, `XcodebuildSession`, `consumeOutput` and the stderr logger: **4.8**.
- `ResultBundleRunListener` and its 13 rows: **4.9**.
- The per-device composite (order, the retire-on-failure listener, recorder, device log, data-container listeners) and the line-listener set: **5.2/5.3/5.6**. The ordering issue A20 (events sent before line listeners see the line) lives in the device code; 4.7 only supplies the parts.
- `DeviceFailureException`/`DeviceFailureReason` (4.3), `TestRequest` (4.4), xcresult models (4.6), `xcresulttool get` (4.4), `RemoteFileManager` (4.10a), the accumulator itself (core, merged).

## Behaviours to reproduce

**`TestRunProgressParser`** (`B/logparser/parser/TestRunProgressParser.kt`; logger `TestRunProgressParser`):
- **Dispatch** (:48–61): started, then finished, then timeout, then failing line (stored, no event), else `null`. Each test is a whole-line Java `matches`; the groups then come from a separate `find`. Use the jcompat fixed patterns (Java `.`, `\s` and `\d` already spelled out); do not write new Rust-dialect regexes.
- **Package and class** (:81–89, repeated at :131–139 and :166–174): if the name has a dot, `pkg` is everything before the **last** dot and `clazz` everything after the **first** dot. So `a.b.C` gives `a.b` / `b.C` (**A5**, keep). Without a dot, `pkg = targetName`, which `XctestEventProducer` gets as `request.testTargetName ?: ""` (`ios/AppleSimulatorDevice.kt:688`; **A7** with 4.8).
- **Started** (:160–184) clears the stored failing line, then emits `TestStarted` (trace log `Test p.c.m started`).
- **Finished** (:76–124):
  - The duration is parsed with `toFloat()` (`[\d.]+` admits `1.2.3`, whose `NumberFormatException` escapes `process`).
  - `endTime = timer.currentTimeMillis()`; `startTime = endTime - roundToInt(duration * 1000f)` in `f32` (`kotlin_round_to_int`).
  - `passed` gives `TestPassed`; `skipped` gives `TestIgnored`.
  - `failed` gives `TestFailed`, whose trace is `"$file:$reason"` built from the **last** failing line stored since the last start (groups 1 and 4, Kotlin-trimmed, :63–74), otherwise `null`.
  - Debug line :95 renders the `Float` the Java way (`5.315`, `10.0`).
- **Timeout** (:126–158): emits `TestFailed` with `startTime = end - duration.toMillis()` and the same trace rule.
  - `parseAppleDuration` (:187–194) builds `"PT" +` the **untrimmed** string, with ` seconds`→`S`, ` minutes`→`M` and ` hours`→`H`, then calls `Duration.parse`.
  - So `1 minute`, `1 hour`, `1 minute, 30 seconds` and ` 3 minutes` all throw `DateTimeParseException` out of `process`. This is candidate **K1**: confirm it with the JVM probe and real Xcode wording.
  - The fixtures `timeout_0` (`3 minutes`) and `timeout_1` (`20 seconds`) pin the working forms.

**`DeviceFailureParser`** (:8–31): checks the 17 literals in list order, and the first one that is a **substring** of the line wins. The event is `TestRunFailed(message = the literal, not the line, reason)`. The catch-all `Test runner exited` comes last; the test at `T/…/DeviceFailureParserTest.kt:42–45` pins that `SystemAppUnavailable` beats it.

**`XctestEventProducer`** (:18–20): the failure parser runs first, and a hit short-circuits the progress parser. It only ever sees stdout. Any stdout line that contains a literal, including an app's or an assertion's own text, aborts the batch through 4.8 (candidate **K2**, keep under D5).

**`TestEvent`**: `TestRunStartedEvent` and `TestRunEnded` are produced **nowhere** in production; only the Kotlin tests send them. As a result, `AccumulatingTestResultListener.testRunStarted`/`testRunEnded` never run in a real batch, `fillEndTime` never runs, and a started-but-unfinished test is reported `INCOMPLETE` with `endTime = 0` (candidate **K3**). Pin the production call sequence with the oracle, not only the tests' sequence.

**`AccumulatingTestResultListener`** (:9–48):
- `testRunStarted` passes `("apple", expectedTestCount)`.
- `testFailed` calls `testFailed(trace ?: "", start, end)` and then `testEnded(test, emptyMap())` with no times. Core's `testEnded` defaults `endTime` to the timer, so failed tests keep the parsed `startTime` but end at "now", and passed and ignored tests keep the `testStarted` time as start.
- `testRunFailed` drops the reason; `testRunEnded` passes `(0, emptyMap())`.

**`TestResultsListener`** (:43–171; logger `com.malinskiy.marathon.apple.listener.TestResultsListener`):
- **Enrichment** (:86–153) always runs; `enhanceUsingXcresult` is constant `true`.
  - Root `ActionsInvocationRecord` (JSON, worker's `xcodeVersion`). If it is null, stop.
  - If `issues.testFailureSummaries` is null or empty, stop **before** any `--id` query (`cleanInvocationRecordSkipsTargetSummaryLookups`).
  - For each action with a `testsRef.id`, in order, query `ActionTestPlanRunSummaries --id`, then collect the non-null `targetName`s and `distinct()` them. With exactly 1, that is the pkg. With 0, warn `No testable targets found in xcresult`; with more, warn `Multiple testing targets found in xcresult`.
  - For each failure summary, in order:
    - Strip `()` from the `testCaseName`.
    - Match among `completedTests` (status ≠ `INCOMPLETE`) on `clazz.method`, and on `pkg` when one is known.
    - With 1 match, append `message` (a null message appends `"null"`, candidate **K4**) and then the `documentLocationInCreatingWorkspace.url` line if it is not blank.
    - With 0 matches, warn `No matching test cases found in xcresult`; with more, warn `Multiple matching test cases found in xcresult. Impossible to possible to add stacktrace to report` (verbatim).
  - Then `testFailed(test, trace = sb.trim())` with no times. This turns stdout passes into `FAILURE` and replaces stdout traces.
  - Debug line: `Enhancing report using xcresult took N ms`.
  - An unreadable root or summaries query must never fail the listener: the next composite member still runs (`keepsLogResultsOnTruncatedXcresult`).
- **Result** (:43–84):
  - Results are taken in the accumulator's insertion order. `toTestResult` looks the test up in the batch with `it.clazz == key.pkg` (**A6**, keep), so the batch `Test` with its metadata almost never replaces the key. Attachments come from the collector by test.
  - `finished` holds the successful results. `failed` holds the reported, non-`INCOMPLETE`, non-successful ones. `uncompleted` is the reported `INCOMPLETE` results followed by `createUncompletedTestResults(batch tests absent from results, batch, deviceInfo)`.
  - One warn per uncompleted test: `uncompleted = <toTestName()>, <serial>`.
  - Then `deferred.complete(TestBatchResults(device, …))`.

**`CompositeTestRunListener`** (:6–46): calls the listeners sequentially in list order with no isolation, so the first error stops the rest and propagates. It forwards the reason (`CompositeTestRunListenerTest`).

**`TestRunListenerAdapter`** (:10–34): maps before→before, started→started, failed/passed/ignored→`testEnded`, after→after. It forwards nothing for run started, ended or failed.

**`DebugTestRunListener`** (:9–45): logger `DebugTestRunListener`, INFO, the exact strings:
- `beforeTestRun` is silent.
- `testRunEnded` and `afterTestRun` print no serial.
- The trace follows `System.lineSeparator()`, and a null trace prints `null`.

**`ArtifactFinderListener`** (:6–28; logger `com.malinskiy.marathon.apple.listener.ArtifactFinderListener`):
- `onLine` takes group 0, which includes the leading whitespace (`find_artifact`), Kotlin-trims it, and adds it to an insertion-ordered set.
- `afterTestRun`, if the set is not empty: with `unique = true` (the only value any caller uses), it copies the set into a Java `HashSet` and logs INFO `"$message " + joinToString(", ")` in **HashSet iteration order** (see proposal S1).

**`DebugLogPrinter`** (:6–18): logger name = prefix, default `DebugLogPrinter`. Each line is logged at DEBUG unless `hideRunnerOutput`. The lazy logger logs the trace `Mirroring remote logs with name 'DebugLogPrinter'` once, on the first line that is not hidden.

**Known bugs that apply:** A5, A6 and A7 (4.7's half: pkg from the log), plus A20's evidence for 5.2/5.6. New candidates K1–K4 above. Rows start at the next free A id when the work is done (4.10a takes A43 onwards).

## Proposed simplifications (pragmatic parity; for orchestrator approval, **not decided**)

- **S1, artifact path order:** log the paths in first-seen order instead of Java `HashSet` order. This only differs when one batch prints two or more distinct paths, and only in an INFO line. The alternative is about 30 lines of `String.hashCode` bucket order, pinned by oracle (c).
- **S2, one anchored match:** run each fixed pattern once, anchored at both ends, instead of `matches` followed by `find`. Leftmost-greedy capture equals the full match for every realistic line; this diverges only on lines that repeat the `Test Case '-[` marker. Oracle (a) shows whether any probed line differs.
- **S3, Float rendering in the debug line:** Rust shortest form plus `.0` for integral values, instead of a full Java `Float.toString`. This differs only at 10⁷ s and above, or below 10⁻³ s, which xcodebuild's `%.3f` never prints.
- **S4, dead switches:** drop `enhanceUsingXcresult` (constant `true`) and `ArtifactFinderListener.unique` (never `false`), and have no `TestEventProducer` trait (one implementation), unless 4.8's tests need a seam.
- **Not proposed:** fixing K1–K4 or A5–A7. They are reachable with ordinary input and stay under D5. K1 and the `1.2.3` case become typed errors out of `process`, never panics.

## Open questions for the orchestrator

1. **The 4.10a dependency.** 4.7 needs only `remote_xcresult_file(batch)` from it, and only to pass a path. Recommendation: `TestResultsListener::new` takes the remote xcresult path, computed by the device (5.2/5.6) through `RemoteFileManager`. This lets 4.7 start before 4.10a merges, ports the Kotlin tests' mocked `/tmp/result.xcresult` argv literally, and removes 4.10a from 4.7's PLAN dependencies. `DebugTestRunListener` needs only core `Device`, and nothing here needs the registry.
2. **`TestRunProgressParserTest` row.** `scripts/parity_matrix.py` cannot enumerate `@ArgumentsSource(TestDataProvider)`, so 9 invocations share one `unknown` row (`success_multiple_0` runs twice, with and without a target). Recommendation: one Rust test that runs all 9 cases and reports each failing case by name, with the single row set to `ported`, instead of teaching the generator about argument providers. Otherwise, extend the generator and regenerate to get 9 rows.
3. **Inventory and matrix check.** The 15 sources and 20 rows are assigned correctly. None belongs elsewhere: `ResultBundleRunListener` with its 13 rows is already 4.9's, `DeviceFailureException` 4.3's and `TestRequest` 4.4's. The `TestResultsListenerTest` rows depend only on merged 4.4/4.6 pieces. No move is needed.
4. **Trait shape.** Confirm:
   - `AppleTestRunListener` as an object-safe trait returning `VendorFuture<'_, ()>`, with `&self` and interior mutability (no lock held across an await);
   - the composite holding `Arc<dyn AppleTestRunListener>`;
   - `process` returning `Result<Option<Vec<TestEvent>>, ParseError>` so that K1 and `1.2.3` are typed errors that 4.8 maps to the batch failure Kotlin gets from the escaping exception.
5. **Where accumulator logs go.** Lifecycle.md requires forwarding `take_logs()` after each callback, but there is no Apple precedent yet. Should they go to the device's `Logger` or through the `VendorContext` the listener is built with? This needs one answer shared with 6.6a.
6. **K1–K4.** Confirm that each is kept under D5 once its probe or source evidence exists, and recorded in `known-kotlin-bugs.md`. For K1, should someone run the real-Xcode capture first? If Xcode never prints singular or compound allowances, K1 is source-only.
