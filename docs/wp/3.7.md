## Deliverables and boundary

In `crates/marathon-core`, new module `execution::queue` (`//! Port of core/src/main/kotlin/com/malinskiy/marathon/execution/queue/QueueActor.kt`):

1. **`QueueMessage`.** It has the eight variants of Q:352–373:
   - `RequestBatch { device, worker_id: Option<JavaString> }`
   - `RequestBatches(Vec<RequestBatch>)`
   - `IsEmpty(oneshot)`
   - `Completed`
   - `ReturnBatch(device, BatchRef, reason)`
   - `RejectBatch(device, BatchRef)`
   - `ConfirmOutcome`
   - `Terminate`

   Devices are `DeviceInfo` snapshots, as in Kotlin (`device.toDeviceInfo()`). Bookkeeping is keyed by `serialNumber`, not identity.
2. **`QueueActor`.** It runs on 3.1's `RuntimeActor` with an unbounded FIFO mailbox and is a child job of the pool supervisor (lifecycle.md:77). Its logger is `QueueActor[<DevicePoolId.toString()>]` (Q:42).
   - It replies on the pool's `FromQueue` handle.
   - It exposes a handle with the operations 3.8 needs: a non-throwing `try_send -> bool` (`DevicePoolActor.kt:236–243`) and the queue job, so that `awaitQueue`'s select over IsEmpty-or-join can be written (`DevicePoolActor.kt:274–280`).
   - `close()` cancels the job and discards the mailbox (0.6 decision 5; Q:250–253).
3. **Queue construction with D13 prefetch.** The steps:
   1. Off core, await `Analytics::prefetch` of `sorting.metrics_keys() ∪ batching.metrics_keys()`.
   2. Then, on core, build `JavaPriorityQueue::new(sorting.process(analytics.lookup(), hooks))`.
   3. Call `add_all(shard.tests ++ shard.flaky_tests)` (Q:44–48, 66–68).

   Kotlin constructs the queue synchronously inside `DevicePoolActor`'s constructor, so the API is split: an async *prepare* step that 3.8 awaits before it spawns, and a synchronous on-core *spawn*. See open question 2.
4. **The message handlers, ported line by line** (next section). They include the fork's retry placement (`workers`, `retryWorkers`, `activeRetries`, `nextBatch`/`ownRetries`/`dispatched`/`onlyOwnRetries`) and the `observe_execution_times` call.

## Behaviours to reproduce

**Message dispatch and ordering (lifecycle.md:206–209):**
- `ConfirmOutcome` replies `OutcomeProcessed(device)` after every earlier message (Q:100–102).
- `IsEmpty` is `queue.isEmpty() && activeBatches.isEmpty()` (Q:81).
- `Terminate` closes without sending `Terminated` (Q:84–86).

**`onRequestBatch` (Q:324–348):**
- It records `workers[serial] = workerId` only when the id is non-null, and never clears it.
- It samples `queueIsEmpty` before acting.
- With a non-empty queue and no active batch for that serial, it builds the batch and stores it in `activeBatches` without any await in between (Q:329). It then sends `ExecuteBatch`.
- Otherwise:
  - If the queue is empty and nothing is active, it sends `Terminated` and closes.
  - If not, it logs the debug line Q:342–344 (keys joined with `", "`) when the queue is empty, then sends `NoBatch`.
- The debug lines Q:325 and Q:331 are output.

**`onRequestBatches` (Q:261–274):**
- Each round serves the first pending request whose worker is not `onlyOwnRetries`, or the first one if all of them are.
- It stops once `terminated` is set.
- `onlyOwnRetries`: false for a null worker or an empty queue; otherwise `ownRetries(worker)` is non-empty and covers every queued element.

**Retry placement:**
- `ownRetries(worker)` (Q:225–228) returns the tests in `retryWorkers` where the count of `worker` in the list equals that test's count in the queue (`groupingBy.eachCount`). These are the tests all of whose queued copies are retries of attempts on that worker.
- `nextBatch` (Q:205–220):
  - If none of those tests are queued, or every queued element is one of them, it batches the whole queue.
  - Otherwise it takes `copies = queue.filter { it in avoided }` in **backing-array order**, then `queue.removeAll(avoided)`, then batches, and **in a `finally`** runs `queue.addAll(copies)`. The re-insertion changes heap order and comparator calls. Both are observable, and they happen even when batching fails.
  - It then sets `activeRetries[serial]` to the `(test, worker)` pairs that `dispatched` returns for the batch's tests in batch order.
- `dispatched` (Q:236–243):
  - `copies = queue.count(test) + 1`, counted **after** the batch has removed its copy. If `copies > workers.size`, the taken copy was not a retry.
  - Otherwise it removes the first worker ≠ the device's worker, or index 0 if there is none, and removes the map entry once the list is empty.
  - A batch that holds two copies of one test (ClassName batching keeps duplicates, `batching.rs` ClassName) sees the same count twice. Port this literally.
- `rerunTest` (Q:245–248) runs `queue.add`, then appends `workers[serial]` to `retryWorkers[test]` only if that serial ever reported a worker.
- `retryWorkers` is a **LinkedHashMap**. `getOrPut` keeps the first position, and removal followed by re-insertion moves the entry to the end. `Notify` sends `retryWorkers.values.flatten().toSet()` in that order (Q:195). Use an insertion-ordered map with order-preserving removal, never a `HashMap`.

**Batch outcomes:**
- `onBatchCompleted` (Q:106–124):
  1. **First** `analytics.observeExecutionTimes(finished + failed)`. Concatenation order; uncompleted results excluded.
  2. Then finished → uncompleted → failed, each only if non-empty.
  3. Then remove `activeBatches[serial]` and `activeRetries[serial]`.
  4. Then `onBatchReleased`.
- `handleUncompletedTests` (Q:126–150):
  - It partitions on the retry count *before* incrementing: `count >= uncompletedTestRetryQuota`, with an `i32` comparison.
  - It then increments every result, including duplicates of the same test, so two incomplete copies in one batch both see the old count.
  - Quota exceeded → `testEnded(final = true)` + `processTestAction`.
  - Otherwise `testEnded(final = false)`: on `Complete` → `processTestAction`; on `null` → `rerunTest`.
- `handleFailedTests` (Q:301–322):
  - `retryStrategy.process(poolId, failed, shard, accumulator)`. FixedQuota runs `retryTest` (AddRetry) before its quota decrement: this is **C5**, the phantom total.
  - For each retried result: `testEnded`, then `processTestAction`, then `rerunTest`. **The test is re-queued even when `testEnded` returned `Complete` and the copies were just removed** (candidate bug K1 below).
  - The non-retried results are those whose *Test* is not equal to any retried Test (Q:314–316). A second failed copy of a retried test therefore gets **no `testEnded` at all** (candidate K2).
- `processTestAction(Complete)` (Q:276–292):
  - It runs `removeAll(setOf(test))`, removing every copy, then `retryWorkers.remove(test)`, then `removeTest(test, diff)`.
  - `diff >= 0` is always true, so `removeTest` runs even with `diff = 0`.
  - `activeRetries` entries for that test are left in place.
- `onReturnBatch` (Q:152–172):
  - One `timer.currentTimeMillis()` read **per test**. Each test gets an `INCOMPLETE` result with `start = t`, `end = t + 1` (Java `Long` wrapping) and the batch id.
  - Then `handleUncompletedTests`, removal of the active entries, and `onBatchReleased`.
  - No observe call. The debug line includes `reason=`.
- `onRejectBatch` (Q:177–187):
  - It checks reference identity, `Arc::ptr_eq` against `activeBatches[serial]`. On a mismatch it logs WARN `Batch <id> is not active on <serial>, not queueing it again` and returns.
  - Otherwise it removes the active batch and runs `queue.addAll(batch.tests)`, with no attempt counted and no completion check.
  - It then restores the `activeRetries[serial]` pairs into `retryWorkers` (appending) and calls `onBatchReleased`.
- `onBatchReleased` (Q:193–200):
  - Non-empty queue → `Notify`.
  - Otherwise, no active batches → `Terminated`, then close.
  - Otherwise nothing.

**Failure and termination:**
- `close()` cancels the actor job. Messages already queued are dropped, and so are later sends: `try_send` → false, logged by 3.8.
- An error escaping a handler ends the actor through the actor's exception handler (`Actor.kt:22–23`; 3.6's completion logging). It leaves the partially applied state as the `?` early return leaves it. The errors that can escape:
  - a `BatchingError` (bundle identifier or replay);
  - a tracker failure surfaced by `test_ended`;
  - a timer error.

  Do not convert these into replies.
- Pass the queue job's cancellation signal to `test_ended` (3.5 handoff).

**Kotlin bugs that apply:**
- **C5** (phantom AddRetry). Replay `tools/oracle/strategy-probes`' retry corpus through the *real* accumulator and queue; the 3.5 brief leaves this integration row to 3.7.
- **C30**: one retry strategy per queue (Q:48), so the quota applies per pool.
- **C4**: no `testStarted`. Do not add one.
- **C33**: through FixedSize batching.

## Proposed simplifications (pragmatic parity; for the orchestrator, **not decided**)

QueueActor is small and literal: a line-by-line port is also the simplest code. Accordingly, none of these change ordinary scheduling.
- **P1, prefetch failure.** `Analytics::prefetch` returns `OperationResult`. Fetch errors are already absorbed into defaults, so an `Err` is cancellation. Propose: fail queue preparation as Cancelled, and do not build a queue that uses fallbacks. Kotlin has no counterpart.
- **P2, observe failure.** Kotlin's `observeExecutionTimes` cannot throw: it is `@Synchronized` and in-memory. Propose: treat an `Err` from `observe_execution_times` as a handler failure (the actor ends, as described above), with no special recovery path.
- **P3, partial state after handler errors.** Port the natural `?` early return. Do not build oracle evidence for every intermediate state after a tracker or timer failure mid-batch: in Kotlin, the queue is dead either way. Pin only that the actor ends, the error is logged, and later sends fail.
- **P4, exotic duplicate shapes.** K2, K3 and the duplicate-incomplete quota partition are ported literally because they cost nothing. Oracle rows are required only for shapes the run can produce (ClassName + flaky copies, flaky + sharding copies), not for hand-built result lists that repeat a test no vendor reports twice.

## Orchestrator decisions (2026-10-25)

1. **Matrix assignment: option (b).** 3.5 is already merged, so the 4 `TestResultReporterAllSuccessTest` rows stay in 3.7 and are ported against the merged 3.5 API. 3.7 owns 20 rows.
2. **Construction split: confirmed.**
   - 3.7 exposes an async `QueueActor::prepare`, which only runs the D13 prefetch, and a synchronous on-core `spawn`. 3.8 awaits `prepare` before it builds the pool.
   - The single `ReplayHooks` instance is the run's. 3.8 passes it through, as 3.6 does for `DeviceActor`. 3.7 never constructs one.
3. **Accumulator ownership.**
   - `PoolProgressAccumulator::test_started`/`test_ended` take `&mut self` and await output flushes and tracker delivery. A `RefCell` borrow would therefore be held across an await, which is forbidden; clippy's `await_holding_refcell_ref` must stay clean.
   - Find the Kotlin suspension points inside `testStarted`/`testEnded`, and whether the pool and the queue can interleave there on the single core thread. Then choose one of two designs:
     - **(a)** Split the accumulator into a synchronous state transition taken under a short borrow, followed by async delivery after the borrow is released. Use this if Kotlin can interleave.
     - **(b)** An async lock on the core (a `!Send`-capable mutex). Use this only if the interleaving is unobservable.
   - Changes to the merged 3.5 module are allowed for (a), as long as they stay minimal. Record the reasoning, with Kotlin line references, in the findings.
4. **Ordered map:** `indexmap` is approved. It is already in `Cargo.lock` transitively, so make it a direct dependency of `marathon-core` and use `shift_remove` to keep insertion order.
5. **Queue start:** follow the start semantics of 3.6's `DeviceActor` and the RuntimeActor contract in `docs/design/lifecycle.md`. Spawn in `spawn`, before 3.8's first message.
6. **P1–P4 approved.** Record each one in the findings.
7. **K1–K4:** confirm each with oracle evidence before adding it to `docs/known-kotlin-bugs.md`. Take the next free C id from current main; main ends at C44.
