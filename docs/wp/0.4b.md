Critical path; Phase 0 cannot close until the world has been validated by running the real Kotlin marathon against it.


> **Scope (orchestrator, following the user's 2026-10-23 direction: few users, prefer the simplest thing that works).** Build the smallest world that lets the real Kotlin marathon complete `ios-smoke`, `macos-smoke` and one iOS media scenario (video + screenshot). Media files must be valid and pullable; compare them by hash and metadata, not decoded frames. Everything beyond that goes in the scenario backlog for its owning WP. When a requirement below would take disproportionate effort for that baseline, record why in the findings and defer it, rather than over-building.

Extend its provisioning-only world; its constant `Shutdown` inventory is not a complete lifecycle model.
Represent worker identity/HOME/USER/architecture, Xcode/SDK/runtime/device-type inventories, macOS version/SIP/TCC, simulator UDIDs, availability and Shutdown/Booting/Booted/Shutting Down states with delayed/failing transitions.
Track installed/running applications, bundle IDs and container contents, privacy/media/keyboard settings; list/getenv/readiness probes must reflect mutations. Keep worker state shared across connections and device state isolated by UDID.
Track xcodebuild discovery/batch sessions, destination, selected tests, active/finished/cancelled state and result bundle path; enforce uploaded xctestrun/bundle prerequisites and script process termination. Recording/logging lifetimes and ps/pkill/kill/lsof results must agree with the same virtual jobs.
Use only 0.4a's `/tmp/marathon` filesystem for transferred/generated bytes, shared bundles, pidfiles and artifacts. Model external SDK/XCTRunner sources, preferences and TCC paths as explicit world resources/handlers; never touch the host's corresponding paths or broaden containment.
Parse xctestrun plist path fields and resolve transferred paths via `resolve_xctestrun_path` (`__TESTROOT__`, `__TESTHOST__`); keep SDK references explicit. Preserve original plist/env bytes and virtual paths; no blanket payload substitution. Account for 0.4a's symlink-write restrictions.
Produce actual nonempty `.xcresult` directory trees at requested paths, plus root/id JSON objects coherent with emitted tests, failure summaries and testsRef targets; implement merge and pull/remote-clean effects. Scripted bundles need not be readable by real xcresulttool; label them as such.
Screenshot/video/transcode/log commands must create pullable files in that filesystem, with valid image/video formats, codec/dimensions and deterministic decoded content; record source/generation recipes. Bind recording completion and file availability to the scripted lifecycle, not a fake success with no artifact.
Use versioned JSON/YAML scenarios: initial world/files, named expectations with raw exact/prefix/glob matchers from 0.4a, per-worker/device/invocation selectors, required counts, state guards/effects, fixture chunks on stdout/stderr, delays/status/hang/signal/fault policies, and expected final state.
Reserve finite expectations atomically across channels, handle cancellation without consuming an unfinished transition, and use command/event barriers for deterministic ordering. No dependence on global connection interleaving or arbitrary sleeps. Give complete runnable examples and diagnostics for mismatches.
Handlers must be cancellation-safe at every await, do no blocking I/O on the executor, and spawn no unowned work. Test concurrent clients, channel loss and run shutdown, including the separate device-log wrapper; keep all jobs bounded and joined before final transcript/state capture.
