## Deliverables and boundary

New module tree `crates/marathon-core/src/strategy/` (one Rust file per Kotlin family; each file's `//! Port of` lists its Kotlin files). Strategies are **enums built from the config enums**: the config sets are closed, so no trait objects are needed. The exception is the seams other WPs implement.

1. **Factories.** `from_config` for each family, porting the strategy half of `K/extension/ConfigurationExtensions.kt:48-60,78-111` (see open question 2). Every Kotlin test in this WP builds its strategy through these factories.
2. **Pooling.** `associate(&self, device: &dyn Device) -> DevicePoolId`. `abi` comes from `Device::abi()`; manufacturer, model and OS version come from `Device::info()`, which is snapshot-only and safe on core.
3. **Sharding.** `create_shard(tests) -> TestShard`.
4. **Sorting.** A per-instance strategy that yields a synchronous `FnMut(&Test, &Test) -> Ordering` for `JavaPriorityQueue<Test, _>`. `RandomOrder` keeps its key cache on the strategy instance, not in the comparator.
5. **Batching.** `process(queue, metrics, identifier, hooks) -> Result<TestBatch, _>` over the concrete `JavaPriorityQueue` (see open question 4). The batch id is allocated through `hooks.allocate_id("core.TestBatch.id")` exactly where Kotlin constructs `TestBatch` (`K/test/TestBatch.kt:5`, a UUID default parameter). That is after the strategy's last queue operation and never in `Clone`/`Default` (model-contract). Errors from `identify` or the hooks propagate; no `unwrap()`.
6. **Flakiness.** `process(shard, metrics) -> TestShard`.
7. **Retry.** `process(&mut self, pool, failed: &[TestResult], shard, progress) -> Vec<TestResult>`, with `RetryWatchdog` and `PoolTestFailureAccumulator` as their own types and tests.
8. **Seams this WP defines** (recommended shapes; open questions 2–3):
   - `MetricsLookup`: synchronous, infallible `success_rate(&Test, Instant) -> f64` and `execution_time(&Test, f64, Instant) -> f64`. Each strategy also declares the `(percentile, limit)` / `limit` keys it can touch. 3.2 ships only the port of the Kotlin test helper `MetricsProviderStub`.
   - `RetryProgress { fn retry_test(&mut self, test: &Test) -> Option<TestAction> }`, the single `PoolProgressAccumulator` call the retry strategy makes. It brings `TestAction` (`K/execution/queue/TestAction.kt`, the single `Complete` value) into core.
   - `Test::to_class_name` (`K/test/Test.kt:33-41`: `pkg.isNotBlank()` decides the `pkg.` prefix). Add `to_test_name`/`to_safe_test_name` (`:25-31,51`) alongside it: 3.4a and 3.5 need them.

## Behaviours to reproduce

**Pooling and sharding.**
- `Combo` (`…/ComboPoolingStrategy.kt:8-16`) joins the names with `_` only when the accumulator is non-empty, so leading empty names vanish: `["", "x"]` → `x` and `["a", "", "b"]` → `a__b`. An empty list gives `""`.
- `Count` (`CountShardingStrategy.kt:9-13`) repeats each test `count` times consecutively (`t0,t0,t1,t1`); `count ≤ 0` gives an empty shard. `Parallel` passes the tests through. `flakyTests` is empty in both.

**Sorting.** These comparators feed `JavaPriorityQueue` only. A Kotlin test that uses `sortedWith` is ported with `slice::sort_by`, inside that test only.
- `ExecutionTime` (`:14-21`, fork-specific) memoises each test's first observed key in a map that is fresh per `process` call and keyed by `Test` equality (metadata ignored). A queued or re-queued test keeps the duration it had at its **first comparison**, even after observed durations change it (test "queued tests keep their order…"). `.reversed()` makes the comparator `compare(b, a)`, so the key of the **second** argument is extracted first. That order decides memo fill, the first-touch fetch and 3.4a's per-test warn-once log order.
- `SuccessRate` (`:9-19`) is not memoised and is reversed unless `ascending`, with the same argument-order rule.
- `RandomOrder` (`:9-15`) takes `comparingInt`, so the first argument is drawn first. It draws `Random.nextInt()` once per distinct test into a cache that lives on the strategy and is never cleared, through `draw_int("core.RandomOrderSortingStrategy.key")`.
- `NoSorting` always returns 0. That is **not** FIFO in a Java heap; the heap order is the order.
- Keys compare with Java `Double.compare` / `Integer.compare`.

**Batching** (the queue is the pool's `JavaPriorityQueue`; every queue operation can call the comparator).
- `ClassName` (`:13-18`): the class of `peek()`, then `toList()` in **backing-array order** filtered by class (the batch keeps heap-array order), then `removeAll(set)` (JDK 21 bulk removal plus heapify). `remove_all(&[T])` is O(n·m); a HashSet-probe variant with identical semantics may go into jcompat if profiling asks for it.
- `Isolate`: one `poll`.
- `FixedSize` (`:14-57`):
  - If the **queue** holds fewer than `lastMileLength` tests (and is non-empty), it returns one polled test.
  - Otherwise it polls up to `size` times. `counter` counts **every** poll, including unbatchable ones.
  - A duplicate (a flaky copy already in the batch) is unbatchable. So is a test whose bundle differs from the locked one. The bundle locks only on a non-null bundle (`testBundle != null && …`), so null-bundle tests mix with whatever comes after them.
  - The duration check runs only when `durationMillis`, `percentile` and `timeLimit` are all non-null (F2 can null `timeLimit`). It adds the expected duration of **every** polled item, unbatchable ones included, and breaks on `sum >= durationMillis` (compared as a double).
  - At the end it re-adds the unbatchable tests with `addAll` (comparisons happen here). The batch is a `LinkedHashSet` in insertion order.
  - Empty-queue paths are unreachable: `QueueActor` checks emptiness first (lifecycle.md ordering table). Return an error or debug-assert; do not invent a null-test batch.

**Flakiness.**
- `ProbabilityBased` (`:20-41`) appends, in shard order, while `fail > maxFail && counter < maxCount`. `fail` starts at `1 − successRate` and `maxFail` is `1 − minSuccessRate` in double arithmetic (`1.0 − 0.8 = 0.19999999999999996`).
- The fail rate is **squared** each step (`currentFailRate *= currentFailRate`, `:35`) instead of being multiplied by the base rate the KDoc describes (`:9-15`). This is a new known-bug candidate (below).
- With 3.4a's `NoOp` the success rate is 0, so every test gets `maxCount` copies (C8). Confirm C8 here with a stub returning 0.0; 3.4a re-confirms it with the real NoOp provider.

**Retry** (`FixedQuotaRetryStrategy.kt:12-31`, `RetryWatchdog.kt:10-26`, `PoolTestFailureAccumulator.kt:27-44`).
- For each failed result in input order:
  1. `record(pool, test)`;
  2. `failures = count + (occurrences of test in shard.flakyTests)`;
  3. `retryPossible(failures)` (`left >= 0 && failures <= perTest`);
  4. `progress.retry_test(test) != Some(Complete)`; `None` counts as not complete;
  5. `requestRetry(failures)` (decrement **first**, then `>= 0 && failures <= perTest`).
- Steps 3–5 short-circuit as in Kotlin. **C5:** at `left == 0`, `AddRetry` runs and the decrement then refuses: a phantom total+1 with no retry. 3.2 confirms the call sequence; the total+1 itself is a 3.5/3.7 assertion.
- The quota lives on the strategy instance, and `QueueActor.kt:48` builds one per pool. `totalAllowedRetryQuota` is therefore **per pool**, although the fork's docs (`docs/runner/configuration/retries.md:53`) say "for all the tests in total". This is a new known-bug candidate.
- The counters are Java `Int`; use wrapping `i32` arithmetic (free).
- `NoRetry` returns empty.

**Known-bug rows.** Confirm C5 and C8. Add rows for the squared fail rate and the per-pool quota. Add the FixedSize behaviours that unbatchable polls consume `size` slots and duration, and that a null bundle does not lock the batch, if reviewers judge them bugs rather than design. Add the unreachable `CountShardingStrategy.equals` (`cnf.count != cnf.count`, `:21`) and the identity hash in `RetryWatchdog.hashCode` (`:40-44`) only if P1 is rejected.

**Metrics (0.6 D4, binding).** "Bulk fetch per (percentile, limit) off core at the first-touch point, absorbing fetch failures as MetricsProviderImpl runCatching/defaults do; synchronous memoising comparator over JavaPriorityQueue; warn-once/TimingLog emitted by the fetch shim. No async/fallible comparator and no eager prefetch."
- 3.2 owns the comparator side: memoisation, argument order, declared keys, and the guarantee that a strategy touches metrics only where Kotlin does.
- 3.4a owns the fetch, the cache and the logs.
- 3.7 owns making the first touch happen off core.
- In Kotlin, the first touch is the first comparison, or the first `FixedSize`/flakiness lookup, for that key. A queue holding one test never fetches.

## Proposed simplifications (pragmatic parity: for orchestrator approval, **not decided**)

Until a proposal is approved, the behaviour above stands. An approved one becomes a PLAN §3.11 entry (or a 0.6 decision amendment) and the rows it supersedes are marked.

- **P1, no strategy `equals`/`hashCode`/`toString`.** No production caller compares, hashes or prints a strategy instance at `e47352f2`: the strategies are built privately in `QueueActor`/`Scheduler`/`Marathon`, and grep finds no interpolation. The implementer re-verifies this. Not porting them also drops the unreachable `CountSharding.equals` self-compare, `RetryWatchdog`'s identity hash and `ExecutionTimeSortingStrategy.toString`'s `logger=` identity. Configuration equality (2.2, F7) is unaffected.
- **P2, eager history fetch at queue construction.** This would **reopen 0.6 D4's "no eager prefetch"**. 3.7 would fetch each declared key off core when it builds the pool queue, so every queue operation could stay on core with no off-core shipping. Kotlin differs in two places only: a pool whose queue never compares (a single test with `ExecutionTime`/`SuccessRate`, or `FixedSize` without duration fields) would issue a history query and a `TimingLog` line that Kotlin skips, and that line moves earlier in the log. Per-test warn-once logs stay lazy and in the same order. If P2 is rejected, see open question 3.
- **P3, no Java `Queue` abstraction.** Batching takes `JavaPriorityQueue` only. The six `LinkedList`-based Kotlin tests that stay in 3.2 (FixedSize ×3, ClassName ×2, Isolate ×1) are ported over a `JavaPriorityQueue` with the `NoSorting` comparator. That is equivalent for their size-only assertions: with all-equal keys, `add_all` keeps insertion order, and the bundle test's second poll still yields `tests[1]`. The alternative is open question 4.
