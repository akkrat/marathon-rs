# WP 7.3b findings: static musl release target

Branch `wp/7.3b-musl-release`, from main `74b22dd1`. The smoke build below ran from code commit
`5b96318a80114358d081c613fa2bd8fc3e96422f`; later commits on the branch change only these findings.

## Design

`release.py build --target x86_64-unknown-linux-musl` runs `cargo zigbuild --locked --release -p marathon-cli
--bin marathon --target x86_64-unknown-linux-musl`. cargo-zigbuild was preferred over hand-wiring
`CC`/`AR`/linker env vars for `zig cc`: it sets the C compiler, archiver and linker per target itself, and
three crates compile C (`ring`, `aws-lc-sys`, `lcms2`). The Rust target is native-arch (x86_64), so zig
is only the C toolchain; the host must be Linux x86_64 (gnu or musl), enforced in `release.py`. The
build ran first time with no source or dependency change.

`package` refuses the binary unless `file` says `statically linked` or `static-pie linked` with no
interpreter and `ldd` says `not a dynamic executable` (or `statically linked`). The check runs before any
output is written. `x86_64-unknown-linux-musl.json` records `toolchain` (zig and cargo-zigbuild versions)
and the `file` description (path stripped). `collect`/`publish` include the musl archive when present and
still require the two original targets; `ci.yml` is unchanged (see Limitations).

Tests: `python3 -I scripts/release/test_release.py`, 15 tests offline (7 new): static predicate accepts
static/static-pie and rejects dynamic, loader-requesting or ldd-dynamic cases; musl packaging records
the toolchain and leaves no output when the binary is dynamic; the build uses `cargo zigbuild` only on a
Linux x86_64 host and fails before building on other hosts or without zig; gnu still uses `cargo build`;
collection includes musl only when built and rejects a corrupted musl archive.

## Tools on the Linux build box

All under the private directory `~/mrs-musl-tools` (535 MB); nothing system-wide, no sudo, no apt.

| Tool | Version | Source / check |
|---|---|---|
| Zig | 0.17.0 (latest stable in the official index at `https://ziglang.org/download/index.json`) | `zig-x86_64-linux-0.17.0.tar.xz`, SHA-256 `1cbe9df9f27e6b78d14ccbca43b6703a404ef79ef1c463de901d7f088d4e2026`, checked with `sha256sum -c` against the index value |
| cargo-zigbuild | 0.24.0 | `cargo install --locked` from crates.io |
| Rust toolchain | 1.99.0 (existing; rustc `b940084d7` 2026-09-28, LLVM 23.1.1) | plus `rustup target add x86_64-unknown-linux-musl --toolchain 1.99.0` (adds `rust-std` inside the existing toolchain directory, the one change outside the private directory) |

Contents: `zig-x86_64-linux-0.17.0/`, `cargo-zigbuild/bin/cargo-zigbuild`, `cargo-home/` (registry used
for the install), `dl/` (the Zig tarball). Install commands:

```sh
T=$HOME/mrs-musl-tools; mkdir -p $T/dl; cd $T/dl
curl -fsSLO https://ziglang.org/download/0.17.0/zig-x86_64-linux-0.17.0.tar.xz

export PATH=$HOME/.cargo/bin:$PATH RUSTUP_TOOLCHAIN=1.99.0
rustup target add x86_64-unknown-linux-musl --toolchain 1.99.0
CARGO_HOME=$T/cargo-home cargo install --locked --root $T/cargo-zigbuild cargo-zigbuild@0.24.0
```

## Smoke build (observed)

Source tree: git bundle of the branch cloned into a private directory; the same commands, run from a
`marathon-rs` checkout, are the release recipe below. Run with `--version 0.0.0-musl-smoke`, no
`GIT_TAG_NAME`, in about 1m25s (cold, private `CARGO_HOME`/`CARGO_TARGET_DIR`/`ZIG_GLOBAL_CACHE_DIR`).
`release.py` ran its own extracted `version`/`--help` smoke against the CLI matrix during the build.

- Archive `marathon-0.0.0-musl-smoke-x86_64-unknown-linux-musl.zip` (9,357,991 bytes), SHA-256
  `2fb6d89ecea9192237f340c8944a2c37416defc5ae1dffc808084658bf4bb73c`. A second build from a different
  commit produced the same hash, so the archive is reproducible here (not claimed in general).
- Single entry `marathon-0.0.0-musl-smoke/bin/marathon`, Unix attributes `100755`; extracted binary
  23,548,528 bytes, SHA-256 `30afbc22b2cb646a2c6fc01a99bd4f064b8d5452556fd75fb597a606267c21f7`.
- `file`: `ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, stripped`.
- `ldd`: `not a dynamic executable` (exit 1). `readelf -lW | grep -ci interp`: `0`.
  `readelf -d`: `There is no dynamic section in this file.`
- Extracted, from `/` with `env -i`: `marathon version` printed `0.0.0-musl-smoke` (exit 0) and
  `marathon --help` printed the usage text.
- Older userland, without installs, using `bwrap` and the Ubuntu Core 24 snap rootfs already on the box
  (glibc 2.39, versus the host's 2.43): the binary bind-mounted over `/usr/bin/true` of that rootfs printed
  `0.0.0-musl-smoke` for `version` (rc 0) and usage for `--help`. In a bwrap with an empty tmpfs root and
  only the binary, `version` also printed `0.0.0-musl-smoke` (rc 0). No glibc-less or pre-2.35 distro was
  available, and the static check is the real guarantee.
- Metadata `toolchain`: zig `0.17.0`, `cargo-zigbuild 0.24.0`; `source_sha` was the build commit.

The build tree and bundle were removed afterwards. `~/marathon-ci` was not touched.

## Release recipe for the orchestrator

```sh
export PATH=$HOME/mrs-musl-tools/zig-x86_64-linux-0.17.0:$HOME/mrs-musl-tools/cargo-zigbuild/bin:$HOME/.cargo/bin:$PATH
export RUSTUP_TOOLCHAIN=1.99.0 ZIG_GLOBAL_CACHE_DIR=$HOME/mrs-musl-tools/zig-cache
GIT_TAG_NAME=<version> python3 -I scripts/release/release.py build \
  --target x86_64-unknown-linux-musl --version <version> --output <fresh output dir>
```

Run from a clean checkout of the release commit (the repository's `rust-toolchain.toml` pins 1.99.0).

## Limitations

- Linux x86_64 hosts only; no aarch64 Linux musl.
- `ci.yml` still builds gnu on `ubuntu-22.04`; it does not install zig or build musl. Replacing or adding
  the Linux job (a runner would need `zig` and `cargo-zigbuild`, e.g. `pip install ziglang` or a pinned
  tarball) is left to the orchestrator. `publish` accepts the musl archive if its artifact is downloaded.
- musl's allocator and DNS resolver differ from glibc's; the smoke exercised only `version`/`--help`, not
  real workers or network, so runtime behaviour on musl is not certified by this WP.
- Zig and cargo-zigbuild versions are pinned only by documentation; the build uses whatever is on `PATH` and
  records the versions in the metadata.

## Incidental bugs

- cargo-zigbuild 0.24.0: `cargo zigbuild --version` is forwarded to `cargo build` and exits 2; the version
  is read from the `cargo-zigbuild` binary instead. Handled in `release.py`; not reported upstream.
