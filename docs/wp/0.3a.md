# WP 0.3a: SSH spike, russh against sshj

**Owner:** Opus, medium effort. **Reviewers:** Sol and Muse. **Depends on:** 0.1.

Read first:
- `CLAUDE.md`;
- PLAN.md §3.6, §4.2 and §6.4;
- `docs/research/ssh.md` (the behaviour inventory and the T01–T20 matrix).

## Goal

Decide, with measurements, whether `russh` 0.64.x can reproduce every sshj behaviour marathon relies on, and which pieces need hand-built parity. This is a spike: the code is throwaway, and the result is a decision document plus a reusable contract-test suite.

## Deliverables

1. **`spikes/ssh-russh/`.** A standalone Cargo package, excluded from the main workspace (`[workspace] exclude`). It has a minimal executor on russh:
   - connect with retries using fresh clients;
   - password and public-key auth;
   - known_hosts verification and accept-any;
   - keep-alive interval and max count;
   - an exec channel per command, with marathon's `shellCommand` quoting;
   - stdout and stderr streaming with the shared idle clock;
   - an exit wait that maps a TERM exit signal to 143 and a timeout to `None`;
   - signal TERM, then close.
2. **`spikes/ssh-sshj/`.** A tiny JVM harness that drives sshj 0.39.0 (the same jar marathon uses, from the Gradle cache or the 0.2a clone) through the same matrix. Use marathon's own `SshjCommandExecutor` if that is practical, so its behaviour is measured rather than imitated.
3. **Test targets:**
   - the `remote-mac` Mac (`ssh remote-mac`: macOS sshd, user from `~/.ssh/config`);
   - an OpenSSH container: the image pinned by the Kotlin `SshdContainer` test helper, run with colima. Install colima and the docker CLI with Homebrew; this is approved.
   - Don't change any setting on the `remote-mac` Mac. Commands run there must be harmless (`echo`, `sleep`, `cat`, `kill` of the spike's own processes). Anything that needs sshd configuration changes, such as `MaxSessions` or forced disconnects, runs against the container only.
4. **The matrix (T01–T20 from the research note).** Run every row on both clients against both targets where it applies. Record a results table in `docs/research/ssh-spike-results.md`: each row gives the sshj result, the russh result, match or mismatch, and the fix if it's a mismatch. The rows must include:
   - keep-alive loss detection time and error shape;
   - whole-second interval truncation;
   - `MaxSessions` exhaustion;
   - output around EOF and close;
   - a TERM that the remote process ignores;
   - each key format: OpenSSH ed25519, RSA PEM, an encrypted key, PuTTY `.ppk` (expected to fail in russh);
   - host-key mismatch;
   - auth failures and their classification against `isTransientConnectionFailure`.
5. **Fake-worker feasibility (input for 0.4a).** With russh's server API, show three things:
   - a stock OpenSSH client (`/usr/bin/ssh`, which rsync's `--rsh` uses) can connect with key auth and with password auth through `sshpass`;
   - an exec request and a `signal` request reach the server handler;
   - `rsync -e ssh` to the fake server can run `rsync --server` both ways.

   Install `sshpass` from a tap only if it's needed. Note which rsync the server spawns: on macOS, `/usr/bin/rsync` is openrsync, and the real workers use the same.
6. **Decision.** Add a section at the top of `ssh-spike-results.md` covering:
   - russh go or no-go;
   - the exact crate versions to pin;
   - the parity items that need hand-built code (they go into WP 4.2's brief);
   - whether PuTTY keys need a deviation (D7 candidate; the orchestrator asks the user);
   - anything that changes PLAN.md.

## Acceptance

- Both harnesses run the full matrix, and the results table is complete. A row may be marked "not applicable here" only with a reason.
- The spike packages build. `scripts/check.sh` still passes: the spikes are outside the workspace.
- No secrets, host names, user names or IPs are committed. Reference targets as `remote-mac` and `container`.
- Branch `wp/0.3a-ssh-spike`.
