# WP 7.2 implementation findings — preparation and retained captures

Worktree `wp/7.2-real-e2e`, based on `226e3229`; frozen Kotlin source `e47352f2`
was read only. This phase ran no real-host preflight, sample build, Kotlin/native
CLI against real tools, SSH contact, simulator/emulator/ADB provisioning, remote
gate or SIP/TCC operation. The orchestrator owns all those operations and review.

## Delivered preparation

* `tools/real-e2e/run`: offline validation, reproducible build recipes, immutable
  product staging, explicit preflight, JVM discovery, two-stage `capture-pair`,
  shared-comparator diagnostics, JVM-qualified outcome release comparison and
  owned-resource recovery cleanup.
* A required ledger of 9 scenarios / 16 profile pairs, with 28 pair executions
  under P2; every coverage row is blocked awaiting real captures. JSON config
  templates generate only existing Marathonfile/Marathondevices fields. Their
  guards require explicit fresh simulator UDIDs, `shutdownUnused: false`, a
  loopback SSH forward with nonzero exit propagation, or the sole owned emulator
  on a non-default private ADB server.
* Worker leases reserve the complete absent `/tmp/marathon` baseline, preserve
  runner leftovers before harness cleanup, and retain failed reservations. Each
  invocation owns a new simulator or AVD and records resource creation/deletion.
  Android's supported profile requires an explicitly reserved empty KVM worker,
  no visible USB devices or existing adb/emulator, private HOME/AVD state, and
  inventory checks before and throughout execution. A rejecting client-SDK adb
  tripwire prevents the provider fallback from starting an untracked server.
  Installed system-image files are hashed for same-image pairing. No namespace
  is provisioned.
* Direct-host macOS follows decision 6: real SIP response and both read-only TCC
  counts before/after, no changes or fake responses. A18's complete-line check
  prevents permission writes; permission captures require the real refusal text.
  Counts are the specifically approved evidence, not a complete database diff.
* The driver supervises fresh process groups with finite deadlines, preserves
  stdout/stderr/exit separately, uses atomic journal writes, signals cancellation only after the slow test's
  observed marker, and distinguishes runner failure from watchdog/cleanup failure.
  EOF/interrupt cleanup is bounded; crash recovery refuses foreign tokens, live
  or reused PIDs and an unjournalled simulator allocation. Changed Apple
  test/tool process inventory blocks reclamation instead of killing by name.
* Real sample builds use signing defaults, generic iOS build-for-testing and
  actual scheme availability; the macOS bounded slow test is a separate overlay
  applied only to disposable source. Android uses the frozen wrapper/build tasks
  and records DEX magic. Identical product bytes and reviewed JVM-selected names
  are required before native capture.
* `scripts/check.sh` adds only offline ledger/input validation and command-double
  guard tests. The production runner, comparator and existing vendor suites are
  unmodified. PLAN §6.6 now assigns Android to Linux KVM and records the scoped
  direct-host macOS exception; §6.7 shadow isolation remains independent.

   arbitrary baseline backup/restore is not implemented. A dedicated empty Linux
   worker is supported, not automated network/device namespace setup. Both are
   proportionate fail-closed subsets; occupied/shared hosts are not silently used.
   Remote builds run on the remote Xcode, while paired CLIs run on the controller
   through the approved forward. Build-only config does not require onward keys.
4. **First-run checklist — capture-derived policy and witnesses.** Run Kotlin
   twice on this Mac's local iOS unit scenario first, before any Rust comparison

   `qualify` records both evidence hashes and the projection fingerprint;
   it rejects any semantic difference. P3 bounds and ordered visual states still

5. **First-run checklist — operational unknowns remain blockers.** Real signing/UI launch, readable TCC
   databases without new permissions, local CoreSimulator/XCTest behavior with a
   fresh client HOME, emulator registration to the selected server, parser dylib
   compatibility, SDK/runtime availability and retention locations are unprobed.

**Why the stop "fails", and what is not explained.** The stop command is
`kill -s INT $(cat pidfile) && lsof -p $(cat pidfile) +r 1 &>/dev/null`, byte-identical on both sides
(Kotlin `AppleSimulatorDevice.kt:781-791`; Rust `crates/marathon-ios/src/apple_simulator_device/worker.rs:366-403`).
Empty stderr plus exit 1 means `kill` succeeded and `lsof` found no live process at its first pass. The listener code is
also a faithful port, and A96 (already in `docs/known-kotlin-bugs.md`) records that Kotlin ignores the stop result and
leaves the pidfile when it fails. The capture shows the same failure on the Kotlin side, at a different test:

| Side, pair | Stop after first test | Stop after last test |
|---|---|---|
| JVM 1 | ok, took ~1.07 s (`stdout:142`) | exit 1, ~40 ms (`stdout:181-182`) |
| JVM 2 | ok, ~1.08 s (`stdout:139`) | exit 1 after 36 ms (`stdout:182-183`) |
| Native 1 | **exit 1 after 65 ms** (`stdout:127`) | stale pid, `No such process` |
| Native 2 | **exit 1 after 69 ms** (`stdout:125`) | stale pid, `No such process` |

Kotlin only reaches the failing stop when no recording follows, so the stale pidfile costs nothing. Native hits it on
the first stop, with another recording due. I could not establish from the retained logs why the recorder is already
gone (or holds no files) 40–70 ms after SIGINT natively when it takes about a second on the JVM side; n is two per
side. The difference that is visible in the logs is dispatch order: Kotlin's per-line parser is held back until the end
handlers finish (the next `Test Case … started` line appears at 24.381, after `Removed file`), while native prints it at
12.563, before the stop at 12.625 (the next app launch is already running). This is a hypothesis, not a finding; the
orchestrator can settle it with one `ps`/timing probe around the stop command on the next real run. The defect
below does not depend on it.

**Proposed minimal fix (needs a D-number, because it deviates from A96).** In `stop_video_recording`
(`worker.rs:379-401`), when the stop command fails, probe the recorder with
`sh -c 'kill -0 $(cat <pidfile>)'`; if the probe also fails (process gone), remove the pidfile and return `true`,
logging nothing. If the process is alive, keep today's warn-and-return-false path. Pass-through for success is unchanged.
This adds a worker command only on a failure path; the alternative that adds no command is to always remove the pidfile
after a stop attempt, but that can orphan a recorder that really failed to stop.

**Proposed test** (`crates/marathon-ios/tests/ios_listeners.rs`, next to
`waiting_start_warns_once_starts_anyway_and_failed_stop_still_logs`): fake worker whose stop command returns exit 1 with
empty output and whose `kill -0` probe fails. Two tests under `ON_ANY`; expect the pidfile removed after the first
test, no `Previous video recording didn't finish yet` warn, a second `started video recording`, and two VIDEO
attachments. Add a second case where the probe succeeds (recorder still alive): the old warn-and-wait behaviour.
`waiting_start_warns_once_starts_anyway_and_failed_stop_still_logs` encodes A96 and will need its stop case adjusted.
Kotlin's A96 row should gain the real-capture witness above.

**`macos-cancel`: what happened.** Driver protocol (`tools/real-e2e/common.py:106-160`, `run:196`): the driver polls the

unobserved here. The capture's rc 2 is the driver's own `blocked: cancellation start marker was not observed`
(`common.py:159`), not the CLI's exit status. The JVM pair-2 capture behaves like pair 1 (marker at 08:45:47.158, exit 130
in 4.0 s).

Why the marker was missed: the marker line *is* in the final native stdout (line 97), stamped with the time it was
logged, yet it was not in the file during the 123 s the driver polled it (the same loop sees it within 4 s for Kotlin).
In Kotlin each log event is written to stdout as it happens (logback console appender). In Rust the vendor-side logs
are only *queued*:

* the Apple log parser's `DebugLogPrinter` (`crates/marathon-apple/src/logparser/parser/debug_log_printer.rs:26-45`)
  logs through `SshLogging`, whose sink is the run's `ServiceLog` (`crates/marathon-core/src/construction.rs:322-329`),
  which does `record.push(...)` into the shared `LogQueue` (`crates/marathon-core/src/logging.rs:53-65`, `LogSender::push`
  at `:185-189`);
* the queue is drained to stdout only by `OutputDriver::flush` (`crates/marathon-core/src/output.rs:66-87`), which core
  calls at its own transitions: `marathon.rs:399,436,462,515` (start-up, parse, scheduling), `:706,724,735` (finish),
  `:828` and `:862` (end of run, signal), and `execution/progress.rs:312,314,330,347` (test started/ended);
* during a single long test none of these runs (`test_started` is never called in production, C4), so every vendor log
  line from the start of the batch up to the test's end appears in one burst, with correct but stale timestamps
  (`LogRecord::wall_millis`, "however late the output task drains"). In the native log the marker (08:43:42.116) is
  followed directly by the next line at 08:45:42.102, the test's end, exactly the signature of one late flush.

Class **(a): a real Rust parity bug**, not a driver or timing artefact. The observable difference is stdout liveness: a
person or CI wrapper following `marathon run` sees no vendor output (xcodebuild output, per-device progress, the
`Test Case … started` lines) until the next core flush, which for a long batch can be minutes. No D-deviation covers it
(D12's native signal relay is about the shutdown path, not the console). It also makes any marker-based harness
unusable on the native side, which is how it surfaced. The driver is correct and is left unchanged: it is the
scenario's required, sleep-free synchronisation (brief, `macos-cancel` row), and a side-channel marker file would
hide the defect.

Proposed fix (product code untouched here):

1. Add a live-mode output pump: `LogSender::push` / `LogQueue::log` wake a core-side job (a `Notify`-style wake on the
   existing shared queue), which calls the run's `OutputDriver::flush` (`output.rs:66`). `flush` already reserves the
   order on core (`serial_output`) and writes off core, so ordering against the explicit flush points and `Raw` records
   is kept (lifecycle.md, "Ordered raw console output"). Install the pump only on a live clock, not in virtual-time
   replay, so tapes stay deterministic; stop it with the run (`marathon.rs:828-835` already flushes at the end).
2. Regression tests: a vendor-side `LogSender` record pushed while core is idle (a pending test future) reaches a fake
   `ConsoleSink` within a bound, before the test completes; and the order of that record against a following core
   `Raw` line is unchanged.
3. Then re-capture the native side of `macos-cancel` (below). If it still does not cancel, the next suspects, in order,
   are the signal relay (`marathon.rs:110-186`, `signal_ignored`/`listen`, installed by `start_relay` at `:843-866`; the
   CLI passes empty hooks, `crates/marathon-cli/src/main.rs:73`) and the bounded disposal: `Marathon::on_finish`
