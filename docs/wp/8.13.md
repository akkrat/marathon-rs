# WP 8.13 (design only): Tokio tasks and cancellation instead of the coroutine emulation

Effort of this design step: **M**. Branch `wp/8.13-tokio-tasks`, based on `main` after WP 8.11 (commit
`816e0000`). **This WP produces a design and a split into implementation WPs; it changes no runtime
code.** WP 8.12 (Apple async reads) runs in parallel.

## Why

The runtime emulates Kotlin coroutines on top of Tokio: jobs and parent/child scopes, structured
cancellation with `CancellationException` causes, `SupervisorJob`, `withTimeout` scopes with identity,
actors with mailboxes, `SharedDeferred`, retry helpers, and the run's single-threaded core executor
(`crates/marathon-core/src/executor/`: `job.rs`, `actor.rs`, `timeout.rs`, `retry.rs`, `shared.rs`,
`bridge.rs`, `clock.rs`, `hooks.rs`, about 2,800 lines; `docs/design/lifecycle.md` describes the model;
vendors use it widely). PLAN.md §3.12 does not pin how concurrency is built, only what the run does:
results, commands sent to workers, pinned progress/summary lines, exit codes, and the deviations already
recorded (for example D52 cancel limits, D54, the 8.8 exit path). Tokio's `JoinSet`, `CancellationToken`
(tokio-util), `task::LocalSet`, `tokio::time::timeout` and channels can express most of this directly.

## What the design must answer

1. **Inventory.** Every emulated construct, where it is used (counts per crate), and what Kotlin
   semantics it reproduces that marathon actually relies on (for example: a child failure cancels the
   parent; a supervisor does not; a timeout scope only catches its own timeout; cancellation reasons are
   kept and reported; actors process messages in order; `finally` work runs on cancel).
2. **Mapping.** For each construct, the Tokio/tokio-util replacement, or why it stays (and in what reduced
   form). Say what stays deliberately custom and why.
3. **What must not change.** The observable behaviour list above, the virtual clock and replay seams that
   make scripted tests deterministic, the single-threaded core executor rule (no blocking on core), the
   exit and signal behaviour fixed in 8.8, and D52/D54 limits. Identify the tests that pin each.
4. **Risks.** Where Tokio semantics differ (drop-cancellation versus cooperative cancellation, `JoinSet`
   abort on drop, panics, `LocalSet` versus `Send` futures, timer resolution under a paused clock) and
   how each is handled.
5. **Split.** A sequence of implementation WPs, each independently mergeable with the gate green and no
   golden change, smallest-risk first (for example: timeouts; then retry; then shared deferreds; then
   actors; then jobs/scopes last), with an effort estimate each and what each deletes.
6. **Recommendation.** Whether the full replacement is worth it, or which parts to stop at.
