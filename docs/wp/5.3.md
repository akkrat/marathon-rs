## Deliverables and boundary

In `crates/marathon-ios` (`src/listener/…`, `src/recorder_type_selector.rs`; the crate doc already reserves "listeners" for it):

1. **`RecorderTypeSelector`** as a pure function over the merged `DeviceFeature` and `IosScreenRecordConfiguration` — no I/O, table-tested.
2. **`ScreenRecordingListener`** (`AppleTestRunListener` + attachment provider): per-test start behind the pidfile wait (100 ms poll, 10 s cap), stop/pull/transcode, batch-failure pull. Includes `await_removal` over the frozen `VendorClock`, so the ported Kotlin test runs on virtual time.
3. **`ScreenCapturerTestRunListener`**: drives the merged core `ScreenCapturer` via `start_owned`, one supervisor per test, cancel-and-join at test end, policy-based delete/attach, batch-failure rename.
4. **`DeviceLogListener`**: background `log stream` start/stop and the `DEVICE_LOG` pull.
5. **`DataContainerClearListener`**: batch-start container clear over the batch's distinct app ids.

**Frozen contracts implemented/consumed:** `AppleTestRunListener` (implement), `AttachmentProvider` via `AttachmentProviderDelegate` (delegate, as Kotlin does), `AppleDevice`/`Screenshottable`, `RemoteFileManager`, `OutputFiles`, `VendorClock`, `VendorError::Transfer`. All worker effects go through existing executor/device calls — no new command forms, no blocking on core, no lock across an await (listener state is interior-mutable per the 4.7 trait shape), no `unwrap()`/`expect()` on I/O, process or network results.

## Behaviours to reproduce (Kotlin `file:line`)

**`RecorderTypeSelector.selectRecorderType`** (`RecorderTypeSelector.kt:8–35`): preferred type wins only if it is supported **and** its own configuration is enabled (:18); otherwise VIDEO if supported and enabled, else SCREENSHOT if supported and enabled, else `null` (:22–26). A preferred-but-disabled or unsupported recorder therefore falls back to the other one; `null` at the call site becomes an empty listener (`D/:627`). `recorderEnabled` reads `videoConfiguration.enabled`/`screenshotConfiguration.enabled` (:29–35).

**`DataContainerClearListener.beforeTestRun`** (`DataContainerClearListener.kt:14–24`): when disabled, nothing — not even bundle identification. When enabled, app ids are `testBatch.tests.map { bundleIdentifier.identify(it).appId }.toSet()` in first-seen order, cleared sequentially. `identify` throws `ConfigurationException` for an unlocated test (`B/AppleTestBundleIdentifier.kt:13–16`), and the composite has no isolation, so that error aborts `beforeTestRun` for the listeners after it. The clear is per **batch**, before the run: tests within one batch that share an app are not cleared between tests. The terminate/container/remove sequence and its swallowed result are 5.2's (`D/:1182–1191`).

**`DeviceLogListener`** (`listener/log/DeviceLogListener.kt`; logger fully qualified, seen in the 0.4b transcript as `<c.m.m.a.i.listener.log.DeviceLogListener>`):
- `supported` is a lazy SDK check: only the four simulator SDKs (:23–31). `beforeTestRun` checks `enabled` first (silent when disabled), then warns `Device <serial> does not support capturing device logs` and returns (:33–40).
- Start (:42–53): `criticalExecute` with `Durations.INFINITE` (7 days, `B/extensions/Duration.kt:8`) of exactly `sh -c "xcrun simctl spawn <udid> log stream --type log --color none --style compact 2>/dev/null > <remoteLog> & echo $!"`. This is a different backgrounding wrapper from recordVideo's nohup/pidfile — keep both. The pid is kept only if the result succeeded **and** the trimmed combined stdout parses as an int; what is stored is the trimmed **string**, not the parsed value (:50–53).
- `afterTestRun` (:56–68): repeats both gates (the unsupported warn fires a second time), then, only if a pid was stored, `sh -c "kill -s INT <pid>"` via `executeWorkerCommand` with the result ignored, then pulls. No pid ⇒ no pull, silently (candidate **A79**).
- Pull (:70–78): `FileType.DEVICE_LOG` with `test = null` and the batch id (the C1 batch filename), `pullFile` result ignored, debug `Pulling finished in <millis>ms <remote> ` — with the trailing space (:77; the video listener's twin line has none).

**`ScreenCapturerTestRunListener`** (`listener/screenshot/…`; logger is the simple name only, :39):
- One core `ScreenCapturer` per batch, built from `screenshotConfiguration.{delay, height, width}` and the screenshot timeout (:40; note the height-before-width order). In Rust that is `CaptureSettings`/`CaptureServices` plus `start_owned`; its frozen contract (one `Arc` per device, cancel-and-join before reading `captures_taken`, never overlap starts) is the mapping of Kotlin's `async(supervisor)` + `cancelAndJoin`.
- `testStarted` (:43–52) stores `lastTestIdentifier`, debug-logs with `toSimpleSafeTestName()`, installs a **fresh** `SupervisorJob` in the field (a previous one is overwritten, not cancelled) and launches capture.
- Ended (:54–82): failed ⇒ `hasFailed = true`; passed/ignored ⇒ false. `testEnded` clears `lastTestIdentifier`, cancel-and-joins, then: not-failed **and** policy `ON_FAILURE` ⇒ delete the test's screenshot file, registered as an `invokeOnCompletion` on the already-joined job (:70–73, proposal P2); otherwise attach `SCREENSHOT_GIF`/`Name.SCREEN` iff `capturesTaken > 0`, else delete the file (:74–81). The file is materialised through `createFile` on both paths.
- `testRunFailed` (:84–93): cancel-and-join, then if the in-flight test's file has `length() > 0` **rename** it to the batch-level screenshot file (no attachment, no policy or capture-count check). `renameTo`'s result is ignored and `lastTestIdentifier` is never cleared here (candidate **A78**).

**`ScreenRecordingListener`** (`listener/video/…`; fully qualified logger, transcript `<c.m.m.a.i.l.v.ScreenRecordingListener>`):
- Constants (:215–216): previous-recording timeout 10 s, pidfile poll 100 ms. `awaitRemoval` (:224–239): read once immediately; if non-null, call `onWaiting` **once**, then delay-then-read per interval; the whole loop is under `withTimeoutOrNull`, own expiry ⇒ `false`. The Kotlin test pins the counts exactly: 1 read/0 ms gone, 5 reads/400 ms, 100 reads/10 000 ms on timeout. Every read is a fresh worker command (`cat <pidfile>` via 5.2's `readTextfile`, null on any failure) — the KDoc's MaxSessions warning is why the delay is load-bearing, do not busy-poll. A present-but-blank pidfile counts as present here, unlike `stop()` (candidate **A76**).
- `beforeTestRun` (:51–54) and `afterTestRun` (:146–148) both call `stop()`. `stop()` (:156–165) is idempotent: cancel-and-join the possibly still-waiting start first, then read the pidfile, and only if the trimmed pid is non-blank call `device.stopVideoRecording()` — its Boolean is bound to an unused `success`, and `stopped video recording pid=<pid>` is debug-logged either way (candidate **A77**). Pidfile removal happens inside the device's stop, only on its success (5.2).
- `testStarted` (:56–84): compute and store `lastRemoteFile`, reset `started`, launch under a fresh supervisor: await the previous pidfile's removal (warn once `Previous video recording didn't finish yet…` while waiting; on timeout warn `…didn't finish in 10s, starting a new one anyway` and start regardless), then `startVideoRecording`; `started = exitCode == 0`; on success re-read the pidfile only to debug-log `started video recording pid=<pid> to <remote>`.
- Ended (:86–102): failed ⇒ `success = false`, passed/ignored ⇒ `true` (inverse naming to the screenshot listener). `testEnded` stops, nulls `lastRemoteFile`, then pulls.
- `pullVideo` (:104–122): `remoteFileManager.test(video)` false ⇒ return, with **no** removal. Policy gate is `ON_ANY || (ON_FAILURE && !success)` (:109–111). Inside the gate: transcode if configured-and-supported, then pull; `removeRemoteVideo` runs whether or not the gate passed. Only `TransferException` is caught (warn `Can't pull video`); everything else propagates through the composite. In Rust that catch is `VendorError::Transfer` only.
- Transcode (:167–187): `move` the original to the temp path first, then one `sh -c` string, exactly `<binary> -i <temp> -vf "scale=<size>:<size>:force_original_aspect_ratio=decrease:force_divisible_by=2" -preset ultrafast <optional> <src>` (:179), where `optional` is `-movflags +faststart` for H264 and empty for HEVC (leaving the double space). Failure is error-logged only when the result is non-null and unsuccessful (:182–184, candidate **A77**); the pull of `<src>` follows regardless. The moved original at the temp path is never removed — **A19**, observed in 0.4b, preserved; this WP updates its status to reproduced. The per-test temp name is `remote_temp_video_for_test` (`-temp.mp4`); the batch path below uses `"<file>.tmp"` instead (:132) — keep both spellings.
- Pulls (:189–205): per-test pull creates the `FileType.VIDEO` file, ignores `pullFile`'s Boolean, debug-logs millis, then unconditionally emits the `VIDEO`/`Name.SCREEN` attachment (candidate **A77**). The batch pull is the same minus the attachment.
- `testRunFailed` (:124–144): gated on `verifyHealthy()` (:241–249) — `echo quickhealthcheck` whose stdout must contain `quickhealthcheck`, exceptions swallowed to null, all under a 10 s `withTimeoutOrNull`, null ⇒ false (open question 4 on the swallowed cancellation). Unhealthy ⇒ warn and no pull. Healthy ⇒ stop, then for `lastRemoteFile`: `test` gate (early return skips removal), optional transcode to `"<file>.tmp"`, batch pull, remove. No `screenRecordingPolicy` check on this path.

**Timing lines:** every `measureTimeMillis` debug line above (`Pulling finished…`, `Transcoding finished…`, `Removed file…`) keeps its logger, level and text; the millisecond values are nondeterministic in Kotlin too and are normalised in comparison. Use the merged code's existing wall-millis pattern — do not introduce a second clock.

## Proposed simplifications (pragmatic parity — for orchestrator approval, **not decided**)

Until one is approved, the behaviours above stand and a divergence is a bug. **Not proposed:** fixing A19's temp-file leak (the final worker filesystem is compared state, §6.4), the 100 ms/10 s pidfile wait, or either backgrounding wrapper.

- **P1, blank pidfile in `awaitRemoval` (candidate A76):** treat a blank read as removed, matching `stop()`'s `isNullOrBlank`. Diverges only when the pidfile exists but is momentarily empty (the `echo $! > pidfile` race), where Kotlin waits the full 10 s.
- **P2, screenshot delete-on-pass (:70–73):** delete directly after the join instead of registering `invokeOnCompletion` on a completed job. Same files and logs; diverges only if `createFile` fails inside the completion handler, where Kotlin routes the exception to the uncaught handler instead of the caller.
- **P3, overwritten supervisors (`testStarted` twice with no end):** cancel the previous capture/recording job on a new start instead of orphaning it. The 4.8 runner's production callback sequence never does this; Kotlin's detached `SupervisorJob()`s would keep capturing into the same file.
- **P4, log-stream pid parse (:50–52):** ASCII `i32` parse only. Java's `toIntOrNull` also accepts a leading `+` and non-ASCII digits; `echo $!` prints neither. The stored/interpolated form stays the trimmed string either way.
- **P5, dead state:** drop `started` (read only for its own log gate) and the unused `success` binding in `stop()`, keeping the pidfile as the only synchronisation state, as the Kotlin comment at :150–155 already describes. No observable change; listed so the reviewer does not flag the omission.
