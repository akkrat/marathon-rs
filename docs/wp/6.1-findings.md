# WP 6.1 findings

The adb client core is in `crates/marathon-adb/src/client/`, next to 0.5's scripted server and 6.3's
instrumentation parser. It ports adam 0.5.8's client as the brief lists, with no cargo feature; `tokio` became a
normal dependency of the crate and the `server` feature keeps its own extras. `server/` is untouched, and the
crate still does not depend on `marathon-core`.

## Decisions taken

### API shape (frozen for 6.2, orchestrator decision 2)

Modules mirror adam's files and keep adam's type names, so 6.2 can port request types one for one:

| `client/stream.rs` | the `produce` half of `AndroidDebugBridgeClient.kt:64-116` |
| `client/request.rs` | `request/{Request,ComplexRequest,AsyncChannelRequest,SynchronousRequest}.kt` |
| `client/transport.rs` | `transport/*`, `transport/vertx/{VertxSocket,VertxSocketFactory}.kt` (semantics only) |
| `client/socket.rs` | `extension/Socket.kt` minus `:142-195` (6.2's) |
| `client/bytes.rs` | `extension/{ByteArray,Int}.kt` |
| `client/{consts,error,log,target,feature,validation,transform}.rs` | `Const.kt`, `exception/*`, `log/AdamLogging.kt`, `request/{Target,Feature,ValidationResponse}.kt`, `request/transform/*` |

- `Request`: `serialize()`, `validate()`, `socket_idle_timeout()` (milliseconds, before the unit bug),
  `simple_name()` (defaults to the Rust type name, which equals adam's class name for the ported requests) and a
  default `handshake()`. Framing helpers are free functions: `create_base_request`, `handshake`,
  `read_synchronous` (`SynchronousRequest.readElement`), `serialize_sync_shell`, `serialize_abb_exec`.
- `ComplexRequest`: `process()` (default: handshake then `read_element`) and `read_element()`.
- `AsyncChannelRequest`: `take_channel()` (the input, a `tokio::sync::mpsc::Receiver`), `read_element(socket,
  send)` pushing zero or more items into a queue and returning `true` to end, `write_element(element, writer)`
  as an associated function (it runs concurrently with reads, so it gets the socket's write half, not the
  request), and `close(send)`, async like adam's `suspend fun` (R1-wonder-2). `write_element` runs on its own
  task from the first pull on; if it panics, the stream fails with `IllegalState` (R1-wonder-6).
- All trait methods return `impl Future + Send`; implementations use `async fn`.
- `AndroidDebugBridgeClient::{new, with_host_name, host, host_name, port, socket_factory, execute,
  execute_channel, execute_compat, close}`. `host()` is an `IpAddr`; Java's `hostAddress` text for serials

  then read `name/ip:port`, as Java's `InetSocketAddress` prints them (probe `connect-refused-named`), and
  `host_name()` is there for 6.5's logs (R1-wonder-3). `SocketFactory::tcp` takes the name beside the address.
  Clients may share one `SocketFactory`, as marathon's do; `close()` closes it for all of them.
- `AsyncCompatShellCommandRequest` is a trait (`cmd`, `supported_features`, `target`, `socket_idle_timeout`,
  `convert_chunk`, `close`, the last async as in adam) for 6.6a's `TestRunnerRequest`; `CompatShellCommandRequest`
  hands chunks on unchanged. `CompatShellStream::request()` returns `Option<&R>`: `None` only while `close`
  runs, as the stream's closing future owns the request (R1-sol-4).
- `AdbError::message()` is Java's `getMessage()`, an `Option<&str>`: `ClosedChannel` has none (R1-sol-2).
- `bytes::{to_int, to_uint}` take `&[u8; 4]` and `bytes::{to_long, to_ulong}` take `&[u8; 8]` (R1-wonder-4).

### Streams (decision 3)

`ChannelStream` is pull-based. It connects, switches transport and handshakes on the first pull; those errors
end the stream, validation errors come from `execute_channel`. A pull in progress is kept inside the stream, so
dropping a `next()` future (a `select!` timeout) loses nothing and `next()` can be called again. Dropping the
stream closes the connection and aborts the shell v2 input writer, the only task the client spawns. That
writer starts after the handshake, on the first pull, so a sender that waits for room before the stream is
pulled needs a large enough channel or its own task (documented on the v2 request; the ported adam test sends
from a task).

A shell v2 stdout or stderr packet is handed on one 16 KiB piece at a time, each as soon as it is read, as
adam sends each piece to its channel; the rest of the packet is request state (R1-sol-1). `CompatShellStream`
keeps a `close` in progress inside the stream too, so dropping its `next()` loses neither the cleanup nor its
final items (R1-sol-4).

`request.close()` runs when the stream ends or fails after connecting, as adam's `finally` does (the brief's
"only at normal end" holds for compat's own `close`, which is what `CompatShellStream` does). If it fails, the
DEBUG `Exception during cleanup. Ignoring` goes to `com.malinskiy.adam.AndroidDebugBridgeClient`.

EOF is only what a read has seen. vert.x also reports it once the FIN has merely arrived after the last
message, so in Kotlin a stream whose server closes right after a message can end cleanly. Our pulls are not
continuous, so honouring that would turn the common case, a server that dies while `track-devices` waits
(Kotlin's producer is always parked in the read then), into a clean end. 6.5's survive-kill-server loop needs
the error (N16), so the Rust client always gives it.

### Transport and timers (decision 4)

- One TCP connection per request, `TCP_NODELAY`. Reads never fail: EOF, a reset, the idle timer and `close()`
  all read as the end of the stream, as in vert.x, where `receiveCatching().getOrNull()` turns a channel error
  into -1. `readFully` stops short at EOF without failing.
- Writes fail with `IllegalStateException("Socket write error: socket is not connected CLOSED")` once the
  connection is closed by the peer (vert.x closes the channel on EOF), the idle timer or `close()`.
- Connect timeout: `toTimeoutInt` milliseconds, 0 = none, default 10,000 ms, via `tokio::time::timeout`.
- Idle timeout: `toTimeoutInt` of the milliseconds, used as **seconds** (N12); 0 = none. Measured from the last
  read or write, checked by pending reads, before each write and during a blocked write. When it fires the
  connection is shut down, so the server sees the end, and a blocked write fails with netty's
  `StacklessClosedChannelException` (no message; probe `idle-blocked-write`, R1-sol-2). Each part of a write
  counts as activity; netty counts only a completed write, which differs only for a write slower than the idle
  timeout, 30,000 s by default.
- `SocketFactory::close()` shuts down every live connection, whether a request is reading it or not: the server
  reads EOF at once (probe `close-peer-eof`, R1-sol-3), reads end and writes fail; new connections fail. The
  factory keeps a weak list of its connections, each with a duplicated handle (`try_clone`) to shut it down
  while a read or write holds the tokio halves; no task is spawned. Before the factory's first request, or
  before the first `execute_channel`, whose producer adam starts at once, `close()` does nothing, as adam's
  vert.x is created lazily (probe `close-before-first-request`, R1-sol-5).

### Logging

`AdamLogging` wraps the run's `MarathonLogging` and a sink `Fn(logger, level, message, throwable)`. adam calls
`KotlinLogging.logger` itself, so its loggers get no level of their own; the client checks
`MarathonLogging::effective_level` without registering the name (registering would give adam's loggers
marathon's DEBUG/ERROR level). Messages are built only when enabled. The WARN line and logger name are
probe-confirmed (`log:com.malinskiy.adam.request.Request`).

### Errors

`AdbError` keeps the classes marathon branches on: `Connect` (`AnnotatedConnectException` for a refusal,
`ConnectTimeoutException` for the timeout; `is_connect_exception()`), `RequestRejected`, `RequestValidation`,
`IllegalState`, `VertxClosed`, `MalformedResponse` and `Io`. `to_throwable()` gives the `Failure`-shaped
`JavaThrowable` (class, message, cause) and `Display` is Java's `toString()`. Connect messages are
`Connection refused: /<ip>:<port>` (probe) and `connection timed out: /<ip>:<port>` (the string constant in
`netty-transport-4.1.100.Final.jar`'s `AbstractNioChannel$AbstractNioUnsafe$1`; marathon ships no native
transport, so NIO is used). Java prints `<hostname>/<ip>` when the `InetAddress` came from a name; 6.5 resolves
names, the client only knows the IP. The address text is `jcompat::net::inet_socket_address`, Java's
`InetSocketAddress.toString()`: IPv6 in brackets and in full, `/[0:0:0:0:0:0:0:1]:<port>` (probes
`connect-refused-ipv6` and `inet-socket-address`, R1-sol-6). A refusal's `JavaThrowable` keeps netty's cause,
`java.net.ConnectException: Connection refused` (probe `connect-refused-cause`, R1-sol-7); the others have
none. `AdbError::ClosedChannel` is the idle timer's failed write. Other connect failures (unreachable network) are `Io`: netty's are
`SocketException`s, not `ConnectException`s, so marathon does not branch on them either.

### `close()` (decision 6, probe-corrected)

The brief expected new requests after `close()` to fail with `IllegalStateException`. The JVM probe shows
`io.vertx.core.impl.NoStackTraceThrowable: Vert.x closed`, a `Throwable` that is not an `Exception`, so
marathon's `catch (e: Exception)` lets it through; `AdbError::VertxClosed` keeps it and `is_exception()` is
false. It also shows that a stream open at `close()` which then ends without an error of its own (a v1 shell
stream) fails with `IllegalStateException: Unknown deployment`, from adam's socket close undeploying a verticle
that vert.x already removed. Both are reproduced (N19): `Socket::close_result()` after a successful request and
at a stream's clean end. `track-devices` fails on the missing message first, which wins.

## Simplifications applied

- **P1** (approved; the round-1 reviewer agreed with the 13 `n/a` rows and the 58 unused-API rows): `shell/v2/{SyncShellCommandRequest,ShellCommandRequest,ShellCommandResult}.kt`,
  `misc/{FetchHostFeatures,KillAdb,ExecIn}Request.kt`, `abb/AbbRequest.kt`, `request/{MultiRequest,
  AccumulatingMultiRequest}.kt` are not ported; their 13 test rows are `n/a`.
- **P2** (approved, D11): no buffer pools, record parser, verticles or busy-spin. The read caps stay: 64 KiB per
  v1 read, 16 KiB per v2 piece, 16 KiB per synchronous read, 4,088 bytes for the pooled-buffer `copyTo` callers.
- **P3** (approved, D11): `StringResponseTransformer` decodes once at the end; the v1 channeled stream decodes
  across reads (`shell::Utf8Stream`: a cut-off sequence waits for the next read, the rest uses
  `jcompat::utf8::decode_utf8`, a sequence cut off by EOF becomes U+FFFD); the compat v1 path hands the raw bytes
  on. The probe pins Kotlin's `a�|�b` and the test pins ours, `a|жb`.
- **P4** (approved): at EOF inside a v2 header or body, the bytes received are handed on and the stream ends
  cleanly without an exit chunk.
- **P5** (approved): a framed payload over 0xFFFF bytes fails with `RequestRejected("Request of <n> bytes is longer
  than the 65535 bytes adb accepts")` before anything is written. The probe shows Kotlin's header for a
  0x1000F-byte request: `1001F…`, which claims 0x1001 bytes.
- **P6** (approved): a device line without a tab is `MalformedResponse` with the Java class and message Kotlin
  throws, `java.lang.IndexOutOfBoundsException: Index: 1, Size: 1` (Kotlin's `split` returns a `SingletonList`;
  probe `devices-line-without-tab`).
- **P7** (approved): the v1 exit code and the server version parse ASCII digits only (`i32::from_str_radix`, which
  also takes Kotlin's leading `+` or `-`). The same rule applies to the four-character hex lengths, where a
  leading `-` is also refused: Kotlin would hand a negative limit to a pooled buffer.

### Two more exotic-input differences (approved in review round 1)

Not covered by P4–P7 by name; the orchestrator approved both as simplifications:

- **Truncated protocol string.** Kotlin's `readFully` returns the requested length even when EOF cut the read
  short, so `readProtocolString` never reports "Incomplete string received"; the body is padded with stale
  pooled-buffer bytes and usually fails later as garbage (the first probe run, with a stub header one byte too
  long, gave `IndexOutOfBoundsException` from the padded device list). Rust reports `RequestRejected("Incomplete
  string received")`.
- **Protocol string over 16 KiB.** adam reads the body into a 16 KiB pooled buffer, so a longer one (a device
  list of roughly 500 devices) fails with `IllegalArgumentException`. Rust reads it.
