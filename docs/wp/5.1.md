## Deliverables and boundary

1. **`FakeSimulatorWorker`, a faithful port** of `T/device/FakeSimulatorWorker.kt` (164 lines). It implements `marathon_apple::cmd::CommandExecutor`. Its in-memory CoreSimulator (`simulators`) is `Arc`-shared so several connections can hold the same map. It has the Kotlin test profile (Xcode 16.4, iOS 18.6, `/Users/worker`, arm64), the `before`/`session`/`on_connected_check` hooks, the settable `connected` flag and the command recorder with its counters (`count`, `lists`, `worker_fact_commands`, `getenv`). This is what every consumer Kotlin test uses. Behaviours are listed below.
2. **A world-backed in-process executor** (`WorldExecutor`) and its `FileBridge` (`WorldFileBridge`). They implement the same traits over 0.4b's `fake_worker::router::Router` and `apple::World`, with that worker's `VirtualFs`, and **no SSH**. A command takes the same path as on the wire: argv → `shell_command` (the same quoting as the SSH executor, so 0.4b's raw matchers and catalogue apply unchanged) → `Request::parse` → `Router::route` → `Plan` → a `CommandSession`. The session streams the chunks, gives the exit status or signal, and has terminate and kill. Background and pidfile jobs, `SignalPid` and `Publish` files share 0.4b's process registry. `Plan::Rsync` is never produced in process: `WorldFileBridge` does `send`/`receive` by direct `VirtualFs` copy, and a raw `rsync` command fails explicitly.
3. **An additive seam in `tools/fake-worker`.** Move the plan execution in `server.rs` (`run_channel`, `run_action` and the background/signal paths, `:675-1029`) behind a transport-independent sink, so that the SSH channel and `WorldExecutor` drive the same code. The SSH behaviour must not change: every 0.4a/0.4b test stays green, and the four recorded scenarios replay unchanged. Under the `fake-worker.md` rule this is an extension, not a second protocol.
4. **Generalise the 0.4b world's baseline-UDID gates** (0.4b-findings §Deferred work; `apple-world.md` §Scenario schema 1). The xcodebuild destination, PlistBuddy keyboard preferences, recording `pkill` and the provisioning probe must work for any initial UDID and for several devices, with the capture/preference profile held per UDID. The recorded scenarios use the baseline UDID and must stay byte-identical.
5. **Contract tests** for (1)–(4) (see Acceptance). No Kotlin test rows are ported here.

**Not 5.1:** `AppleSimulatorDevice` and its installer and media importer (5.2); the listeners (5.3); `WorkerProvisioningContext`, the provisioner, the factory, `DeviceTracker` (5.4); the provider (5.5a/b); macOS (5.6). That also excludes the scripted behaviours that only those WPs can exercise: delayed or failing boot transitions, runner crash or hang, pidfile races, container clearing, dynamic inventories (0.4b backlog row 5.1–5.6). Each owner adds its own `before`/world scripts next to its production code. Also not here: the per-test fakes (`RecordingFileBridge`, `BatchWorker`, `XcodebuildWorker`, `RunningXcodebuild`, and `StartupPhasesTest.answerPreparation`), which stay in their test files and are ported with the rows that use them; the full differential comparison (7.1); and `FakeCommandExecutor`, which is already ported (4.1).

**Placement (recommended; open question 2):** `crates/marathon-test-support/src/apple/{fake_simulator_worker,world_executor}.rs`. `marathon-test-support` gains `marathon-apple` (feature `test-support`) and `fake-worker` as dependencies, and `marathon-ios` takes it as a dev-dependency. This creates no cycle, because nothing here needs `marathon-ios` types. `marathon-apple` needs one additive public helper to build a finished session from a `CommandResult` (today `CommandSession::with_result` is `pub(crate)`), and `FakeCommandExecutor` should be refactored onto it.

## Behaviours to reproduce (`T/device/FakeSimulatorWorker.kt`)

- **Construction** (`:24-33`): `host_id` (default `"local"`) becomes `CommandHost{id, charset:"UTF-8"}`. Rust `KotlinProcessHost::host()` has no id parameter, so build the `CommandHost` directly. Also `arch` (mutable, default `arm64`), `home` (`/Users/worker`), and `simulators` (shared, injectable). A `Simulator` has `udid`, `device_type`, `runtime`, a mutable `available` (default true) and `model = "model-<udid>"`.
- **Connection** (`:38-52`): reading `connected` first runs `on_connected_check`, which may block, and then returns the flag; writing it sets the flag. `close()` does nothing (`:90`). Setting `connected = false` doesn't make `execute` fail; the Kotlin fake still answers. Keep it that way: consumer tests may still send commands after disconnecting, and the fake must keep answering them.
- **Execute** (`:77-88`): record the argv first, then `session(argv)` if it returns `Some`, else `before(argv).await` if it returns `Some`, else the built-in answer. An error raised by `before` propagates from `execute` (it must keep the class: `net.schmizz.sshj.connection.ConnectionException` reaches `safe_execute`'s classification, `BatchTest:270`). The recorded command is argv, not wire text. `timeout`, `env` and `workdir` are ignored.
- **Built-in answers** (`:92-107`), as exact argv equality or prefix:
  - `xcrun simctl list --json` returns the inventory.
  - `env` returns `HOME=<home>`, `USER=worker`.
  - `xcrun xcodebuild -version` returns the `xcodebuild_version` lines (default `Xcode 16.4` / `Build version 16F6`).
  - `uname -m` returns `arch`.
  - argv[0] `/usr/sbin/system_profiler` returns `<string>spdisplays_metalfamily</string>`.
  - `xcrun simctl getenv <udid> <key>`: `HOME` → `<home>/Library/Developer/CoreSimulator/Devices/<udid>/data`; `SIMULATOR_MODEL_IDENTIFIER` → the model; `SIMULATOR_RUNTIME_VERSION` → `18.6`; any other key → empty, exit 1. An unknown simulator → stderr `Invalid device: device`, with the literal word, exit 148 (`:110`).
  - `xcrun simctl create <name> <type> [runtime]` → a new uppercase random UUID, stored with runtime defaulting to iOS 18.6.
  - `xcrun simctl delete <udid>` → ok, or `Invalid device: <udid>`/148.
  - Anything else → stderr `unsupported command`, exit 1.
  - Results come as a finished session: closed stdout/stderr channels and `await` returning the result (`:138-149`, the same shape as `FakeCommandExecutor`).
- **Inventory** (`:119-136`): one device type (iPhone 15 Pro, `IPHONE`) and one runtime (`IOS`, "iOS 18.6", "18.6"), whatever the simulators hold. Devices are grouped by their own runtime key, so a simulator created with another runtime appears under a key missing from `runtimes`. Each device is `{udid, name=udid, state:"Shutdown", isAvailable, logPath:<home>/Library/Logs/CoreSimulator/<udid>, deviceTypeIdentifier}`. It goes through the production 4.4 parser, so serde_json layout is fine; the field set and values must match.
- **Counters and constants** (`:68-75,151-163`): `add(udids…, device_type, runtime)`; `count(argv)` counts exact matches; `lists = count(LIST)`; `worker_fact_commands` counts `ENV`, `XCODEBUILD_VERSION`, `UNAME` or any argv starting with `SYSTEM_PROFILER`; `getenv(udid,key)` counts. Export `IPHONE`, `IOS`, `SYSTEM_PROFILER`, `LIST`, `ENV`, `XCODEBUILD_VERSION`, `UNAME`, `WORKER_FACTS`, `ok(…)` and `invalid(udid)` for the consumer tests.
- **Concurrency**: `@Volatile` fields and `CopyOnWriteArrayList`/`ConcurrentHashMap` mean hooks can be swapped and state changed while commands are running. Use short synchronous locks or atomics that are never held across an await (`lifecycle.md`).
- **Iteration order**: Kotlin's inventory order is `ConcurrentHashMap` hash order. With the reference JDK, the keys `b1,b2,b3` iterate as `[b2, b3, b1]` (and `a1…a4` iterate in order). Before choosing a Rust order, the implementer must check whether any consumer assertion depends on it. Simplification S2 proposes not to reproduce it.

**Kotlin bugs:** no `docs/known-kotlin-bugs.md` row applies directly, because the fake is test code and the A rows concern production code. A4 (`create`'s UDID regex) and A41 (`dumpstate` exit status) are where its answers meet production parsers; consumer WPs keep them. The fake's own quirks (the literal `Invalid device: device`, a fixed one-element `devicetypes`/`runtimes` list, a constant `Shutdown`) are kept, because consumer expectations rely on them. They are recorded in the findings' fake-quirks table, not as known Kotlin bugs.

## Scripted behaviour 5.2+ needs from the world-backed executor

The Kotlin rows need only deliverable 1. The world-backed path is for the Rust in-process scenario tests that PLAN §6.4 and the 0.4b backlog assign to 5.x. 5.1 provides only what every one of them needs:

- **Same commands, same evidence:** each 0.4b catalogue form gets the same `CommandResult` (stdout/stderr lines, status) in process as over SSH. The world state (inventory, lifecycle, installed apps, sessions, TCC captures) is the one `World` value, cloned across executors exactly as across SSH connections. Expectation reservation, rollback and `validate()` behave as in 0.4b.
- **Session control:** long-running xcodebuild and recordVideo sessions stay alive until their completion or barrier; `terminate`/`kill` deliver TERM/KILL to the virtual job; the background `nohup`/pidfile and device-log `& echo $!` jobs and `SignalPid` follow the 0.4b registry; dropping or cancelling a session leaves no running job (final `active_processes: []`).
- **Fault injection:** 0.4a `Script` rules still come before the extensions (delays, hang, status, signal, chunked streams). In process, transport faults are expressed through a `before`-style hook on `WorldExecutor` (fail the next `execute` with a given `Failure` class, or flip `connected`), not through SSH channel loss.
- **Multiple simulators:** arbitrary UDIDs, several per world, an independent lifecycle and capture profile per UDID (deliverable 4).
- **Deferred to the owning WP**, each adding world effects next to its tests: boot delay or failure and the second attempt (5.2); container clearing, `pkill`/`ps` races, media formats and HEVC (5.3); inventory mutation between `list` calls and worker-fact invalidation (5.4); dynamic updates, a lost worker and recovery (5.5a/b); SIP/TCC/cancel (5.6).

## Proposed simplifications (pragmatic parity, for orchestrator approval; **not decided**)

- **S1, no verbatim test fake under `docs/known-kotlin-bugs.md`:** treat the fake's quirks as fixture behaviour (findings table), not Kotlin bugs. They affect no user.
- **S2, deterministic inventory order:** the order in which simulators were inserted (or sorted by UDID), instead of emulating `ConcurrentHashMap` hash order. Keep this only if no consumer assertion depends on the hash order. If one does, record it and either emulate it for that case or have the consumer WP adjust the assertion with a reviewer's agreement.
- **S3, a non-blocking `on_connected_check`:** Kotlin blocks the thread inside the `connected` getter (`Reconnect:583`). Propose a hook that may block only on a vendor-runtime worker thread, documented as test-only, with the 5.5b test using a `std` rendezvous and a timeout. The other option is an async check point, which would change the frozen sync `connected()`. That is not proposed.
- **S4, no in-process rsync:** `WorldFileBridge` copies directly inside `VirtualFs`, and rsync wire behaviour stays covered by the SSH path (4.3, 0.4a).
- **S5, recorded argv only:** `FakeSimulatorWorker` records argv only. `timeout`/`env`/`workdir` are not recorded unless a consumer test reads them; `FakeCommandExecutor` already records the timeout.

## Open questions for the orchestrator

1. **Dependency gap.** 4.5b (4 rows), 4.8 (4) and 4.10b (18) port Kotlin tests that construct `FakeSimulatorWorker` (`StartupPhasesTest`, `SkipCopyingDerivedDataTest`), but none of them depends on 5.1 in PLAN §7. 5.1 depends only on 4.4 and 0.4b, so it can land first. Recommendation: add 5.1 as a dependency of 4.5b (4.8 and 4.10b inherit it through 4.10b → 4.5b and 4.8 → 4.10b). The other option is to move those 26 rows to 5.2, but `SkipCopyingDerivedDataTest` is plainly 4.10b's subject. The matrix assignment is otherwise right: no rows belong to 5.1.
2. **Placement.** Use `marathon-test-support` (PLAN §4.1, recommended) or the `marathon-ios` `test-support` feature (4.1 decision 5's pattern for `FakeCommandExecutor`). `WorldExecutor` needs `fake-worker` (with tokio "full" and russh) as a dependency. Keeping that out of a product crate's feature graph argues for `marathon-test-support`.
3. **Ownership of the fake-worker seam.** Deliverable 3 changes `server.rs` in a tool that 0.4b validated against Kotlin. Is a semantic replay of the four scenarios enough evidence, or should 5.1 also run them again with `--update` against the reference CLI and show the evidence diff is empty except for run IDs?
4. **World profile.** Should `WorldExecutor` also be able to load the Kotlin test profile (Xcode 16.4, iOS 18.6), so a 5.x test can switch backends without changing its expectations? Recommendation: no. The two profiles stay separate, and the world keeps 0.4b's measured Xcode 27.1 profile.
5. **Hook error type.** `before` returns `VendorResult<Option<CommandResult>>`, and raised errors carry a Kotlin class name (`Failure`). Should `marathon-test-support` provide constructors for the four classes the consumers use (`ConnectionException`, `TransportException`, `IOException`, `CancellationException`), or should each test build its own `Failure`?

## Acceptance and gates

1. **Contract tests for `FakeSimulatorWorker`**, one per behaviour above:
   - every built-in answer and its exit status, including `Invalid device: device`/148 and `unsupported command`/1;
   - the precedence of `session` over `before` over the built-in answer, with recording happening first in all three cases;
   - a `before` error that propagates with its class, and `safe_execute` classifying `ConnectionException`;
   - two connections sharing `simulators`: a `create` on one is listed by the other;
   - `connected=false` still answering, and `on_connected_check` running on every read;
   - the counters, including `lists`/`worker_fact_commands` across a mixed sequence;
   - the inventory parsed by the 4.4 production simctl list parser, giving the expected devices, availability and runtime grouping;
   - hooks swapped while commands are in flight, with no deadlock and no lock held across an await.
2. **`WorldExecutor`**: the 0.4b Apple contract tests also pass in process. Two worlds stay independent. A long-running session is terminated and killed, and joins. Background/pidfile and device-log jobs are stopped through `SignalPid`, with `active_processes: []` at the end. `WorldFileBridge` push/pull round-trips bytes and modes in `VirtualFs`. A raw rsync fails explicitly.
3. **Equivalence**: each catalogue form that is supported and reachable without uploaded products returns the same `CommandResult` through the merged 4.4 wrappers, both in process and through the loopback SSH fake worker with the 4.2 executor. The test is generated from the catalogue, not hand-listed.
4. **The generalised gates**: a world with two non-baseline UDIDs completes a discovery and batch session for each through `WorldExecutor`, with independent preferences, recording and destinations. The four recorded scenarios replay unchanged, and `cargo test -p fake-worker` and `python3 -I tools/fake-worker/test_apple_evidence.py` pass.
5. **Code rules**: each module starts with `//! Port of vendor/vendor-apple/ios/src/test/kotlin/com/malinskiy/marathon/apple/ios/device/FakeSimulatorWorker.kt`. `WorldExecutor` names the 0.4b world it adapts. There is no `unwrap`/`expect` on I/O, and no blocking call on the core executor.
6. **Rows and docs**: no parity rows change (there are none for 5.1). If question 1 is approved, PLAN §7 gains the dependency. Write `docs/wp/5.1-findings.md` with the decisions taken, the fake-quirks table, the hash-order check (S2), the replay commands and results, and an **Incidental bugs** section in the `docs/found-bugs.md` format (say "none" if there are none). Update `docs/design/apple-world.md` for the generalised gates and the in-process seam.
7. **Gates**: run `scripts/check.sh` and report its exact result. The orchestrator runs `scripts/remote-check.sh` before merging and coordinates the cross-family and same-family reviews. Make focused commits with the CLAUDE.md trailer; no push and no merge.
