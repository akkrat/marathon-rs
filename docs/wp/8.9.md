# WP 8.9: A maintained serde YAML library instead of the Jackson YAML emulation

Effort **M**. Branch `wp/8.9-yaml-writer`, based on `main` after WP 8.7 (commit `108d9c57`). WP 8.8 is in
flight in parallel; whichever merges second rebases.

## Why

Phase 8 removes Java emulation while keeping the contract in PLAN.md §3.12. YAML output is still written
by `jcompat::writers::JacksonYamlWriter` (`crates/jcompat/src/writers/yaml.rs`, a port of Jackson 2.17
`YAMLGenerator` over the SnakeYAML 2.2 emitter) from hand-built `WriterValue` trees with Java number
spellings (`JavaNumber`). Two production uses:

- `marathon_core::report::projection::parse_results`: the `marathon parse` result file (a result file:
  §3.12 point 3, compared as parsed data).
- `marathon_config::render::serialize`: `ConfigurationFactory.serialize`, the configuration as
  Marathonfile YAML that the loader must parse back to an equal configuration (find its callers and
  tests; `examples/corpus.rs` and `tests/serialization.rs` use it).

WP 8.4 moved JSON to serde; this WP does the same for YAML.

## Library

Use a canonical, maintained serde YAML crate. `serde_yaml` is archived (2024) and `serde_yml` is
unmaintained; do not use either. Candidates:

- **`serde-saphyr`** (serde over the safe-Rust `saphyr` parser/emitter; the replacement RustSec's
  advisory points to). The default choice.
- **`yaml_serde`** (the YAML organization's maintained fork of `serde_yaml`; libyaml-derived unsafe
  code). The fallback if `serde-saphyr` cannot meet the requirements below.

Check both on crates.io for the current version, release activity and licence, and record the choice and
why in the design note. Pin an exact current version. Only serialization is in scope: **the Marathonfile
reader stays our `snakeyaml` port** (§3.12 point 1, YAML 1.1 input).

## Requirements on the output

1. **Same data.** `parse` output and serialized configurations parse to the same data as today: same key
   order, same null-versus-missing (Jackson `NON_NULL` omits nulls where it does today), integers stay
   integers, floats stay floats (a re-spelled float such as `1.0E10` vs `1.0e+10` is fine where the value
   is equal), strings stay strings.
2. **YAML 1.1 safe.** Readers of these files include YAML 1.1 parsers (our own loader, SnakeYAML, PyYAML).
   Any string that a YAML 1.1 parser would read as another type must be quoted: `yes`/`no`/`on`/`off`/
   `y`/`n` in any case, `~`, `null`, numbers with leading zeros or `_`, sexagesimal `1:20`, `.inf`,
   timestamps, `<<`, and so on. If the library quotes only for YAML 1.2, add a small string serializer
   wrapper that forces quoting for these (a documented list), rather than post-processing text.
3. **Round trip.** `serialize` followed by our loader gives an equal `Configuration` for every config in the
   corpus (`fixtures/configuration/**`, the config corpus golden inputs). Add a property test over strings
   (random, plus the YAML 1.1 hazard list, plus multi-line, leading/trailing spaces, unicode, control
   characters) that round-trips `parse_results`-shaped data and configuration strings through our loader.
4. Multi-line strings, empty collections, and special floats (NaN, ±infinity) are written so our loader
   and a YAML 1.1 parser read the same value back. Find what today's writer does on each path that can
   carry them and keep that data.

## Scope

1. Derive `Serialize` structs (or use the library's value type where the shape is dynamic) for the two
   outputs, in the current key order.
2. Delete `JacksonYamlWriter`, the YAML-only parts of `writers`, `WriterValue` and `JavaNumber` once
   nothing uses them, and `LICENSE-SNAKEYAML` under `writers/` if no SnakeYAML-derived code is left there
   (the `snakeyaml` crate keeps its own licence). `KotlinValue` (Kotlin `toString` rendering) stays: it is
   a separate later candidate; move it if its module goes away.
3. `projection.rs` number formatting that only existed for `JavaNumber` goes with it.

**Out of scope:** the Marathonfile reader, `KotlinValue`, JSON writers, any other output.

## Goldens

The gate compares YAML results as data. Native goldens and the config corpus golden must pass
**unchanged** (no re-bless): `git diff 108d9c57 -- fixtures/` empty. If a golden fails, the data changed:
fix the code. If you believe a change is a JVM artefact the contract allows dropping, stop and report.
No D-row is expected.

- Keep `//! Port of ...` headers and comment density; delete comments that only explained Jackson
  spelling.
- No `unwrap()`/`expect()` on I/O, process or network results; serialization errors propagate.
