## Deliverables and boundary

In `crates/marathon-dex` (today a 3-line stub, no dependencies):

1. **DEX reader** (dex `spec/` package): header/magic/endian validation, string/type/proto/field/method ids, class defs and class data, annotations directory/sets/items, `EncodedValue` decoding, LEB128. Only the sections discovery actually reads must be materialised, but offsets and counts are validated exactly where the Kotlin reader validates them (below) — a malformed file must become an error, never a panic, an out-of-bounds read or an unbounded allocation (CLAUDE.md: no `unwrap()`/`expect()` on I/O-shaped input; a DEX file is untrusted input).
2. **JUnit3/4 discovery** (dex `parser/` package): `find_test_methods(apk_path, custom_annotations) -> Result<Vec<TestMethod>, DexError>` mirroring `DexParser.findTestMethods` (`DexParser.kt:84-95`), with `TestMethod`/`TestAnnotation`/`DecodedValue` mirrors. Marathon calls it with the default empty custom-annotation list (`A/DexTestParser.kt:21`); the parameter stays because the external tests exercise it. The Clikt CLI/`main` in `DexParser.kt:29-62` is not ported (proposal P6). Discovery is synchronous CPU+file work; it runs off the core executor, and the `LocalTestParser` adapter (item 4) is where async begins.
3. **AXML + `ApkParser` + `InstrumentationInfo`**: a binary-XML reader covering what `ApkParser` drives (string pool, start tags, attribute names and string values), and `parse_instrumentation_info(apk)` / `parse_app_package_name(apk)` returning a 3-field `InstrumentationInfo` (`application_package`, `instrumentation_package`, `test_runner_class`, `A/InstrumentationInfo.kt:3-7`). Field order matters: Kotlin's locals are swapped relative to their names (`testPackage` holds the manifest `package`, `appPackage` the `targetPackage`, `ApkParser.kt:39-42`) and the constructor call at `:60` un-swaps them — port the result, not the local names.
4. **`DexTestParser` adapter → frozen core types.** `A/DexTestParser.kt` is a `LocalTestParser` (`crates/marathon-core/src/vendor.rs:76-78`: `extract(context) -> VendorFuture<Vec<Test>>`). It needs `VendorConfiguration.AndroidConfiguration` + `testBundlesCompat()` and `AndroidTestBundleIdentifier.put` — none of which is 6.4's (config slot in 2.3a, identifier and bundle in 6.5; `crates/marathon-config/src/schema.rs` still has `AndroidConfiguration` as an unconstructible slot). Recommended split, subject to open question 1: `marathon-dex` stays a vendor-independent leaf (0.6) exposing dex-local types; the `toMetaProperty` conversion (`DexTestParser.kt:47-67`) and the `LocalTestParser` impl land in `crates/marathon-android`, which already depends on both `marathon-dex` and `marathon-core`. Whoever hosts it, the conversion constructs exactly what model-contract.md froze: top-level scalars unboxed to the corresponding `MetaValue` (String/Type/Enum all become `MetaValue::String` — the distinction survives only inside arrays), top-level `DecodedNull` → `MetaValue::Null`, top-level array → `MetaValue::Array(Arc<MetaArray>)` with `jvm_class = "[Lcom.linkedin.dex.parser.DecodedValue;"` and every element a `MetaValue::Decoded(DecodedWrapper)`, never recursively unboxed (C28).
5. **`MetaValue::Object` reachability audit** (0.6 decision D2): enumerate every `MetaValue` producer in the merged tree (this WP, 6.3's `TestAnnotationParser` — strings only, Apple parsers) and state in findings whether `Object` is unreachable. Removing the variant is a core change touching 3.3/3.9 projections; do it only if the orchestrator approves (open question 4), otherwise leave the variant and record the audit result.

**Not 6.4:** `AndroidTestBundle`, `AndroidTestBundleIdentifier`, `testBundlesCompat()`, vendor wiring and local/remote parser selection (6.5, behind 0.6 `VendorServices`); the remote parser `AmInstrumentTestParser` and everything over adb (6.6a, consuming 6.3's parsers — a different producer of the same `MetaProperty` type; do not unify); Android config schema fields (2.3a); annotation filtering (3.3), raw/JSON report projection of wrappers (3.9b, C19); APK signing, resources.arsc, split-APK discovery semantics (Kotlin discovery reads only `testApplication` — `splitApks` is carried in the bundle and ignored here, keep it that way); any general-purpose DEX disassembly.

## Behaviours to reproduce (with sources)

### APK/DEX reading (`DexParser.kt`, `spec/`)

- **Entry selection and order.** `readDexFiles` (`DexParser.kt:97-106`) streams the APK with `ZipInputStream` in archive order and keeps every entry whose name `endsWith(".dex")` (case-sensitive, any directory, `classes2.dex` included). Order is observable: JUnit4's `associateBy(className)` keeps the last duplicate class, and JUnit3 discovery is order-sensitive (below). Use the workspace `zip` crate (PLAN §4.2) but preserve archive order; do not sort entries. No dex entries ⇒ empty result, no error. Missing/unreadable APK ⇒ the `FileInputStream` failure propagates unwrapped out of `DexTestParser` (no try/catch in `DexTestParser.kt`); in Rust it becomes `VendorError::TestParsing(Failure)` at the adapter, with the Kotlin exception class name preserved in `Failure.class` (open question 5).
- **Header validation is thin.** `DexFile` init (`spec/DexFile.kt:31-44`) parses header then string/type/proto/field/method ids and class defs at header offsets/sizes, little-endian. `validate()` checks only the magic and `endianTag == 0x12345678` (`spec/HeaderItem.kt:61-68`). The magic check (`spec/DexMagic.kt:22-34`) requires `dex\n`, then version bytes `'0'`, `'3'`, and third byte `>= '5'` as a signed-byte comparison, then `0x00` — so DEX 035–039 pass, DEX 040 is rejected, and so is anything newer marathon's users might already build with. Keep the rejection (it is what the JVM parser does on the same input) and pin it with a test; relaxing it is proposal P3's neighbour, not a silent fix. Checksum, signature and `fileSize` are parsed and never verified.
- **Strings.** Every name/value read goes through `ParseUtils.parseStringBytes` (`parser/ParseUtils.kt:52-62`): skip the ULEB128 utf16-size (parsed, unused), read bytes to the terminating `0x00`, then `String(bytes)` — the JVM default charset (UTF-8 since JEP 400 on the reference JDK), **not** DEX MUTF-8. Supplementary characters (MUTF-8 surrogate-pair encodings) and encoded NULs therefore decode differently from a spec-correct MUTF-8 reader. This is observable in annotation string values and in exotic identifiers. Reproduce it until proposal P1 is decided; whichever way it goes, store results as `JavaString` (UTF-16) exactly once, at decode.
- **Encoded values.** `EncodedValue.create` (`spec/EncodedValue.kt:55-86`) splits `valueArg` (top 3 bits) and `valueType` (low 5 bits); unknown type ⇒ `DexException("Bad value type: …")`. Short/char/int/long and the index types are read through `getPaddedBuffer`, which zero-pads missing high bytes — including for the *signed* types, where the DEX spec sign-extends; float/double go through the mirrored right-padding helper. Port the helpers as written first (negative annotation values are the witness case), generate a JVM oracle probe for a negative short/int/long annotation value, and only then judge proposal P2. `VALUE_BOOLEAN` is `valueArg == 1` exactly (`:82`), other nonzero args decode as false.
- **Unsupported values become null.** `DecodedValue.create` (`parser/DecodedValue.kt:40-73`) maps `EncodedField`, `EncodedMethod` and `EncodedAnnotationValue` (the three `// TODO`s) through `else -> DecodedNull`. A nested `@Nested(...)` annotation value therefore surfaces as null — top-level `MetaValue::Null`, or a `DecodedNull` wrapper inside an array — never as a nested `MetaProperty`. Keep; do not "complete" the TODOs. This is also why no DEX input can produce `MetaValue::Object` (item 5).

### JUnit4 (`parser/JUnit4Extensions.kt`, `TestMethod.kt`, `AnnotationUtils.kt`)

- **Candidate methods are virtual methods only.** `findMethodIdxs` (`parser/DexFileUtils.kt:8-27`) walks `virtualMethods` with cumulative `methodIdxDiff`; `directMethods` (private/static/constructor) are never candidates, for JUnit3 either. A `private @Test` method is invisible to marathon. `classDataOff == 0` ⇒ no methods.
- **Test = annotated method whose merged annotations contain `org.junit.Test`** (or a custom annotation). Merged = class-level annotations first, then method annotations (`TestMethod.kt:52-61`), and `containsTestAnnotation` (`JUnit4Extensions.kt:72-81`) checks the merged list — so a class-level `@Test` would promote every annotated method. Only methods present in the annotations directory's `methodAnnotations` are considered at all (`:88-95`). Method-annotation lookup matches by whole `MethodIdItem` equality, not index (`AnnotationUtils.kt:47-56`).
- **Inheritance.** Interfaces are excluded from the class map entirely (`filterNot isInterface`, `JUnit4Extensions.kt:46`); abstract classes are mapped but produce no tests of their own (`isConcrete` filter, `:29`). Each concrete class recursively unions: inherited superclass tests renamed to the subclass, with parent annotations dropped when the child class redeclares the same annotation name; overridden methods keep only `@Inherited`-marked superclass annotations plus their own (`:106-165`). `inherited` is determined per DEX file: the annotation class must be defined in the *same* dex and carry `Ljava/lang/annotation/Inherited;` there (`AnnotationUtils.kt:80-95`, `spec/DexFile.kt:46-64`). The recursion is memoised with `getOrPut` but has no cycle guard, and `getSuperclassName` (`JUnit4Extensions.kt:101-106`) indexes `typeIds[superclassIdx]` with no `NO_INDEX` (−1) check — both are crash shapes on malformed input that Rust must turn into `DexError` (P3), with the JVM failure class recorded.
- **Names.** `formatDescriptor` (`parser/FormatUtils.kt:19-26`) strips the leading `L` and trailing `;` and turns `/` into `.` — blindly: a descriptor that is not `L…;` loses its first and last characters. Test name is `<formatted class>#<method>` (`TestMethod.kt:58-61`); results are sorted by `testName` only (`Comparable` in `TestMethod.kt:12-14`, applied three times in `DexParser.kt:91-94`), and JUnit3+JUnit4 duplicates of the same method are both kept.

### JUnit3 (`parser/JUnit3Extensions.kt`)

- Fifteen hard-coded SDK root descriptors (`:18-34`, `junit/framework/TestCase` and the `android.test.*` cases). A class matches if its **direct** superclass descriptor is in the growing descriptor set; matching classes add their own descriptor (`:76-98`). Discovery recurses over the dex list dropping the last file each round (`:44-66`, self-described O(n!)) — the result is a set, so an iterative fixpoint gives the same set (proposal P4); until approved, match the set, and note the algorithm shape need not be copied if the set is proven identical on the corpora.
- Method filter is `testName.contains("#test")` (`:70-73`): no visibility, return-type, arity or abstract-class checks — an abstract `TestCase` subclass's `#test…` virtual methods are reported as tests of the abstract class itself. Keep.

### Marathon layer (`A/DexTestParser.kt`, `A/ApkParser.kt`)

- `extract()` (`DexTestParser.kt:18-45`) flat-maps `testBundlesCompat()` in order (configured outputs, then the legacy single output, `ConfigurationExtensions.kt:53-67`), calls `DexParser.findTestMethods(bundle.testApplication.absolutePath)` per bundle, registers each test against a freshly constructed `AndroidTestBundle` copy, and splits the name: `split("#")` must yield exactly 2 parts or `IllegalStateException("Can't parse test $testName")` (`:29`); package is everything before the **last** `.` of the class part (`""` when none), class the remainder (`:34-38`).
- `toMetaProperty` (`DexTestParser.kt:47-67`) unboxes only the top level per kind, in the order written; `DecodedArrayValue -> value.values` hands over the raw `Array<DecodedValue>` (C28/C19 — the `MetaValue::Array` construction in item 4). The values map is `mapValues` over the parser's insertion-ordered map; duplicate element names keep the first position with the last value, which `MetaMap::insert` already gives. `TestAnnotation.inherited` is dropped here — `MetaProperty` has no such field.
- `ApkParser` walks the AXML pull parser from `parser.type` (START_DOCUMENT) to END_DOCUMENT, reading attributes only on `manifest`/`instrumentation` start tags by **local name** (`package`, `targetPackage`, `name`; namespaces ignored), last occurrence wins (`ApkParser.kt:28-50`). `checkNotNull` order is runner, test package, app package with messages `"Could not find test runner class."` / `"…test application package."` / `"…application package."` (`:52-54`) — these are `IllegalStateException`s and are **not** wrapped. Relative runners: leading `.` ⇒ `testPackage + name`; no `.` at all ⇒ `"$testPackage.$name"`; otherwise verbatim (`:57-61`). Only `IOException` is caught and rethrown as `RuntimeException("Unable to parse test app AndroidManifest.xml.", cause)` (`:62-64`) — in `parseAppPackageName` too, whose message still says "test app" (`:99-101`, copy-paste; keep the wording, §3.10 is about our own text, and this string reaches logs). A missing `AndroidManifest.xml` entry makes `getInputStream(null)` throw outside the `IOException` catch. `parseAppPackageName` breaks out of the attribute loop on first `package` but keeps scanning the document (`:84-95`). Note the `ZipFile` is never closed in either method (only the entry stream is, `:65-67`) — a JVM handle leak with no observable output; do not reproduce the leak, do not add a bug row for it without reviewer agreement.
- AXML attribute values come from `getAttributeValueString` = string-pool lookup of the raw `valueString` index (`AXMLParser.java:150-152,234`): no typed-value coercion, no resource resolution. A manifest whose `package` is not a pooled string produces whatever index −1 does upstream — probe it (below) rather than inventing TypedValue handling.

Known-bug rows in play: C28 and C19 are reproduced by construction (item 4) and should move to `confirmed` with Rust test names when the corresponding tests land. Anything new found in dex-test-parser/axmlparser behaviour (e.g. the zero-padding under P2, if the probe confirms it) gets a `docs/found-bugs.md` entry via findings' "Incidental bugs", not a `known-kotlin-bugs.md` row — that file is for marathon's own code.

## Proposed simplifications (pragmatic parity — for orchestrator approval, **not decided**)

Per the user's direction: few users; do not emulate quirks only exotic inputs reach. Until approved, the behaviours above stand and a divergence is a bug. Each approved item becomes a PLAN §3.11 / deviations entry and its probe/fixture expectations are marked, not deleted.

- **P1, MUTF-8.** Decode DEX strings as proper MUTF-8 into `JavaString` instead of reproducing `String(bytes)` default-charset decoding. Diverges only for supplementary-plane characters and encoded NULs in identifiers/annotation strings — where the JVM parser's output is mojibake that then fails downstream matching anyway.
- **P2, sign extension.** If the JVM probe confirms zero-padding of signed `EncodedShort/Int/Long`, sign-extend per the DEX spec instead of reproducing it. Diverges only for negative annotation values encoded in fewer bytes (e.g. `@IntRange(from = -1)`), which today filter/report as large positives.
- **P3, malformed-input hardening as one error shape.** Checked offsets/counts, `NO_INDEX` superclass, inheritance cycles, negative sizes ⇒ one `DexError`/`TestParsing` failure instead of reproducing which of `DexException`/`BufferUnderflowException`/`ArrayIndexOutOfBoundsException`/stack-overflow the JVM happened to throw, or its message. Accept/reject stays identical on well-formed files; §3.10 already allows our wording — this proposal is only about not taxonomising JVM crash classes per offset.
- **P4, JUnit3 fixpoint.** Replace the O(n!) drop-last recursion with an iterative descriptor-set fixpoint, proven set-identical on the fixture APKs. No observable difference on any input; listed because it changes worst-case behaviour on many-dex APKs from "effectively hangs" to "finishes".
- **P5, AXML subset.** Port only what `ApkParser` drives (chunk walking, UTF-8/UTF-16 string pools, start-tag names, attribute name/string-value) instead of the full XmlPullParser-shaped surface (namespaces, resource-id map, text events, `ResXmlEncoders`). Unknown chunk types are skipped by size, as upstream does. Diverges only for hypothetical other AXML consumers, of which marathon has none.
- **P6, dead upstream surface.** Do not port dex-test-parser's Clikt CLI/`main`/`findTestNames` convenience wrapper; `find_test_methods` is the only entry marathon and the tests need (external tests' `findTestNames` calls map over `testName` in the test port).
- **P7, `MetaValue::Object` removal.** If the item-5 audit confirms no producer can construct it, remove the variant in this WP (with the 3.3/3.9 projection arms) rather than carrying a dead representation. This is the removal 0.6 D2 explicitly left to 6.4's audit; it is a proposal here only because it edits frozen core types.
