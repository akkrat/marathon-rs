## GitLab pipeline proposal

- **Test:** run `scripts/check.sh` with the pinned Rust toolchain on Linux and macOS, provisioning its declared prerequisites. Report any gate skips (reference checkout absent, unavailable secret), including fork/MR limits. Preserve the existing offline fixtures/oracle checks; do not silently drop tests requiring tools.
- **Build:** native runner per approved target, `cargo build --locked --release -p marathon-cli --bin marathon --target <target>`, then package and smoke the extracted result on that target. Prefer native runners initially (P1); runner selectors/images are deployment variables. Pass one resolved version as `GIT_TAG_NAME`, save version/target/SHA/checksum metadata and the two zips in separate target artifact directories; retain artifacts for two weeks. Reject missing outputs or mismatched embedded versions.
- **Publish:** only authorized release-branch/tag pipelines, after successful test and both target build/smoke jobs. Use GitLab-provided API/project/job-token variables and the selected target namespace (Q1), fail on failed uploads, and publish the exact tested artifacts. MR pipelines can test/build but cannot publish. Keep credentials out of command tracing and URLs in retained logs; no hard-coded registry host, project ID or runner host.
- **Latest:** depend on successful versioned publication of both targets, one resource group, re-read the configured release branch head at execution time; handle failure/stale/matching cases as above. Promote both target files from the same build metadata and expose failure of a partial promotion; do not claim two HTTP uploads are atomic. Tags alone must not move latest. Preserve source semantics until Q2/P3 are decided.
- Do not port `.gitlab-ci.yml:33–49` upstream mirroring/force-push automation, Maven/Sonatype publishing or signing (`Deployment.kt:75–145`); those are not the native zip release channel. Do not change Git remotes or enable a live pipeline in this WP. Document setup for a GitLab project/mirror because the plan's repository is hosted on GitHub.

## Proposed simplifications — orchestrator decision required

These are proposals under the user's pragmatic-parity direction, **not decisions**. Preserve the contracts above until approved; record accepted choices in an Orchestrator decisions section and the findings.

- **P1:** native builds on the two approved architectures, no cross-compile/SDK discovery, universal binaries, installer, updater or additional formats. This avoids a second toolchain surface; macOS runner availability remains a prerequisite.
- **P2:** one release-archive mode with CLI/archive version equality, no emulation of Gradle's non-RELEASE `-SNAPSHOT` mismatch. Restrict archive/publish versions to a documented safe, nonempty path component, rejecting separators/control characters and traversal rather than reproducing Gradle/shell behavior on exotic `GIT_TAG_NAME` values. Preserve direct CLI compilation's existing fallback and verbatim version; boundary validation belongs in release tooling.
- **P3:** use a neutral untagged version suffix or publish only tags, instead of reproducing the source suffix and tag-filter convention. Tag-only publishing would also change branch latest behavior; decide the complete branch/latest policy together, not piecemeal.
- **P4:** require semantic zip-tree/mode/content correctness, with checksums of shipped artifacts; do not reproduce Gradle zip entry ordering, timestamps, compression bytes or generated shell-launcher quirks. Native binary payloads already prevent byte-identical JVM archives.
