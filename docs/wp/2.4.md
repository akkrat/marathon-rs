## Behaviours to reproduce (with sources)

- **Stage (a) order and side effects** (`ConfigurationFactory.kt:54-202`): substitution on the whole text first, outside the wrapper (`:55`); binding failures (`JsonProcessingException`) wrapped as `ConfigurationException("Error parsing config file ${marathonfile.absolutePath}", cause)` (`:200-202`) — `bind_bytes` already does this. Everything the vendor branches throw is **not** caught by that catch and propagates unwrapped with its own class: the two `ConfigurationException`s (`"No android SDK path specified"` `:62`, `"No vendor configuration specified"` `:190`), every bundle `validate()` error (2.3b's classes incl. `ZipException`/`NoSuchFileException`), and `canonicalFile` `IOException`s from `resolveAgainst` (`:211`). The re-extraction side effects of bundle validation (extraction dir deleted first, F20/F25) happen at this stage, on the freshly resolved bundle copy the factory builds (`:80-87,141-148`) — 2.3a's `resolve_bundle` already drops previously resolved paths to match.
- **Tracking merge** (`:192-199`): the result is `false` if the CLI-supplied flag **or** the bound config value is `false`, else `true` — independent per flag, applied after the vendor branch (so an `Empty` rejection precedes it). Kotlin's factory parameters are nullable (`null` = no opinion); `BindingContext` carries plain `bool`s, so `true` must mean "not disabled by the CLI" and the merge is `context && bound`. The three tracking rows in `ConfigurationFactoryTest` pin the combinations; existing test contexts that set both flags `false` are section-level only and must not be copied into whole-config tests.
- **Stage (b) order and exact messages** (`LogicalConfigurationValidator.kt:13-89`): the file's statement order is the precedence when several violations coexist. All nine custom messages verbatim, including the interpolated values (`got $it`, `got $capacity` lives in the 2.3a `validate()`s) and the issue URL in the flakiness/sharding message (`:18-20`). Filtering validation runs before the analytics check, which runs before any vendor `validate()`; execution-mode rules run last. macOS: compare the whole `xcresult.queue` against a default-constructed one and `provisioningConcurrency` against the default (`:50-57`) — any deviation, even a valid-for-iOS one, is the "supported only for iOS simulators" error, while a *below-one* macOS provisioning value reports that same message, not iOS's "at least 1" (its `validate()` never runs, F6).
- **Vendor `validate()` reach** (2.3a/2.3b bodies, called from here): iOS validates `maxBatchesWithoutProgress`, SSH (F18: `FileNotFoundException` for a missing key/known-hosts file keeps its class through the stage-(b) converter — do not flatten it into `ConfigurationException`), worker connection, xcresult queue, threading, then the bundle — cloned, so extraction runs a second time exactly as Kotlin's stage-(a)+stage-(b) pair does (2.3b decision 5; keep the clone, the frozen hooks take `&VendorConfiguration`). Android checks its APK files exist and are regular files (`VendorConfiguration.kt:86-105` absolute-path messages). Stub/Empty do nothing at stage (b) (`else -> Unit`, `LogicalConfigurationValidator.kt:60`).
- **`toMap()` rendering** (`Configuration.kt:55-80`): data-class `toString()` is `Name(field=value, …)` in constructor order with Kotlin property names; collections `[a, b]`, maps `{k=v}` in iteration order, `Regex` renders as its pattern, `File` as its stored path (only `outputDir` is made absolute), enums as their names, `Duration`/`Instant` ISO, doubles via Java `Double.toString` (jnum). Set-typed fields render in the stored first-seen order (2.3a P7: Kotlin's `HashSet` order is unspecified — there is nothing to match). Two approved divergences land here and must be visible, not hidden: dropped `null` filter-`values` elements (D9 narrowed S4) do not appear where Kotlin shows `null`, and map keys are the binder's `String`s (a surrogate-carrying key was already rejected at bind under D9, 2.3a findings). No Kotlin test pins `toMap()` output — see oracle evidence below.
- **Round trip** (`ConfigurationSerializationTest.kt:65-104`, `TimeoutConfigurationTest.kt:67-71,93-97`, `XcresultQueueConfigurationTest.kt:85-92`): parse → serialize → write to a *different* directory → parse again through the full loader → equal. The second parse re-runs everything (bundle re-extraction against the already-resolved absolute paths, SDK environment lookup again, `pull` → `pullingPolicy` again since `pull` stays in the config). Equality is 2.2's ordered full-field equality, so the serializer must emit set-typed fields in stored order and the binder's duplicate-collapsing keeps it stable; comparisons against *Kotlin* (config-dump, 2.6) remain order-insensitive for sets (2.3a P7 hand-off). The queue round-trip row serialises a lone `XcresultConfiguration` through a bare mapper and asserts on the YAML text (`workerCapacity: 8` present, no `effectiveWorkerCapacity`) — the projection must be usable at section level, not only for a whole `Configuration`.
- **Serializer details the bind side will notice:** polymorphic `type` values are the registered `@JsonSubTypes` names (for iOS, whichever name Jackson picks for a class registered under several — witness it, don't guess); singleton objects and the empty vendor class serialise as empty objects plus `type` where polymorphic; enum spellings follow `@JsonProperty` where present; `File` writes its path string as stored. Nulls are omitted (`NON_NULL`), which is safe only because missing and explicit-null bind differently per field — check the nullable fields where an omitted key would rebind to a default instead of `null` (the explicit-null queue `workerCapacity` row is the canary: it must rebind to the defaulted configuration Kotlin produces, whatever Kotlin does — its oracle, not our intuition, decides).
- **Errors are values, off-core:** no `unwrap()`/`expect()` on I/O, process or filesystem results (CLAUDE.md); binding/extraction/canonicalisation block, so the impls must be callable from an off-core task without holding anything across an await, and the loader must not call `post_process` twice (model contract).

## Proposed simplifications (pragmatic parity — for orchestrator approval, **not decided**)

Until one is approved, the behaviours above stand and a divergence is a bug. Each approved item follows the D9 pattern (deviation recorded, corpus rows marked, not dropped).

- **P1, serializer fidelity:** round-trip-sufficient, not byte-exact. Emit through 1.5's `JacksonYamlWriter` with our field order/quoting instead of reproducing Jackson's exact `Configuration` YAML text. No production path consumes `ConfigurationFactory.serialize` output (only tests re-parse it; P3 output is a different type and stays byte-exact in 3.9b), and 2.6 compares configs via config-dump's canonical form, not serialized text. This is most of the effort difference in open question 4.
- **P2, stage-(b) bundle re-extraction:** keep it. (Listed to be explicit: skipping the cloned re-`validate()` when stage (a) already resolved the bundle would save a destructive re-extraction, but the double extraction is a plain, reachable filesystem effect that 2.6 compares — recommend **rejecting** this simplification.)
- **P3, `toMap()` value rendering for exotic content:** reuse the section `Debug`-mirrored masked shapes only where a JVM witness shows `Debug` and Kotlin `toString()` agree; for anything else require a `KotlinValue` projection — i.e. no blanket "render via `Debug`" shortcut, but no hand-verification of every leaf type either; the witness set above bounds the work.
- **P4, error `path`/`span` for stage-(a)/(b) post-binding errors:** leave them empty (the free functions and `validate()`s have no node context), keeping only stage, class, message and causes exact. Config-dump prints class/message/causes; key paths exist only for binding-stage errors, as in 2.1.

## Open questions for the orchestrator

1. **Assignment check (looks right, one caveat).** All 52 rows genuinely need this WP's assembly or serializer; nothing should move out. The caveat is coverage, not ownership: the logical validator's strategy/execution-mode branches and `toMap()` have no Kotlin tests at all, so their acceptance rests on the new JVM witnesses above plus Rust unit tests — confirm that is the intended evidence bar (as with 2.1's test-only schemas).
2. **`devices()` and the P2 context.** `bind_devices_bytes` trusts the caller's `BindingContext.profile`; 2.3b carried "WP 2.4's loader must build the P2 context for `devices`". The trait receives `&BindingContext` and `BindingContext` is not `Clone`, so the loader cannot silently rewrite the profile without an API change. Options: (a) document that callers pass a P2 context and assert it; (b) derive an owned context inside `devices()` (needs `Clone` or field-wise rebuild — touches the frozen type). Recommend (b) field-wise: a P1 context reaching P2 silently re-enables Marathonfile-relative `File` canonicalisation (F4), which is exactly the kind of bug the loader exists to prevent.
3. **`LoadError` → `ConfigurationError` mapping at the trait edge.** `BindingFuture` has no room for `LoadError`'s `Substitution`/`NullDocument`/`Worker` variants. Substitution maps cleanly (class from `SubstitutionError::java_class`, stage Parse, model contract). `NullDocument`: Kotlin crashes with an NPE outside the wrapper on `.copy(...)` (`ConfigurationFactory.kt:57,192`) — which class name does the Rust error carry (`java.lang.NullPointerException`?), and does 2.5's exit matrix treat it as a crash (exit 1, "crashed") rather than a config error? `Worker` (binding-thread spawn failure) has no Kotlin counterpart; propose `java.io.IOException` at Parse. Settle all three before 2.5 codes against them.
4. **Effort and P1.** PLAN sizes 2.4 as M, but a byte-exact Jackson serializer for the entire schema (every 2.2/2.3a type, name tables, singleton and alias rules) is the largest single item here. With P1 approved, M stands; without it, treat this WP as H or split the serializer out. Decide P1 at launch.
5. **Where the impls live.** One concrete loader/hooks/validator in `marathon-config` (e.g. a `loader` module) with the CLI constructing it in 2.5 — or does the orchestrator want the types kept separate so 3.10's test-support can substitute a validator? Kotlin hard-codes `LogicalConfigurationValidator()` in `Marathon.kt:63`; recommend concrete types in `marathon-config`, traits only at the frozen boundary.
6. **F6 status flip.** F6 is `seeded` with "binding test in 2.4": the F6 witness above should flip it to `confirmed` in this WP. Confirm no other seeded F-row is expected to close here (F8/F18 are confirmed already; their staging through the new converters needs regression tests, not status changes).
