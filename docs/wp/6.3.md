## Deliverables and boundary

Three pure, synchronous parsers. No I/O, no async, no sockets, no process work: bytes/lines in, typed events out. They run wherever 6.1/6.5/6.6a call them, off the core executor (`docs/design/lifecycle.md`); keep them allocation-honest but do not invent a streaming framework.

1. **Text instrumentation transformer** in `crates/marathon-adb` (PLAN §4.1: adam's replacement lives there, as the 0.5 server-stub port already does). Port `InstrumentationResponseTransformer` as a stateful `process(&mut self, bytes) -> Option<Vec<TestEvent>>` + `transform(&mut self) -> Option<Vec<TestEvent>>` pair mirroring adam's `ProgressiveResponseTransformer<List<TestEvent>?>`, together with the event model it produces: `TestEvent` (all variants marathon matches on, below), `TestIdentifier`, `Status`, `TokenType` spellings. All text is `JavaString`; metric maps keep insertion order (Kotlin `linkedMapOf`). This is the type-level contract for 6.1 (which feeds it shell chunks) and 6.6a (which consumes the events) — 6.3 does not port the feeding or the consuming side.
2. **`TestAnnotationParser`** in `crates/marathon-android`: `extract_annotations(&TestEnded) -> Vec<MetaProperty>` over the frozen 0.6 `marathon-core` types. Values are `MetaValue::String` (Kotlin's `Map<String, Any?>` holds plain strings on this path; do not stringify through any other variant). Keys go through `MetaMap::insert`, which already gives Kotlin's last-wins-in-place map semantics.
3. **Logcat `-v long` parser** in `crates/marathon-android`: `LogLevel`, `LogCatHeader`, `LogCatMessage`, the stateful `LogCatMessageParser` (`process_log_header`, `process_log_lines`), and `LogcatAccumulatingListener` (`setup`/`finish`/`start`/`stop`). The Kotlin parser takes an `AndroidDevice` it never uses (`getPackageName` is a stub returning `"?"`, `LogcatMessageParser.kt:141-144`); the Rust parser takes no device — 6.5's `LogcatManager` adaptation is a one-line call-site difference, recorded in findings. Do not invent a device trait here to preserve a dead parameter.

**Not 6.3:** `TestRunnerRequest` and `InstrumentOptions` (the `am instrument -w -r …` command construction and transformer selection, adam `TestRunnerRequest.kt:60-121`) — the request is built by 6.6a's `AndroidDeviceTestRunner.prepareTestRunnerRequest` / `AmInstrumentTestParser` over 6.1's shell channels; 6.3 only guarantees the transformer can be driven chunk-by-chunk and finished, as `TestRunnerRequest.convertChunk`/`close` drive it (`TestRunnerRequest.kt:112-120`). The shell v1/v2 transport, framing, feature negotiation and cancellation (6.1); sync/install/framebuffer (6.2); `AmInstrumentTestParser` itself, `ArgumentsFactory`, `TestResultsListener` and friends, the `listener`/`-e log true` arguments (6.6a, PLAN §3.9); `LogcatManager`, `AdamAndroidDevice`, provider and installer (6.5); the `LogcatListener`/`LogcatProducer` interfaces as inventoried (6.6a — see open question 1, they block item 3); DEX annotation extraction (6.4 — a different producer of the same `MetaProperty` type; do not unify the parsers); the fake-adb scenario for remote parsing (backlog in `docs/design/fake-adb-scenarios.md`, owner 6.6a/7.1).

## Behaviours to reproduce (with sources)

### Instrumentation transformer (adam `InstrumentationResponseTransformer.kt`)

- **Chunking/framing.** `process` appends `String(bytes, offset, limit, UTF_8)` to one buffer (:44-45; `Const.DEFAULT_TRANSPORT_ENCODING` is UTF-8), then drains atoms: an atom ends at the first `\n` or `\r` at/after the first occurrence of `INSTRUMENTATION_STATUS_CODE` or `INSTRUMENTATION_CODE` anywhere in the buffer; everything before that line break — including garbage preceding the token — is the atom, split with Kotlin `lines()` (:60-80). No token or no following line break ⇒ wait for more bytes. Events from one `process` call accumulate in order; `null` (not empty list) when an atom yields nothing matters to the caller (`convertChunk` forwards nulls as no emission).
- **Atom dispatch** is on the atom's **last** line only (:102-118): `INSTRUMENTATION_STATUS_CODE` ⇒ status handling over the preceding lines; `INSTRUMENTATION_CODE` ⇒ session end over the whole atom; `INSTRUMENTATION_FAILED` ⇒ finished, no events; anything else ⇒ dropped silently.
- **Parameter maps** (`toMap`, :265-278): non-empty lines rejoined with `\n`, split on `INSTRUMENTATION_STATUS: ` (or `INSTRUMENTATION_RESULT:` for the result atom), each piece trimmed, split at its **first** `=`; pieces with nothing after the `=` are dropped. Multi-line values (stack, stream) therefore survive intact, including embedded `=` signs. `KNOWN_KEYS` = `test, class, stack, numtests, Error, shortMsg, stream, current, id` (:261) are excluded from metrics.
- **Run start.** The first status atom — whatever its code — flips `startReported`; if it carries `numtests`, that becomes `testsExpected` and a `TestRunStartedEvent(n)` precedes any other event from the atom (:134-141). Note `numtests` is read with `toInt()`, not `toIntOrNull()`: a non-numeric value throws out of `process`.
- **Status codes** (`Status.kt:19-47`: 0 SUCCESS, 1 START, 2 IN_PROGRESS, −1 ERROR, −2 FAILURE, −3 IGNORED, −4 ASSUMPTION_FAILURE, else UNKNOWN): SUCCESS/IGNORED/ASSUMPTION_FAILURE/ERROR+FAILURE emit the per-test events exactly as written (:143-202) — `TestEnded(id, testMetrics)` hands over the accumulated metrics map and resets it; IN_PROGRESS only merges non-known keys into `testMetrics` (:160-162), so metrics leak into the next ended test if no end intervenes; ERROR/FAILURE without class/test but with `stack` becomes `TestRunFailing(stream ?: "Unexpected failure during execution", stack)` (:174-176); missing `stack`/id pieces suppress events but **still increment `testsExecuted`** (every branch except START/IN_PROGRESS does, event or not). UNKNOWN is `TODO()` — it throws (see P2).
- **Session end.** `INSTRUMENTATION_CODE: -1` is `Status.ERROR` by value and is the *success* path (:224-240): parse `Time: <double>` seconds ×1000 truncated to `Long` from the result `stream`, metrics = result params minus known keys, emit `TestRunEnded(time, metrics)`. Any other code ⇒ `TestRunFailed(shortMsg ?: "Unexpected INSTRUMENTATION_CODE: $code")` then `TestRunEnded(time, empty)` (:241-256); `shortMsg` is scraped by the fixed prefix `INSTRUMENTATION_RESULT: shortMsg=` and `substring(33)`. Both set `finishReported`.
- **`transform()` at stream end** (:82-100): if `finishReported`, nothing. If no start was ever reported, **prepend** `"No test results\n"` to whatever raw buffer remains, trim, and emit that as `TestRunFailed` — this is how a crashed/missing-listener run surfaces its raw output (adam test `missingListenerTest`, log_13; marathon's 6.6a retry logic string-matches on related errors). If `testsExpected > testsExecuted`, `TestRunFailed("Test run failed to complete. Expected $testsExpected tests, executed $testsExecuted")` (exact wording; downstream logs show it). Otherwise a synthetic `TestRunEnded(0, empty)`. Quirk: neither failure branch sets `finishReported`, so a second `transform()` repeats (and re-prepends) — keep or waive via P3; the dead `if (!startReported)` inside the final else (:92-94) is unreachable and needs no port.

### `TestAnnotationParser` (marathon `TestAnnotationParser.kt`)

- **Version selection is by key presence, newest first** (:8-12): `…TestAnnotationProducer.v4` ≻ `v3` ≻ `v2` ≻ none ⇒ empty list. A present-but-malformed v4 never falls back to v2; the metric values come from `TestEnded.metrics`, i.e. whatever the transformer accumulated — the producer side is on-device code (PLAN §3.9), out of scope. The only production caller is remote parsing (`AmInstrumentTestParser.kt:156`); batch execution ignores annotations.
- **All length arithmetic is in Java UTF-16 code units.** The `<len>L<payload>` framing (v4 :16-28, v3/v4 parameters :66-76/:37-47) counts Kotlin `String` length. Operate on `JavaString` code units throughout; indexing by byte or by `char` silently corrupts non-BMP annotation values. New unit tests must include a supplementary-plane value.
- **v4**: strip surrounding `[`/`]` only if both present (`removeSurrounding`); then repeatedly: digits up to first `L` (non-numeric or missing ⇒ stop, silently), take that many units as one annotation, drop one `,` and leading whitespace (`trimStart()`, Kotlin whitespace). Per annotation: name = up to first `(` (no `(` ⇒ skip the annotation, :31-32); parameters use the same `<len>L` framing; a parameter is kept only if `length > 1 && contains("=")`, split at the **first** `=` (`substringBefore`/`substringAfter`, :44-46). Out-of-range lengths throw `StringIndexOutOfBounds` in Kotlin — uncaught here, caught by 6.6a's parse retry; see P4.
- **v3** (:55-80): annotations found by the v2 regex, parameters by the v4 length framing. There is **no upstream test for v3**; port it and add derived unit tests (reuse the v4 payloads' parameter sections). Note v3/v2 do *not* skip `(`-less matches — the regex guarantees one, and `serializedAnnotation.substring(index)` keeps the `(` for `removeSurrounding("(", ")")`.
- **v2** (:82-101): parameters split on `:` then on `=`; a parameter survives only if the `=`-split has **exactly 2** parts, so any value containing `=` or `:` is dropped wholesale. The regex is N6 (`known-kotlin-bugs.md`): `\p{Graph}+\([^\)]*\)` is not balanced — `a(b(c))` extracts `a(b(c)`; default Java `\p{Graph}` is ASCII (`[!-~]` in jcompat's port), so a non-ASCII annotation name extracts nothing. Already reproduced by `jcompat::regex_patterns::METRIC_ANNOTATION_V2`; use `find_all`, trim each match (Kotlin `trim()`), drop empties. Confirm N6's row and set it `confirmed` with the Rust test once ported.

### Logcat `-v long` (`LogcatMessageParser.kt` and friends)

- **Header grammar** (:76-107): whole-line match (`Matcher.matches()`) of `^\[ (MM-DD HH:MM:SS.mmm) +(\d+): *(\w+) ([VDIWEAF])/(.*?) +]$`, Java ASCII classes; jcompat's `LOGCAT_HEADER` already encodes this — consume its capture groups, do not re-derive the pattern. The timestamp stays a string; **there is no year** — U26: the fake-adb fixture `logcat.txt` carries `[ 2026-10-12 …]` headers, so every line is rejected as a header and (having no previous header) dropped; the parser must reproduce that rejection, and the fixture is never edited. Add a new, correctly formatted stream as a new fixture/test input instead.
- **Stateful line processing** (`processLogLines`, :51-74): empty lines are skipped entirely (so blank lines inside a multi-line message vanish and each following line becomes its **own** `LogCatMessage` under the same header — messages are never joined); a non-header line before any header is dropped (the KDoc's `IllegalStateException` claim is stale — the code `continue`s); `previousHeader` persists across calls, which `LogcatManager.kt:36-40` relies on by feeding arbitrary `lines()` chunks of a hanging `logcat -v long` stream (WP 6.5). The input being `String.lines()` output means `\r\n`/`\r` are already gone at this boundary — 6.5 owns that split; keep this parser line-based like the Kotlin.
- **Field parsing**: pid `toInt()` → −1 on `NumberFormatException` (incl. overflow) (:109-115); tid `Integer.decode` → −1 (:117-124) — decode means `0x`/`#` hex and leading-`0` **octal** are honoured, and a bare hex-looking word (`abc`) fails to −1; priority via `getByLetterString` (first char only) with `F` special-cased to `ASSERT` and any other unknown letter to `WARN` (:134-139, `Log.kt:73-77`) — through the header regex only `VDIWEAF` arrive, so the WARN arm is reachable only by direct calls, but `parsePriority` is a public companion function: port and test it directly. `appName` is always `"?"` (:141-144) — this is observable in every bridged log line (`AdamAndroidDevice.onLogcat` formats `"<ts> <pid>-<tid>/<appName> <letter>/<tag>: <msg>"`, 6.5), so it is parity, not a stub to fix.
- **`LogcatAccumulatingListener`** (:12-19): only tag `AndroidRuntime`, only levels ERROR/WARN, appended as `"<letter>/<tag>: <message>\""` + newline — the trailing `\"` is in the Kotlin string literal and ends up in the "Device log:" warning 6.6a logs (`AmInstrumentTestParser.kt:84`). That is a (previously unrecorded) Kotlin bug: reproduce it and add its row to `docs/known-kotlin-bugs.md` (next N-number) per CLAUDE.md, or waive it explicitly via P6 — do not silently fix it. `start()` clears, `stop()` returns and clears, `setup()`/`finish()` register/unregister; `stop()` is called from a `finally` even after `finish()` (`AmInstrumentTestParser.kt:195,205-207`), so double-stop must yield `""`, not panic.

## Proposed simplifications (pragmatic parity — for orchestrator approval, **not decided**)

Per the user's direction: few users; do not emulate quirks only exotic inputs reach. Until one is approved, the behaviours above stand and a divergence is a bug. Each approved item becomes a `docs/deviations.md` entry.

- **P1, skip the protobuf transformer.** Marathon constructs `TestRunnerRequest` in exactly two places (`AndroidDeviceTestRunner.kt:193`, `AmInstrumentTestParser.kt:126`), neither passes `protobuf = true`, and no config key reaches it — `ProtoInstrumentationResponseTransformer` is dead code in this fork. Porting it costs a protobuf runtime, the generated `InstrumentationData` types, and a temp-file/`MappedByteBuffer` emulation for one adam test. Propose: port the text transformer only; mark the proto test row `n/a` with this reason (reviewer agreement required).
- **P2, unknown status codes.** adam's `Status.UNKNOWN -> TODO()` kills the run with `NotImplementedError` on any unrecognised `INSTRUMENTATION_STATUS_CODE` (or non-numeric value, via `valueOf(null)`). Propose: ignore the atom (still counting nothing) instead of emulating the crash. Diverges only on malformed/future-runner output, where Kotlin crashes the whole batch.
- **P3, `transform()` idempotence.** Propose setting the finished flag in the two failure branches too, so a repeated finish returns nothing instead of re-emitting (and re-prepending `"No test results\n"`). Affects only callers that finish twice; 6.6a's channel close calls it once.
- **P4, annotation length overruns.** v4/v3 lengths beyond the remaining text throw in Kotlin and abort remote parsing into its retry loop. Propose: stop extraction and return what was collected (the framing already stops silently on non-numeric lengths). Diverges only on corrupt producer output; note the observable knock-on: 6.6a would no longer retry in that case.
- **P5, dead `Log` object.** Do not port `Log.mSpaceLine`/its `init` (nothing reads it) or `LogCatHeader`'s Java `hashCode` arithmetic (17/31 chain, enum identity hash — unobservable; Rust `Hash` need only be consistent with `Eq`). Port `LogLevel`, header equality over all six fields, and both `toString` forms, which are observable in logs and `.expected`-style output.
- **P6, accumulating-listener trailing quote.** Propose *keeping* the stray `\"` (it is one character in a warning log users may grep), recorded as a known Kotlin bug; listed here only so the orchestrator can decide otherwise in one place.
