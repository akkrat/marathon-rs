## Additive repairs to the 0.6 freeze — approved in review round 1

No existing method signature was changed or removed. Two missing explicit
cancellation contexts required additions to `runtime.rs`:

1. `Job::cancellation_signal() -> Arc<dyn CancellationSignal>` exposes a request
   before completion. A completion-only callback cannot interrupt the job's own
   delay: waiting for completion there deadlocks. `Job::join_in(caller: JobRef)`
   supplies the caller explicitly and preserves its cancellation reason. The
   original `join()` remains a protected completion wait, useful for cleanup;
   it cannot observe a caller the frozen signature does not supply. There is
   no ambient job or thread-local inference. Downstream cancellable joins must
   call `join_in(context.job.clone())`. The observed-child traversal remains the
   frozen lazy traversal; a caller can race its traversal future with its own
   explicit signal when it needs a cancellable traversal.
2. `VendorTaskBody` and `VendorRuntime::spawn_cancellable(body)` supply the
   worker's own cancellation signal to its body. The original `spawn(future)`
   dispatches the prebuilt future off core and remains joinable. Such a future
   has no argument through which it can receive the newly created task signal;
   cancellation-aware new worker bodies use `spawn_cancellable`. Neither path
   aborts/drops a body to deliver cancellation. Blocking operations remain
   joinable after cancellation and their completion is authoritative.

`tests/contracts.rs::cancellation_aware_runtime_contract` compiles both repairs;
behavioural tests exercise each. These are the only 0.6 trait additions. Review
round 1 approved both additions and Tokio's `rt-multi-thread` feature.
`join`, `cancel_and_join` and observed-child traversal are protected waits;
ordinary cancellable callers use explicit-context `join_in`.

## Runtime and consumer handoff

- `executor::CoreExecutor::run` accepts a Send factory, constructs all Rc state
  on a dedicated `marathon-core` thread, and runs a Tokio current-thread runtime
  plus LocalSet. Its synchronous entry point must be called outside an executor;
  it rejects nesting. The factory can construct non-Send futures/state on core.
- `job`, `spawn`, `spawn_cleanup`, `context`, `clock`, `timeouts`, `vendor`, and
  `vendor_clock` expose the frozen services. One vendor multi-thread runtime is
  owned outside core, so its shutdown never blocks core. Tasks catch panics and
  complete with typed `Failed(Failure)`; timeout bodies do so too.
- Job requests, body completion, child completion and final completion are
  distinct. First failure is retained. Parents own their attached children;
  detached roots and cleanup jobs have no inferred parent. Cleanup receives its
  own context and can explicitly join independently-cancelled operations.
- `RuntimeActor::new(core, parent, clock, handler, label)` creates an owner
  `Job(parent)` and a separate receiver child, and installs `started`
  synchronously before dispatch. `started` receives the owner context; `receive`
  receives the executing receiver context for cancellable suspension. Actor-scoped
  launches use `context.actor.job()` (the owner). Receiver cancellation closes the mailbox without completing
  that owner. The task retains the handler through completion
  callbacks and releases it afterward, even if the actor handle remains alive.
  Own-job callbacks should capture weak self handles, as the contract specifies.
  All cancellable handler waits must use their explicit job/signal (clock delay,
  `join_in`, or the result/channel cancellation-aware wait). Arbitrary futures
  which ignore cancellation remain cooperative, just as non-suspending Kotlin
  code does; the runtime does not abort them and skip their cleanup.
- `SharedDeferred<T>` is parentless; `wait_in(signal)` cancels only that waiter.
  `SharedChannel<T>` is a consuming provider channel; `receive_in(signal)` has
  the same waiter isolation. `core.event_channel(label)` registers a provider
  mailbox automatically. Actor construction also registers its mailbox.
  Low-level `SharedChannel::new` is available for independent channels; when
  used as a replay provider mailbox it must be explicitly registered.
- Actor close discards; provider close drains; provider cancellation also
  overrides a preceding graceful close. Queues are unlimited. No diagnostics or
  backpressure were added.
- `StateMachine<S,E,A>` uses enum matcher closures via `create`/`define`/`on`,
  plus `transition_to`, `dont_transition`, and `on_transition`. It has no await
  inside a transition and returns the action for its caller. New state is
  visible to listeners before notification. Enter/exit hooks are included to
  verify exact notification order. The original BSD notice is preserved.
- `completion_logging::completion_log` is reusable by vendor implementations.
  Core records are emitted only for unhandled failures at their exception
  boundary, once after propagation; normal success and cancellation are silent.
  The reusable three-branch formatter retains level, exact message and typed exception;
  the `logging()` handle is the shared per-run
  `jcompat::logging::MarathonLogging` registry used by VendorDependencies.
  `CompletionLog::render` filters and formats through jcompat on the output executor.
  `take_completion_logs` supplies records for the run's output integration; there is
  no direct core-thread console/file I/O. Final appender wiring belongs to 3.10.
- Scheduler's default remains `join_observed_children().await`; replacing that
  call with `for child in job.children_snapshot() { child.join().await?; }` is
  the isolated alternative. Both share one linked child/callback list; list promotion is retained after
  removals and completion callback registration can promote it. Tests show
  the different attachment outcomes. No Scheduler call site is implemented here.

## Clocks and controlled replay

Live scheduler delay uses Tokio only inside the clock implementation. Core and
vendor clocks share the same timeline. Virtual construction and the reusable
`ControlledReplay` driver are behind the `marathon-core/test-support` feature;
a self dev-dependency enables this feature for the default workspace test gate.

`run_virtual` gives a factory both the core and driver. Use `advance_to` before
an external event and `drain_current` afterward, or `driver.event(at, closure)`
for both boundaries. Equal timestamp events are delivered in call/tape order.
Timers fire at their deadlines, including intermediate deadlines, and never
advance beyond the requested timestamp. Runnable tracking wraps each core and
vendor task and its waker; due timers are released by deadline/registration
sequence one at a time, and vendor continuations and the resulting core bridge
wakes must settle before the next timer is released or a drain returns. Future timers do not stop
quiescence. Open or closed buffered mailboxes do; discarded and drained ones do
not. Driver errors persist through `finish`, including caught failures.

`RuntimeHooks::{live,taped}` implement the same labelled seams. Typed `Tape`
input supports clock modes, explicit per-site reads/draws/IDs, patterned IDs,
object-token identity aliases and live barriers. Missing/exhausted/wrong-type
entries fail without fallback; `verify_consumed` preserves caught failures and
checks unused explicit entries and barriers. An absent barrier script passes
through. Admission cancellation leaves its token unconsumed; only explicit
permit `finish` consumes it. `driver.set_hooks` makes `finish` verify the hooks.

The small JSON reader is only `tests/support/tape.rs`; it reads the real
`tools/oracle/scenario-tape.json` clock/ID subset. General JSON/script validation,
external-event consumption accounting and Rust-versus-patched-Kotlin scenario
comparison remain with 3.10/7.1. This WP makes no end-to-end scenario parity claim.
