# WP 0.3b: YAML spike, the parser and the `Node` design

**Owner:** Opus, medium effort. **Reviewers:** Sol and Muse. **Depends on:** 0.2a (the corpus).

Read first:
- `CLAUDE.md`;
- PLAN.md §3.2 and §4.2 (YAML row), and WP 2.1;
- `docs/research/yaml.md`: the Jackson/SnakeYAML behaviour, the saphyr evaluation and the proposed `Node` design;
- `fixtures/oracle/README.md`, and `fixtures/oracle/yaml-corpus.jsonl`, which holds the JVM ground truth: Jackson token streams and binding outcomes for about 1,344 rows.

## Goal

Decide, with measurements, how marathon-rs turns YAML text into the token stream Jackson would see, and fix the `Node` design that WP 2.1 builds its Jackson-compatible binding on.

## Deliverables

1. **`spikes/yaml-node/`.** A standalone Cargo package, excluded from the workspace. It is a prototype that takes text, produces SnakeYAML 2.2 / Jackson 2.17 tokens, and builds the `Node` tree from `docs/research/yaml.md`. The tree keeps raw scalar text, scalar style, tags, anchors and alias names, duplicate keys and source positions.
   - Base it on `saphyr-parser` (latest 0.2.x). The research note expects a small vendored change so that alias events carry the anchor name; make it, and keep it as a `.patch` file.
   - Implement SnakeYAML's YAML 1.1 scalar resolution exactly, together with Jackson's token mapping: VALUE_NULL for a plain empty value, the int/float/bool/null rules, `!!` tags, aliases surfacing as name strings, `<<` as an ordinary key, a null document, and the limits (3 MiB code points, depth 1000).
   - **Fallback, if saphyr can't be made to match:** a SnakeYAML-compatible scanner of our own. Say how big it would be, and prototype the hard part.
2. **Corpus runner.** For every corpus row, compare the prototype's token stream with the JVM's tokens, and the error class/position for rejected input.
   - Binding rows: implement just enough binding for the corpus's simple target types (string, int, long, double, bool, enum, nullable, list, map) to compare outcomes, including the error class names mapped to a Rust error taxonomy.
   - The mutation rows (`M-*`) over marathon's full `Configuration` are out of scope here (WP 2.6); only their *token* streams must match.
3. **`docs/research/yaml-spike-results.md`**, with the decision at the top:
   - parser choice and exact crate pin, with the vendored patch or the own-scanner plan;
   - the final `Node` design (types and invariants) for WP 2.1's brief;
   - pass rates per corpus family;
   - every divergence, with its cause and fix (or the reason it is acceptable);
   - the error-position and message strategy (PLAN §3.10: Jackson's own wording is not reproduced, but the stage and the key path are).

## Acceptance

- **Token streams:** 100% agreement over all corpus rows. Any exception must be listed and approved by the orchestrator.
- **Binding:** 100% agreement on the simple-target rows.
- `scripts/check.sh` passes; the spike is outside the workspace. Branch `wp/0.3b-yaml-spike`.
