## Deliverables and boundary

In `crates/marathon-core`, in a new `analytics` module (suggested: `analytics/{mod,provider,noop,factory,coverage}.rs` and `analytics/remote/{mod,graphite,influx,influx2}.rs`):

1. **`MetricsProviderImpl`** over an async, Send `RemoteDataSource`. It implements the frozen `wiring::MetricsProvider` and covers:
   - two caches keyed by `MetricsKey`;
   - three attempts with 50 ms between them;
   - failure absorbed into an empty cached measurement, with the original warning and TimingLog line;
   - warn-once per test name;
   - observed durations;
   - coverage;
   - `close` delegating to the data source.
2. **`NoOpMetricsProvider { backend_unavailable }`**, plus the factory (`MetricsProviderFactory`/`AnalyticsFactory`): Disabled gives NoOp, a failed Influx v1/v2 setup gives a warning and NoOp(unavailable), Graphite never falls back.

   - Influx setup is reached through a seam that 3.4b fills (open question 2).
3. **The run-wide memoising facade** that D13 requires (open question 3 proposes its type). It covers:
   - `prefetch(&[MetricsKey])`: off core, idempotent, serialised. Each key is fetched once per run across all pools and the 3.10 call sites. Concurrent callers for a key in flight wait for that fetch and never start another.
   - A `MetricsLookup` view that answers from memory on core. It covers success rate, execution time with the observed-duration fallback, and warn-once logs emitted lazily in lookup order.
   - `observe_execution_times`, which the lookup sees at once, so later batching uses new observations.
4. **`report_execution_time_coverage(config, shard, provider)`**: the port of `ExecutionTimeCoverage.kt`. 3.10 calls it at `Marathon.kt:181`.

## Behaviours to reproduce (with sources)

**Cache, query and failure** (`MetricsProviderImpl.kt`):
- **Separate caches** for success rate and execution time (`:41-42`). The key is a data class `MeasurementKey(key = NaN, limit)` (`:16`): NaN is canonical and the two zeros differ. `MetricsKey` already has these semantics.
- **Success rate** (`:51-78`). Cache miss: the fetch, then `warn(it){"Cannot fetch success rate from database"}` on failure, then the TimingLog line, then the cache entry. The entry is empty on failure, so a failed key is **never re-queried this run**.
- **Execution time** (`:104-123`). The same, with `"Cannot fetch execution time from database"`. On success it first logs `debug { list }`: the whole `List<ExecutionTime>` in Kotlin data-class `toString` form (`[ExecutionTime(testName=…, percentile=5000.0), …]`).
- **Retry** (`:80-84,181-185`, `Retry.kt:8-24`):
  - three attempts with `delay(50)` between them, so two delays;
  - the last error is rethrown into `runCatching`, which catches **every** `Throwable` from the data source, including parse errors (`toDouble`) and mapper errors;
  - lifecycle forbids moving this catch boundary. Cancellation: see P4.
- **TimingLog text** (`:62,112-115,191`). It goes to logger `Timings` at INFO with no "since start" suffix:
  - `Success rate history query (since <Instant>) returned <n> tests in <ms> ms`;
  - `Execution time history query (percentile <Double> since <Instant>) returned <n> tests in <ms> ms`;
  - `failed` replaces `returned <n> tests` on failure.

  `<ms>` is `(nanoTime₂ − nanoTime₁) / 1_000_000` over the labelled monotonic hook and includes the retries. `<n>` counts list elements, duplicates included.
- **Serialisation:** `@Synchronized` on every public method (`:51,87,135,144`). The run-wide provider is shared by all pools.

**Lookup:**
- **Success rate** (`:70-77`). A miss returns `defaultSuccessRate` with `warn {"No success rate found for <safe name>. Using <Double>"}`, once per test name per run (`:179`).
- **Execution time** (`:93-101`). The order is history, then the observed estimate, then `defaultDuration.toMillis()` as a Double. A miss logs `debug {"No execution time found for <name>. Using <expected> ms"}` once per name (`:178`), with the value computed at that first miss.
- **The value maps** come from `associateBy`, so the last duplicate test name wins (`:64,118`).

**Observed durations** (`:47,128-142,197-201`):
- Recorded only if `observedDurationMinTests != null`. Only PASSED and FAILURE results count, and only when `endTime − startTime >= 0` (wrapping Long). Values are appended per safe name in a **LinkedHashMap**.
- **The estimate:**
  1. the test's own nearest-rank percentile: `ceil(p.coerceIn(0,100)/100·n).toInt().coerceIn(1,n)`;
  2. otherwise, if fewer than `minTests` distinct tests are recorded, nothing;
  3. otherwise `average()` of the per-test percentiles **in insertion order**, so the floating-point summation order is part of parity.

  Tests that have history also count toward `minTests` and the mean.

**Coverage** (`:144-176`; `NoOpMetricsProvider.kt:23-32`; `ExecutionTimeCoverage.kt:11-25`):
- The tests are distinct safe names over `shard.tests + shard.flakyTests`. With none, it returns **before** querying.
- Otherwise it queries through the same cache, so this is the first ET query of a run. The message is the INFO line or the WARN line (`withoutHistory·2 > total`), with the two fallback texts and two advice texts given verbatim at `:151-172`.
- NoOp: INFO "analytics is disabled", or WARN "the analytics backend could not be set up", each ending "…so every test is expected to take 0 ms".
- **Which strategies report, in order:**
  1. the FixedSize batching key, only when `durationMillis`, `percentile` and `timeLimit` are all non-null, with usage `"the batch duration limit"`;
  2. then ExecutionTime sorting, `"execution time sorting"`.

**Factory** (`MetricsProviderFactory.kt:20-58`):
- Influx v1 builds `InfluxDBDataSource(db, dbName, retentionPolicyConfiguration.name)`; v2 builds `InfluxDB2DataSource(db, bucket)`. Each is wrapped in `try … catch (e: Exception)` → `warn(e){"Cannot read history from the analytics backend"}` → NoOp(unavailable).
- Graphite: `QueryableGraphiteClient(configuration.host)`, so the configured `port` is **not** used for queries (port 80, `QueryableGraphiteClient.kt:14`).
- Every branch passes all three `defaults` fields.

**Logger names and levels:**
- The names are simple class names, not FQCNs: `MetricsProviderImpl`, `NoOpMetricsProvider`, `MetricsProviderFactory`.
- Each logger is requested in the constructor. In Kotlin that happens while Koin resolves `Marathon` (`Modules.kt:27`), **before** `configureLogging`. By PLAN §3.5 they would then keep DEBUG for the whole run, so the warn-once, coverage and `debug { list }` lines would print even with `debug: false`. Confirm this with the oracle (open question 5).

**Graphite** (`GraphiteDataSource.kt`, `QueryableGraphiteClient.kt`):
- **Paths and nodes.** The paths are `tests.*.*.*.*.*.{success,duration}` with `withPrefix` (`"$prefix.$path"` unless null or empty). The `aliasByNode` index is `1 + (prefix has text ? count('.')+1 : 0)`.
- **Success-rate target.** `aliasByNode(asPercent(summarize(P,'10years','sum',true),summarize(P,'10years','count',true)),N)`, after removing **Java `\s`** whitespace (`:17-28`).
- **Execution-time target.** `aliasByNode(summarize(nPercentile(P, <Double>), '10years', 'average', true), N)`, with its spaces kept (`:40`).
- **Request.** `http://<host>:80/render?target=<URLEncoder.encode UTF-8>&format=raw&from=<format_graphite>`, with 60 s connect, read and write timeouts. The body is split on `\n` and empty lines are dropped. A null body gives an empty list.
- **Line parsing.** The name is `substringBefore(',')` with `--` replaced by `.`. The value is Java `toDouble` of `substringAfter('|')`, divided by 100 for the success rate. `None` or several datapoints make the **whole query** fail; see the candidate bug rows below.

**InfluxQL** (`InfluxDBDataSource.kt:35-72`):
- The `trimIndent` text is `SELECT MEAN("success")` / `SELECT PERCENTILE("duration",<Double>)` + `FROM "<rp>"."tests"` + `WHERE time >= '<Instant>'` + `GROUP BY "testname"`, on database `dbName`. The policy name and the limit are interpolated unescaped.
- **Mapping** (influxdb-java 2.24 `InfluxDBResultMapper.toPOJO`):
  - an error result throws;
  - only series named `tests` are read;
  - `testname` comes from tags and `mean`/`percentile` from columns;
  - rows with a null in either are dropped.

**Flux** (`InfluxDB2DataSource.kt:29-66`):
- **Exact text.** The success-rate query's first line has no indentation, so `trimIndent` strips nothing and the `|>` lines keep their 14 leading spaces. The execution-time query starts on a new line and is dedented to 2 spaces.
- **Interpolated values.** `range(start: <limit.epochSecond>)`; `quantile(q: <Double.toString(percentile / 100)>, …)` (e.g. `0.9990000000000001`).
- **Mapping.** `testname` and `_value`, dropping nulls.

## Proposed simplifications (pragmatic parity: for orchestrator approval, **not decided**)

Until one is approved, the behaviours above stand. Each approved item becomes a findings entry (or joins D13, or a new D-row if it changes externally visible behaviour).

- **P1, influx result mapping.**
  - Kept: the series-name filter, error → failure, and null-row dropping.
  - Not emulated: influxdb-java's reflection type quirks, such as the `ClassCastException` on non-Double numerics or `time` handling, nor FluxResultMapper's per-type conversions.
  - Numeric values are taken as f64, and anything else fails the query (absorbed). Real servers send doubles here.
- **P2, Graphite encoding inputs.** Require a UTF-8 `host` and `prefix`; a lone surrogate fails the query instead of reproducing `URLEncoder`'s `?` replacement. This follows D9's key/path rule.
- **P3, factory catch width.** Every setup failure falls back to NoOp(unavailable). Kotlin's `catch (e: Exception)` lets JVM `Error`s escape, which only OOM-like conditions reach.
- **P4, cancellation during a fetch.**
  - Kotlin's `runBlocking` cannot be cancelled: the fetch finishes, logs and caches.
  - Rust: a cancelled prefetch returns `Cancelled`, logs nothing, caches nothing, and the next caller fetches afresh.
  - This is reachable only when the run is aborted during queue construction.
- **P5, serialised lookups.** Kotlin's `@Synchronized` makes a lookup or `observe` wait for an unrelated in-flight fetch. In Rust, lookups read memory and never wait. Only timing changes, never values or log order.

1. **Parity assignment: 10 of the 41 rows look misassigned.**

   - Also: port `shouldReturnNoopProviderWhenConfigurationIsInvalid` here against a setup seam that fails the way influxdb-java does for host `"host"`. 3.4b then adds the same assertion over its real setup.
2. **The client boundary with 3.4b.** The inventory gives 3.4a the data sources and `QueryableGraphiteClient`, and 3.4b the providers. Recommend:
   - **3.4a**:
     - all of `QueryableGraphiteClient`, bringing `reqwest` into `marathon-core`: it is self-contained, and the factory test needs it to fail on `"not a host"` without network;
     - both Influx data sources over two narrow async transports: InfluxQL `query(command, db) -> QueryResult`, a model of influxdb-java's dto, and Flux `query(flux) -> Vec<Record>`;
     - an async `InfluxSetup` seam that the factory calls.
   - **3.4b** implements the transports and setup over HTTP and pins them with real-service transcripts.
   - Alternative: move `QueryableGraphiteClient` to 3.4b and keep only a pure URL builder here.
3. **The facade type.** The memoised maps, warn-once sets and observed durations are `MetricsProviderImpl` internals. A generic wrapper over `dyn MetricsProvider` cannot keep the warnings lazy or the observed fallback live, and `RunDependencies.analytics: Arc<dyn MetricsProvider>` cannot prefetch.
   - Recommend a concrete `Analytics`, the Kotlin type that `Marathon`, `Scheduler`, `DevicePoolActor` and `QueueActor` take. It would implement the frozen trait **unchanged**, plus an inherent `prefetch(&[MetricsKey])` and `lookup() -> Arc<dyn MetricsLookup>`, over NoOp, Impl, or a test double that wraps 3.2's `MetricsProviderStub`.
   - `RunDependencies.analytics` would change to `Arc<Analytics>`. That is one field of 0.6's `wiring.rs` and needs approval.
4. **Prefetch semantics.**
   - (a) Serialise all fetches behind one async mutex, the analogue of `@Synchronized`, with a check-then-fetch-then-insert under it. This gives single-flight without per-key machinery and keeps the TimingLog order equal to the call order. All pools declare the same run-wide keys, so it costs nothing. Approve this over per-key concurrent single-flight.
   - (b) A lookup of a key that was never prefetched is a contract violation. Proposal: `debug_assert!`, and in release answer as for a failed query (defaults and warn-once, no query, no TimingLog). Never block on core.
5. **Logger levels.** Requesting the three loggers before `configureLogging` keeps them at DEBUG by §3.5 (`MarathonLogging.kt:9`).
   - If the oracle confirms it (evidence item 3), the warn-once lines, coverage lines and the `debug { list }` dump print in every run.
   - Recommend: 3.4a requests its loggers at construction and reproduces the dump with jcompat's data-class `toString`; 3.10 owns the construction order against configure, verified end to end.
   - The dump can be large (one entry per test with history). Confirm we keep it.
6. **Logging from core.** Warn-once lines come from synchronous lookups on core. Lifecycle forbids core blocking on the `Arc<Mutex<MarathonLogging>>` registry, and there is no merged core log sink yet (compare `executor/completion_logging.rs`, which renders on the output executor).
   - Recommend: the lookup enqueues `(logger, level, message)` records, rendered off core in order.
   - Who owns that sink: 3.4a minimally, or 3.10/3.1?
7. **Retry clock.** `executor::retry::with_retry` is core-only (`SchedulerClock`, `LocalFuture`), but history fetches run off core.
   - Recommend a Send twin over `VendorClock::delay`, with the same semantics: attempts, the last error returned, cancellation not retried. Put it beside 3.1's helper in `executor/retry.rs` rather than in analytics, so 4.x/6.x can reuse it.
