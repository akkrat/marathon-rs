## Deliverables and boundary

All of this goes in `crates/marathon-apple`:

1. **`XcodebuildSession`** (`B/XcodebuildSession.kt`). An `Arc`-shared session object:
   - `produce(open, consume) -> event receiver`;
   - `stop(timeout) -> Option<Failure>`, `await_closed(timeout) -> bool`, `check_closed(serial) -> VendorResult<()>`;
   - the `closed` and `abandoned` flags;
   - `CLOSE_TIMEOUT = 1 min`.

   The producer runs as a tracked task on the vendor runtime, never on core. It survives a `stop` that has timed out, so the session can still become `closed` later (see the behaviours below).
2. **`AppleDevice::execute_test_request(request, session, ctx)`**, added to the 4.10a trait (4.10a decision 2). Also a **shared event-producing body** that 5.2 and 5.6 delegate to. Both Kotlin bodies are the same except for the device label (`simulator <udid>` or `macOS <udid>`) and the argument source (`simulator_test_args` or the raw `xcodebuildTestArgs`). The shared body covers:
   - the `XctestEventProducer` over stdout;
   - stderr filtered by `trim().isNotBlank()` and logged through `xcodebuild_message`;
   - one lock serialising the line listeners;
   - the debug line `Finished test batch execution with exit status <code>`.

   This is where the PLAN row's "`Xcodebuild` stderr logger" lands. The logger itself is 1.6's (open question 3).
3. **`AppleDeviceTestRunner`** (`B/AppleDeviceTestRunner.kt`): `execute(configuration, test_bundle, batch, listener, ctx)`.
4. **`NmTestParser`** and **`XCTestParser`**, both `impl RemoteTestParser`, and **`AppleTestBundleIdentifier`**, which implements `impl TestBundleIdentifier` plus `put`.
5. **The embedded `libxctest-parser` dylibs**: the five per-platform binaries, copied unchanged and compiled in with `include_bytes!`.

## Behaviours to reproduce

**`XcodebuildSession`:**
- **Producer (`:50–70`):** `open()`, then `consume(command)`, then the channel is closed normally.
  - A non-cancellation failure closes the channel **with** that failure. If the reader is already gone, the failure is logged at debug instead: `xcodebuild session failed after its events were no longer read`.
  - Only after that, in `finally`, does `command.close()` run. A close error is stored as `closeFailure` and never thrown.
  - The order matters: the reader sees a failure before a slow close finishes (the rows "failed output reaches the run before…" and "output failing with an error…").
  - Kotlin's `produce` channel is rendezvous (capacity 0; see S1).
- **`stop` (`:77–83`):** cancels the job, then joins it for up to `timeout`, without being cancellable itself.
  - The result is `closeFailure` if the job joined, or `TimeoutException("xcodebuild session has not closed within PT1M")` if it did not. The duration is rendered as an ISO-8601 Java `Duration`, using jcompat.
  - Any failure sets `abandoned = true`.
- **`closed` (`:41–42`)** is `job.isCompleted && closeFailure == null`. The job is a bare `Job()`, so it completes only after `stop` cancels it **and** the producer has finished.
  - A session that was never stopped is never `closed`.
  - An abandoned session whose close later succeeds becomes `closed`, so a later `check_closed` passes.
  - A session whose `produce` never ran is closed as soon as it is stopped.
- **`awaitClosed` (`:90–93`)** waits without stopping the session, and is cancellable.
- **`checkClosed` (`:100–104`)** fails with `DeviceLostException(IllegalStateException("Previous xcodebuild session on <serial> has not been closed", closeFailure))`.

**Shared `executeTestRequest` body** (`ios/AppleSimulatorDevice.kt:678–708`, `macos/MacosDevice.kt:185–213`):
- It calls `check_closed` on the previous session, then records the new one. Both steps belong to the device, but the order must hold.
- stdout: `process(line)`, then `send` of any events, then the locked line listeners. A20 applies: events go out before the listeners see the line.
- stderr: lines that are blank after trimming are dropped, on both the log and the listener path. The other lines are logged as WARN `<label>: stderr=<line>` on logger `Xcodebuild`, then passed to the line listeners.
- The exit code is only logged at debug.

**`AppleDeviceTestRunner`:**
- **Request (`:41–55`):** `TestRequest` holds the workdir (the parent of the remote xctestrun), the remote xctestrun, the batch's tests, the xcresult path from `remote_xcresult_file(batch)`, `coverage = isCodeCoverageEnabled` and `testTargetName = testBundle.testBundleId`.
  - Debug lines: `Remote xctestrun = …`, then `Tests = [<Test.toString>…]`, rendered with 4.7's Kotlin `Test` rendering.
  - The `bundleIdentifier` constructor parameter is never used.
- **Main path (`:61–70`):** `before_test_run`; `execute_test_request` with a new session; each event list goes through `processEvents`; then debug `Execution finished`.
- **`processEvents` (`:117–131`):** a one-to-one mapping onto the listener. `TestRunFailed` calls `test_run_failed(message, reason)` and then throws `DeviceFailureException(reason, message)`; nothing after it in the same list or in later lists is processed.
- **Cancellation (`:71–77`):** ERROR with throwable, `Tests [<toTestName>, …] got stuck. You can increase the timeout in settings if it's too strict`. Then `test_run_failed(message)`, which uses the default reason `Unknown`, and the cancellation is rethrown. In Rust, cancellation arrives as `VendorError::Cancelled` from `consume_output` or the context, and the cleanup below **must still run** (lifecycle.md:241).
- **`finally` (`:81–94`):** `after_test_run`.
  - If it throws an `Exception` while the run has already failed, that exception is added to the run failure as suppressed.
  - If the run had not failed, it becomes the failure and is thrown.
  - Then, in an inner `finally`, the channel is cancelled and `closeSession` runs.
- **`closeSession` (`:101–115`):** `stop(sessionCloseTimeout)`.
  - On success, debug `xcodebuild session on <serial> closed in <ms> ms`.
  - On failure, the error is `IllegalStateException("xcodebuild session on <serial> has not been closed", failure)`. For a cancelled run it is logged as WARN `Cancelled run left its xcodebuild session unclosed`, and the cancellation keeps propagating.
  - Otherwise the run failure is added to it as suppressed, and `DeviceLostException(notClosed)` **replaces** the exception in flight.
  - The 10 `AppleDeviceTestRunnerTest` rows pin these orders, classes and chains (open question 4 covers the suppressed failures).

**`NmTestParser`:**
- **Retry (`:32–47`):** the whole extract runs under `withRetry(3, 0)`. Every failure, the last one included, logs debug `Remote parsing failed. Retrying` with its throwable.
  - Inside the retry, a registry miss throws `ConfigurationException("Unexpected device type for remote test parsing")`, so it is retried three times.
  - A missing bundle or xctest throws `IllegalArgumentException("No test bundle provided")`.
  - Then the `AppleTestBundle` is built (its own errors propagate).
- **Upload (`:54–71`):** debug `Found test binary <bin> for xctest <xctest>`.
  - With `skipCopyingDerivedData`, the remote xctest comes from `requireDistributedTestBundle(bundle, TestParsingException)`, with no mkdir and no push.
  - Otherwise: `create_remote_directory`, `create_remote_shared_directory`, then `push_shared(xctest, remote_xctest_file())`. A push that returns false throws `TestParsingException("failed to push xctest for test parsing")`.
  - The remote binary is `join_path(remoteXctest, relativeBinaryPath…, testBinary.name)`.
- **Scans (`:76–82`, `:116–120`):** the Swift and the ObjC scan start **together**, and both are awaited even if one fails, because an SSH command keeps its session until it exits.
  - Then, Swift first, a scan that failed with a `CommandException` is repeated **once**, after debug `Scanning <binary> again`.
  - Any other failure is rethrown, the Swift one first.
  - The 4 `StartupPhasesTest` rows pin this, including six scans over three attempts and `the command did not finish`.
- **Symbols (`:83–109`):**
  - Swift lines are trimmed with Kotlin's `trim` (`bin/kt.rs`) and split on `.`; a line is kept when it has exactly 3 parts and the third starts with `test`. A line whose method signature contains `DISABLE` is dropped. The method is cut before the first `(`, and the test is `Test(bundle, class, method)`.
  - ObjC lines are split on `' '`; a line is kept when it has exactly 2 parts and the second starts with `test`. The test is `Test("", class, method)` (A7).
  - Order: Swift, then ObjC. Duplicates are kept.
  - **All** of these tests are registered in the identifier **before** the filter `testClassRegexes.all { matches(clazz) }` (`TestClassRegex::matches`; the default stays special under D6).

**`XCTestParser`:**
- **Setup (`:33–81`):** the same retry, error messages and device lookup as the nm parser. Then:
  - `prepare_installation(device, use_xctest_parser = true)`.
  - The embedded dylib for `sdk.platform_name()` is written to a new local temp file and sent with `push_file` (not `push_shared`) to `remote_xctest_parser_file()`. A false result throws `TestParsingException("failed to push libparse-tests.dylib for test parsing")`; the wrong file name is Kotlin's.
  - Debug `Remote xctestrun = …`. The request is `TestRequest(workdir, xctestrun, coverage = false)`: no tests, no xcresult, no target.
- **Parse (`:82–116`):**
  - The line buffer is reset, then the parser registers itself as a line listener on the device.
  - Each `TestStarted` adds `id.copy(pkg = testBundleId)` to an insertion-ordered set. Other events are ignored, including `TestRunFailed`.
  - Cancellation is **swallowed**: ERROR `Test parsing got stuck. You can increase the timeout in settings if it's too strict`, and the parse goes on to return what it has collected (K1).
  - `finally`: the channel is cancelled, then `stop`. A failure logs WARN `xcodebuild session of test parsing on <serial> has not been closed` with its throwable. Then the listener is removed.
  - Other errors propagate after the `finally` and are retried.
- **Result (`:118–125`):** with zero tests, WARN `XCTestParser failed to parse tests. xcodebuild output:` + line separator + the buffer (each line followed by `\n`), and the parser returns an **empty list**, not an error. Every test is registered. No `testClassRegexes` filter is applied.

**`AppleTestBundleIdentifier`:** a concurrent map from `Test` (Kotlin equality, without the meta properties) to an `Arc` of the bundle, where a later `put` overwrites. `identify` on a miss is `ConfigurationException("Invalid test <toTestName>: can't locate test bundle")`, i.e. `Err`, never `Ok(None)`. Each parse attempt builds one bundle, and batching compares bundles by identity.

**Logger names** (`NmTestParser` and `XCTestParser` by simple name; the runner and the session by `logger {}`), levels and texts are as above. Pin them with the probe.

**Known Kotlin bugs:**
- Existing rows: A7 (owned with 4.7) and A20 (in the shared body). C36 and A44 are the precedent for swallowed cancellation.
- Candidate rows, to confirm with the JVM probe and number from A47 on:

  - **K2:** the push error names `libparse-tests.dylib`.
  - **K3:** one temp file is leaked per attempt (if S2 is rejected).
  - **K4:** the wrong-device `ConfigurationException` is retried three times.

## Proposed simplifications (pragmatic parity; for the orchestrator, **not decided**)

- **S1:** a capacity-1 event channel instead of exact rendezvous. The only difference is that reading can run one event list ahead of the listener. A20 is already a race in Kotlin. The order of close versus failure is unchanged.
- **S2:** delete the temp dylib after the push. Kotlin leaks one `*.tmp` file in `java.io.tmpdir` per attempt (K3). This is not visible in any output; PLAN :418 compares pushed content only.
- **S3:** for an SDK with no embedded dylib (`iPhoneOS`, `AppleTVOS`, `WatchOS`, `XROS`), Kotlin fails with `NullPointerException` after creating the temp file, three times. Fail with a `TestParsingException` naming the platform instead, keeping the retry shape. No v1 provider produces these SDKs.
- **S4:** do not port the dead code: `NmTestParser.kt:123–142`, and the unused constructor parameters (`configuration` in both parsers, `bundleIdentifier` in the runner). The inventory is unaffected.

No simplification is proposed for any argv, log text, error class, or ordering of session close.
