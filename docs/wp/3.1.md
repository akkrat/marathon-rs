## Deliverables and boundary

In `crates/marathon-core` (today: frozen traits in `runtime.rs`/`time.rs`, no executor, no tokio dependency — adding tokio `=1.53.2` as already pinned elsewhere in the workspace is part of this WP). Every item implements a named 0.6 trait; changing a frozen signature needs orchestrator approval and a `contracts.rs` update in the same commit.

1. **Core executor and vendor bridge** (`CoreRuntime`, `VendorRuntime`/`VendorTask`, `runtime.rs:116-133`). One dedicated thread owns a tokio `current_thread` runtime + `LocalSet`; all core state transitions and mailbox receivers run there and `LocalFuture` stays non-`Send`. The vendor runtime is multi-threaded and `VendorFuture` is `Send` (`lifecycle.md:10-15`); the bridge starts vendor work there and resumes the awaiting core task on core — never poll vendor work on core merely because it is `Send`. `spawn`/`spawn_cleanup` take `TaskBody` and hand the **new task's own** `TaskContext { job, core, clock }` to the body (`runtime.rs:14,19-23`); no ambient or thread-local job is inferred (`lifecycle.md:32-40`). No blocking calls on the core thread; blocking work goes through `spawn_blocking` and stays joinable after its awaiter is cancelled (`lifecycle.md:92-98`). Rust `Drop` runs no observable cleanup.
2. **`Job`** (`Job`/`JobState`/`Completion`/`JobKind`/`CompletionRegistration`, `runtime.rs:28-62`). Parent/child tree with ordinary vs supervisor parents and detached roots; `Active`/`Completing`/`Cancelling`/`Completed` are distinct, cancel is idempotent and separate from completion, a job completes only after body **and** children finish, and a stand-alone ordinary `Job` needs explicit `complete()` (`lifecycle.md:102-117`). `join` does not rethrow the joined job's failure; `cancel_and_join` requests then suspends. Completion callbacks run exactly once, including when registered on an already-completed job, and run on core. Ordinary child failure cancels parent and siblings; supervisor child failure is isolated; `OperationError::Cancelled` never counts as a child failure (`error.rs:26-42`, `lifecycle.md:42-49`). Both child APIs ship: `children_snapshot` for callers that need a snapshot, and `join_observed_children` as the lazy traversal (D3, below). The child list must be structured so switching Scheduler to the snapshot is a **one-line change**, with the traversal as the default and only behaviour 3.8 uses.
3. **`Deferred<T>` and `EventChannel<T>`** (`runtime.rs:69-77,98-106`). Concrete, generic, in-crate constructors with explicit runtime/parent inputs — the 0.6 generic factory traits were deleted and must not return (`lifecycle.md:51-59`). `Deferred` is parentless, shared `Send + Sync`, first-writer-wins (value, exceptional completion, or cancellation seals it), `complete`/`cancel` return whether they won, `completed()` inspects synchronously, `wait` is repeatable; dropping a handle or cancelling one await never seals the cell (`lifecycle.md:135-142`), and completion never runs core callbacks inline on a vendor thread (`runtime.rs:69-71`). `EventChannel` is the provider channel: shared consuming handle, explicit `close` **drains** buffered events, `cancel` discards them (`lifecycle.md:166-169`) — the opposite of actor close.
4. **`Actor<M>`** (`Actor`/`ActorHandler`/`ActorContext`/`SendError`, `runtime.rs:24-27,78-97`). Unbounded FIFO mailbox per actor, no cross-sender order; `send` fails on closure, `try_send` returns the rejected message, `safe_send` skips only an already-closed mailbox and keeps Kotlin's check-then-send race (`lifecycle.md:155-161`). `started` (default no-op) runs once at construction, before any dispatch, with the actor's own job/self-handle; `receive` gets `ActorContext` per message. `close()` **cancels the actor job and discards queued messages**, interrupts a suspended handler, and is safe to repeat (`Actor.kt:50-53`, `lifecycle.md:163-165`). The runtime retains bookkeeping through completion, then releases handler/context; no strong self-handle captured in an own-job callback (`lifecycle.md:26-30`). Actor constructors take explicit parent/runtime/clock/handler arguments; no service lookup.
5. **`StateMachine`** (no 0.6 trait; a new module porting the vendored BSD-licensed library in `StateMachine.kt`, header at `:1-26` kept). Synchronous `transition(event)`: look up the current state's definition, take the **first** matching transition in insertion order, store the new state, then notify exit → enter → transition listeners, and notify transition listeners even for an `Invalid` transition (`StateMachine.kt:46-67,73-99`; `lifecycle.md:175`). Only the surface the two consumers use is required (proposed simplification P1 covers the rest): `create { initialState; state<S> { on<E> { transitionTo / dontTransition } }; onTransition }` as in `DeviceActor.kt:39-90` and `PoolProgressAccumulator.kt:32ff`. Keep the generic `STATE`/`EVENT`/`SIDE_EFFECT` shape and `Transition::{Valid{to_state, side_effect}, Invalid}`; 3.5 and 3.6 define their own state/event/action types — 3.1 must not bake either machine's graph in.
6. **Scheduler clocks and timeouts** (`SchedulerClock`, `TimeoutScope`, `VendorClock`, `CancellationSignal`; `time.rs:34-37`, `runtime.rs:63-68,135-180`). One shared scheduler timeline for core and vendor (`lifecycle.md:244-250`); wall and monotonic clocks stay separate and are **not** the scheduler clock. `delay(millis, job)` observes the explicitly supplied job and preserves its cancellation reason. All millis are signed `i64`, never clamped into `std::time::Duration` (`lifecycle.md:202-207`). `with_timeout` reports its own expiry as `Cancelled(Cancellation::Timeout { scope, .. })` with a fresh scope per invocation; `with_timeout_or_null` returns `Ok(None)` **only** for its own expiry (`Ok(Some(()))` on success) and propagates inner timeouts (original scope intact), external cancellation and ordinary failures unchanged; both await the cancelled body's cleanup before returning, and typed results cross via captured cells/`Deferred` (`lifecycle.md:209-243`). The vendor mirror expresses its own expiry as `VendorError::Cancelled(Cancellation::Timeout { .. })`. Direct `tokio::time` calls bypassing this seam are forbidden for replay-controlled operations, in tests as well. Ship both a live clock (tokio-backed) and the virtual clock used by the replay driver (item 8); virtual time never advances on its own.
7. **`withRetry` and the coroutine exception handler** (`Retry.kt`, `ThreadPoolDispatcher.kt`). Async `with_retry(attempts, delay_millis, job, f)`: cancellation is rethrown immediately and never retried; any other failure delays and retries until the last attempt rethrows the **last** failure (`Retry.kt:8-24`). Delay goes through `SchedulerClock` with the caller's job, so cancellation during the delay aborts the retry. Invoke the exception handler only at a real unhandled-exception boundary: successful and cancelled tasks emit no records, and an unhandled failure emits one record after structured failure propagation. Keep its reusable branch formatter: finished → debug "CoroutineContext finished", cancelled → debug "CoroutineContext cancelled" with the exception, otherwise error "CoroutineContext closing due to unrecoverable error" (`ThreadPoolDispatcher.kt:7-13`, wired at `Actor.kt:24`), via `jcompat::logging`. (The file is misnamed in Kotlin — it contains no dispatcher; name the Rust module for what it holds and keep the `//! Port of` header.) `withRetrySync` is **not** ported here: its only caller is the SSH factory (4.2); see P4/open question 4.
8. **Controlled-replay hooks** (`ReplayHooks`, `ReplayDriver`, `ReplayBarriers`, `MailboxProbe`, `ObjectIdentity`; `time.rs:21-55`, `runtime.rs:107-115`). Live and tape-backed `ReplayHooks` (wall/instant, monotonic nanos, signed-i32 draws, stable-key choice, per-site IDs, identity suffixes by `ObjectIdentity` token — repeated references to one object reuse its suffix, C19); exhausted tapes fail, never fall back to host time/randomness; `verify_consumed` surfaces accumulated failures and unused explicit entries even if a caller caught the error (`lifecycle.md:362-367,382-383`). `ReplayDriver`: register every actor **and** provider mailbox by label, track runnable core work including readiness/completion callbacks, `advance_to` runs due timers and drains runnable work **before** delivering the external event at that timestamp and drains again after, equal-time events keep tape order, nothing auto-advances to the next timer, and a virtual clock without a driver fails (`lifecycle.md:369-374`). Quiescence = no runnable work and no queued message on an open registered channel, with closed-but-buffered, drained and discarded channels distinguished by `MailboxState`; a stalled non-empty mailbox fails the scenario (`lifecycle.md:376-383`). `advance_to` advances core **and** vendor timers, and quiescence includes vendor timer continuations and their bridge callbacks (`lifecycle.md:244-247`) — test this cross-executor case explicitly, it is the seam 0.6 R1-wonder-2 added. Live-mode `ReplayHooks` must be a no-cost pass-through of the same seams, not a second code path.

**Not 3.1:** the concrete actors and their graphs — `DeviceActor` (3.6), `QueueActor` (3.7), `DevicePoolActor`/`Scheduler` (3.8), `PoolProgressAccumulator` (3.5); the run flow, `runBlocking`/`supervisorScope` root, shutdown order and `NonCancellable` error-path finish as *call sites* (3.10 — 3.1 only supplies `spawn_cleanup` and the protected context they need); retry/quota strategies (3.2) and the metrics retry call sites (3.4a); vendor `withTimeoutOrNull` call sites (e.g. `AppleSimulatorDevice.kt:519,921`, Phase 5) beyond the `VendorClock` service itself; `SystemTimer` (already implemented in 0.6, `time.rs:64-89` — do not redo); the scenario/replay *test suite* comparing Rust against the patched Kotlin oracle (3.10/7.1 — 3.1 supplies the driver and its own unit/race tests, not the end-to-end scenarios); SSH/transport cancellation semantics (4.2's spike checklist, incl. T07/T14 — a generic cancellation signal does not claim to solve them, `lifecycle.md:270-275`).

## Behaviours to reproduce (with sources)

- **Job graph is explicit, never inferred from Rust ownership or thread** (`lifecycle.md:61-79`): actors replace the context job with their own `Job(parent)` (`Actor.kt:23-35`); `Marathon.run` is `runBlocking` → `supervisorScope` → `async` (`Marathon.kt:71-90,191-201`). The runtime must make 3.8's graph expressible exactly: supervised run child owns the device subscription (`Scheduler.kt:74-86`); Scheduler's own `Job()` at `Scheduler.kt:45` is **detached** and only passed as an argument; each pool actor job and its separate `SupervisorJob` are both children of that detached job (`DevicePoolActor.kt:35-39,61`); queue/device actor jobs hang under the supervisor (`:63-74,308`); device tasks are children of the device-actor job while its result `Deferred` at `DeviceActor.kt:59` is parentless. Do not "fix" any of this by reparenting.
- **Lazy observed-child traversal (0.6 decision D3, retained).** Scheduler runs `for (child in job.children) child.join()` (`Scheduler.kt:67-69`) — not `job.join()`, not a wait-until-empty loop. In pinned 1.8.1 bytecode the sequence reads state once: a single child node yields one child then stops; a list reads `nextNode` **after** each yielded child is joined, so newly attached nodes can appear but later children are not universally joined (`lifecycle.md:119-133`, with the `javap` offsets). Port that traversal as `join_observed_children`; a concurrently-attached child that the traversal misses is correct behaviour, and a test must pin both the single-child and the list cases. Any change to snapshot semantics needs controlled-replay evidence and explicit approval (D3).
- **Cancellation cascade.** Cancelling a job cancels its children (supervisor included as a parent; supervisor only isolates child *failure*) (`lifecycle.md:102-106`); cancellation interrupts a suspended `receive`, a `delay` on that job, and a `join` — with the original reason preserved through `OperationError::Cancelled` and `?` (`error.rs:32-36`, `lifecycle.md:42-49`). `spawn_cleanup` bodies survive caller cancellation (the `NonCancellable` seam, `Marathon.kt:83-87`) but still observe independently-cancelled operations they await. Dropping a future must never be how cancellation is delivered to code containing cleanup: resume its cancellation path or register the cleanup and await it (`lifecycle.md:211-217`).
- **Actor close vs channel close.** Actor `close(cause)` ignores the cause, cancels the job and returns `true` unconditionally — including on repeat close (`Actor.kt:50-53`); queued messages are discarded, there is no drain (`lifecycle.md:163-165`). Contrast `EventChannel::close` (drains) vs `cancel` (discards) for provider channels (`lifecycle.md:166-169`, `DeviceProvider.kt:12-19` — borrow happens before consuming the one shared channel). Tests must cover: send-after-close, try_send-after-close (message returned), handler suspended in receive at close, messages queued at close (never delivered), provider close with buffered events (still delivered).
- **Exception-handler logging.** Unhandled completion is *logged*, not swallowed silently and not propagated to senders: cancellation is debug-level, any other failure is error-level "closing due to unrecoverable error" (`ThreadPoolDispatcher.kt:7-13`). A handler returning `Failed` ends that actor (its job completes failed; ordinary-parent cascade applies) — the runtime must not loop on to the next message after a failed `receive`. Confirm against Kotlin whether the receive loop in `Actor.kt:33-35` can continue after `receive` throws (it cannot: the exception exits the `for` loop and completes the actor job) and pin it with a test.
- **StateMachine notification order and failure modes.** New state is stored **before** listeners run, so a listener reading `state` sees the target state (`StateMachine.kt:50-52` then `:54-65`); exit listeners of the from-state precede enter listeners of the to-state, which precede transition listeners; transition listeners also fire for `Invalid` (`:64,97-99`). First matching event transition wins and first matching state definition wins, both in insertion (linked-map) order (`:74-80,83-87,128,163`). A state with no matching definition throws via `checkNotNull` (`:87`) — in Rust this is a `Failed(Failure)` with the Kotlin exception class, not a panic. `synchronized(this)` (`:41-47`) makes Kotlin transitions atomic across threads; on the single-threaded core executor the equivalent is: no await point inside `transition`, and side effects are *returned* (`side_effect`) for the caller to run after — exactly how `DeviceActor.kt:83-90` consumes them in its `onTransition`. Re-entrant `transition` from inside a listener is possible in Kotlin (`synchronized` is reentrant); if the Rust port forbids it (e.g. `RefCell` borrow panic), say so in findings — that is P2's territory, not a silent divergence.
- **Timeout ownership races.** Simultaneous completion/timeout is a scheduling race live and an ordered event under replay (`lifecycle.md:215-217`): the virtual clock must make the winner deterministic (timers at the target run before the external event at that timestamp). `with_timeout_or_null` catching a *nested* timeout is the classic bug — scope identity (`error.rs:19-23`) exists precisely to prevent it; pin nested-timeout, external-cancel-during-timeout, and body-completes-as-timer-fires cases for both core and vendor clocks. Signed edge values (`0`, negative, `i64` extremes from config millis, `DeviceActor.kt:167`'s 10 000 ms vs `Marathon.kt:132`'s 0 ms retry delay) need oracle-probed semantics before freezing (open question 3); do not guess from Rust conventions.
- **Retry.** Attempts count from 1; the failure of attempt *n* < attempts delays then loops; the last attempt's throwable propagates unchanged; `CancellationException` short-circuits before the attempt check, so a cancelled final attempt reports cancellation, not the earlier failure (`Retry.kt:9-23`). Call sites pin the parameters: prepare 30×/10 s (`DeviceActor.kt:165-183`), remote parse 3×/0 under `withTimeoutOrNull` (`Marathon.kt:130-143`), analytics 3×/50 ms (PLAN §3.8). `attempts <= 0` never terminates in Kotlin unless `f` succeeds (the `attempt == attempts` check at `:16` is skipped once `attempt` passes it) — reproduce or flag under P3, do not silently normalise.
- **Deferred result protocol.** First writer wins across threads: a vendor completing with a value and *then* returning an error (or an actor sealing with cancellation at `DeviceActor.kt:138-151` and then reading whichever completion won) are both legal and must observe the first seal. `wait` cancellation leaves the cell untouched for later waiters. These are 3.6's semantics but 3.1's mechanism — test them here with a test-only payload, not in 3.6 for the first time.
- **Known Kotlin bugs.** No `docs/known-kotlin-bugs.md` row is owned by 3.1, and none should be marked confirmed by it. But the runtime must keep three later rows reachable: C25 (cleanup guard set before closes, failing close skips the rest — needs `spawn_cleanup` + sequential awaited closes, no runtime-level "close everything anyway"), C26 (parse skips `onFinish` — needs no RAII/shutdown-on-drop anywhere in the executor), C27 (serial-only `RemoveDevice` — needs reference identity distinct from any ID the runtime assigns). Bugs found while porting (in the Kotlin code or in tokio/library semantics relied on here) get new rows per `CLAUDE.md`; the detached-job race above is already documented in `lifecycle.md` and is not a new row.

## Proposed simplifications (pragmatic parity — for orchestrator approval, **not decided**)

Per the user's direction: few users, do not emulate quirks only exotic inputs reach. Until one is approved, the behaviours above stand and a divergence is a bug. Each approved item becomes a `docs/deviations.md` entry (a new D-number), not a silent gap. **Not proposed:** replacing the lazy traversal with a snapshot — 0.6 D3 already decided that, and the one-line-switch structure is the deliverable.

- **P1, StateMachine generality.** Port only what the two consumers use: reified-type state/event matching, `transitionTo`/`dontTransition`, `onTransition`. Drop `Matcher.where` predicates, `Matcher.eq` state/event forms, `state(value) { }`, `onEnter`/`onExit` registration and the `with()` graph-copy (`StateMachine.kt:69-71,141-146,181-183,224-236`) — no call site at `e47352f2` uses any of them (verified by grep over `core/src/main`). The notification *order* for exit/enter still holds trivially (no listeners can be registered); if a later WP needs one, it is added then with a test.
- **P2, StateMachine reentrancy and definition matching.** Implement `transition` as a plain generic match over the consumer's enums behind the builder surface, without emulating class-based matcher dispatch or reentrant `synchronized` transitions from inside listeners. Diverges only if a future graph (there are exactly two, both fixed) relies on subclass matching or listener-triggered transitions; neither `DeviceActor` nor `PoolProgressAccumulator` does.
- **P3, degenerate retry/timeout parameters.** For `attempts <= 0` and negative timeout/delay millis — unreachable from any config-driven call site at `e47352f2` — apply one documented rule (fail fast with a clear error, or treat as immediate) instead of reproducing Kotlin's non-termination/overflow corners exactly. In-range and zero values stay exact and oracle-probed either way.
- **P4, `withRetrySync`.** Do not port it in 3.1 at all: its single caller (`SshjCommandExecutorFactory.kt:49`) is WP 4.2's, `Thread.sleep` has no place on either runtime here, and its warn-log-and-sleep loop is five lines for 4.2 to own over `spawn_blocking`. Needs the inventory note for `Retry.kt` adjusted (currently just `withRetry`) rather than an `n/a` row — the file is still ported.
- **P5, unused Actor surface.** Do not port `onSend` (select clause), `invokeOnClose` or the deprecated `offer` alias (`Actor.kt:42-48,55`): no core call site uses them (the three `offer` hits under `vendor-apple/ios` are on plain channels, Phase 5). `try_send`/`send`/`safe_send`/`close` cover every frozen consumer.
- **P6, replay scope.** Implement `ReplayHooks`/`ReplayDriver` fully, but only the tape *reading* needed to drive this WP's own tests; the general tape parser/validator shared with scenario tests lands with 3.10, against `docs/design/replay-tapes.md` as the format contract. Avoids building an input format twice; risks a throwaway mini-parser here (keep it in `marathon-test-support` or a test helper, not in `marathon-core`'s public API).
