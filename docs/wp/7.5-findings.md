### U99 cause and reproduction

The highest allocated global U ID in found-bugs.md and every WP findings file
was U98; the prior mention of U99 explicitly left it unused. `U80000000` is a
Unicode escape in U13's reproducer, not a bug ID.

Opening `fail` wakes two independent vendor tasks; it does not deliver two
completed outcomes atomically. The Linux trace shows A1 failing, B3 taking its
retry, then B1 failing while B3 succeeds. B3's fresh IsReady reaches the pool
before B1's Notify is processed. Its single RequestBatch gets ahead of
the parked A2 request and consumes B1's retry. B3 therefore runs both test1 and
test2; A2 and B2 take neither. The executor did finish the work:
this is not an assertion preceding pool termination or a premature replay drain.

The event handlers agree with Kotlin DevicePoolActor.kt:170–215 and
queue/QueueActor.kt:261–275,324 onward. A newly ready successful device requests
work directly. Only failed devices wait for ConfirmOutcome; only devices in one
RequestBatches group are reordered to avoid their own retries. A lone requester
may take its own worker's retry when nothing else is queued. The source unit's
single dispatcher gives its immediate successful doubles an ordering that a
shared gate does not establish across Rust's vendor threads. Changing production
fairness to enforce this test's assumed ordering would change those handlers.
[WP 3.8's accepted transcript scope](3.8-findings.md) already records how
async tracker/output boundaries reorder vendor completions without changing
the ported event handlers.

Diagnostic evidence (temporary instrumentation removed):

- Unmodified scheduling logic passed 1,000 focused local runs, another 1,000
  under 16 CPU hogs, and 100 full-suite local runs. All hogs were reaped.
- Under the Linux CI lock, full-suite run 98/500 failed (rc=101), preserving
  all actor messages and assignments in
  `/tmp/mrs-core-flake-diagnostic-linux.log`; decoded messages are in
  `/tmp/mrs-core-flake-diagnostic-decoded.log`.
- A temporary tracker gate holds B1's failed outcome while the first retry

### What the harness now guarantees (offline-tested)

* **Source selection.** `build --source frozen|release` (default `frozen`) is the only place a source is chosen. For
  `release` it reads `docs/release-source.sha`, proves the commit exists in the Kotlin checkout, and writes into
  `build.json`: `source` (full SHA), `source_kind` and `samples` (tree hashes of the archived sample at the selected and
  at the frozen commit, plus `matches_frozen`). A release build whose sample tree differs from the frozen one is refused.
  Measured offline: `sample/ios-app` `c1802243ad15…` and `sample/android-app` `b2961fe0e537…` are the same tree at both
  commits; the macOS sample is this repository's own `sample/macos-app` (`0f397ab763c1…`), recorded with `origin:
  repository`.
* **JVM reference from a builder receipt (R1-sol-1, R2-sol-5).** `tools/oracle/build.sh` deletes its variant's old receipt
  first thing (before the JDK check, clone, checkout, patches, tree check and Gradle, so a failure anywhere leaves none) and,
  after the tree check, Gradle and the smoke test succeeded, writes `receipt-<variant>.json` next to the clone
  (`tools/oracle/build[-<sha>]/`): source, HEAD, the verified tree hash (commit tree plus patches), patch hashes, the
  hashes of the installed jars, Gradle exit 0. `run reference` refuses a clone without that receipt, recomputes the
  verified tree itself, and requires the receipt, the installed jars and the given distribution to agree; the record it
  writes embeds the receipt. Jars copied into a clone, left over from another source, or swapped after the build do not
  match. The exact command to build the release reference is therefore `ORACLE_SOURCE_SHA=<release sha> tools/oracle/build.sh
  reference` (the `reference` step below does it); an older build of 7.5 has no receipt and must be rebuilt.
* **Binding for every new capture (R1-sol-2).** A capture of either source needs a `jvm_reference` record whose source
  equals the inputs'. `capture.json` carries `source`, `source_kind` and `jvm_reference_source`; the reader rejects any
  contradiction. A capture with no `source` field is accepted **only** if its evidence digest is on the audited list
  `tools/real-e2e/legacy-captures.json` (95 retained 7.2 captures, listed by the sha256 of their `evidence.json`) and it also
  has the 7.2 shape; field absence alone grants nothing (R2-sol-2). It is a trusted local receipt, not an attestation: it
  resists stale or swapped jars, not someone who fabricates the JSON.
* **Retained build record (R1-sol-3).** The reader checks `in/build.json` against the hashed input inventory and requires
  its source to equal the capture, contract, evidence and reference source. Release labels over a frozen build fail.
* **Log presence of near-instant tests (decision 7 of 7.5).** The projection treats the presence of a test's log as
  informational on the side that lacks it when that side recorded `endTime - startTime` under 10 ms (one raw attempt, one Allure result, one detail row, a
  non-negative integer duration): the LOG attachment, the Allure `text/plain` attachment and the matching per-test and global
  kinds are set aside on both sides, the scenario's per-test LOG requirement is waived for the same tests, and the
  difference is listed in `comparison.json` as `log_attachment_presence_informational`. Everything else gates: a log that is
  present on both sides, a retried or untimed test, a test of 10 ms or more, any other attachment kind. The HTML log link is
  not projected, so it never gated. Contents of logs are not projected either (they carry ambient device lines); a log
  reference whose file is missing still fails as a missing attachment.
* **Policies (R1-sol-4, orchestrator decision).** The projection fingerprint covers `outcomes.py`, so the 7.2 r3 policies
  no longer release unchanged. They are used here only as **drafts**: `qualify` writes a fresh policy from the new JVM
  captures, as 7.2's R1-R3 did whenever the projection changed. No legacy-policy compatibility exists, and none is wanted.
  Decision 7 changed the projection after the captures, so every closure policy was requalified from the same JVM pairs
  into a `<scenario>-outcomes-d7b.json` next to the first one (`-d7` was the first requalification, superseded by R1-sol-1), and every
  released pair compared again with `run compare --release --verdict release-d7b.json` (the retained `release.json` stays; see "Closure sweep results").
* **linux-kvm sample.** The worker gets the release sample the way the frozen one was staged: its bare repository
  `kotlin-src` receives a second path-limited pack (commit, all trees, the `sample/android-app` blobs); `build` archives
  the selected SHA and the tree-hash record proves it equals the frozen tree. Archiving the frozen commit for a
  "release" build was rejected on purpose.

### Scripts and guards

All commands are **bash** scripts (`set -euo pipefail`), not zsh. Host-specific values come only from the git-ignored host
configs and three environment variables; nothing private is committed.

| File | Purpose |
|---|---|
| `tools/real-e2e/sweep/sweep.sh` | the steps below, for the profile of `MRS_HOST` |
| `tools/real-e2e/sweep/common.sh` | the load guard, the guarded capture, the leftover check |
| `tools/real-e2e/sweep/plan.py`, `plan.json` | scenario table (products, 7.2 starting points), selection/draft/host-config/audit helpers |
| `tools/real-e2e/sweep/linux-stage.sh` | Mac side of the linux-kvm profile |
| `tools/real-e2e/sweep/worker-install.sh` | worker side of the linux-kvm profile |

* `MRS_HOST` absolute path of the profile's host config; `MRS_RUNS` absolute path of the NEW runs root; `MRS_OLD` absolute
  path of the retained 7.2 runs root (read only). Relative paths are rejected.
* **The guard fails closed.** Before every capture: `pkill -x yes` for this user, then load average below 10 and no `yes`
  process (`pgrep` status 1 only; any other status, a missing `pgrep` or an unreadable load stops with status 5), up to 60
  tries 20 s apart; otherwise the step stops with status 3 and no capture runs. The capture's own exit
  status is the step's status, and a leftover (`/tmp/marathon`, the lock, on Linux an adb/emulator/qemu process) after a
  capture fails the step with 4, and a failing `ps` on Linux counts as a failed inventory. Tests with stubs cover all of this (`SweepScripts` in `test_real_e2e.py`).
* **One capture attempt at a time, and clean up after a failure.** Never wrap a capture step in a retry loop and never run two
  at once. After any failed attempt run `run cleanup --host "$MRS_HOST" --output <new dir> --run-id <id> --approved` (the id is
  the failed attempt's journal directory name) and check that no reservation lock, adb, emulator or qemu process remains
  before the next attempt. A looping wrapper once left a stale reservation lock after the first failure; the next attempts
  were refused by it, consumed the attempt budget, and none started an emulator.
* **Resumable steps.** `sweep.sh build` skips a directory that already holds its `build.json` (the record is still
  checked), reuses a preflight directory that holds `preflight.json`, and stops with a message on a blocked preflight
  directory (no `preflight.json`) or an interrupted build directory (no `build.json`): move those aside, retained, and re-run.
  `sweep.sh build macos-build` (or `ios-build`, `android-build`) runs one directory only, so the macOS part can follow the iOS one.
* **The audit follows the sweep's record, not HEAD.** `sweep.sh audit` takes the native commit from the `native_source` of
  the runs root's `*-build/build.json` files (they must agree), requires every capture and the build record retained in it to
  name that commit and the release source, and lists every `release*.json`. HEAD moves with offline commits after the captures.
* **One native commit.** Run the sweep from a worktree at the reviewed commit that contains these scripts, with a clean
  tree and no further commits (`capture.json` records `git rev-parse HEAD`); the scripts refuse a dirty tree. Both
  profiles use the same commit; the worker checkout is a bundle of it.
* **iOS**: the **iOS 26.4 runtime on Xcode 27.2** (`com.apple.CoreSimulator.SimRuntime.iOS-26-4` in `runtime`).
* **macOS**: the terminal host needs **Full Disk Access** for the TCC snapshot (preflight stops with `authorization
  denied` otherwise; ask the user to re-grant, never change SIP or TCC). If `macos-cancel` stalls with `Timed out waiting
  for a temporary device` the stale `testmanagerd` (U102) is back: stop and ask the user to reboot.
* **Android**: only on the reserved Linux worker with its private `adb_port`/`emulator_port` (7.2 used 45037 and 5584);
  never port 5037, the user's adb server, devices or emulators; no SDK install; Gradle downloads only into the private
  build home (7.2 decisions 12/13).
* **Failure rule.** A harness failure (watchdog, cleanup, guard) is retained and the capture repeated in a new directory,
  at most twice; a result difference is never retried away. Stop and report anything unexplained.

### Decision 7 witness: the near-instant test's log (android-remote-screenshots)

Both native pairs lacked the logcat attachment of `com.example.FailedAssumptionTest#failedAssumptionTest`; both JVM captures had it. The first-pass
`compare --release` therefore reported exactly two differences on each pair (`/allure/1/attachments/text~1plain` and the test's `per_test_kinds`),
nothing else. From the retained test results:

| Capture | Window `endTime - startTime` | LOG attachment | Log file |
|---|---|---|---|
| JVM pair 1 / pair 2 | 2 ms / 5 ms | yes | 491 / 361 bytes, ambient lines of the previous test's teardown |
| native pair 1 / pair 2 | 0 ms / 0 ms (`startTime == endTime`) | no | none |

Kotlin attaches a test log only if the window caught a line (`LogListener.kt:36-43`) and Rust does the same (`artifacts.rs:376`), so the presence of
the log of a test that runs for a few milliseconds depends on timing on both sides (7.2: both sides had it; the file was 8468 and 11731 bytes on the
JVM side). Decision 7 makes the presence informational on the side that lacks it under 10 ms; the requalified comparison lists it:
`log_attachment_presence_informational` = `FailedAssumptionTest#failedAssumptionTest`, JVM `[[2, true]]` / native `[[0, false]]` (pair 1) and `[[5, true]]` /
`[[0, false]]` (pair 2). It is listed in no other scenario's comparison. Regression tests (`test_outcomes.py`): the 0 ms case passes and is listed; the
same test at 10 ms or more fails (and the per-scenario LOG requirement also holds from 10 ms); a missing attachment of another kind still
fails; retried (a retry shows in raw.json or the Allure results even though the detail reporter keeps only the final result), untimed and negative-duration tests are never waived; a dangling log reference and a log missing from a 100 ms test still fail.
The Kotlin behaviour is recorded as C84 in `known-kotlin-bugs.md`.
