## Follow-up: iOS video recorder lifetime (2026-10-31)

Branch `wp/5.3-video-recorder-lifetime`. Question from the WP 7.2 real captures (`ios-ui-video-pair-{1,2}`): native
`ios-ui-video` records only the first of two UI tests, because the first stop command (`kill -s INT $(cat pidfile) &&
lsof -p … +r 1`) exits 1 within 40–70 ms, the pidfile stays (A96), and the second recording is never started. Kotlin's
same stop takes ~1.07 s and succeeds. The 7.2 note proposed a deviation that removes the stale pidfile. That was
rejected: it treats the symptom. This note records what the code and the retained logs say about the cause.

### Result: no Rust-side early death was found

**Not established.** No code path in Rust ends the recorder before the SIGINT, and the retained logs do not show that it
died early. A fix would be a guess, so none was made.

### What was checked, and what refutes each hypothesis

* **(a) The start job's command is killed when the job ends or is cancelled: refuted.**
  * The recording command is `sh -c "nohup xcrun simctl io … recordVideo … > /dev/null 2>&1 & echo $! > pidfile"`
    (`crates/marathon-apple/src/cmd/mod.rs:176-191` `safe_execute_nohup`; Kotlin `CommandExecutor.kt:88-107`). The `sh`
    exits at once and leaves the recorder detached; the start job's only work is that one command, and it finished 17 ms
    after the test started (`native/process/stdout:101`, `started video recording pid=76843`).
  * The only signals the local executor ever sends go to the `sh` child itself (`kotlin_process_command_executor.rs:173-181`,
    `close` at 278-301), which is already gone. There is no `kill_on_drop`, process group, session or `killpg` anywhere in
    the workspace outside Android.
  * Cancelling a finished job does nothing (`listener/mod.rs:74-82`).
  * Checked with the real local executor and a stand-in recorder that handles SIGINT and needs 0.4 s to finalise:
    `crates/marathon-apple/tests/local_nohup_recorder.rs`. The recorder is alive 500 ms after its start session ended;
    the production stop command interrupts it, waits for it and exits 0.
* **(b) Rust cancels or joins the start job before SIGINT, Kotlin does not: refuted.** `ScreenRecordingListener::stop`
  (`listener/video.rs:71-82`) does `cancel(job)` then the pidfile read then the stop, exactly as Kotlin's `stop()`
  (`ScreenRecordingListener.kt:156-166`: `cancelAndJoin`, read, `stopVideoRecording`). The job has finished by then in
  both.
* **(c) The next test's start runs before the end handlers: refuted.** In `native/process/stdout`, `testFailed` is
  followed by the stop (127-128), transcode, pull and `Removed file` (129-132); the second `testStarted` is logged after
  that (line 133, `12.815`). The only ordering difference is the raw `Test Case … started` log line, printed at 12.563
  natively against 24.381 on the JVM side. That line is printed by the line listener; xcodebuild is not held back by it
  on either side (the pipe holds far more than a few lines), and its own `Start Test at` timestamp is the same on both.
* **Listener level.** `two_tests_keep_the_recorder_alive_until_stop_and_attach_both_videos`
  (`crates/marathon-ios/tests/ios_listeners.rs`) drives two tests under `ON_ANY` against a fake worker that models the
  recorder as alive from its nohup start until the INT of the stop command. The recorder is alive at both stops, both
  recordings start, both VIDEO attachments exist and the pidfile is gone. It passes on the unchanged listener, so the
  listener cannot be what ends the recorder.

### What the logs say instead

* `kill -s INT` **succeeded** in the failing stops (stderr is empty; a dead pid prints `kill: (pid) - No such process`,
  as native `stdout:165, 188` and JVM `stdout:207` do for the second, stale stop). So the recorder existed when SIGINT
  arrived. The first video is complete, decodable H.264 (`7.2-findings.md`), which a recorder killed by anything other
  than SIGINT would not give.
* Exit 1 with empty output is what `lsof -p <pid> +r 1` returns when the pid has **no open files at its first pass**;
  it exits 0 only after seeing the process alive at least once (checked here with a `sleep` stand-in: alive at the first
  pass exit 0 after ~1 s, gone exit 1). So 1.07 s means "recorder still alive about 30 ms after the INT, gone at the
  second pass 1 s later", and 40–70 ms means "recorder already gone when lsof first looked". It is a race between the
  recorder's shutdown after SIGINT and lsof's first scan, inside one `sh` on the worker. Neither side of that race runs
  in marathon's own process.
* The same fast outcome appears **on the Kotlin side**: JVM pair 1, last test, 42 ms, exit 1 (`jvm/process/stdout:181-182`);
  pair 2 the same at 36 ms. Kotlin shows both outcomes, native only the fast one; with n=2 per side and a single
  worker, the data cannot tell a systematic native difference from the recorder's shutdown time depending on what the
  simulator is doing at the moment (idle after the last test, busy relaunching the app after the first).

### The probe that would settle it (real host, not run here)

The first question is whether the recorder's shutdown time after SIGINT, not marathon, decides the stop result.
On the capture host, with **no marathon involved**, for each of "simulator idle" and "app being terminated and
relaunched by `xcodebuild test` in the background", repeat ~10 times:

```sh
nohup xcrun simctl io <udid> recordVideo --codec h264 --display internal --mask ignored --force /tmp/p.mp4 \
  > /dev/null 2>&1 & echo $! > /tmp/p.pid
sleep 3
python3 -c 'import time; print(time.time())'
sh -c 'kill -s INT $(cat /tmp/p.pid) && lsof -p $(cat /tmp/p.pid) +r 1 &>/dev/null'; echo "rc=$? "
python3 -c 'import time; print(time.time())'
```

A bimodal result (rc=1 within ~50 ms under one condition, rc=0 after ~1 s under the other) makes the stop result a
property of the recorder, so the native capture differs only by the simulator state at the instant of the INT.
If native and JVM then differ under the *same* condition, run the same stop from each side with a 5 ms `ps -o stat= -p
<pid>` poll started just before the `kill` and compare how long the recorder lives after the INT.
Whichever way it goes, A96 stays as ported, and the remaining question is a decision for the orchestrator: keep
Kotlin's fragility (a fast recorder loses the next video) or deviate. A deviation needs a D-number and is not made here.

### Follow-up (2026-10-31): timelines and the real-host probe

#### Per-side timelines (WP 7.2 `local-27-ios26/ios-ui-video-pair-{1,2}/*/process/stdout`, times are the log's wall clock)

"end" is xcodebuild's `Test Case … failed/passed` line, which is also where `TestRunProgressParser` reports the result. `stop`
is the start of the stop command, taken as `stopped video recording` minus the stop's duration.

| | JVM pair 1 | JVM pair 2 | native pair 1 | native pair 2 |
|---|---|---|---|---|
| first end → `testFailed` logged | 23.048 → 23.052 (4 ms) | 23.369 → 23.376 (7 ms) | 12.559 → 12.560 (1 ms) | 33.853 → 33.853 (0) |
| first end → SIGINT sent | ~9 ms | ~8 ms | ~1 ms | ~0 ms |
| old app `Terminate` (xcodebuild: Start Test + 0.02 s) | ~20 ms after end | ~20 ms | ~14 ms | ~7 ms |
| relaunch (`IDELaunchParametersSnapshot`) | 24.108 (+1.06 s) | n/a | 13.635 (+1.08 s) | n/a |
| first stop result | 1.07 s, ok | 1.08 s, ok | 65 ms, rc=1 | 69 ms, rc=1 |
| next `Test Case … started` line printed | 24.381 (1.33 s after end) | 24.779 | 12.563 (3 ms after end) | 33.853 (0) |
| last test: end → `testPassed` → stop duration | 29.101 → 29.104 → 39 ms, rc=1 | 29.401 → 29.404 → 36 ms, rc=1 | 18.496 → 18.497 → 31 ms, `No such process` (stale pid) | 39.805 → 39.806 → 30 ms, same |

What this shows:

* **`testEnded` is delivered at the same point on both sides**: when the `Test Case … passed/failed` line is parsed, within
  0–7 ms of it. The Kotlin and Rust parsers and listeners do not disagree about where the result is reported. SIGINT
  follows the end line by 8–9 ms on the JVM and 0–1 ms natively, a few ms of difference in a window where the recorder is
  idle anyway.
* **What xcodebuild does in between is the same**: it terminates the old app about 20 ms after the end line and relaunches
  about 1.06–1.08 s later, on both sides. When SIGINT arrives, the simulator is in the same state on both.
* **The one visible difference is log-line timing, not xcodebuild timing.** The JVM prints xcodebuild's next
  `Test Case … started`, `Start Test at` and `Terminate` lines only after the first test's whole end handling
  (stop, transcode, pull, remove: ~1.3 s), because its line pipeline is serial. Their own timestamps (`Start Test at
  10:21:23.048`, `t = 0.02s`) show xcodebuild did that work at once. Native prints them at once. xcodebuild itself is not held
  back on either side (its stderr lines keep flowing on the JVM during the stop, e.g. 24.108).
  This changes when the line is logged only; nothing in the stop depends on it. Making Rust serial like the JVM would
  reproduce a log-timing artefact, not the stop behaviour, so no change was made.

#### Probe on the real host (no marathon involved)

Setup: one fresh simulator `mrs-probe-<epoch>` (iOS 26.4, iPhone 17 Pro, booted, then shut down and deleted; no other
simulator touched; no CPU stress; `pgrep -x yes` empty, load average 1.4–1.9 throughout). Recorder started with the
production nohup command, 3 s of recording, then the production stop command
`sh -c 'kill -s INT $(cat pidfile) && lsof -p $(cat pidfile) +r 1 &>/dev/null'`, timed from the Python caller.
"churn" = `simctl launch`/`terminate` of Settings in a loop (0.15 s apart) from 0.4 s before the stop until it returned.
stdin of the recorder and of the stop command was `/dev/null` (what Rust children inherit under the capture harness, which
starts marathon with `stdin=DEVNULL`) or an open pipe held by the caller (what the JVM's `ProcessBuilder` gives children).

| condition | stdin | runs | rc=1 | stop duration |
|---|---|---|---|---|
| idle | /dev/null | 20 (10 + 10, the second batch with a page that failed to open, so also idle) | 20 | 31–54 ms |
| idle | pipe | 10 | 10 | 40–53 ms |
| app launch/terminate churn | /dev/null | 10 | 10 | 30–37 ms |
| app launch/terminate churn | pipe | 10 | 10 | 30–32 ms |

All 50 stops failed fast with empty stderr; none gave the 1.07 s success that Kotlin showed on the first stop. Second
measurement, 35 runs without lsof (poll the recorder's exit every 1 ms after SIGINT): the recorder exits **6–31 ms after
the INT, median 10 ms**; only 2 of 35 took 30 ms or more (idle, churn and an 8 s recording alike).

Reading:

* The stop result is decided by a race **inside the stop command**: the recorder's shutdown after SIGINT (about 10 ms,
  tail to ~30 ms) against the first `lsof` pass (`sh` startup, two `cat`s, `kill`, `lsof` startup: roughly 30–50 ms after
  the INT). The recorder is normally gone first, so `lsof` exits 1. The success (1.07 s) Kotlin got is the tail: the
  recorder still alive at the first pass.
* Neither the recorder's stdin (Rust's inherited `/dev/null` against the JVM's pipe) nor app launch/terminate activity moved
  the result. With the tail at roughly 5% in this probe, two JVM successes and two native failures at n=2 per side are
  not enough to call the sides different, and the real captures record a busy test screen, which the probe did not
  reproduce (an animated Safari page could not be opened).
* Nothing in marathon's own process is on either side of the race, and both sides issue the same command at the same
  point relative to xcodebuild's end line. The Kotlin implementation is exposed to the identical fast-failure outcome (its
  last-test stops, 36 and 42 ms, are exactly that, and it would be the first stop's outcome most of the time in this probe).

#### Decision: (b), inherent to the recorder; documented as an A96 consequence

No Rust-specific timing difference was found, so no production change was made. The consequence of A96 is: whenever the
recorder dies before `lsof`'s first pass (the common case in the probe), the stop reports failure, the pidfile stays and
the next test's recording waits for it for 10 s and gives up, so every test after the first loses its video under
`ON_ANY`. Kotlin has the same behaviour; its captures looked better only because the recorder was alive at the first
`lsof` pass on both first stops.

**Proposed deviation for the orchestrator: D17** (not implemented). After a stop whose `kill -s INT` was delivered (i.e. the
failure came from `lsof`, not from `kill`), treat the stop as successful and remove the pidfile. Alternatives, from least to
most invasive: remove the pidfile whenever the recorded pid no longer exists after a failed stop; or wait for the recorder
with a `kill -0` poll instead of `lsof +r 1`. The first-test video is unaffected either way (it is complete and decodable);
D17 would restore the second and later test videos, which Kotlin loses in the same circumstances.

### D17 implemented (2026-10-31)

Variant: after a failed stop, `stop_video_recording` (`worker.rs`) runs `sh -c "ps -p $(cat <pidfile>) -o pid="`. Exit 1 with
empty output (no such pid) counts as stopped and removes the pidfile; anything else (pid alive, probe error, null result) keeps
the warn-and-false path. Chosen over trusting "the INT was delivered" because that cannot be read reliably from the combined
command (kill and lsof both exit 1; only stderr text differs) and would drop the pidfile of a live recorder when lsof fails for
other reasons; over a `kill -0` poll because it changes the Kotlin stop command. A reused pid reads as alive, the safe side.
Tests: `fast_recorder_exit_keeps_failed_stop_from_blocking_next_recording`, `live_recorder_and_failed_stop_keep_pidfile_and_warn`;
`waiting_start_warns_once_starts_anyway_and_failed_stop_still_logs` now answers the probe as alive (its fake otherwise returned
exit 1 for everything, which D17 reads as a gone pid).
