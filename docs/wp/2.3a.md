## Deliverables and boundary

In `crates/marathon-config`, against the merged 2.1 binder only (`Binder`/`Value`/`Object`/`Field::primitive|reference|nullable`, `Value::nullable` composites, `polymorphic` returning `Result<Option<T>>`, `list`/`map`, `Value::enumeration` / `Value::enum_creator`, `Value::{file, regex, duration}`):

1. **Filled vendor schema types.** Replace the `AndroidConfiguration`, `IosConfiguration` and `MacosConfiguration` slots in `schema.rs` with the real Kotlin field layouts, and add every nested type the 37 sources declare (Android leaves, Apple shared leaves, iOS leaves, the macOS permissions leaf, and all their enums). The 0.6-frozen `VendorConfiguration` enum (`Android`/`Ios`/`Macos`/`Stub`/`Empty`) and `Configuration`'s field order do not change. No serde derives and no `Default` impls that smuggle binding defaults into the type layer (0.6 rule); defaults — including derived defaults computed from sibling fields — live in the `bind_*` functions and in the explicit constructors the Kotlin tests use.
2. **The vendor binder for 2.2's seam.** One hand-written `bind_*` entry point (`fn(Value) -> Result<Option<VendorConfiguration>>` in the 2.1 style) implementing the `type`-property dispatch of `VendorConfiguration.kt:44-55`, passed by 2.4's loader (and by 2.2's tests) as the vendor-binder parameter of `bind_configuration`. Plus a `bind_*` function per nested type, composable exactly as the 2.1 findings sketch shows. If 2.2 has merged first with a test stub that handles only `Empty`/absent, this WP replaces that stub; it does not edit 2.2's top-level binder beyond removing the stub.
3. **SDK lookup.** The `EnvironmentReader` surface as a pure lookup over `BindingContext.environment` (ordered pairs, no direct `std::env` reads in the config crate): `ANDROID_HOME`, else `ANDROID_SDK_ROOT`, else none (`SystemEnvironmentReader.kt:12-13`). The CLI supplies the process environment in the context (2.5). No second environment reader type in core or CLI.
4. **Vendor stage-(a) post-processing pieces**, as functions shaped for 0.6 `VendorConfigurationHooks::post_process` (`binding.rs:81-87`), which is where `ConfigurationFactory`'s vendor branches land: the Android SDK fill, the Apple path re-resolutions, the missing-`devices` default, and `xcresult.pull` → `pullingPolicy` (details below). Only the vendor pieces: assembling `ConfigurationLoader::parse`, the tracking-flag AND-merge, and the `Empty` rejection staging are the loader's (2.4). Whether 2.3a also writes the `VendorConfigurationHooks` impl that calls these pieces is open question 4.
5. **`validate()` definitions and small derived helpers** on the vendor types: `AndroidConfiguration.validate()`/`safeAndroidSdk()`, `IOSConfiguration.validate()` and `MacosConfiguration.validate()` minus the bundle call (open question 2), `SshConfiguration.validate()`, `WorkerConnectionConfiguration.validate()` + `pause_after()`, Apple `ThreadingConfiguration.validate()`, `XcresultQueueConfiguration.validate()` + `effective_worker_capacity()`, with the Kotlin messages verbatim. Only the definitions: who calls them, in which order and stage — including macOS never getting its `validate()` called at stage (b), F6 — is `LogicalConfigurationValidator` / `VendorConfigurationHooks::validate`, i.e. 2.4.
6. **Apple base accessors.** `ConfigurationExtensions.kt` (vendor-apple/base; moved to this WP by orchestrator decision): `bundle_configuration()`, `xctestrun_env()`, `xcresult_configuration()` and `skip_copying_derived_data()` over `VendorConfiguration`. Where they live in Rust is open question 5.
7. **`Eq`/`Hash` under F7.** Pattern-based, mutually consistent equality for the one regex-bearing type here (Apple `NmTestParserConfiguration`), following 0.6 D1 and 2.2's approved S1; Kotlin's own inconsistency gets a known-bug row (below). Derive `Hash` only where something needs it (2.2 decision 4).

**Frozen traits.** This WP implements no 0.6 trait by default (see open question 4 for the possible `VendorConfigurationHooks` half). It consumes 0.6 `BindingContext` (P1 `Profile`; `marathonfile_dir` for `File` binding and for every post-processing resolution; the ordered `environment` for SDK lookup) and the 2.1 binder/`pipeline` error taxonomy, and it produces the `VendorConfiguration` values and post-processing pieces that 2.4's `ConfigurationLoader` assembles. It does not implement `ConfigurationLoader` or `ConfigurationValidator`. Post-processing does filesystem work (`canonicalFile`), so everything in deliverable 4 runs off the core executor and returns errors, never `unwrap()`/`expect()` on I/O (CLAUDE.md, `lifecycle.md`).

**Not 2.3a:** the top-level schema, strategies, filters and analytics (2.2, in parallel — boundary above); `AppleTestBundleConfiguration.validate()` with its `.ipa`/`.zip` extraction side effects, the resolved `app`/`testApp`/`xctest` fields, P2 Marathondevices and the dynamic frame decoder (2.3b — but the `bundle` field's *data layout* is a shared edge, open question 2); `LogicalConfigurationValidator`, `Configuration.toMap()`, leaf serializers and the serialization round trip (2.4); CLI and `config-dump` (2.5); the whole-`Configuration` differential/mutation suite (2.6); anything that *uses* these configs at runtime — serial strategies (6.5), screen-recorder commands (6.6b), simulator provisioning/boot/late-join (5.2/5.4/5.5b), macOS device behaviour (5.6), xcresult transfer queue (4.9).

## Behaviours to reproduce (with sources)

**Vendor dispatch is `type`-property `Id.NAME`** (`VendorConfiguration.kt:44-55`), through 2.1's `polymorphic` (late `type`, unknown id, and the consumed-occurrence hiding from 2.1 R1 included):

| `type` name(s) | Binds to |
|---|---|
| `Android` | `AndroidConfiguration` |
| `iOS`, `watchOS`, `tvOS`, `visionOS` | `IOSConfiguration` (all four names, one type — `names = arrayOf(...)`, `:51`) |
| `macOS` | `MacosConfiguration` |
| `stub` | `StubVendorConfiguration` (Kotlin `object`, singleton) |
| `empty` | `EmptyVendorConfiguration` (a plain class, **not** an object) |

Names are case-sensitive Jackson ids (`android` is not `Android`); `iPadOS` appears in the doc comment (`:164`) but is **not** a registered name. The same mechanism nests: `DeviceProvider` (`static`/`marathondevices`/`dynamic`, `DeviceProvider.kt:13-15`), `SshAuthentication` (`password`/`publicKey`, `SshConfiguration.kt:52-55`), Android `TestParserConfiguration` (`local`/`remote`) and Apple `TestParserConfiguration` (`nm`/`xctest`). Which spellings Jackson accepts for the singletons and the fieldless `Empty`/`local`/`xctest` types (empty map, extra keys, scalar forms) must be oracle-pinned, not guessed (fixtures below). An absent `vendorConfiguration` is 2.2's Builder default `Empty`; the parse-stage rejection `No vendor configuration specified` (`ConfigurationFactory.kt:190`) is the loader's staging (2.4), not this binder's — the binder must be able to *produce* `Empty`.

**Creator binding with Kotlin defaults, field by field.** Every vendor type binds through its primary constructor under the 2.1 `Field` policies: missing keeps the Kotlin default, a primitive field takes zero on explicit `null` even with a default (`adbInitTimeoutMillis: null` ⇒ 0, not 30,000), a non-null reference rejects `null`, a nullable field takes `null`, and a `null` collection/map stays `null` per the 2.1 rules as narrowed by 2.2 decision 3 (a `null` *element* is rejected at bind, D9 — this fixes the shape of `splitApks`, `extraApplicationsApk`, `outputs`, `importMedia`, `adbServers` and the set fields). Several Android leaves declare no `@JsonProperty` (`AdbEndpoint`, `AllureConfiguration`, `FileSyncConfiguration`, its entries, android `ThreadingConfiguration`, android `TimeoutConfiguration`), so their YAML keys are the Kotlin property names; where `@JsonProperty` renames (`applicationApk` → `applicationOutput`, `devices` → `devicesFile`, `importMedia` → `mediaFiles`, `ffmpegPath` → `binary`, `app`/`test` → the env maps), bind by the annotation name and keep the Kotlin-side name for `toMap()`/output (2.4).

**Derived defaults are computed from the values actually supplied** (PLAN §3.2). Kotlin evaluates a default expression at construction from the already-bound parameters, regardless of YAML key order, so each affected `bind_*` must first collect the inputs, then derive: Android `TimeoutConfiguration.listFiles`/`uninstall`/`portForward` default to the bound `shell` (`TimeoutConfiguration.kt:5-17`, android); Apple `erase`/`shutdown`/`boot`/`install`/`uninstall`/`importMedia` default to bound `shell`, `delete` to bound `shutdown` (so `shutdown: PT5M` alone moves `delete` but not `erase`), `xcresulttool = maxOf(shell, 120 s)` and `bootWait = maxOf(boot, 180 s)` (`TimeoutConfiguration.kt:18-34`, apple — note `bootWait` chains through the possibly-defaulted `boot`, hence through `shell`). An explicit value always wins, even below the floor (`xcresulttool: PT20S` stays 20 s) and even when it appears before `shell` in the file. The same derivation applies in the plain constructors the tests use (`TimeoutConfiguration(shell = …).xcresulttool`), so put it in one constructor function the binder also calls — do not implement it twice. `XcresultQueueConfiguration.effectiveWorkerCapacity()` is the lazy variant: `workerCapacity ?: maxOf(1, capacity / concurrency)` with **integer** division (`XcresultConfiguration.kt:27,53`), computed at call time, never stored (the round-trip row asserts it is not serialised — 2.4's serializer must not invent it either).

**Enums: three regimes.** (a) Plain enums bind by constant name, case-sensitive, integer/string ordinals accepted, via `Value::enumeration` with the constants in declaration order (`PathRoot`, `AggregationMode`, and the JDK's `TimeUnit`, whose seven names/ordinals come from the JDK — pin them with the oracle, do not transcribe from memory). (b) `@JsonProperty` enums bind by the annotation spelling (`LifecycleAction`, `Permission`, `Lifetime`, `PullingPolicy`, `String`-valued `Display`/`Mask`/`Codec`/`Size`/`TestType`…): pass those spellings to `enumeration` **in declaration order** so ordinals still line up, and keep the separate `value` string (simctl/TCC/xctestrun spelling) on the Rust type — YAML spelling and `value` differ exactly where a downstream bug would hide (`Lifetime.KEEP_ALWAYS` binds as `KEEP_ALWAYS` but means `keepAlways`; iOS `Permission.UserTracking` binds as `user-tracking` but means `kTCCServiceUserTracking`). (c) The three `@JsonCreator` enums take any case and go through 2.1's `Value::enum_creator`: `SerialStrategy` uppercases with `Locale.ENGLISH` (`SerialStrategy.kt:18`), iOS `RecorderType` likewise (`ios/ScreenRecordConfiguration.kt:22`), but Android `RecorderType` uses the **JVM default locale** (`android/ScreenRecordConfiguration.kt:21`) — under a Turkish locale `video` uppercases to `VİDEO` and is rejected. All three creators accept `null` and return `null` (hence `preferableRecorderType: null` and an explicit-null `serialStrategy` need oracle rows: creator-null vs the field's non-null default), and an unknown name surfaces as the `ValueInstantiationException`/`IllegalArgumentException` chain the binder already builds. Whether numeric input reaches a creator as its spelling (`"1"`) must be oracle-pinned before relying on `enum_creator`'s `string()` coercion.

**Sets and maps.** Kotlin `Set` fields (`lifecycle.onPrepare`/`onDispose`, iOS `permissions.grant`, each value of the macOS permissions map) and `MutableSet` (`fileSyncConfiguration.pull`/`push`) arrive as Jackson sets: duplicates collapse, iteration order is insertion order, and set equality is order-insensitive while `toMap()`/serialisation renders the iteration order. String maps (`instrumentationArgs`, `xcodebuildTestArgs`, `xctestrunEnv`, macOS `permissions.grant`) keep Jackson's duplicate-key last-wins in insertion order. Follow whatever representation 2.2 freezes for maps/sets rather than inventing a vendor-only one; if 2.2 lands without a set representation, that is open question 6. The internal representation must preserve first-occurrence order and duplicate collapse so 2.4's output matches byte for byte.

**Android specifics.** The 25 constructor parameters of `AndroidConfiguration` (`VendorConfiguration.kt:57-82`) mix five nullable no-default `File`/`List<File>` parameters first (`androidSdk`, `applicationApk`, `testApplicationApk`, `splitApks`, `extraApplicationsApk` — missing ⇒ creator-required-but-nullable, per the 2.1 rules; oracle-pin missing vs explicit `null` for exactly these, since the samples rely on omitting `applicationApk`) with defaulted fields (`outputs = null`, `autoGrantPermission = false`, `adbInitTimeoutMillis = 30_000`, `installOptions = ""`, `serialStrategy = AUTOMATIC`, `waitForDevicesTimeoutMillis = 30_000`, `testParserConfiguration = local`, `adbServers = [127.0.0.1:5037]`, `disableWindowAnimation = true`, …). `AndroidTestBundleConfiguration.testApplication` is the one required non-null `File` in the whole WP. **F5:** `adbInitTimeoutMillis` and `threadingConfiguration.adbIoThreads` are accepted, stored and serialised but never used downstream — port them as plain fields, confirm F5's row in `docs/known-kotlin-bugs.md`, and do not "wire them up". `validate()` checks existence-then-regular-file for `applicationOutput`, `testApplicationOutput`, each of `splitApks`/`extraApplicationsOutput`, then each `outputs` bundle in order (`:86-104`), with messages `"<absolutePath> does not exist"` / `"<absolutePath> must be a regular file"` — definition here, stage-(b) call in 2.4. `safeAndroidSdk()` throws `ConfigurationException("No android SDK path specified")` — the same message the factory uses, at a different stage; keep both call sites distinct in the error's stage field.

**SDK lookup (stage a, Android branch).** `ConfigurationFactory.kt:59-70`: the environment is consulted **only** when the bound `androidSdk` is `null`; a non-null file value wins untouched and the environment is never read. When read: `ANDROID_HOME` else `ANDROID_SDK_ROOT` else `ConfigurationException("No android SDK path specified")` (`SystemEnvironmentReader.kt:12-13`, `ConfigurationFactory.kt:62-63`). The found string becomes `File(it)` verbatim (`SystemEnvironmentReader.kt:9`): no `FileDeserializer`, so a relative `ANDROID_HOME` stays relative (against the process directory, like Kotlin's `File`), an empty-string variable yields `File("")` and *no* exception, and nothing checks that the directory exists. In Rust the lookup reads `BindingContext.environment` in order; which occurrence wins if the ordered environment repeats a name follows the pipeline's existing substitution lookup — do not read `std::env` here.

**Apple path rules: two different mechanisms, keep them separate.** (1) At bind time, every `File` field already went through 2.1's `FileDeserializer`: relative ⇒ `canonicalFile` against the Marathonfile directory, absolute ⇒ verbatim (2.1 decision: P3 rejected). (2) At stage-(a) post-processing, the factory *re-resolves* a specific subset (`ConfigurationFactory.kt:71-131` iOS, `:132-188` macOS): bundle paths and iOS `mediaFiles` via `marathonfileDir.resolve(path)` — **no** canonicalisation, a no-op for the already-absolute paths binding produced, observable only for programmatically built configs; but `devices`, `ssh.knownHostsPath` and the public-key `key` via `resolveAgainst` = `dir.resolve(this).canonicalFile` (`:211`), which *does* canonicalise even an absolute path with `/../` in it — so these three fields end up spelled differently from every other `File` field, and that difference reaches logs, `toMap()` (2.4) and the Marathondevices load. A missing `devices` becomes `marathonfileDir.resolve("Marathondevices")` (not canonicalised, `:91-92`/`:149-150`). Password authentication and `null` authentication pass through untouched; only `publicKey` gets its `key` rewritten. The bundle branch then calls `bundle.validate()` — extraction side effects, 2.3b; this WP's post-processing pieces must be composable so 2.4 can order re-resolution → bundle validation exactly as the factory does (bundle first, then media/devices/ssh/xcresult within the same `copy`, `:71-124`). Failure staging: re-resolution and the SDK fill run *inside* the factory's try but throw `ConfigurationException` directly (not re-wrapped as `Error parsing config file …`, which is only for `JsonProcessingException`, `:200-202`); `canonicalFile` I/O failures are likewise not Jackson failures — keep the 2.1 error taxonomy, stage `Parse`.

**`xcresult.pull` → `pullingPolicy` (stage a, iOS and macOS).** `ConfigurationFactory.kt:109-121` and `:167-179`: `pull = true` ⇒ `pullingPolicy = ALWAYS`, `pull = false` ⇒ `NEVER`, `pull = null` (absent or explicit) ⇒ the bound `pullingPolicy` stands. The rewrite preserves the other `xcresult` fields (the Kotlin `copy` mentions only `pullingPolicy` and, redundantly, `remoteClean` — same value; do not read meaning into it). Note the bound `pull` itself stays in the resulting configuration and is serialised by 2.4; the deprecated field is not cleared.

**Apple validation definitions and their messages.** `IOSConfiguration.validate()` (`VendorConfiguration.kt:197-208`) checks in this order: `maxBatchesWithoutProgress` (`"maxBatchesWithoutProgress should not be negative, got …"`), `ssh.validate()`, `workerConnection.validate()`, `xcresult.queue.validate()`, `threadingConfiguration.validate()`, then the bundle presence + `bundle.validate()` (2.3b edge). `MacosConfiguration.validate()` (`:228-233`) checks only SSH then bundle — and is never called by `LogicalConfigurationValidator` (F6; the validator's macOS branch instead compares `xcresult.queue` and `threadingConfiguration.provisioningConcurrency` against fresh defaults, `LogicalConfigurationValidator.kt:49-61` — those two comparisons are 2.4's, but they require value equality on `XcresultQueueConfiguration`/`ThreadingConfiguration` and default instances constructible here). `SshConfiguration.validate()` (`SshConfiguration.kt:27-42`) throws **`FileNotFoundException`**, not `ConfigurationException`, for a missing private key (`"Private key not found at <absolutePath>"`) and missing known-hosts file (`"knownhosts file not found at <path>"` — note: the `File`'s own spelling there, not `absolutePath`), then `ConfigurationException` for `keepAliveMaxCount < 1`; order is key → known-hosts → count. `WorkerConnectionConfiguration.validate()` (attempts/backoff/lateJoinCutoff/retryInterval, in that order) and `pauseAfter()`'s doubling (`attempt → min(backoff · 2^(attempt-1), retryInterval)`, zero backoff stays zero, past `attempts` it is `retryInterval` iff late join else `null`) port as pure functions (`WorkerConnectionConfiguration.kt:28-59`). `XcresultQueueConfiguration.validate()` interpolates the bound capacity into the concurrency/workerCapacity messages (`XcresultConfiguration.kt:29-43`). All of these are definitions only here; none runs during binding, and none is called by `post_process`.

**Regexes, equality and secrets.** The only user regex in scope is `NmTestParserConfiguration.testClassRegexes` (`Collection<Regex>`, default `["^((?!Abstract).)*Test[s]*$"]`, `apple/TestParserConfiguration.kt:16`). Under D6 that default pattern does not compile in the Rust `regex` crate (negative lookahead); per WP 1.4/2.1, keep it as the distinguishable default (`jcompat::regex_patterns::DEFAULT_TEST_CLASS_PATTERN` + `default_test_class_matches`) and compile only explicitly supplied patterns via `Value::regex`, failing at load naming pattern and field. The representation therefore cannot be a plain `Vec<JavaRegex>` holding the default — see open question 7. Kotlin's `equals` compares pattern strings while `hashCode()` hashes the `Regex` *objects* (`:17-29`), the F7 inconsistency again: record it as a new row in `docs/known-kotlin-bugs.md`, and implement the approved consistent pattern-based equality (0.6 D1). For secrets, follow 2.2's approved line: hand-written `Debug` that cannot print `SshAuthentication` passwords (Kotlin `toString` shows only the username, `SshConfiguration.kt:58-60`) or Android's `consoleToken`; the real `toString`/`toMap()` rendering stays 2.4's and must reproduce Kotlin's masking exactly (password auth only — `publicKey` and `consoleToken` are *not* masked by Kotlin's data-class `toString`; keep that asymmetry in 2.4, flag it here so the types don't lose the information).

**Apple accessors are pure projections.** `ConfigurationExtensions.kt` (62 lines incl. blanks): `bundleConfiguration()`/`xctestrunEnv()`/`xcresultConfiguration()` return the iOS/macOS fields and `null` for Android/Stub/Empty; `skipCopyingDerivedData()` returns the iOS field and `false` otherwise (macOS included). No defaults are invented for the `null` cases — callers in Phase 4/5 handle them, as in Kotlin.

## Proposed simplifications (pragmatic parity — for orchestrator approval, **not decided**)

Per the user's direction: few users; don't emulate quirks only exotic inputs reach. D6/D8/D9 already apply. Until a proposal is approved, the behaviours above stand and a divergence is a bug; an approved item is recorded with the deviations (PLAN §3.11 style) and its corpus rows are marked, not dropped.

- **P1, one locale for all three enum creators.** Use `Locale.ENGLISH` uppercasing for Android `RecorderType` too, instead of reproducing its JVM-default-locale creator. Diverges only on machines whose default locale uppercases differently (Turkish/Azeri `i`), where Kotlin either rejects `video` or accepts spellings English rejects; consistent with D8's en-US stance.
- **P2, empty `ANDROID_HOME`/`ANDROID_SDK_ROOT` count as unset.** Fall through to the next source (and then to `No android SDK path specified`) instead of accepting `File("")` as an SDK. Diverges only when a variable is set-but-empty, where Kotlin proceeds with a meaningless path and fails later with an unrelated message.
- **P3, one path rule in post-processing.** Apply the same `resolve` + `canonicalFile` treatment to the bundle/media paths as to `devices`/`knownHostsPath`/key (or to none), instead of keeping the factory's two mechanisms. Diverges only in retained spellings (`/../`, symlinked prefixes) of paths that binding already made absolute — i.e. only for programmatically built configurations and absolute Marathonfile paths with redundant components.
- **P4, `infrastructure` nulls in nested sections take the default instance.** Treat an explicit `null` for a whole nested section (`timeoutConfiguration: null`, `ssh: null`, `xcresult: null`…) as the section's default instead of rejecting it as a non-null reference. This **changes accept/reject**, unlike most entries here; listed because hand-edited files plausibly contain it, but it needs an explicit decision against the 2.1/2.2 null rules.
- **P5, don't port the builders and `var` mutability.** Skip `AndroidConfigurationBuilder` (programmatic convenience, no YAML role at `e47352f2`; add a Rust constructor helper only if 3.10/CLI construction needs one) and model the Kotlin `var` timeout fields as plain values (nothing in the config layer mutates them after binding; the factory uses `copy`).
- **P6, drop `pull` after the rewrite.** Clear the deprecated `xcresult.pull` once `pullingPolicy` is derived, so `toMap()`/serialisation (2.4) never shows both. Diverges in 2.4's output for files that still set `pull` — probably reject this; listed so the round-trip expectation is decided once, here or in 2.4.
- **P7, sets as ordered vectors throughout.** Represent every Kotlin `Set`/`MutableSet` field as the binder's ordered, duplicate-collapsed sequence without a distinct set type or order-insensitive equality. Diverges only where Kotlin *compares* configurations as sets (validator default comparisons — `XcresultQueueConfiguration` has no set field, so the F6 comparisons are unaffected — and round-trip equality in 2.4, where both sides come from the same file).
