# WP 3.8: `DevicePoolActor` and `Scheduler`

**Implementer:** Claude Opus (or Muse Wonder Full). **Reviewers:** Muse Wonder Full and an instance from a different model family than the implementer. **Effort:** H. **Depends on:** 3.6, 3.7 (PLAN §7). 3.6 is merged. 3.7 is under review on `wp/3.7-queue-actor`, so start from its API and rebase once it merges. **Branch:** `wp/3.8-pool-scheduler`.
Critical path: … 3.6 → 3.7 → 3.8 → 3.10 (PLAN §7). This WP is the hub of a run. Every batch outcome passes through the pool on its way to the queue and the accumulator, and the pool's termination decides when the Scheduler returns and what the run's result is. Two things are expensive to get wrong: losing a result to a premature shutdown, and a shutdown that never comes.

## Behaviours to reproduce

**DevicePoolActor** (P):
- **Dispatch** (P:41–56): one handler per message, run serially in mailbox order. While the handler suspends (only in `terminate`'s `awaitQueue`), later messages wait in the mailbox, and `close()` discards them.
- **`addDevice`** (P:301–311):
  - If the serial is already present: WARN `device <serial> already present in pool <name>`, and return.
  - Otherwise: DEBUG `add device <serial>`, then `DeviceActor::spawn` under the supervisor, then insert by serial, then `try_send(Initialize)`.
- **`removeDevice`** (P:283–297):
  - DEBUG `remove device <serial>`. Remove by **serial alone** (C27: a stale disconnect removes the replacement).
  - If an actor was removed: push its device onto `terminatingDevices`, run `releaseDevice`, and `try_send(Terminate)`.
  - DEBUG `devices.size = <n>`.
  - If `noActiveDevices()`: DEBUG `pool <id>: noActiveDevices`, then `terminate()`. This happens even when the serial was unknown to this pool.
- **`deviceReady`** (P:170–182):
  - Drop the message unless `devices[serial]` is this very device. Drop it while a request, an assignment or a parking for that device exists.
  - If the device has a pending `failedBatches` entry: store it as `ready` and wait. Otherwise `requestBatch`.
- **`requestBatches`** (P:184–204):
  - Reserve `requests[serial] = actor` **before** sending, and only devices without a request in flight ask.
  - One device sends `RequestBatch(info, workerId)`; several send `RequestBatches(list)`.
  - If the send fails, unreserve and park every asker.
- **`requestParkedDevices(retryWorkers)`** (P:209–213): split the parked devices with a stable partition. Devices whose `workerId` is in `retryWorkers` go last; devices with a null worker go first. Clear the parked set, then send one `requestBatches`. Parked devices are a `LinkedHashSet`, so they keep insertion order (lifecycle order table).
- **`parkDevice`** (P:215–217): remove the request; park the device only if the request held a live actor. A `null` entry (the device left) is dropped.
- **`executeBatch`** (P:219–229):
  - If no request entry exists, or the entry is `null` (a left device): DEBUG `pool <id>: device <serial> left before receiving batch <id>`, then `RejectBatch(info, batch)`, so no attempt is used.
  - Otherwise record the `Assignment(device, batch)` and `try_send(Execute)`. A closed device later reports `Terminated`, which rejects the batch.
  - Note that `requests.remove` returns `null` both for a missing key and for a `null` value.
- **`deviceCompleted`** (P:148–152): release the assignment, send `Completed`, then `awaitOutcome` **only** if failed or uncompleted is non-empty.
- **`deviceReturnedTestBatch`** (P:122–127): release the assignment, send `ReturnBatch(info, batch, reason)`, then `awaitOutcome`.
- **`awaitOutcome` / `outcomeProcessed`** (P:158–168): `ConfirmOutcome` is sent after the outcome. The `FailedBatch` entry is recorded only if that send succeeded. On `OutcomeProcessed`, the stored ready actor asks, if it is still `devices[serial]`. Lifecycle requires the queue's `Notify` to come before `OutcomeProcessed`, and the parked devices to ask first.
- **`deviceTerminated`** (P:129–146):
  - Remove the device from `devices` only on identity; remove it from `terminatingDevices` by identity; run `releaseDevice`.
  - An unreleased assignment means the batch never started: DEBUG `… terminated before starting batch <id>`, then `RejectBatch`.
  - DEBUG `… terminated. devices.size = <n>`.
  - If `noActiveDevices()`: ERROR `pool <id>: all devices terminated, remaining tests will not run`, then `terminate()`. The ERROR fires even if no test remains; the oracle will show when.
- **`releaseDevice`** (P:247–255): a request in flight becomes `null`, so the reply is rejected, not delivered. Unpark the device, and drop its `FailedBatch`, both by identity.
- **`onQueueTerminated`** (P:114–120): DEBUG, then `try_send(Terminate)` to every device in map order (a `LinkedHashMap`, so insertion order), then `terminate()`.
- **`terminate`** (P:263–281):
  - DEBUG `terminate pool <id>`.
  - `awaitQueue`: if `try_send(IsEmpty)` fails, return at once. Otherwise wait for the reply **or** the queue job's completion (`select(rx, handle.job().join())`). The Boolean answer is ignored.
  - Then cancel the supervisor (queue and devices), then `close()` (cancel the own job, discard the mailbox).
  - A later `terminate` cannot happen, because the mailbox is gone.
- **`sendToQueue`** (P:236–242): `QueueHandle::try_send`, with DEBUG `pool <id>: queue is closed, <Variant> is dropped` on failure, where `<Variant>` is the Kotlin simple class name.
- **`FromScheduler::Terminate`** (P:45) has no sender at `e47352f2`. It still maps to `terminate()`.
- **3.7's open question 1 is answered here:** the pool closes itself only in `terminate`, after `awaitQueue`, so the queue never sends to a closed pool while it still has a reply to give. The reply to `IsEmpty` is the last thing it sends, except for `Notify`/`ExecuteBatch` replies already sent, which `close()` discards. Pin this with a test.

**Scheduler** (S):
- **The job graph** (lifecycle :70–80): the subscription is launched in the **run's** context (S:74–87), not under the detached `job` (S:45). The pool actor's context is the subscription's context, with its own `Job(job)` (S:79,121).
- **`execute`** (S:55–72):
  1. Start the subscription.
  2. Under `withTimeout(deviceInitializationTimeoutMillis)`, poll `pools.isEmpty()` with `delay(100)` on the scheduler clock. A non-empty map is seen without any delay. A timeout ≤ 0 expires at once. The values are signed i64 (lifecycle :229–232).
  3. On timeout (**only** a `TimeoutCancellationException`): cancel and join the detached job, then fail with `NoDevices` with the empty message `""`. The subscription keeps running, because it is not a child of that job.
  4. Otherwise run `for (child in job.children) child.join()` with the **lazy observed-child traversal** (`join_observed_children_in(caller)`), never a snapshot.
  5. Return `results.all { aggregateResult() }`. This short-circuits at the first `false`, so a later pool's `Expected to run <test> but no events received` ERROR lines (`PoolProgressAccumulator.kt:361`) are not logged. Take each accumulator's lock (3.7 open question 2).
- **The subscription loop** (S:74–87): one event at a time, in channel order. It ends only when the channel closes (3.10 terminates the provider) or the run is cancelled.
- **`onDeviceConnected`** (S:102–128):
  1. Filter. If the device is filtered out: DEBUG `device <serial> is filtered out by configuration. skipping`.
  2. `associate`, then DEBUG `device <serial> associated with poolId <name>`.
  3. Create the accumulator if absent (`computeIfAbsent`, before the pool).
  4. Create the pool if absent: DEBUG `pool actor <name> is being created`. With D13 this is preceded by `QueueActor::prepare` awaited **in the subscription loop** (open question 1).
  5. `safeSend(AddDevice)` (S:123). A pool that has terminated stays in `pools`, closed, so a device that connects later for that pool is **silently dropped** (B1). The `?: logger.debug { "not sending…" }` branch is unreachable.
  6. `track.deviceConnected(poolId, info)`. This is called even when the AddDevice was dropped.
- **`onDeviceDisconnected`** (S:89–100): the same filter (DEBUG `… is filtered out by configuration. skipping disconnect`), then DEBUG `device <serial> disconnected`, then `safeSend(RemoveDevice)` to **every** pool, not only the associated one. **No `deviceDisconnected` is tracked** (B2): `Track.deviceDisconnected` has no caller in `e47352f2`.
- **`filteredByConfiguration`** (S:130–141): a device is filtered out unless (the include list is empty, or any include regex fully matches the serial) **and** (the exclude list is empty, or no exclude regex matches it). The regexes are the D6 `JavaRegex` with `matches`.
- **`safeSend`** (`actor/extensions.kt:8–11`): check `isClosedForSend`, then `send`. On the single core thread this is `try_send` with the failure ignored (lifecycle :182, S3).

**Kotlin bugs.** **C27** is reproduced here: it needs a runtime test (`stale_disconnect_removes_the_replacement`, since D40 `stale_disconnect_leaves_the_replacement_d40`), after which its row becomes `confirmed`. Candidates to confirm with the oracle, and to add as the next free C rows if kept (main ends at C47):
- **B1:** a pool that has terminated is never recreated, so devices that connect for it later are dropped while still being tracked as connected (S:119–127).
- **B2:** disconnects are never tracked (S:89–100).
- **B3:** `RemoveDevice` is broadcast to every pool. A pool that does not know the serial still runs the `noActiveDevices` check (P:283–297); harmless in practice, but each such pool logs DEBUG lines.
- **B4:** a pool's ERROR `all devices terminated, remaining tests will not run` fires even when nothing remains, if a device terminates before the queue's `Terminated` arrives (P:142–145). Keep this only if the oracle shows it.

## Proposed simplifications (pragmatic parity; for orchestrator approval, **not decided**)

Until one is approved, the behaviour above stands. Each approved item becomes a findings entry, or a D-row if it changes externally visible behaviour. Its oracle rows are marked, not deleted.

- **S1, the three `EstimateHook` rows:** port them with a test-support seam in place of the metrics hook. See open question 2. This changes no production behaviour.
- **S2, pool iteration order:** Kotlin iterates `pools`/`results` in `ConcurrentHashMap` order: `DevicePoolId(name).hashCode()` spread, the table size, and resizes. This order shows in only two places: the order in which RemoveDevice reaches the pools (DEBUG interleaving across pool loggers), and which pools' `Expected to run …` ERROR lines appear when two or more pools fail. Use pool **creation order** (`IndexMap`) instead. Only multi-pool runs with failures reach the difference.
- **S3, `safeSend`:** Kotlin's check-then-send can throw `ClosedSendChannelException` if the pool closes between the two calls on another thread, which would end the subscription. On the single core thread no such window exists. Use `try_send`, ignore the failure, and do not reproduce the race.
- **S4, pool creation under D13:** await `prepare` in the subscription loop, so device events keep their Kotlin order. If `prepare` fails (by 3.7 P1, in practice a cancellation), end the subscription with that error, as an exception thrown in Kotlin's `computeIfAbsent` would. Do not retry or skip the pool. The pool appears in `pools` only after `prepare`, so the first-device wait can expire during a slow prefetch; in Kotlin the pool appears at once. Accept this; it is reachable only with a remote metrics backend slower than `deviceInitializationTimeoutMillis`.
- **S5, the characterization row:** port its assertions (first wave, makespan, zero idle time) and its printed table. Do not assert the `request next batch` and `wakeUps` counts, which Kotlin only prints. Log the table through the test's stdout, as Kotlin does.

## Open questions for the orchestrator

1. **Where `QueueActor::prepare` is awaited** (3.7 decision 2 leaves this to 3.8). Recommend S4: inline in the subscription loop, before `pools` gets the pool, with the accumulator created first as Kotlin does (S:115–121). The alternative is to spawn the pool at once and prefetch concurrently. That reorders AddDevice relative to later device events and needs a pending-pool state Kotlin does not have. Lifecycle's "single-flight across concurrent pool builds" is then never exercised by 3.8, which is harmless.
2. **The three `EstimateHook` rows** (`batch picked for a device that has left…`, `…replaced device…`, `batch of a device that stops before starting it…`) inject RemoveDevice/AddDevice or a crash while the queue is picking a batch. They rely on `executionTime` being queried synchronously inside the batch pick. Under D13 that query happens at `prepare`, so the hook would fire before any device exists. Recommend a `test-support` hook on 3.7's queue that runs just before the `ExecuteBatch` reply is sent: 3.7's `with_observer` runs after the message, which is too late. This is the same moment the Kotlin tests target. The alternative is to drop to `n/a`, which loses the only coverage of the `requests[serial] = null` path. This touches 3.7 code: approve the additive seam here, or route it through the 3.7 review.
3. **The C27 runtime test and B1–B4:** confirm that each is first confirmed with the oracle and then reproduced (D5), as in 3.6 and 3.7.
4. **`execute`'s error type:** `NoDevices("")` is `VendorError::NoDevices` (0.6 taxonomy, `exceptions/NoDevicesException.kt`). `aggregate_result` returns `VendorResult<bool>`, whose `Err` (an empty-test pool, `Empty collection can't be reduced.`) Marathon's guard makes unreachable. Recommend `execute() -> VendorResult<bool>`, propagating both. 3.10 maps them.
5. **The Scheduler's `Tracker` call is async** (`Tracker::device_connected` returns a `VendorFuture`). Kotlin's call is synchronous inside the loop. Recommend awaiting it in the loop, with a dispatch off core if the tracker implementation needs one (3.9a). Confirm this does not conflict with 3.9a's plans.
