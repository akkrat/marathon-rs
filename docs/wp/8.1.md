# WP 8.1: The Phase 8 contract and Rust-owned golden tests

Effort **M**. Branch `wp/8.1-native-contract`, based on tag `0.12.0-rc.1` (commit `21c4d67b`).

## Why

Phases 0–7 ported marathon and proved parity against the Kotlin original (oracle tables, JVM
differential records, ported Kotlin tests). `0.12.0-rc.1` is the last release held to that standard.
Phase 8 removes Java and Kotlin emulation from the code (`JavaString`, the Gson and Jackson writers,
logback emulation, the coroutine `Job` emulation, ImageIO quirks, Clikt emulation, the SnakeYAML port),
one WP at a time. Each of those WPs needs a gate that says "the contract still holds" without asking
"is it byte-identical to the JVM". This WP builds that gate and writes the rules down. **It changes no
runtime behaviour.**

## The contract (decided by the owner, 2026-11-09)

Must stay:

1. **Input.** Every Marathonfile and Marathondevices the code accepts today is accepted with the same
   meaning: YAML 1.1 scalars (`yes`/`no`/`on`/`off`), `${VAR}` and `${VAR:-default}` substitution, ISO-8601
   durations and instants (`PT5M`, `-P14D`, `-PT168H`), the Jackson coercions the binder applies. Inputs
   rejected today stay rejected (the error wording may change).
2. **CLI syntax.** Subcommands, flags, their defaults and the exit codes. Help, usage and error wording
   may change.
3. **Results.** The same output files at the same paths with the same names, and the same **data**
   in them: JSON, XML and YAML files compare as parsed data with key order, element order and
   attribute sets preserved, not as bytes (`<` vs `<`, `1.0E10` vs `10000000000.0` are equal).
   Text, image and binary outputs compare as they do today. The fragmentation hash (which tests go to
   which shard) and Allure history IDs stay exactly the same.
4. **Commands sent to workers** (adb, ssh, rsync, xcrun, xcodebuild), as today.
5. **Logs.** The per-test progress lines (`[<pool>] ... passed` and their siblings) and the end-of-run
   summary block (`Marathon run finished`, the `\tRaw: ...` lines) keep their text format; CI scripts
   parse them. Any other log text may change.

May change (each change gets a D-row in PLAN.md §3.11 and, where it touches a result file, a reviewed
golden update):

- JVM artefacts that leak into output: identity strings such as `…Configuration@6d4b1c02` in Allure
  `environment.xml`, `[Ljava.lang.Object;@…` in annotation values, Java exception class names in
  messages. Replace them with real values.
- Kotlin bugs that only show on exotic input (lone surrogates, supplementary-plane sort order, and the
  like), when keeping them costs emulation code.

## Deliverables

### 1. Rules (docs)

- **PLAN.md:** a new §3.12 "Phase 8 contract" holding the section above (rephrase freely, keep every
  point), and a "Phase 8: Native cleanup" table in §7 with rows 8.1 and 8.2 (8.2: replace `JavaString`
  with `String`, M, depends on nothing; see `docs/wp/8.2.md`). Keep `scripts/check_plan_dag.py` green.
  Below the table, a short bullet list of the later candidates (no IDs): `JavaPath` and the small jcompat
  modules (jnum, jtime, utf8, net); typed errors instead of Java class strings in `Failure`; serde writers
  instead of Gson/Jackson emulation; `tracing` instead of logback emulation; plain async reads instead
  of the Apple polling readers; `BTreeMap` with a sequence tie-breaker instead of `JavaPriorityQueue`;
  the `image`/`gif` crates instead of ImageIO/AWT and the JDK sRGB profile; `Display`/serde instead of
  Kotlin `toString` rendering; tokio `JoinSet`/`CancellationToken` instead of the coroutine emulation;
  `clap` instead of Clikt emulation; a YAML library with a small YAML 1.1 scalar layer instead of the
  SnakeYAML port (last, highest input risk). State that `0.12.0-rc.1` is the JVM-parity baseline.
- **CLAUDE.md:** the "Behaviour parity" bullet and its sub-bullets become: Phases 0–7 followed JVM
  parity (port the bugs, record them); from Phase 8 on, the contract in PLAN.md §3.12 is the rule, a
  contract change needs a D-row, and golden updates are reviewed. The `jcompat` bullet: Phase 8 WPs may
  replace jcompat types with std or crate equivalents as their brief says; until a WP does so, the old
  rule holds for new code. The `Tests` bullet: a Phase 8 WP may delete or rewrite a test that pins a
  removed JVM quirk; its parity-matrix row becomes `n/a` with reason `8.x: <D-row>`. Keep the rest.
- **docs/design/differential.md and tools/differential/README.md:** say that JVM captures are
  historical (no new JVM generations) and how the native goldens below are checked and re-blessed.

### 2. Native goldens for results and worker commands

`tools/differential` already runs 15 bounded whole-vendor cases natively (`run native-vendors`) and
compares them with pinned JVM records through a typed comparator (`docs/design/differential.md`
"Typed comparison"). Add a Rust-owned reference:

- A `bless` command that captures the native records of every registered case from the current tree
  and stores them as the selected golden (a new generation, e.g. `native-v1`), with provenance (commit,
  host profile). Never run by the gate. Capture `native-v1` from this branch.
- The gate's `check` compares native runs with the native golden; the JVM records stay in the repo as
  history but no longer gate. Structured files (JSON, XML, YAML) compare as parsed data per contract
  point 3; everything else as today. Keep the existing normalizations for run-dependent values.
- Keep added fixture volume small (aim < 10 MB): store normalized views where the full record is not
  needed for the comparison.
- Adversarial self-test: a changed JSON value, a reordered key, a missing file and a changed worker
  command each fail; `<` vs `<` and `1.0E10` vs `10000000000.0` pass.

### 3. Config corpus golden

A Rust test (e.g. `crates/marathon-cli/tests/config_contract.rs`) over every Marathonfile and
Marathondevices under `fixtures/` (configuration, differential inputs, schema corpus, vendor fixtures):
accepted or rejected, the exit code, and for accepted ones a canonical dump of the parsed
configuration, compared with goldens under `fixtures/contract/config/`. Use the existing canonical dump
(`marathon-config/src/dump.rs`, the hidden `config-dump`) for now; a later WP that replaces it re-blesses
only if the data changes. Provide a bless switch (env var) that rewrites the goldens; the test never
rewrites them by itself.

### 4. CLI table

`crates/marathon-cli/tests/cli_contract.rs`: a table of argv cases covering every subcommand and flag
of the CLI (see `crates/marathon-cli/src/args.rs` and the Clikt definition it ports), asserting exit code
and the parsed effect, not wording. Include `--help`, `--version`, an unknown flag, a missing
Marathonfile, and each value-taking flag with a valid and an invalid value.

### 5. Log-line pins

A test that pins the exact text format of the progress lines and the summary block (contract point 5).
Reuse existing reporter tests if they already pin it; then just name them in the doc.

### 6. Gate

`scripts/check.sh` runs the new checks. Keep the source-inventory, parity-matrix and fixture-sync
steps (they are skipped without `MARATHON_KT`). Keep the oracle-table validation while the tables exist.

## Out of scope

Any change to runtime code under `crates/*/src` other than what a test hook strictly needs (say why in
the report). Replacing any jcompat module. New JVM captures.

## Acceptance

- `scripts/check.sh` passes (export `MARATHON_KT` to the Kotlin checkout first; see CLAUDE.md).
- The new goldens match the current tree; the adversarial cases fail as intended.
- The docs say exactly what the contract is and how to re-bless.
- Report: what was added, the fixture volume added, anything in the contract you could not cover with
  a test (and why).
