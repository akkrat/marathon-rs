## Deliverables and boundary

In `crates/marathon-core` (new module `execution::device`, ported from the four Kotlin files):

1. **`DeviceState`, `DeviceEvent`, `DeviceAction`** as Rust enums. `Running` carries the `BatchRef` and the result cell (`Arc<SharedDeferred<TestBatchResults>>`, parentless, created inside the `Ready + Execute` rule). The actor's `DeviceEvent` must not collide with the provider's `vendor::DeviceEvent` (`vendor.rs:64`). Keep them in separate modules; do not rename either.
2. **`DeviceActor`**: an `ActorHandler<DeviceEvent>` run by 3.1's `RuntimeActor`, with an in-crate constructor taking the pool id, the pool handle, `Arc<Configuration>`, `DeviceRef`, the parent job (the pool's supervisor, passed in by 3.8), and the runtime, clock, hooks and logging. State machine, prepare/execute job slots, the once-only `Terminated` flag and the stored owner context live in shared actor state (`Rc<RefCell<…>>` on core). `started` stores the owner `TaskContext` and registers the own-job completion callback, which holds a weak reference to the actor (lifecycle "Explicit execution context").
3. **Vendor bridge for `prepare`/`execute`**: dispatch the `Send` vendor future off core. Pass the core task's cancellation as `VendorContext.cancellation`, then wait for the vendor's **own** outcome, joinably, through its cleanup. Kotlin's catch table classifies what the vendor threw (`K/execution/device/DeviceActor.kt:191–207`), not the core's cancellation reason. Wrap each call in the barriers `core.DeviceActor.prepare:<serial>` and `core.DeviceActor.execute:<serial>`, exactly where patch 0002 puts them (prepare: inside the `isActive` check and the inner `try`, once per attempt).
4. **The "Carried to 3.6" items from 3.1** (section below). These are changes to 3.1's executor, with regressions.
5. **The pool-facing message type**: see open question 1. At minimum, `FromDevice::{IsReady, CompletedTestBatch, ReturnTestBatch, Terminated}`, carrying `DeviceRef`, `TestBatchResults`, `BatchRef` and the `JavaString` reason.

**Not 3.6:** the pool's reservation, parking and identity checks, and `RemoveDevice` by serial (C27); everything in `DevicePoolActor`/`Scheduler` is 3.8. The queue and the use of the `ReturnBatch` reason are 3.7. `StubDevice`/`StubVendor` (inventory 3.10; see open question 2). Vendor `Device` implementations. Root run flow, shutdown, appender wiring (3.10). Scenario-level replay comparison with patched Kotlin (3.10/7.1). No 0.6 trait signature changes beyond the approved-style additive one in carried item C3.

## Behaviours to reproduce (`K/execution/device/DeviceActor.kt` unless stated)

- **Graph** (`:39–81`). Connected: `Initialize`→Initializing [Initialize]; `Terminate`→Terminated [Terminate()]. Initializing: `Complete`→Ready [NotifyIsReady()]; `Terminate`→Terminated. Ready: `Execute`→Running(batch, new cell) [ExecuteBatch]; `Terminate`→Terminated. Running: `Terminate`→Terminated [Terminate(this)]; `Complete`→Ready [NotifyIsReady(this)]. Terminated: `Complete`/`Terminate` → `dontTransition()`, a Valid transition with no side effect and no log. Anything else is Invalid: ERROR `Invalid transition from <state> event <event>` (`:82–87`), no side effect, no exception. Reachable in practice: `Execute` arriving at a Terminated actor that has not closed yet (the pool relies on `Terminated` to reject the assignment, `DevicePoolActor.kt:225–228`).
- **Side effects** (`:88–104`): the new state is stored first (`StateMachine.kt:46–65`), then account for the batch, then readiness/termination. Reasons are exactly `Device <serial> reported no results` (`:94`) and `Device <serial> terminated` (`:101`). Kotlin runs these inside a reentrant `synchronized` transition. Rust's `&mut` machine is not reentrant, so run them after the borrow is released, before any await. No side effect may cancel or complete a job while the machine is borrowed: a synchronous completion callback would re-enter it. Test this.
- **`accountFor`** (`:138–152`): first try to seal the cell with a cancellation carrying `reason`, then read whichever completion won. A value gives `CompletedTestBatch(device, results)`. An exception gives `ReturnTestBatch(device, batch, failure.message ?: reason)` plus DEBUG `Returning batch <id>. Reason: <r>`. It uses a synchronous `try_send`; on failure, WARN `Pool is closed, outcome of batch <id> is dropped`. Exactly one transition leaves Running. A late vendor `complete` returns `false` (test at `:149–172`).
- **Readiness** (`:154–158`): a sibling task under the **owner** job (from the stored `started` context, never the execute task's job) that does a suspending `send(IsReady)`. It never runs if the owner is cancelled first, so readiness can be lost. A send to a closed pool ends the task as a cancellation (silent, does not fail the actor). Pin this with the oracle.
- **`initialize`** (`:163–185`): DEBUG `initialize <serial>`. A task under the owner job runs `with_retry(30, 10_000)` (`Retry.kt:8–24`): attempts count from 1, the 10 s delay is on the scheduler clock under the initialize task's own job, and cancellation is never retried. Before each attempt `if (isActive)` (`:168`) checks the initialize task's job; if it is inactive, the attempt "succeeds" without calling prepare, and `Complete` follows. A non-cancellation prepare failure logs DEBUG `device <serial> initialization failed. Retrying` with the exception on **every** attempt, including the 30th (`:174`). Success leads to `transition(Complete)`. Any escaping `Exception` leads to ERROR `Error <message>` with the exception (`null` message prints `Error null`), then `transition(Terminate)` (`:180–182`). That `Exception` can be the 30th failure, a vendor cancellation, `LeavePool` NotBooted/NotAdmitted (a `CancellationException` subclass, test at `:129–149`: one attempt, then Terminated), or the task's **own** cancellation.
- **`executeBatch`** (`:187–209`): DEBUG `executeBatch <serial>`, then a task under the owner job. Vendor outcome → effect, following lifecycle's table. `Ok`: `Complete`. `Cancelled`/`LeavePool`: WARN `Device execution has been cancelled` (with the exception), then `Terminate`. `DeviceLost`: ERROR `Critical error during execution`, then `Terminate`. `BatchExecution`: WARN `Test batch failed execution`, try to seal the cell with `"Test batch failed execution:\n" + <trace>`, then `Complete`. Every other `VendorError` (`DeviceSetup`, `IncompatibleDevice`, `TestParsing`, `NoDevices`, `Transfer`, `Other`, and panics): ERROR `Unknown vendor exception caught. Considering this a recoverable error`, try to seal with `"Unknown vendor exception caught:\n" + <trace>`, then `Complete`. The trace is our rendering of the `Failure` chain (§3.10). A task cancelled before its first poll runs no body, logs nothing and makes no transition (`launch_retained`, Kotlin DEFAULT start).
- **`terminate`** (`:211–219`): DEBUG `terminate <serial>`. A sibling task under the owner: cancel the initialize task and join it, cancel the execute task and join it, `notifyTerminated`, then `close()`. Each join is **cancellable** (Kotlin `cancelAndJoin` = `cancel()` + `join()`, which throws if the caller is cancelled). Use `cancel` + `join_in(context.job)`, not the protected `cancel_and_join`. `close()` cancels the owner and discards the mailbox (`Actor.kt:50–53`).
- **Completion callback** (`:111–118`, registered in `started`): on any owner completion, `transition(Terminate)` then `notifyTerminated()`. From Running this accounts for the batch, even if the execute task never started (test at `:215–260`). The `terminate()` it launches never runs.
- **`notifyTerminated`** (`:221–225`): once only (a `Cell<bool>` on core replaces `AtomicBoolean`); a failed `try_send` is ignored without a log.
- **Mailbox** (`:120–129`, `Actor.kt:29–35`): FIFO, no yield between buffered messages (Rust's receive loop matches). So `Execute` and `Terminate` queued together run before the execute task polls, the vendor is never called, and the batch is returned as terminated. `GetDeviceState` completes its cell with the current state outside the machine (but see S4).
- **Logger** `DevicePool[<pool name>]_DeviceActor[<serial>]` (`:37`). State and event text in logs comes from `DeviceState.kt:18`/`DeviceEvent.kt:13` (`DeviceState.Connected`, `DeviceEvent.Complete`), **but** the data classes `Running`, `Execute` and `GetDeviceState` generate their own `toString` (to confirm with the oracle; see S1).
- **Ordering** (lifecycle order table): the outcome is enqueued before `Terminated` and before any later `IsReady`. The parentless result cell is never sealed by a waiter's cancellation.

**Kotlin bugs.** None of `docs/known-kotlin-bugs.md` is owned by 3.6. Candidates to confirm with the oracle and add as rows if kept: (K1) an orderly terminate during preparation logs ERROR `Error <coroutine cancellation message>`, because `catch (e: Exception)` at `:180` catches the task's own cancellation; (K2) the last failed attempt is logged as `…initialization failed. Retrying`, although no retry follows (`:174`).

## Carried to 3.6 from 3.1 (`docs/wp/3.1-findings.md`)

- **C1:** `spawn_blocking` work is not wrapped by replay runnable tracking. Track it as runnable until it completes, so `drain_current`/quiescence cannot return while blocking work is in flight. Add a regression.
- **C2:** a future that blocks inside `poll` can hang controlled replay, including the in-executor watchdog. See S5 (fix or document).
- **C3:** add a public cancellable observed-child traversal, `Job::join_observed_children_in(caller: JobRef)`, as a provided method mirroring `join_in`. It is an additive 0.6 trait repair like 3.1-U1; 3.8's Scheduler is its consumer. Regressions: caller cancellation during a traversal, and the existing JVM traversal rows.
- **C4:** recursive job-completion cascades can exhaust the stack. Make completion propagation iterative and keep the callback order (early child → parent → late child, JVM row). Regression: a deep chain (≥100,000 jobs) on the default test-thread stack.
- **C5 (round 3):** the Deferred "already completed" latch is set only through the `Notify` wake, so a completion from another thread before the first poll can lose to a cancellation that is already pending. 3.6 introduces exactly that: a vendor-thread `complete` racing core-side waiters and seals. Read the cell's state directly before considering the waiter's cancellation. Regression: a repeated vendor-thread race, reporting its iteration count.

## Proposed simplifications (pragmatic parity; for orchestrator approval, **not decided**)

Until one is approved, the behaviour above stands. Each approved item becomes a deviation note and its oracle rows are marked, not deleted.

- **S1, invalid-transition text:** log `DeviceState.Running` / `DeviceEvent.Execute` (plus the batch id) instead of the data-class `toString`. The real text contains a `CompletableDeferredImpl{…}@<identity hash>` and the whole `Test` list with metadata. Only an ERROR line in a termination race differs.
- **S2, coroutine-internal cancellation messages:** keep vendor-originated messages exact, and match Kotlin's internal texts (`DeferredCoroutine was cancelled`, `Job was cancelled`, `Parent job is Cancelling`) only on the paths the oracle shows. Always drop JobCancellationException's `; job=…@hash` suffix. This affects the K1 ERROR line, WARN throwables and DEBUG return reasons only.
- **S3, JVM `Error` in prepare:** Kotlin retries `Error`s, and after the 30th lets one fail the actor job instead of logging `Error …`. Rust has no Error class, so treat every non-cancellation `VendorError` and every panic as an `Exception`. Only OOM/StackOverflow-class failures differ.
- **S4, `GetDeviceState`:** it has no caller at `e47352f2` (`grep -rn GetDeviceState` finds only its declaration and `:122`). Omit the event.
- **S5, carried item C2:** do not make replay robust to futures that block in `poll`. Instead, add a wall-clock watchdog thread outside the executor to test-support `run_virtual`, which fails the scenario with a diagnostic. Production is unaffected.

## Open questions for the orchestrator

1. **`DevicePoolMessage.kt` (31 lines) is inventoried to 3.8**, but 3.6 must send `FromDevice` messages and depends only on 3.1. Recommend moving the whole file to 3.6 (inventory `3.8 → 3.6`; it is a plain enum over existing model types), with the pool handle typed `Rc<dyn Actor<DevicePoolMessage>>`, held so that it does not form an `Rc` cycle with the pool's device map.
2. **`StubDevice`** (inventory 3.10) underlies all 16 rows: 4 of the 5 `DeviceActorTest` rows construct it, and all 11 `BatchAccounting` rows delegate to it. Recommend a test-local `ScriptedDevice` in `crates/marathon-core/tests/support/`, covering the `StubDevice` parameters these tests use (delays, the crash flags, `reportResultsBeforeCrash`, `executionResults`). 3.10 ports `StubDevice` itself. Alternative: move `StubDevice.kt` (87 lines) to 3.6.
3. **Logging from core.** DeviceActor emits about 12 distinct lines under a per-actor logger. 3.1 offers only `CompletionLog` (no logger name) and no general core log-record API, and core may not do I/O. Recommend a small structured record queue (logger name, level, message, `Option<Failure>`) that generalises `CompletionLog`, rendered off core, with appenders wired by 3.10. 3.7/3.8 code against it, so settle its shape now.
4. **Vendor bridge location:** a reusable executor helper (3.10's remote parse and others need the same forward-cancel, await-own-outcome call) or private to DeviceActor? Recommend the executor.
5. **C3's trait addition** (`join_observed_children_in`) changes the frozen `Job` trait additively. Approve it here, as 3.1-U1 was.
6. **Two test vehicles differ from Kotlin; a reviewer must agree.** `actor failing before a dispatched batch starts executing` relies on the vendor launching an unjoined child into the prepare coroutine. `VendorContext` has no job, and no production vendor does this (`grep currentCoroutineContext|CoroutineScope(coroutineContext)` over `vendor/` finds only `isActive` checks). Port it by failing the owner job through a test-side core child (`core.spawn(actor.job(), …)`); the observable result is the same. `results of a completed batch reach the pool even if the actor stops right after` relies on single-thread dispatcher queueing. Port it as an explicit replay ordering: the parent is cancelled after the vendor's return is bridged and before readiness runs.
7. **Configuration in tests:** the Kotlin tests use `Configuration.Builder(name="", outputDir=File(""))` with the Stub vendor. Confirm that tests may build one through the merged 2.2/2.3a binding of a minimal Marathonfile, rather than adding a test builder to `marathon-config`.
